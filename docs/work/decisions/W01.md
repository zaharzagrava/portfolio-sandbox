- **W01.D-01** Should a new visitor be signed in automatically after registering, or be sent to the login page to sign in themselves?
  - default: no automatic sign-in; registration ends at `/login?notice=registered`, so every new member must sign in a second time.
  - alternatives: sign in automatically after sign-up (smoother, but it reveals which e-mail addresses already have an account); sign in automatically only after the e-mail is verified.
  - if wrong: an extra step on the first visit may lose some sign-ups; the opposite choice lets anyone test whether an address is registered, which is a privacy leak.
  - source: "`register()` signs the visitor in and goes home" [BREAKING]
  - status: open

- **W01.D-02** Should the "Sign in with Google" button appear now, or stay hidden until Google sign-in works end to end?
  - default: the button is built but hidden behind the `AUTH_OIDC_ENABLED` switch until the backend creates a proper web session for Google users. The GitHub button is removed.
  - alternatives: show the Google button now; keep GitHub as a visible "coming soon" option.
  - if wrong: if shown too early, Google users are signed in at the API but look signed out in the site. If hidden too long, you lose the one-click sign-up option.
  - source: "C-OIDC: S02 + S48 — S02's callback sets" [CONTRACT]
  - status: open

- **W01.D-03** Is a 12-character minimum password (up to 128) acceptable for customers, instead of the current 8?
  - default: password length 12–128 characters. The "Full name" field is removed from sign-up and nothing replaces it.
  - alternatives: keep a minimum of 8; use 12 for sellers and admins only.
  - if wrong: a stricter rule lowers sign-up completion; a looser one weakens account security and may conflict with the backend rule.
  - source: "Register form has "Full name" (not accepted" [BREAKING]
  - status: open

- **W01.D-04** Should we remove the "Remember me" checkbox from login, or offer a real longer-lived session?
  - default: the checkbox is removed. Session lengths are fixed by the platform and members cannot choose.
  - alternatives: build a working "Remember me" with a longer session; keep sessions short and say so on the login page.
  - if wrong: members who expect to stay signed in on their own device will sign in more often, which is annoying but not harmful. A longer session needs backend work.
  - source: "Login form has a dead "Remember me" checkbox" [BREAKING]
  - status: open

- **W01.D-05** If sign-out fails on the server, should the member stay signed in with a retry message?
  - default: the member stays signed in and sees a retry toast. The site never shows "signed out" while the server session is still alive.
  - alternatives: always sign the member out in the browser and retry on the server in the background; show a warning but clear the screen anyway.
  - if wrong: on a shared computer, a failed sign-out leaves the account open until the member retries. The alternative can show "signed out" while the session still lives.
  - source: "Sign-out ignores failure and always clears" [BREAKING]
  - status: open

- **W01.D-06** Should the forgot-password page show an error when the reset e-mail could not be requested?
  - default: "Check your email" appears only after the server accepts the request. Errors, including no network, are shown, and a new reset page is added.
  - alternatives: always show "Check your email" (as today); show a generic message that does not confirm sending.
  - if wrong: showing "sent" when nothing was sent leaves members waiting for an e-mail that never comes and raises support requests.
  - source: "Forgot-password posts to `/api/auth/forgot-password`, swallows" [BREAKING]
  - status: open

- **W01.D-07** Should the reset-password link carry its token after `#` instead of `?`, which changes the link in the reset e-mail?
  - default: the link becomes `<front>/reset-password#token=…`, and the page removes the token on load. This changes the e-mail template owned by another capability (S28).
  - alternatives: keep `?token=` and accept the logging risk; send a short one-time code instead of a link.
  - if wrong: a query token can end up in access logs and referrers, so someone could take over an account. Reverting later means editing the e-mail template again, and links already sent may break.
  - source: "D2: S28 — reset link `<front>/reset-password?token=<resetToken>`" [CONTRACT]
  - status: open
