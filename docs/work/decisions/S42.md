- **S42.D-01** Do we break existing sellers' stock integrations by replacing "set stock to N" with "add or remove N" (delta) updates?
  - default: `POST /v1/stock/bulk` takes deltas with an `operationId` per item, up to 100 items answered at once, up to 10,000 as a background job in chunks of 100; the old absolute "set to N" call is dropped.
  - alternatives: keep absolute "set to N" in the old API version and offer deltas only in the new one; support both in the latest version, accepting that absolute writes can overwrite sales made meanwhile.
  - if wrong: sellers whose scripts send absolute stock levels get errors after upgrading and must rewrite them; keeping the old behaviour instead means live stock can be silently overwritten and customers oversell.
  - source: "Stock write `POST /v1/stock/bulk {items:[{productId, stock}]}` sets" [BREAKING]
  - status: open

- **S42.D-02** Which version should a shop that has never pinned one be moved to, and do we want it fixed at first key creation?
  - default: the shop is pinned to the latest version when its first key is created, once; a newer version never moves it; a request header can override per call; an unknown version gets `400`.
  - alternatives: keep "latest at every call" for unpinned shops (today's behaviour); pin existing keyed shops to the oldest supported version `2026-01-15` instead of the latest.
  - if wrong: existing integrations that rely on "always latest" stop getting new behaviour, or, if pinned wrongly, see response shapes change under them and break.
  - source: "Unpinned shops get "latest at every call"" [BREAKING]
  - status: open

- **S42.D-03** Do we accept the deprecation timeline for the current API version, and the hard shutdown (including temporary test outages) at the end?
  - default: version `2026-01-15` is deprecated on 2026-10-01 with sunset on 2027-04-01 (6 months); after sunset calls get `410`; before that, scheduled brownout windows return `410` with `Retry-After`.
  - alternatives: a longer sunset (12 months) for slower sellers; deprecate with headers only and no brownouts or hard `410`.
  - if wrong: too short a window breaks paying sellers' integrations and generates support load; too long keeps the old version costly to maintain.
  - source: "Deprecation covers one route only and never ends" [BREAKING]
  - status: open

- **S42.D-04** Should creating or rotating a live API key require a fresh multi-factor check, and should this block sellers without MFA?
  - default: yes, live key creation and rotation need MFA (`403 mfa_required`); revoking is never blocked; test keys are not affected.
  - alternatives: require MFA only for sellers above a certain size or role; no MFA step, relying on the `shop.manage` permission only.
  - if wrong: too strict locks sellers without MFA out of creating keys; too loose lets a stolen session mint live credentials.
  - source: "Key management routes need only `shop.manage` → create/rotate/revoke" [BREAKING]
  - status: open

- **S42.D-05** Do we cap how many keys a shop can have, and how does rotation behave?
  - default: at most 25 active or rotating keys per shop; rotation only from an active key, one at a time, with an overlap of 0 to 168 hours (default 24); a revoked or expired key cannot be rotated.
  - alternatives: a higher or per-plan cap; unlimited keys with only alerts.
  - if wrong: sellers with many integrations hit `422 key_limit_reached` and ask for more; a cap that is too high allows key sprawl.
  - source: "Key creation has no per-shop limit → at most" [BREAKING]
  - status: open

- **S42.D-06** If the usage or billing store is down, should seller API calls keep working past their monthly quota check?
