- **S02.D-01** When someone signs in with Google using an e-mail that already belongs to a password account, should we link them and wipe the old password, authenticator and all sessions?
  - default: link only if Google says the address is verified; in the same step clear the password, reset the second factor and sign out every session
  - alternatives: link but keep the password and factor (the user may be locked out less, but a squatter keeps access); ask the user to prove ownership of the old account first
  - if wrong: a genuine user can lose their password and authenticator unexpectedly and get confused or locked out; too weak a rule leaves an account takeover open
  - source: "Google-login for an account whose address matches" [BREAKING]
  - status: open

- **S02.D-02** Should a company's own single sign-on (per-shop login) never be allowed to claim an account by e-mail?
  - default: shop sign-on is trusted by its own subject ID only; it never links by e-mail, always creates a new account with no e-mail, and keeps the claimed address only as a hint
  - alternatives: allow e-mail linking for shops whose domain was verified; allow it with a confirmation e-mail to the existing account
  - if wrong: too strict means shop staff who already have accounts get a second, empty account and ask support to merge; too loose lets a shop admin take over any customer's account
  - source: "Shop (`shop:<uuid>`) providers (today the same" [BREAKING]
  - status: open

- **S02.D-03** Is it acceptable that Google sign-in and password reset can never bypass or switch off the authenticator, even if the user loses their device?
  - default: an enabled factor can't be re-enrolled or removed by a session alone; a password reset never changes it; Google-created accounts have no password reset path; the only fallback is recovery codes (accepted limit)
  - alternatives: add a support-led or e-mail-based recovery with a waiting period; allow reset by e-mail after a delay with notification
  - if wrong: users who lose both device and recovery codes are locked out for good and need manual support; or, if loosened later, the security promise weakens
  - source: "S01 password reset and MFA → reset must" [CONTRACT]
  - status: open

- **S02.D-04** How many wrong second-factor codes should lock an account out, and for how long?
  - default: challenge burned after 3 wrong codes; 5 wrong codes in 15 minutes per account locks further tries (even a correct code); 20 per minute per IP
  - alternatives: looser limits (for example 10 per 15 minutes) to reduce lockouts; stricter limits with a longer lockout
  - if wrong: too tight lets an attacker lock real users out on purpose; too loose makes 6-digit codes guessable
  - source: "Second-factor brute-force limits (today only `auth.login.ip`" [BREAKING]
  - status: open

- **S02.D-05** Should an account be limited to one Google identity, refusing a different Google account with the same e-mail?
  - default: one identity per provider per user; a different Google subject with a matching e-mail is refused as `link_conflict`
  - alternatives: allow several Google identities per account; allow replacement after unlinking with confirmation
  - if wrong: users who changed Google accounts or e-mail are blocked from signing in and need support; too loose allows recycled addresses to take over accounts
  - source: "One identity per provider per user and store-level" [BREAKING]
  - status: open

- **S02.D-06** Are you fine with changed Google login and second-factor behaviour that breaks existing clients and requires re-sealing stored authenticator secrets?

- **S02.D-07** Should a user with an authenticator also be challenged when signing in with Google, and should a pending enrolment never change login?
