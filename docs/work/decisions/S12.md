# Decisions needing your call: S12 Order export (streamed CSV to object storage, progress) including moving its routes and queue out of catalog-sync (debt D-10)

- **S12.D-01** Should exported files and their download links disappear 7 days after the export finishes, and the records after 90 days, rather than being kept forever?
  - default: files deleted 7 days after finishing (download then answers 410), finished records deleted after 90 days
  - alternatives: keep files longer (for example 30 days) or until the seller deletes them; keep records indefinitely for audit
  - if wrong: sellers who come back after a week must re-run the export; too long a retention keeps a bulk copy of sales and customer data around and widens a privacy exposure
  - source: "Files and records are kept forever → files deleted 7 days" [BREAKING]
  - status: open

- **S12.D-02** Who may start, see, download and cancel an export, and does that access end when someone leaves the shop?
  - default: only a current member of the shop with the `orders.manage` permission; exports belong to the shop, not to the person who started them, and every refusal looks like "not found"
  - alternatives: only the creator can see their own export; a broader or narrower permission
  - if wrong: a former team member could still reach sales data, or colleagues cannot see or download an export they need
  - source: "Live channel: topic `job:{id}` (prefix shared with imports" [BREAKING]
  - status: open

- **S12.D-03** Should the download link be issued only on request, valid for 10 minutes, and logged with who fetched it?
  - default: the export status never shows a link or storage key; a separate download call returns a 10-minute link, only once the export is done, and each issue is audited
  - alternatives: a longer link lifetime; a link in the status as today, with no audit
  - if wrong: a too-short link frustrates sellers on slow connections; a leaked or long-lived link exposes order data
  - source: "The status route returns `{status, rows, objectKey, downloadUrl}`" [BREAKING]
  - status: open

- **S12.D-04** How many exports may a shop run, and how often?
  - default: one active export per shop at a time (a second start is refused with 409), 5 starts per shop per hour, and a required idempotency key
  - alternatives: allow several concurrent exports; a different hourly limit or a daily limit
  - if wrong: too strict blocks sellers who need repeated exports; too loose lets a double click or a script multiply jobs on millions of rows, which costs money and load
  - source: "Starting needs no key and any number can run at once" [BREAKING]
  - status: open

- **S12.D-05** Are the old export paths removed outright with no redirect, and does the response change shape (`jobId` becomes `exportId`)?
  - default: old paths answer 404 immediately, new paths are `/shops/:shopId/order-exports`, there is no alias or deprecation notice, on the assumption that there are no external clients
  - alternatives: keep the old paths as aliases for a period with a Deprecation header; announce first
  - if wrong: any script or integration that uses the old paths breaks at once
  - source: "Routes `POST /shops/:shopId/exports/orders` and `GET /shops/:shopId/exports/:jobId`" [BREAKING]
  - status: open

- **S12.D-06** Is the changed file content acceptable to sellers who already use the export?
  - default: `order_id` now holds the order ID and a new `shop_order_id` column holds what `order_id` used to hold; columns are renamed and added; UTF-8 BOM, CRLF line endings, a leading apostrophe on text cells starting with `= + - @`, tab or CR; deterministic ordering
  - alternatives: keep the old column meaning and add new columns after it; no BOM or apostrophe guard
  - if wrong: sellers' spreadsheets or imports that read the old columns break; without the guard, a malicious product title could run a formula in the seller's spreadsheet
  - source: "File content: `order_id` currently holds the **shop-order** ID" [BREAKING]
  - status: open

- **S12.D-07** Is it acceptable that the export is no longer an exact point-in-time snapshot?
  - default: the file excludes orders created after the request, but each line shows its status as of the moment its batch was read, so a status change during a long run can differ between lines
  - alternatives: keep one long read for an exact snapshot (holds a database connection for the whole run); cap export size
  - if wrong: a seller reconciling figures may see lines whose status changed mid-export; the other option puts database load at risk
  - source: "Streaming reads through one server-side cursor held inside" [BREAKING]
  - status: open

- **S12.D-08** Is a seller unable to download an export once the shop has started closing down, and are all their export files then deleted?

  - if wrong: a leaving seller loses access to their order history, which is a possible complaint or legal issue
