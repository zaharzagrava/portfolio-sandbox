# G5 notes (media, asset-library, community, assistant, content, chat)

I read every fixed wait in the 80 files and could not run anything, so I only changed what I could prove safe by reading.

## Changed
- media/video-upload.e2e-spec.ts: the wait for a 1-second upload permission to run out went from 2.1 s to 1.2 s. The store counts whole seconds, so 1.2 s is always past the end. Saves about 0.9 s. Could break: only if the store's clock and the test's clock were far apart (same machine, so no).
- asset-library/asset-upload.e2e-spec.ts: same wait, 2.2 s to 1.2 s (permission lives 1 s). Saves about 1 s. Same risk.
- assistant/assistant.e2e-spec.ts: two "nothing is aborted while a viewer is attached" checks. Grace period 1.5 s to 0.5 s with a 0.9 s wait (was 2.5 s) in the first; wait 1.5 s to 0.9 s in the second (its grace stays 0.4 s). Each wait is still longer than the grace period, so the check still proves the same thing. Saves about 2.2 s. Could break: a very slow machine where 0.9 s is not enough for the viewer to stay attached (it only needs to be attached, so unlikely).
- community/discussions-comments.e2e-spec.ts: the "reply racing with delete of its parent, 20 times" test now runs its 20 rounds side by side (each round has its own parent and its own two people) instead of one after another. Still 20 races, same checks. Saves about 2 to 4 s. Could break: more load at once on the database; the final counts are only checked after all rounds end.

## Looked at, could not improve safely
- community/discussions-votes: the 100 voters already vote at once. The "20 times" race loop calls flushDiscussionCache (wipes the shared cache), so running rounds side by side could disturb other rounds. Left as is.
- community/discussions-comments other loops: each round checks a running total (2 + round), so they must stay in order.
- assistant/assistant-metering (1 s "stays at one row"): proves nothing more arrives; kept.
- community/feed-celebrity (1.5 s) and feed-rebuild (2 s): a slow author must be slower than the code's own time limit; shortening would change what is proved.
- content/story-sitemap (400 ms x2), story-publish (600/200 ms), chat-read-state (400 ms), discussions-resilience (200 ms), asset-operations (200 ms): tiny, each under half a second, and they prove "nothing happens" or an in-flight overlap.
- All other waits (knowledge-*, video-delivery, video-events, video-pipeline, discussions-markdown) already check every 10 to 100 ms until the thing happens.
- No file in my folders could safely use describe.concurrent: nearly all run a global reset in beforeEach (t.reset() / h.reset()) and share one app.
- The rest of the 80 files were scanned for sleeps, long limits and loops of waits; nothing else worth changing was found. Real time in these files is mostly app start and the reset between tests, which lives in the shared helpers outside my folders (testing/video-app, assistant.harness, etc.): the biggest remaining saving is there.
