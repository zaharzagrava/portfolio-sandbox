# G1 notes (identity, tenancy, seller-onboarding, shop-functions)

I read all 70 files by searching for waits, loops and long time limits. These folders are already fast: most waits are polls, and the app starts once per file. Only four spots were worth changing.

## Changed
- libs/domains/shop-functions/shop-functions-ops.e2e-spec.ts: the 100 inserted "rejected" versions now go in at the same time instead of one after another. Saving about 1 to 2 s. Could break: only if the database connection pool is tiny (100 inserts wait in line); the rows are independent, so the data is the same.
- libs/domains/shop-functions/shop-functions-judge.e2e-spec.ts: same change, same saving, same risk (test "a function with 100 versions refuses another").
- libs/domains/identity/auth-refresh.e2e-spec.ts: the 60 wrong refresh requests (before the 61st that must get 429) are sent at the same time. All 60 are still checked for 401, and the 61st is sent after all of them finish. Saving about 1 to 2 s. Could break: if the rate limiter counted requests unevenly under load (it should not, it counts all 60 before the 61st).
- libs/domains/tenancy/shop-sso.e2e-spec.ts: the 30 look-ups from one address are sent at the same time. Now ALL 30 must answer 404 (before only the last one was checked), then the 31st must be 429. Saving about 0.5 to 1 s. Could break: same as above.

## Looked at, not improved (reason)
- identity/consumers-admin: the sleeps (1.5 s, 2 s) prove that a paused group does nothing; the rule behind them says "within 2 s", so they cannot be shorter. The rest already polls.
- identity/auth-sessions (20 sessions in a row): the order matters, the oldest must be the one evicted.
- identity/auth-password-reset: one 0.3 s "nothing happens" wait; too small to touch.
- tenancy/tenancy-errors, shop-lifecycle (10 shops in a row): saving under 0.5 s and the creation order may matter; left alone.
- shop-functions/shop-functions-checkout: 300 to 400 ms waits are tied to the 300 ms stand-ins and the 80 ms budget in the same test; shortening them changes what the test proves.
- seller-onboarding/onboarding-extraction: 150 ms wait is part of a race on purpose (a document replaced while being read).
- tenancy/member-revocation, clock-admin: already wait until the thing happens.
- All other files: no waits, loops or repeated app starts found; the time goes into the database and app work itself. describe.concurrent was not used anywhere because every file wipes data in beforeEach (t.reset()) or shares one app and clock.
