# G6 notes (seller-insights, experimentation, notifications, projector, composition)

## libs/domains/seller-insights/dashboard-live.e2e-spec.ts
- Changed: the wait between "is the lease free yet" tries went from 250 ms to 50 ms (AS-43); the fake slow step that must overlap the next tick went from 1200 ms to 400 ms (AS-44); the slow step in the shutdown test went from 600 ms to 300 ms (AS-49).
- Saving: about 1.2 s. The 5 s lease limit and every expected value are unchanged.
- Could break: AS-44 and AS-49 only need the slow step to still be running when the next tick starts, and that tick starts at once, so 400 and 300 ms are plenty. If the machine is very slow and the test turns flaky, put the old numbers back.

## libs/domains/notifications/notifications.e2e-spec.ts
- Changed: three fixed 1.5 s waits (used to prove "no second email was sent") now wait until the email queue is really empty (3 checks in a row, about 0.45 s) and then run the same check.
- Saving: about 3 s.
- Could break: it relies on the router having put any extra message on the queue before `project()` returns. The old fixed wait would also have caught a message that appears much later.

## notifications-delivery, notifications-inbox, notifications-preferences, notifications-quiet-caps, notifications-routing (.e2e-spec.ts)
- Changed: the small "wait until this happens" helper at the top of each file now looks every 30 ms instead of every 100 ms. Same overall limit (45 s), same checks.
- Delivery also: the wait for the rate bucket to refill now tries every 100 ms instead of 500 ms.
- Saving: about 0.05 s per wait, many waits per file; roughly 8 to 12 s over the five files, plus about 1 s in delivery.
- Could break: nothing in the checks changed. More tries means a few more cheap database or HTTP calls.

## libs/domains/experimentation/experiments-admin.e2e-spec.ts
- Changed: the tests that put 199, 198 and 120 experiment rows into the database one after another now insert them all at once.
- Saving: about 1.5 s. Rows have their own random keys and layers, so the order does not matter.
- Could break: if the database connection pool were tiny the inserts just queue; no change in the result.

## libs/composition/bff/bff.e2e-spec.ts and libs/composition/bff/seller/seller-overview.e2e-spec.ts
- Changed: 300 requests that each must answer 400 before the 301st answers 429 are sent 50 at a time instead of one by one. Each still expects 400; the final 429 check is unchanged.
- Saving: about 1 s per file.
- Could break: the counter in Redis is exact, so 300 allowed then the next one refused still holds. If the limit were a time-based refill, a slow machine could only allow more, never fewer.

## analytics-ingest, flags-client, experiments-assignment, analytics-ops (experimentation)
- Changed: the "120 requests are fine, the 121st is refused" loops send 30 at a time instead of one by one (each answer is still checked where it was checked before).
- Saving: about 0.5 to 1 s per file.
- Could break: same reasoning as above (exact counter).

## libs/domains/seller-insights/competitor-crawl.e2e-spec.ts
- Changed: the loop that waits for 19 targets to be crawled looks every 50 ms instead of 200 ms.
- Saving: about 0.1 s. The real waits in this file (10 s page deadline, 9 s slow page, politeness gaps) prove time rules and are left alone.

## Looked at, not changed (why)
- libs/composition/bff/bff-session, bff-graphql, bff-boundary, forward/bff-forward, upstream/upstream-client, and the rest of bff.e2e-spec: they already use a fake clock; their real waits (300 ms to 1.5 s) are the budgets being tested; all share one stub server that is reset in beforeEach, so no concurrency.
- libs/domains/experimentation/flags-sdk: the fake 1.5 s slow read is cut by the SDK at about 0.5 s, so shortening it saves nothing; 200 ms "nothing arrives" wait is tiny.
- libs/domains/seller-insights/leaderboard-snapshots: the 5 ms poll is the test itself (reading while a freeze runs).
- apps/projector/src/*-wiring (21 files): each boots its own small app once in beforeAll and has 1 to 3 quick checks. The cost is the start-up, which cannot be shared across files.
- Everything else (seller-insights leaderboard-*, read-models, competitor-* except crawl, observability, crawler, index, dashboard-history; experimentation flags-*, experiments-results, analytics-store; notifications foundation, catalog, callbacks, observability, dev-mailbox, topics): no fixed sleeps, no repeated boots, and they share data wiped in beforeEach, so no safe gain found. No concurrency used anywhere.
