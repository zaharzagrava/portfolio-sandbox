# G4 notes (payments, billing, statements, fulfilment, marketing)

Paths are under packages/backend. Nothing was run; every saving below is an estimate.

## Changed files

- libs/domains/statements/statement-export.e2e-spec.ts
  - The test where a second database session holds a lock now holds it for 2.5 s instead of 4 s. The export time limit in that test is 1 s, so the lock still lasts longer than the limit. Saves about 1.5 s.
  - The test "a third export is refused" waited a fixed 0.4 s for the two slow exports to start. It now waits until both have really started (checks every 10 ms). Saves a fraction of a second and is less likely to fail on a slow machine.
  - Could break: only if the lock is no longer longer than the time limit (it is: 2.5 s against 1 s).
- libs/domains/payments/payout-run.e2e-spec.ts
  - The "two runs at once, twenty times" test created 20 sellers one after the other in each of 20 rounds (400 slow steps). It now creates the 20 sellers of a round together. Same checks. Saves roughly 5 to 15 s.
  - Could break: if creating sellers together hits a shared counter. The other test in the same file already creates 25 sellers together, so it should be fine.
- libs/domains/payments/payment-intent.e2e-spec.ts
  - The test where the order fact arrives during the 2 s wait now sends it after 0.3 s instead of 1 s. Still inside the wait. Saves 0.7 s.
- Rate-limit tests (the "121st request in a minute is refused" kind): the first 120 requests are now sent in 4 groups of 30 at once (300 requests in 10 groups for the clusters test) instead of one by one. Every answer is still checked to be 200 and the last request is still sent after all of them. Saves about 1 to 3 s each, about 10 s in total.
  - libs/domains/payments/ledger-balances.e2e-spec.ts
  - libs/domains/payments/payment-read.e2e-spec.ts
  - libs/domains/payments/payout-api.e2e-spec.ts
  - libs/domains/statements/statement-read.e2e-spec.ts
  - libs/domains/marketing/ads-serving-clicks.e2e-spec.ts
  - libs/domains/fulfilment/pickup-search.e2e-spec.ts (two tests)
  - libs/domains/fulfilment/pickup-clusters.e2e-spec.ts
  - Could break: if the test client cannot handle 30 open requests at once (unlikely), or if the counter works per second instead of per minute (then the old way was also borderline).
- libs/domains/marketing/ads-platform.e2e-spec.ts
  - The test reading the aggregate topic waited a fixed 3 s. It now waits until the 200 clicks are seen (up to 10 s), then 0.5 s more so a late duplicate would still show up. Same check (total is exactly 200). Saves about 2 s.

## Looked at, not changed

- payments/payout-transfer: the 20-round and 50-round race loops use shared fake counters and a full reset each round, so rounds cannot overlap, and cutting the round count would weaken the proof. Left as is. The owner could decide whether fewer rounds are acceptable (the biggest single saving in the group, maybe 30 s).
- payments/payment-transitions, ledger-posting (50 rounds), subscribe, subscription-change, subscription-lifecycle, ledger-payment-postings, reconciliation-issues, payout-api (50-round cancel race): same reason, rounds share counters, the clock or the same ledger accounts.
- billing/billing-run: the 50 subscriptions are made one by one through the real API and each one moves the shared clock and login, so they cannot be made together.
- marketing/ads-aggregation: reads the topic with a fixed 2.5 s quiet wait about 8 times (about 20 s). Several of those prove that nothing is visible, so the wait stays. Idea for the owner: end the wait early once the group has read to the end of the topic.
- All short fixed waits of 0.3 s that prove nothing happens (share links, "limiter store down" tests, payment "settle" helpers): kept.
- fulfilment (all files): no sleeps; setup is already once per file (app) and one reset per test, which lives in shared test helpers outside this group.
- Files I did not get to read in detail: the remaining files in billing, marketing and fulfilment not named above. Nothing was changed in them.
