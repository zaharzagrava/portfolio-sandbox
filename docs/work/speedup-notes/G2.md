# G2 notes (catalog-sync, catalog, discovery)

Nothing was run (the rules forbid it). Every saving below is an estimate from reading the code. All files were checked with prettier and the type checker only.

## Changed files

### discovery/trending-stream.e2e-spec.ts
- What changed: six tests that used the default settings (AS-30, AS-16, AS-22, AS-20, AS-19 and the "bounded TTL" test) now share ONE started app, topic and reader group, made on first use and closed at the end. Before, every test started its own app and joined a new Kafka group. Each of them still wipes the data and the reader's memory first (`clean()`), which is what a fresh start gave them before. The waiting helper now checks every 25 ms instead of every 100 ms (same time limits).
- Expected saving: about 5 app starts, roughly 30 to 50 seconds (a guess; one start was 8 to 15 s in other suites).
- What could break: the six tests now share one topic, so a leftover from an earlier test could show up in a later one. I checked: the only test that reads the dead-letter topic (AS-30) counts letters from its topic, and no other shared test sends a bad message. Tests that restart readers, stop them, use two partitions, use special settings or the Redis fault proxy still start their own app.

### discovery/trending-platform.e2e-spec.ts, discovery/search-platform.e2e-spec.ts, discovery/autocomplete-platform.e2e-spec.ts, catalog-sync/import-boundary.e2e-spec.ts
- What changed: each of these runs the "module boundary" check (walks the whole backend) and the "table ownership" check one after the other. Now the two run side by side, and the module-boundary check is run once per test process and its answer is shared by the files that ask (a small helper `runOnce` in each file, answers kept on `globalThis`). Same commands, same assertions (search-platform now also asserts the boundary exit status is 0, which it did implicitly before because the old call threw on a failing exit).
- Expected saving: with one process for all files (Vitest) the boundary check runs once instead of 4 times in my folders (other folders have the same check in assistant, experimentation, media, payments, orders: they could use the same key `check:boundaries` with `pnpm --silent check:boundaries` run in `packages/backend`). A boundary run is likely 30 to 90 s, so 100 to 250 s in my folders. With separate processes (Jest) only the side-by-side part helps, about 10 to 30 s per file.
- What could break: if the sources change during the suite the shared answer is stale (does not happen in a run). The trending test keeps the pnpm banner on the ownership output (as before), so its "output is not empty" check still means what it did.

### catalog-sync/import-fairness.e2e-spec.ts
- What changed (a fix, not a speed-up): the test "limiter store down" cut the app's Redis connection and the next test (AS-63) hit the half-reconnected connection ("Stream isn't writeable", 503). Now the cut test ends by waiting until the app's Redis answers a ping again. No check was changed. Not run, so please confirm AS-63 now passes.

### discovery/autocomplete-suggest.e2e-spec.ts, discovery/recommendations-read.e2e-spec.ts, discovery/trending-read.e2e-spec.ts, catalog-sync/sync-access.e2e-spec.ts
- What changed: the "N requests are fine, the next is a 429" tests sent 600, 600, 300 and 120 requests one at a time. Now they go out in groups of 30 at once, and EVERY answer must be 200 (before only the last one was checked). The 429 check after them is unchanged and still sequential.
- Expected saving: about 2 to 4 s per file (about 10 to 15 s in total).
- What could break: if a limiter had a short burst rule below 30 at once, a group could get an early 429. The rules in these tests are per minute counts, so I do not expect it.

### catalog/product-write.e2e-spec.ts
- What changed: the 120 product creations before the "121st is 429" check go out in groups of 20 at once instead of one by one. Same checks (all 201, then 429, 120 products).
- Expected saving: about 3 to 6 s.
- What could break: creation takes a per-shop lock when a plan limit exists, so concurrent creates are serialized there; titles are all different. If a create under load got a 409 the test would show it.

## Looked at and not improved (reason)
- discovery/trending-read, trending-platform (rest): app is already started once per file; sleeps are 50 to 300 ms waits for reconnects.
- catalog/collab-rooms, collab-routing, collab-ops, drafts-consumers: the fixed sleeps (200 to 500 ms, about 5 s total in collab-rooms) prove "nothing arrives" or wait for a socket reconnect; not shortened.
- catalog-sync import-* and integration-*: app started once per file, waits already poll every 25 ms; no repeats to shrink.
- search-admin, search-measurement, shop-product-search, search-query rate-limit loops: they stop at the first 429, so they must stay in order.
- All other files in the three folders: only read through the search for sleeps, big limits and loops (see lists above); I found no safe saving without running the tests. Heavy files I did NOT read line by line: integration-lifecycle, integration-manage, integration-connect, integration-sync, collab-rooms, product-write (except the loop), drafts-publish, search-projection.
