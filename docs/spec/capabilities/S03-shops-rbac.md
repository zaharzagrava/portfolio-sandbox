# S03 - Shops as tenants: memberships, roles and permissions, invites, per-shop SSO, cells, offboarding
## Purpose
A shop is the tenant of the marketplace: a seller organisation with a team, a plan, a verification status and a place in the infrastructure. This capability decides who may do what inside a shop. It makes sure one shop never sees or disturbs another, as described in {{concept:tenant-shop-rbac}}. Sellers, shop staff and other capabilities need it to create shops, manage the team, invite people and read shop data.

## Entry points
- `POST /shops`: a signed-in user creates a shop and becomes its `OWNER`. [code: packages/backend/libs/domains/tenancy/api/shop.controller.ts#ShopController]
- `GET /shops/mine`: lists the caller's shops with their role, cursor-paginated. [code: packages/backend/libs/domains/tenancy/api/shop.controller.ts#ShopController]
- `GET /shops/:shopId`: a member reads the shop, `myRole` and `myPermissions`.
- `PATCH /shops/:shopId`: a member with `shop.manage` renames the shop.
- `GET /shops/:shopId/members`: lists members.
- `PATCH /shops/:shopId/members/:userId`: changes a member's role (`204`). [code: packages/backend/libs/domains/tenancy/api/members.controller.ts#MembersController]
- `DELETE /shops/:shopId/members/:userId`: removes a member, or a member leaves.
- `POST /shops/:shopId/invites`: creates an invite. [code: packages/backend/libs/domains/tenancy/api/invites.controller.ts#InvitesController]
- `GET /shops/:shopId/invites`: lists invites.
- `POST /shops/:shopId/invites/:inviteId/resend`: renews an invite.
- `DELETE /shops/:shopId/invites/:inviteId`: revokes an invite.
- `POST /shop-invites/accept`: the invited person accepts with a token.
- `PUT /shops/:shopId/sso`: an owner configures the shop's identity provider. [code: packages/backend/libs/domains/tenancy/api/sso.controller.ts#SsoController]
- `GET /shops/:shopId/sso`, `DELETE /shops/:shopId/sso`: an owner reads the configuration (never the secret) or removes it.
- `GET /shops/by-slug/:slug/sso`: anonymous lookup whether a shop has company sign-in.
- `POST /shops/:shopId/offboarding`, `DELETE /shops/:shopId/offboarding`: an owner starts (with the slug as confirmation) or cancels closing the shop. [code: packages/backend/libs/domains/tenancy/api/offboarding.controller.ts#OffboardingController]
- `GET /shops/:shopId/export`: an owner downloads what tenancy holds about the shop.
- `POST /admin/shops/:shopId/suspend`, `POST /admin/shops/:shopId/reinstate`, `GET|PUT /admin/shops/:shopId/directory`: platform administrators with a sensitive session suspend, reinstate and move a shop between cells. [code: packages/backend/libs/domains/tenancy/api/admin-shops.controller.ts#AdminShopsController]
- Consumers: `identity.federated_identity_linked` (membership for company sign-ins), `shop.onboarding_submitted`, `shop.verified`, `shop.rejected` (verification), `billing.subscription_plan_changed` (plan).
- Jobs: `tenancy.purge-deleted-shops` (hourly), `tenancy.purge-expired-invites` (daily), `tenancy.reseal-sso-secrets` (daily, idempotent). [code: packages/backend/libs/domains/tenancy/infra/jobs/purge-shops.jobs.ts#PurgeShopsJobs]
- `GET /shop-roles`: returns the role and permission matrix. [code: packages/backend/libs/domains/tenancy/api/shop-roles.controller.ts#ShopRolesController]
- `GET /batch/shops`: anonymous batch read of `{id, name, slug}` for the BFF. [code: packages/backend/libs/domains/tenancy/api/shop-batch-read.controller.ts#ShopBatchReadController]
- Queue `tenancy-invite-requested`: carries the invite message to the notification capability.
- Topic `shop:<shopId>:live`: realtime topic admitted only to members. [code: packages/backend/libs/domains/tenancy/api/realtime-topics.ts#ShopTopics]
- Exported services: `ShopAccessService`, `ShopQueryService`, `MembershipQueryService`, `ShopProvisioningService`, `ShopCellService` for other capabilities.

## Rules
- **S03.R-01** A [non-member](../terms/shop-membership.md), an unknown shop, a malformed identifier and a [deleted shop](../terms/shop-status.md) MUST all answer the same [`404 shop_not_found`](../terms/shop-not-found.md). [proof: S03 AS-09, S03 AS-15] [code: packages/backend/libs/domains/tenancy/domain/errors.ts#Domain_ShopNotFoundError]
- **S03.R-02** Every endpoint except the [public ones](../terms/public-upstream.md) MUST answer [`401 invalid_token`](../terms/invalid-token-error.md) without [credentials](../terms/credential.md). [proof: S03 AS-05]
- **S03.R-03** The shop MUST come from the path or the [`X-Shop-Id` header](../terms/x-shop-id-header.md), never from the body. A path and header that differ MUST answer [`400 shop_mismatch`](../terms/shop-mismatch.md). [proof: S03 AS-10] [code: packages/backend/libs/domains/tenancy/api/shop.guard.ts#ShopGuard]
- **S03.R-04** Answers MUST follow this order: `401`, `404`, [`403 permission_denied`](../terms/permission-denied.md), then the [status gate](../terms/shop-status-gate.md). [proof: S03 AS-12]
- **S03.R-05** A [`SUSPENDED`](../terms/shop-status.md) shop MUST allow only [`shop.read`](../terms/permission.md), `members.read` and [`shop.export`](../terms/permission.md), plus `products.read` and `orders.read` on the seller dashboard's own reads only (the shop's product list and product, its photo gallery, its order list), so the seller can still see the shop's data; every other route, including drafts, sync, shop search and live editing, MUST refuse them, and the status gate refuses the rest with [`403 shop_suspended`](../terms/shop-status-gate.md). [proof: S03 AS-12]
- **S03.R-06** The allowed [permission](../terms/permission.md)s of each [role](../terms/shop-role.md) MUST equal the [matrix of FR-020](../terms/role-permission-matrix.md). An unknown role or permission MUST be denied. [proof: S03 AS-11, S03 AS-16] [code: packages/backend/libs/domains/tenancy/domain/permissions.ts#ROLE_PERMISSIONS]
- **S03.R-07** The [permissions](../terms/permission.md) of a [lower role](../terms/shop-role.md) MUST be a subset of those of the adjacent higher role. [proof: S03 AS-17]
- **S03.R-08** Only an [`OWNER`](../terms/shop-role.md) MAY assign, change or remove `OWNER` or [`ADMIN`](../terms/shop-role.md). An `ADMIN` MAY manage [`STAFF`](../terms/shop-role.md) and [`VIEWER`](../terms/shop-role.md) only. Violations MUST answer [`403 insufficient_role`](../terms/insufficient-role.md). [proof: S03 AS-18, S03 AS-19] [code: packages/backend/libs/domains/tenancy/domain/role-policy.ts#canManage]
- **S03.R-09** Every member MAY remove themselves, even without [`members.manage`](../terms/permission.md). [proof: S03 AS-25] [code: packages/backend/libs/domains/tenancy/domain/role-policy.ts#canLeave]
- **S03.R-10** A shop MUST always keep at least one `OWNER`; a change that removes the last one MUST answer [`409 last_owner`](../terms/last-owner.md), also under [concurrent changes](../terms/optimistic-concurrency.md). [proof: S03 AS-22, S03 AS-23]
- **S03.R-11** After three [serialization conflicts](../terms/transaction-conflict.md) in a row, a change MUST answer [`503 serialization_failure`](../terms/transaction-conflict.md) with [`Retry-After: 1` ↗](../sw-external-terms.md#retry-after) and change nothing. [proof: S03 AS-24]
- **S03.R-12** A user MUST own at most 10 [shops](../terms/shop-tenant.md), also under [concurrent creates](../terms/max-owned-shops.md). [proof: S03 AS-04] [code: packages/backend/libs/domains/tenancy/domain/seat-policy.ts#MAX_OWNED_SHOPS]
- **S03.R-13** A [slug](../terms/shop-slug.md) MUST be 3 to 40 characters of `[a-z0-9-]`, without a leading or trailing hyphen; [reserved handles](../terms/reserved-slug.md) answer `422 slug_reserved` and used slugs [`409 slug_taken`](../terms/slug-taken.md). [proof: S03 AS-02, S03 AS-03] [code: packages/backend/libs/domains/tenancy/domain/slug-policy.ts#checkSlug]
- **S03.R-14** An [invite token](../terms/invite-token.md) MUST be stored only as a [digest](../terms/invite-token-digest.md), MUST be [single-use](../terms/invite-token.md), and MUST NOT appear in any API response. [proof: S03 AS-28, S03 AS-34, S03 AS-38] [code: packages/backend/libs/domains/tenancy/domain/invite-token.ts#digestInviteToken]
- **S03.R-15** Every failed [invite acceptance](../terms/invite-acceptance.md) (unknown, expired, [revoked](../terms/invite-revoke.md), used, wrong address, inactive shop) MUST answer the same [`404 invite_not_found`](../terms/invite-not-found.md). [proof: S03 AS-33]
- **S03.R-16** An [invite](../terms/pending-invite.md) MUST NOT grant [`OWNER`](../terms/shop-role.md). [proof: S03 AS-29]
- **S03.R-17** [Seats used](../terms/seat.md) (members plus [unexpired pending invites](../terms/pending-invite.md)) MUST NOT exceed the [plan limit](../terms/plan-limit.md): `STARTER` 5, `PRO` 25, `ENTERPRISE` 250. [proof: S03 AS-31] [code: packages/backend/libs/domains/tenancy/domain/seat-policy.ts#seatLimit]
- **S03.R-18** A shop MUST NOT create more than 20 invites per hour, and a user MUST NOT make more than 10 failed accepts in 15 minutes; both answer [`429`](../terms/rate-limited.md) with [`Retry-After` ↗](../sw-external-terms.md#retry-after). [proof: S03 AS-39] [code: packages/backend/libs/domains/tenancy/domain/tenancy-rate-policies.ts#tenancyRatePolicies]
- **S03.R-19** [Tenancy tables](../terms/tenancy-tables.md) MUST be unreadable without a [tenant set](../terms/tenant-setting.md), and the [tenant setting](../terms/tenant-setting.md) MUST NOT [leak between transactions on one connection](../terms/tenant-setting.md). [proof: S03 AS-57, S03 AS-58]
- **S03.R-20** The [cross-tenant bypass](../terms/cross-tenant-bypass.md) MUST accept only [allowlisted reasons](../terms/bypass-reason-allowlist.md), and [production start](../terms/startup-validation.md) MUST fail if the database role has [superuser or bypass rights ↗](../sw-external-terms.md#row-level-security). [proof: S03 AS-59, S03 AS-60] [code: packages/backend/libs/domains/tenancy/domain/cross-tenant-reason.ts#isCrossTenantReason]

- **S03.R-21** The issuer of a [shop's](../terms/shop-tenant.md) [identity provider ↗](../sw-external-terms.md#identity-provider) MUST be an `https` URL on a public address whose [discovery document ↗](../sw-external-terms.md#oidc-discovery-document), fetched once within 3 s [outside any transaction](../terms/active-transaction.md), names the same issuer; otherwise [`422 sso_issuer_invalid`](../terms/sso-issuer-errors.md), `sso_issuer_mismatch` or `sso_issuer_unreachable` and nothing is stored. Only an [`OWNER`](../terms/shop-role.md) MAY configure it. [proof: S03 AS-40, S03 AS-41] [code: packages/backend/libs/domains/tenancy/infra/oidc-discovery.adapter.ts#OidcDiscoveryAdapter]
- **S03.R-22** The client secret MUST be [stored sealed](../terms/secret-box.md) with the context [`shop-sso:<shopId>`](../terms/seal-context.md), MUST NOT appear in any response, and MUST be handed in plain form only to the [sign-in registry](../terms/oidc-provider-registry.md) at the moment a login resolves the provider; a disabled provider, a shop that is not [`ACTIVE`](../terms/shop-status.md) and a [sandbox shop](../terms/sandbox-shop.md) MUST [resolve as unknown](../terms/resolve-as-unknown.md). Removing the configuration MUST delete the row. [proof: S03 AS-40, S03 AS-44, S03 AS-45] [code: packages/backend/libs/domains/tenancy/application/shop-sso.service.ts#ShopSsoService]
- **S03.R-23** A user who signs in through a shop's provider MUST become a member with [`source: sso`](../terms/membership-removal-source.md) and the provider's [default role](../terms/provider-default-role.md) once, only while SSO is enabled, the shop is `ACTIVE` and a [seat is free](../terms/seat.md); a member who exists keeps their role and a removed member MUST NOT be added again by a [redelivered event](../terms/at-least-once-delivery.md). [proof: S03 AS-47, S03 AS-48, S03 AS-49] [code: packages/backend/libs/domains/tenancy/application/sso-provisioning.service.ts#SsoProvisioningService]
- **S03.R-24** Routing a shop to a [database cell](../terms/shop-cell.md) MUST [fail closed ↗](../sw-external-terms.md#fail-open-fail-closed): a cell the process has no connection for, cannot reach, or whose [pool stays full ↗](../sw-external-terms.md#connection-pool) for the [acquire timeout](../terms/acquire-timeout.md) (2 s) MUST answer [`503 cell_unavailable`](../terms/cell-unavailable.md) and MUST NOT use the [pooled database](../terms/pooled-database.md); other shops stay unaffected. [proof: S03 AS-53, S03 AS-54] [code: packages/backend/libs/domains/tenancy/infra/tenant-connection.resolver.ts#TenantConnectionResolver]
- **S03.R-25** Only a [platform `ADMIN`](../terms/platform-admin.md) with a [session that is not revoked](../terms/session-revocation.md) MAY move a shop between cells; the move MUST be conditional on the [directory version](../terms/directory-version.md) ([`409 stale_version`](../terms/stale-version.md)) and name a configured cell ([`422 unknown_cell`](../terms/unknown-cell.md)). The [cell lookup](../terms/shop-cell-service.md) is cached in the process for 5 minutes and dropped on a move. [proof: S03 AS-52, S03 AS-55] [code: packages/backend/libs/domains/tenancy/application/shop-cell.service.ts#ShopCellService]
- **S03.R-26** Only an `OWNER` MAY start or cancel [offboarding](../terms/shop-offboarding.md), with the [slug as confirmation](../terms/shop-slug.md) ([`422 confirmation_mismatch`](../terms/confirmation-mismatch.md)); a [repeat start MUST answer the same result without a second event ↗](../sw-external-terms.md#idempotency); a [suspended](../terms/shop-status.md) shop MUST NOT be closed through the API. [proof: S03 AS-66, S03 AS-67] [code: packages/backend/libs/domains/tenancy/application/shop-lifecycle.service.ts#ShopLifecycleService]
- **S03.R-27** The [purge](../terms/shop-purge.md) MUST run once per [due shop](../terms/job-due.md) in its own transaction and leave a [tombstone](../terms/shop-tombstone.md) (`DELETED`, name `[deleted]`, slug `deleted-<id>`) with no member, invite, SSO configuration, [directory row](../terms/directory-row.md) or [status history](../terms/shop-status-history.md); it MUST publish [`tenancy.member_removed`](../terms/member-removed-event.md) (reason `shop_deleted`) and [`tenancy.shop_deleted`](../terms/shop-deleted-event.md) and end the sessions of former `sso` members. [proof: S03 AS-69] [code: packages/backend/libs/domains/tenancy/application/shop-lifecycle.service.ts#ShopLifecycleService]
- **S03.R-28** [Verification status](../terms/shop-verification.md) and [`payoutsEnabled`](../terms/payouts-enabled.md) MUST change only through the verification events and the [machine of the lifecycle ↗](../sw-external-terms.md#state-machine); the same event twice MUST change nothing, and a [decision that arrives before the submission](../terms/verification-decision-ordering.md) MUST leave the shop decided. [proof: S03 AS-72] [code: packages/backend/libs/domains/tenancy/application/verification.service.ts#VerificationService]

## Behaviors
- **S03.B-01** Given a signed-in user and a [free slug](../terms/shop-slug.md), when they [`POST /shops`](../terms/post-shops.md), then the answer is `201` with [plan `STARTER`](../terms/plan-limit.md), status `ACTIVE`, verification `UNVERIFIED` and `payoutsEnabled` false. [proof: S03 AS-01]
- **S03.B-02** Given an 11th shop for one owner, when created, then [`409 shop_limit_reached`](../terms/shop-limit-reached.md) and nothing is stored. [proof: S03 AS-04]
- **S03.B-03** Given a member, when they `GET /shops/:shopId`, then they receive the shop, [`myRole`](../terms/my-role.md) and [`myPermissions`](../terms/permission.md). [proof: S03 AS-06]
- **S03.B-04** Given a user in three shops, when they list [`GET /shops/mine?limit=2`](../terms/get-shops-mine.md), then two items and an [opaque `nextCursor`](../terms/pagination-cursor.md) return, and the next page returns the third with `nextCursor: null`. [proof: S03 AS-07]
- **S03.B-05** Given a member with [`shop.manage`](../terms/permission.md), when the body carries `slug`, [`plan`](../terms/plan-limit.md) or [`status`](../terms/shop-status.md), then [`400 validation_failed`](../terms/validation-failed-error.md). [proof: S03 AS-08]
- **S03.B-06** Given an owner, when they [demote](../terms/shop-role.md) a member, then `204` and the target's [cache entry](../terms/cache-entry.md) is dropped. [proof: S03 AS-21, S03 AS-13]
- **S03.B-07** Given a member removed from a shop, when they subscribe to [`shop:<shopId>:live`](../terms/realtime-topic.md), then the [subscription is refused](../terms/realtime-subscription.md). [proof: S03 AS-27]
- **S03.B-08** Given a member removed with source [`sso`](../terms/membership-removal-source.md), when the removal commits, then their [sessions are revoked](../terms/session-revocation.md) with reason [`shop_membership_removed`](../terms/session-revocation.md). [proof: S03 AS-26]
- **S03.B-09** Given a member with [`members.manage`](../terms/permission.md), when they invite `" New@Mail.com "` as [`VIEWER`](../terms/shop-role.md), then `201` returns the lower-cased address, a [7-day expiry](../terms/pending-invite.md) and [no token](../terms/invite-token.md). [proof: S03 AS-28]
- **S03.B-10** Given an address that is a member or has a [pending invite](../terms/pending-invite.md), when invited, then [`409 already_member`](../terms/already-member.md) or [`409 invite_pending`](../terms/invite-pending.md). [proof: S03 AS-30]
- **S03.B-11** Given one [valid token](../terms/invite-token.md) and [two simultaneous accepts](../terms/invite-acceptance.md), then one `201` and one [`404 invite_not_found`](../terms/invite-not-found.md). [proof: S03 AS-34, S03 AS-32]
- **S03.B-12** Given an invitee who is already a member, when they [accept](../terms/invite-acceptance.md), then `200` with [`alreadyMember: true`](../terms/already-member-flag.md) and the role stays unchanged. [proof: S03 AS-35]
- **S03.B-13** Given a [pending invite](../terms/pending-invite.md), when a [manager](../terms/invite-manager.md) [revokes](../terms/invite-revoke.md) it, then `204` and the [token](../terms/invite-token.md) stops working; a [resend](../terms/invite-resend.md) gives a fresh expiry and kills the old token. [proof: S03 AS-36, S03 AS-37]
- **S03.B-14** Given an [anonymous caller](../terms/x-anonymous-id.md), when they `[GET /batch/shops?ids=…](../terms/batch-shops-lookup.md)`, then an array in request order of `{id, name, slug}` or `null` for [sandbox](../terms/sandbox-shop.md), [suspended](../terms/shop-status.md), deleting or deleted shops. [proof: S03 AS-80]
- **S03.B-15** Given an anonymous visitor, when they look up a [shop slug](../terms/shop-slug.md) for [SSO](../terms/shop-sso-lookup.md), then the answer is `200` or an [identical `404`](../terms/identical-not-found.md). [proof: S03 AS-46]
- **S03.B-16** Given [legacy sellers](../terms/legacy-seller.md), when [`ensureShopsForLegacySellers`](../terms/ensure-shops-for-legacy-sellers.md) runs twice, then each seller has exactly one shop and the second call creates nothing. [proof: S03 AS-62]
- **S03.B-17** Given a [live shop](../terms/live-shop.md), when [`ensureSandboxShop`](../terms/ensure-sandbox-shop.md) runs twice, then exactly one [sandbox shop](../terms/sandbox-shop.md) exists. [proof: S03 AS-63]
- **S03.B-18** Given a [`billing.subscription_plan_changed` event](../terms/subscription-plan-changed-event.md) with an [older version](../terms/aggregate-version.md), then the [plan](../terms/plan-limit.md) stays unchanged. [proof: S03 AS-73]
- **S03.B-19** Given an owner who sends [`PUT /shops/:shopId/sso`](../terms/shop-sso-config.md) without a [secret](../terms/secret-fields.md) for an existing configuration, then the stored secret is kept; [a replay of the same body gives the same result ↗](../sw-external-terms.md#idempotency). [proof: S03 AS-42]
- **S03.B-20** Given an owner of a shop with SSO, when they [`GET /shops/:shopId/sso`](../terms/shop-sso-config.md), then they see [issuer ↗](../sw-external-terms.md#jwt-iss), [client id ↗](../sw-external-terms.md#oauth-client-id), [default role](../terms/shop-role.md) and [`secretSet`](../terms/secret-set.md), never the secret; before any configuration the answer is [`404 sso_not_configured`](../terms/sso-not-configured.md). [proof: S03 AS-43]
- **S03.B-21** Given a member of a company who signs in through [`shop:<shopId>`](../terms/shop-sso-config.md), then the new account has no e-mail address and is [never linked to an existing account by address](../terms/oidc-account-link.md). [proof: S03 AS-50]
- **S03.B-22** Given a [platform administrator](../terms/is-admin.md), when they suspend an active shop, then [status `SUSPENDED`](../terms/shop-status.md), a [history row](../terms/shop-status-history.md) with actor and reason, [`tenancy.shop_status_changed`](../terms/shop-status-changed-event.md) and a [dropped provider cache](../terms/authorization-cache.md) follow; suspending a suspended shop or reinstating an active or closing one answers [`409 invalid_transition`](../terms/invalid-transition.md). [proof: S03 AS-65]
- **S03.B-23** Given an owner of a [closing shop](../terms/shop-status.md), when they [`DELETE /shops/:shopId/offboarding`](../terms/delete-shop-offboarding.md), then the shop is `ACTIVE` again with no [`purgeAt`](../terms/purge-at.md) and [`tenancy.shop_offboarding_cancelled`](../terms/shop-offboarding-cancelled-event.md) is published; on an active shop it answers [`409 invalid_transition`](../terms/invalid-transition.md). [proof: S03 AS-67]
- **S03.B-24** Given an owner, when they [`GET /shops/:shopId/export`](../terms/get-shop-export.md), then the answer carries the shop, members with addresses, invites and the [SSO configuration](../terms/shop-sso-config.md) without secrets, with [`Cache-Control: no-store` ↗](../sw-external-terms.md#cache-control-no-store), also while the shop is [suspended](../terms/shop-status.md) or closing. [proof: S03 AS-68]
- **S03.B-25** Given a closing shop, when the [purge job](../terms/shop-purge-job.md) runs before `purgeAt`, then nothing changes; after it, the shop is a [tombstone](../terms/shop-tombstone.md), the old [slug](../terms/shop-slug.md) can be registered again and the former owner gets `404`. [proof: S03 AS-69]
- **S03.B-26** Given a suspended or closing shop, then no invite is created, [resent](../terms/invite-resend.md) or accepted and no member is [provisioned](../terms/member-provisioning.md) from a [company sign-in](../terms/shop-sso-config.md). [proof: S03 AS-70]
- **S03.B-27** Given the [daily invite purge](../terms/invite-purge-job.md), when invites are 30 days past [expiry, revocation or acceptance](../terms/invite-lifecycle.md), then only those are deleted together with their addresses. [proof: S03 AS-70]
- **S03.B-28** Given a new shop, then its [directory row](../terms/shop-cell-directory-row.md) is [`pooled`](../terms/pooled-placement.md) at [version 1](../terms/directory-row-version.md) in the default or requested [allowed region](../terms/allowed-region.md), and the region changes only through the [administrator's move](../terms/shop-cell-move.md). [proof: S03 AS-51, S03 AS-56]

## Lifecycles
Shop status: `ACTIVE`, `SUSPENDED`, `DELETING`, `DELETED`. Allowed moves: `ACTIVE→SUSPENDED`, `SUSPENDED→ACTIVE`, `ACTIVE→DELETING`, `SUSPENDED→DELETING`, `DELETING→ACTIVE`, `DELETING→DELETED`. Every other pair is `invalid_transition`. [proof: S03 AS-64] [code: packages/backend/libs/domains/tenancy/domain/shop-status.ts#nextState]
Verification: `UNVERIFIED→PENDING`, `PENDING→VERIFIED` or `REJECTED`, `REJECTED→PENDING`; `VERIFIED` is final; `payoutsEnabled` is true only when `VERIFIED`. [proof: S03 AS-71] [code: packages/backend/libs/domains/tenancy/domain/verification-status.ts#applyVerification]
Invite: `pending`, `accepted`, `revoked`, `expired` (derived from time).

- Tables: `Shop`, `ShopMembership`, `ShopInvite`, `ShopSsoConfig`, `ShopDirectory`, `ShopStatusHistory`.
- Queue: `tenancy-invite-requested`.
- Events: `tenancy.shop_created`, `tenancy.shop_updated`, `tenancy.shop_status_changed`, `tenancy.shop_verification_changed`, `tenancy.shop_plan_changed`, `tenancy.member_added`, `tenancy.member_role_changed`, `tenancy.member_removed`, `tenancy.invite_created`, `tenancy.shop_cell_moved`, `tenancy.shop_offboarding_started`, `tenancy.shop_offboarding_cancelled`, `tenancy.shop_deleted`. State changes and events commit in one transaction; a failed outbox append rolls back the change. [proof: S03 AS-78]
- Consumes: `billing.subscription_plan_changed`, `identity.federated_identity_linked`, `shop.onboarding_submitted`, `shop.verified`, `shop.rejected`, `tenancy.member_removed` (to end open realtime streams).
- Jobs: `tenancy.purge-deleted-shops`, `tenancy.purge-expired-invites`, `tenancy.reseal-sso-secrets`. The former `tenancy.backfill-shops` no longer exists: owning domains backfill their own shop ids through `ShopProvisioningService.ensureShopsForLegacySellers`.
- Rate-limit policies: `tenancy.shop-create.user`, `tenancy.shop-write.shop`, `tenancy.invite.shop`, `tenancy.invite-accept.user`, `tenancy.invite-accept.ip`, `tenancy.sso-lookup.ip`.
- Configuration: `TENANCY_REGIONS`, `TENANCY_CELLS` (JSON cell name to database URL), `TENANCY_CELL_POOL_MAX` (default 5), `TENANCY_CELL_ACQUIRE_TIMEOUT_MS` (default 2000), `TENANCY_CELL_CONNECTION_LIMIT` and `TENANCY_CELL_RESERVED_CONNECTIONS` (defaults 100 and 20); startup fails when the pool arithmetic does not fit the cell.
- Authorization cache: shared store, entries live at most 15 s (negative 10 s); sensitive permissions always read the database.

## Decisions
- Tenant resolution runs once per request, so every check, log line and event carries the same shop. [proof: S03 AS-14]
- Not-found answers are uniform so callers cannot probe which shops exist.
- The authorization cache is never the source of truth; writers delete entries after commit.
- The last-owner invariant is enforced by the store under serializable isolation with bounded retry.
- Tenancy reads user data only through the identity directory and writes no other domain's tables.
- Connection routing is fail-closed: an unknown cell gives `503 cell_unavailable`, never the pooled database.
- Row-level security is set per transaction, not per session.

## Known gaps
- No test carries a proof id for AS-12 status-gate details beyond those listed in rule R-05; the `DELETING` gate (`409 shop_offboarding`) is not tied to a rule here.
- Seller onboarding (S04) produces `shop.onboarding_submitted` and `shop.verified` on `shops.events` with more fields than tenancy reads; `shop.rejected` is read but not yet produced by anyone. The plan event of billing (S17) is read by contract and not yet produced.
- The pooled database and every cell are checked for `statement_timeout`, but the cell database of the tests shares the server of the test database; a cell on its own server is covered only by configuration validation.
- A suspended shop cannot be closed through the API (the status gate allows only reading and exporting); the machine's `SUSPENDED→DELETING` move is for the platform and has no route.
- AS-27 and AS-83 realtime admission: only the removed-member case has a test (AS-27).
- AS-61 schema rules, AS-74 to AS-77 and AS-79, AS-81 are covered by tests but not summarised as separate rules here.
- Rules R-14 and R-18 are tied to tests only partly: the digest-only storage and the 429 limits come from AS-28 and AS-39 and are not checked separately.
