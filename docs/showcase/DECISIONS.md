# Showcase Program — Decisions Log

Goal: implement every system design from `interview-prep/10-System-Design`
and every pattern/lesson from the other `Interview-Prep` folders, **adapted to the marketplace
domain** (e.g. Reddit-style → product discussion posts; Ticketmaster → booking seats for
product launch events like an "iPhone launch"). Each feature must make business sense —
no implementation for the sake of implementation.

No "everything in Postgres" designs. | 2026-10-01 |
| D24 | **NoSQL as primary store when load demands it** (user, 2026-10-01): a feature's data may live *only* in NoSQL — Postgres is not mandatory. Split: **DynamoDB** (AWS-native, key-value / single-table design) for KV-lookup & per-entity hot data — share links, carts, sessions, idempotency records, courier positions history, seat-hold ledger. **Cassandra-compatible ScyllaDB** locally / **Amazon Keyspaces** on AWS for wide-row, write-heavy time series — feed timelines, live-stream comments, votes, activity logs, notification inbox. Postgres stays for relational invariants (money, orders, inventory truth, tenancy/RBAC). Every section states its store choice + partition key in its Scale block. | 2026-10-01 |
| D25 | **"Market-level scale" design targets** (user, 2026-10-01). Designed for, not proven at: catalog/search reads **100k RPS** peak; product page p99 < 100 ms (edge/CDN + Redis); writes on hot transactional paths (orders, bids, holds) **10k RPS** peak; flash-sale arrival **1M users / 5 min** behind admission control; analytics/event ingestion **200k events/s**; realtime **1M concurrent SSE/WS** across a gateway fleet; 100M users, 50M products. **Proof model**: (1) a capacity model per section (back-of-envelope: nodes, partitions, shards, memory, cost driver), (2) k6 proves **linear horizontal scaling** (throughput at 1→2→4 instances) + SLO thresholds at laptop scale, (3) scaling path documented: next step = cells per region (blast-radius isolation). Never claim untested absolute numbers. | 2026-10-01 |
| D26 | **CQRS is the default read-scaling pattern** (user, 2026-10-01): write model where the invariant lives (Postgres for money/orders/inventory; NoSQL per D24 otherwise) → **transactional outbox or Debezium CDC (Postgres WAL)** → Kafka (keyed by aggregate ID for per-entity ordering) → **projectors** build read models in the store that fits each query (Redis, ES, ScyllaDB/Keyspaces, DynamoDB, ClickHouse). Projectors are idempotent (version-guarded upserts), replayable (rebuild from topic / snapshot), and expose lag metrics. Reads never hit the write DB on the hot path. Generic framework: section F-05. | 2026-10-01 |
| D11 | Before adding a section, check existing README showcases 1–28 and `libs/common` — reuse/extend, don't duplicate. | 2026-10-01 |
| D27 | **Test pyramid across clients** (user, 2026-10-02): the backend API is the primary product (web, mobile and third-party bots all use it), so **API-level e2e is the deep layer** — every edge case, validation error, auth/tenant boundary, rate limit, idempotency and concurrency rule is tested there, once. **UI e2e (Playwright, FE phase) covers only happy paths / critical journeys** per client and never re-tests API edge cases; UI-only validation goes to FE unit tests. **Unit tests** only for complex isolated logic (math, parsing, merge rules, signatures). Duplicated full suites per client are rejected: AI makes writing cheap, not running/maintaining (CI time, flakiness). **Specs are the single source of truth**: section docs (Obsidian-compatible markdown) list acceptance scenarios with a *Test plan* table (scenario → API spec / UI journey / unit), and spec files name their section in `describe`. | 2026-10-02 |
