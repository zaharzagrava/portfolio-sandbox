# Priority-first flow order: reach a working browser flow early, then finish everything.
#   ORDER=by-flow COMMIT=1 scripts/sdd/implement-specs.sh
#
# "ID:P1" builds only the user stories of priority P1 (plus Setup and Foundational) of that spec; a plain "ID" later in
# the file builds the rest (the loop resumes at the first open task). The text after "# needs:" declares which
# capabilities a limited pass really uses, and scripts/sdd/check-order.py verifies it against the file. Nothing is
# stubbed: what a P1 pass cannot reach yet degrades the way the spec's own error handling says, and is listed under
# "Deferred until a later pass" in that spec's gaps.md.
#
# "!STOP <label> <message>" stops the run once for a human to try what exists (the next run passes it; with COMMIT=1 the
# marker specs/.checkpoints/<label> is committed, delete it to stop there again).
# The point: a problem between two capabilities shows at the first checkpoint that needs both.
#
# Why this is shorter than by-layer: the P1 stories of the storefront, checkout, login and shell need about 20 capabilities
# at P1 depth. Discussions, ask-this-product, share links, videos, sponsored cards, analytics, auctions, chat, flags,
# the public API and the widget belong to P2/P3 stories and wait for the second pass.
