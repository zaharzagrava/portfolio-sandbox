Seller dashboard, orders and money pages for a seller: /dashboard/seller/{shopId}/orders, then payouts, statements and exports in the same menu. First make real data: as a buyer register, buy 1 item, 3 items from one shop, and one cart with items from two shops (pay with the Visa test card, payment method id pm_card_visa); also leave one order unpaid and cancel one. Then as the owner: the orders table lists reference, status, items, subtotal and date, newest first, and shows NO buyer name, e-mail or address anywhere on the page, in the page source, or in the API answer (B-32); a slice holds only this shop's items from a mixed cart; subtotal equals the sum of the item prices times quantity in the shop currency (compare with the database "Order" rows); a paid order appears within a few seconds without a reload if the live panel is on; paging with ?cursor= over 45 orders with no duplicates; status filter if present; an empty shop shows an empty state, not a blank table; a bad cursor shows the friendly message. Money must be formatted from integer minor units and the currency of the same response (R-07): check a zero-decimal currency if the shop has one, and large amounts. Another seller's order id typed into the address must answer the same not-found as an unknown one. A STAFF member without orders.read must see the forbidden panel and the API must answer 403 (R-02); the sidebar must not offer links the member cannot use (R-01). Payouts and statements: the balance card equals the ledger (database, ledger entries for the shop), a statement lists the same orders as the orders page for its period and its totals add up, a payout request below the minimum or above the balance is refused with a clear message, a double press requests once; the export page: start an order export, see the state change, download, and check the file has the same rows as the screen and that cells starting with = + - @ are guarded. Suspended shop: reads work, writes disabled with the banner reason. Look at the table at 390 px (cards) and keyboard use. Out of scope: buyer side order pages, refunds by the admin.

You may: use the seller screens in the browser (Playwright as a library), call the API with curl as the signed-in seller (read the cookie or token the browser got), register extra accounts, open extra shops, read the database (SELECT only), read the API log, the queue server and the outbox. You may not: edit repository files, change the database by hand, delete other people's data, or report anything the page lists under "Known gaps". Record each finding in the report (REPORT_PATH) in the usual DEFECT block; it is copied to scripts/qa/findings.tsv and, for a seller run, to specs/.checkpoints/qa-seller/findings.tsv by the runner. Write each Playwright script you used into SCRIPTS_DIR with a name like shop-01-double-submit.js so a fixing agent can turn it into a test.
