As a signed-in user, open GET /auth/mfa and see state none, then POST /auth/mfa/enroll and read the otpauthUri and manualEntryKey, enrol again and check the old secret's code no longer confirms, then POST /auth/mfa/confirm with a current code and keep the ten recovery codes. Log out and sign in with a password: the login returns a challenge, so finish it with POST /auth/mfa/verify using a TOTP code, then repeat with a recovery code in lower case, with spaces and without the hyphen. Then try the Google path: GET /auth/oidc/providers, POST /auth/oidc/google/start with a returnTo, follow the callback, and link a Google identity from a signed-in session with /auth/oidc/google/link/start, list it at GET /auth/identities and unlink it with DELETE /auth/identities/:identityId. Try to break it: enrol while already enabled, confirm in state none, confirm with 5 or 7 digits, letters or an extra field, reuse a code in the same 30-second step, send the same confirm or the same recovery code twice at once, use a challenge token as Bearer on a management call, give a challenge that is expired or used up after 3 wrong codes, make 5 wrong codes and then a correct one, hammer verify past 20 a minute, and send a foreign Origin, an unknown provider, a returnTo like //evil.example, a backslash or a scheme, a callback with a missing, replayed or expired state, one opened in another browser, and another user's identity id. Check behind the screen that no status, callback URL or error body leaks a secret, token, code, state or e-mail, that callbacks are 302 with no-store, and that the database holds one identity per provider, spent codes and the last accepted step. Out of scope: password reset, shop enterprise providers, session cookies beyond verify.
