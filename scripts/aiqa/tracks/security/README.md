# Track "security": scanners over the code, the API and the built web app

Plain words: five ready-made tools look for known kinds of holes, so a human or an AI tester does not have to think of them. Semgrep reads the code for dangerous patterns (and our own rules: "a shop route without the shop guard"); gitleaks looks for passwords left in the code and its history; `pnpm audit` checks packages for published holes; Schemathesis fires thousands of odd requests at the written API description; OWASP ZAP browses the built web app looking for missing safety headers. Example: the audit found Next.js 16.3.8 with two critical published holes (S-1 in `findings/security.md`).

## What this finds that the other tracks miss

Holes nobody tests by hand: outdated packages with known attacks, a leaked secret, headers missing, an API route that crashes on odd input, a shop route added without the permission guard (our Semgrep rules). The map-driven tests check behaviour that is in the spec; scanners check what is not.

## Prerequisites

- Docker (the tools run as `docker run --rm` containers; no compose stack is started or stopped) and network access to pull images and read advisory data.
- `static` mode needs no running app. `api` and `zap` need the dev stack (API :8000). `api` starts the public-api app on :8005 by itself and stops it again; `zap` builds/starts the production web server on :3100 (`tracks/prod-build/prod-server.sh`) and stops it only if it started it.
- Memory: the production build is the heavy part (a few GB while building); do not run it next to the backend test stack or a full Playwright run.
- A throwaway test API key (`sk_test_...`) is made for the demo seller and revoked at the end (the script prints `revoked test key: 204`).

## How to point it at a NEW feature

1. New code folders: add them to `WEB_DIRS` / `BACK_DIRS` at the top of `run.sh` (they are the Semgrep scope).
2. New routes in the written API description: Schemathesis only reads the paths matching `--include-path-regex '^/v1/(products|stock|orders|batch)'`; widen the regex for new resources.
3. New rules: add a rule to `semgrep-rules.yml` and a bad sample that must trigger it in `selftest/` (the script warns if a rule does not fire on its sample, so a broken rule never gives a false "clean").
4. New pages for ZAP: it scans from the start page only; add extra start URLs or a context file when a feature sits behind a sign-in.

## Commands

```
scripts/aiqa/tracks/security/run.sh static     # Semgrep, gitleaks, pnpm audit
scripts/aiqa/tracks/security/run.sh api        # Schemathesis (ST_EXAMPLES=25 and ST_SECONDS=240 are the defaults)
scripts/aiqa/tracks/security/run.sh zap        # OWASP ZAP baseline against the production build
scripts/aiqa/tracks/security/run.sh            # all three
```

## How to read the results

Per tool: `scripts/aiqa/findings/security-<tool>.md` (generated by `summarize.mjs`; plain language, every flag with file and line). The human verdict for each flag (real or false alarm, with the reason) lives in `tracks/security/triage/<tool>.md` and is appended at every run, so a re-run never loses it. The short list of real findings is `scripts/aiqa/findings/security.md` (S-1, S-2, ...).

## How results become map lines, findings and register entries

Security findings do not have map lines by default. A real finding gets a row in `docs/work/qa-bug-register.md` and, when it can be tested in the browser or API, a permanent test (for example the "no buyer id in the seller order list" rule is both a Semgrep rule and a spec). A rule that must never come back becomes a Semgrep rule plus its selftest sample.

## Known limits

- Semgrep and ZAP flag things that are not bugs (dev-only, test files); every flag needs a hand verdict.
- Schemathesis only knows what the written API description says; that description is looser than the real rules in 14 places (S-7).
- ZAP baseline is passive (it does not attack); a real penetration test is not part of this track.
- Dependency advisories change daily: the audit result is only valid on the day it ran.
