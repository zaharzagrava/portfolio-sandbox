# Research: W04 — Seller dashboard

Facts verified in the tree on 2026-10-17 (file reads and greps; not behaviour reviews) and the decisions taken. `NEEDS CLARIFICATION`: none left. `questions.md` defaults stand.

## Verified facts

- **R-01 Backend routes exist.** Domain controllers serve: `GET /shops/:shopId/{stats,rank,dashboard/today}` (seller-insights); `shops`, `shops/mine`, `shops/:shopId`, members, invites (`resend`, delete), `shop-invites/accept`, `shop-roles` (tenancy); `shops/:shopId/orders` (orders); `keys` (create, list, rotate, revoke), `api-version` (get, put), `logs`, `usage` (developer-platform); webhooks (create, list, get, patch, enable, disable, rotate-secret, expire-previous-secret, attempts, events/:eventId, replay, ping, delete) and `webhook-event-types`; `shops/:shopId/products/search` (discovery). So `gaps.md` E2, E5–E10 are *present*; W04 only has to consume them. Still to confirm per route in Phase 0 by reading the response schema: key and log list pages return `{items, nextCursor}`; `GET keys` accepts `limit`/`cursor`.
- **R-02 BFF path.** The forwarder (`composition/bff/forward/route-table.ts`) allows every path except `bff/*`, `graphql` and credential routes, and routes `streams`/`assistant`/`live/*/events` to the SSE origin. Web `next.config.ts` rewrites `/api/bff/:path*` to the BFF and `/api/:path*` to `/api/bff/f/:path*`. So `/api/shops/**`, `/api/shop-roles`, `/api/shop-invites/accept`, `/api/streams` need no forwarder change (E4 closed), and the aggregate is reached as `/api/bff/seller/:shopId/overview` like W03's `/api/bff/orders/:id`.
- **R-03 Overview aggregate missing.** `composition/bff` has cart, orders, page (product), session, graphql, forward; no seller aggregate. `packages/contracts/src/bff` has no `seller-overview.ts`. Built in Phase 1 on the `OrderPageService` pattern (`CredentialsGuard`, `@RateLimit`, `ZodPipe`, `Cache-Control: private, no-store`, abort on close, per-section outcome via `page/section-outcome.ts`).
- **R-04 Contracts have source** (gap T9/E12 closed): `shopSchema` (`myRole`, `myPermissions` both **optional**), `shopListItemSchema`, `shopMemberSchema`, `shopInviteSchema`, `shopRolesSchema`, `productMemberSchema`, `productPageSchema`, `shopProductSearchResponseSchema`, `sellerStatsSchema`, `dashboardTodaySchema`, `shopRankSchema`, `liveDashboardFrameSchema`, `shopOrderPageSchema` (items carry `buyerId`, never rendered), `apiKey*`, `apiVersionStateSchema`, `requestLogPageSchema`, `usageReportSchema`, `webhook*`. Missing: `sellerOverviewResponseSchema`, a `shopRolesSchema` check against `GET /shop-roles` body (S03 AS-82), `problemSchema` use by W04 (W01's `problemFromError` is used instead).
- **R-05 Stream.** `lib/realtime/user-stream.ts` already has `subscribeUserEvents(handler, userId)`, `addTopic(topic, eventTypes)` (ref-counted; recreates the connection once when the topic set changes), `onTopicEvent`, `onResync`, `onRevoked`, health/poll snapshot, `watchStreamSilence`. W04's `subscribeTopic(topic, handler)` is a thin wrapper; it adds no connection.
- **R-06 Auth helpers exist** (`lib/auth/guards.ts`, `session.server.ts`, `return-to.ts`, `session-ended.ts`, `components/auth/problem-alert.tsx`, `lib/api/errors.ts`/`problem-copy.ts`, `lib/api/csrf.ts`, `lib/api/idempotency.ts`, `hooks/use-auth-actions.ts` with refresh). Phase 0 reads their exact export names and uses them; W04 never re-implements.
- **R-07 Test tooling is installed** (RTL, user-event, jest-dom, MSW 3, axe-core/playwright, vitest include widened; Playwright `mobile` 390×844 and `desktop` 1280×800 projects; `tests/visual/` exists with `axe.ts`). `tests/seller.spec.ts` is the old single journey (uses `data-testid`).
- **R-08 Config.** `PLATFORM_CURRENCY` exists in `libs/common/config/api-config.service.ts` (backend); web `lib/config.ts` has neither it nor `PUBLIC_API_BASE_URL`. Added to web server config (B-3) with fraction digits taken from `Intl.NumberFormat(…).resolvedOptions()`; both are server-only values handed to client components as props of the form.
- **R-09 Existing dashboard pieces.** `app/dashboard/seller/[shopId]/{balance-card.tsx,payouts,statements}` exist (J01/S14–S16); the draft `seller/view.tsx`, `inventory/view.tsx`, `developers/{api-keys,webhooks}/view.tsx`, `components/dashboard/dashboard-shell.tsx` (client guard, role claim, `Loading...`) and `lib/api/{shops,developers}.ts` are the targets to replace. `lib/query-keys.ts:87-89` has the unused `seller.dashboard/products`.

## Decisions

| # | Decision | Rationale | Alternatives |
|---|---|---|---|
| R-10 | `myPermissions` is optional in `shopSchema`; `shopCan` treats a missing array as "no permission" for presentation and the UI still handles the API's `403`. Phase 1 (B-4) checks the controller always sends it and makes it required in the schema if so. | fail closed in presentation; API stays the authority (VI.5) | optional-means-all (rejected: leaks controls) |
| R-11 | The overview is **server-seeded and client-refetched**: the page (Server Component, behind Suspense) calls `lib/server/seller.server.ts` to read the aggregate as the member and passes it as `initialData` to `OverviewView` (TanStack Query, key `queryKeys.seller.overview`). A section retry refetches the same aggregate (`errors[]` is per section; the retry replaces only failed sections in the render, the key is one). | one home for server data (VI.4), no waterfall | four section queries (rejected: N+1, FR-017) |
| R-12 | No `@next/playwright` `instant()` dependency; instant-navigation is covered by `next build` validation and the visual skeleton specs. | the optional helper adds a dependency for a check `next build` already makes | install it (kept as a later option) |
| R-13 | The invitation journey needs the invite link. `tests/helpers.ts#readInviteLink` reads it from the dev notification outbox if S28/W01 expose one. If none exists, `seller-team.spec.ts` is marked blocked with the reason (L-003: no hollow test, no token in a normal API response); the unit test `accept-invite.test` still proves AS-80..AS-82. | the link is a credential | parse the e-mail in the page (rejected) |
| R-14 | Optional event consumers (`catalogsync.offline_conflict_opened` to S28/S43/S40) are not W04 work; W04 lists conflicts through the S09 HTTP routes only (F3). | the event has other owners | subscribe from the UI (rejected: no topic for it) |
| R-15 | Forms: plain controlled state with one `useActionState`-free `useReducer` per dialog; field errors from `problemFromError(...).errors`; `react-hook-form` only where a form already uses it (none in the seller area today). | spec rules (validate after first blur/submit, map `errors[]`) are simpler to unit-test without a form library | `react-hook-form` everywhere |
| R-16 | Tables are real `<table>` at ≥ 1024 px and the same markup restyled as cards below 640 px with CSS (`display: block` rows, `data-label` pairs rendered as visible text), never a second DOM, so tests query one structure. | AS-95 table semantics + AS-97 cards | two components |
| R-17 | Dialog / sheet / menu primitives: the existing radix-based `components/ui/*`; a new `ConfirmDialog` and `RevealSecretDialog` wrap them (Escape and outside click disabled for reveal). | focus trap, return focus, `aria-*` come from the primitive; the only new code is the rules of AS-46/AS-94 | custom dialog |
| R-18 | Rate-limit countdown is a hook `useCountdown(seconds)` that announces start and end through one polite region and ticks without announcing (AS-90). | one implementation for AS-06, AS-64, AS-77, AS-90 | per-screen timers |
| R-19 | Live frame throttling: invalidation of `today`/period keys at most every 30 s uses a timestamp ref in the panel (not state). `Reconnecting…` after 5 s without a frame uses one timer reset on each frame. | AS-21, AS-24 | per-frame invalidation (rejected) |
| R-20 | Phase 9 screens are planned as independent slices; each ships only with its own backend contract file read first (`specs/domains/<id>/contracts/*`), and any mismatch found is written to `gaps.md` as a sibling follow-up instead of changing the sibling's spec. | cross-spec rule 1 | build against assumptions |
| R-21 | Living spec: new page `docs/spec/capabilities/W04-seller-dashboard.md`; no human-signed page changes in this plan. If W03's page needs the `subscribeTopic` addition mentioned, it is a bullet under "Sibling-spec follow-ups" in `gaps.md`, not an edit. | rule 0 and 1 | editing W03's page |
