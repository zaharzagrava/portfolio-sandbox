## Scope

In scope (every screen and state a visitor or member reaches through these flows):

- **Home** (`/`): hero with the search box, category shortcuts, the **Trending now** rail with its fallback, and the project's static showcase blocks.
- **Search box and autocomplete**: the combobox used on Home, on the search page and (through W07's navbar) on every other page.
- **Search results** (`/search`): results grid, **facets**, filters, **sort**, cursor paging, meaning (semantic) search, "available for pickup near me" mode, sponsored labels, click logging, every loading, empty, error and degraded state. All view state is in the URL.
- **Rails**: "Trending now" (S35) on Home, "Frequently bought together" (S34) and "Trending in {category}" (S35) on the product page.
- **Product page** (`/products/[productId]`, plus the `/p/[productId]` redirect): summary, gallery, shop, purchase area (hosting W03's add-to-cart and the chat link), **Pickup near me** with its map view, **Discussions**, **Ask this product**, **Share link**, product videos and the sponsored slot (both conditional, P3).
- **Visitor events** the storefront emits (`product_view`, `video_view`) and the first-party **attribution cookie** captured from `?ref=`.
- **Rendering and data-flow rules** of these pages: Server Components by default, what is cached and what streams, which state lives where (constitution VI), and the accessibility and layout baseline at mobile (≤ 640 px) and desktop (≥ 1024 px).

Out of scope (owned elsewhere):

- What the backend guarantees (ranking, visibility, typo tolerance, caching headers, rate limits, moderation, retrieval): **S32, S33, S34, S35, S19, S25, S47, S48, S37, S36, S30, S29, S39**. This spec cites their requirement IDs and specifies only how the UI shows and handles the outcome (VII.7).
- The navbar frame (logo, theme, cart, notifications), footer, global not-found and error pages, security headers and CSP: **W07**. W02 supplies the search box component that the navbar mounts.
- The cart, checkout and the add-to-cart control itself (**W03**), seller chat (**W05**, linked only), the seller screens that create products, pickup points, documents and videos (**W04**), sign-in screens and session handling (**W01**).
- Shop storefront pages and brand stories (no web capability owns them yet; the shop name on the product page is therefore text, not a link), reviews, wish lists, compare, flash sales and auctions (their sections in the S48 aggregate are ignored by W02).
- Localisation: all copy is English; money is formatted from `priceMinor` and `currency` with the browser's English locale.

## Routes and visible states

| Route | Who can open it | Visible states |
|---|---|---|
| `/` | Anyone | Static shell; rail loading (skeleton); rail loaded; rail fallback to catalogue; nothing to show ("No products yet."); category shortcuts present or omitted |
| `/search` | Anyone | Static shell with the box and skeletons; results; results refreshing (previous results dimmed); empty; each error of AS-24; near-me states (AS-28..AS-31); meaning-search degraded notice |
| `/products/[productId]` | Anyone | Loading skeleton; full page; **partial page** (any optional section missing); not found; temporarily unavailable; tabs `details`, `pickup`, `ask`, `discussions` |
| `/p/[productId]` | Anyone | `308` redirect to `/products/[productId]`, query kept; a non-UUID id renders the not-found page |
| Same-origin web endpoint for attribution | The product page only | Sets the first-party `ref` cookie (FR-124); never a page |

**URL view state** (constitution VI.4). `/search`: `q`, `category`, `brand`, `minPriceMinor`, `maxPriceMinor`, `minRating`, `inStock`, `sort`, `semantic`, `near`, `radiusKm`, `cursor`. `/products/[productId]`: `tab` (`details` default, `pickup`, `ask`, `discussions`), `sort` and `window` (discussion list), `post` (the expanded discussion), `ref` and `ad` (attribution inputs, FR-124). Unknown or invalid values are dropped from the address bar, never echoed (AS-12). **No coordinates, token, e-mail or question text ever appears in a URL** (AS-31).

Every acceptance scenario has a stable ID `AS-nn`; `test-plan.md` maps each to exactly one row. Backend rules are cited, never re-specified: "S32 AS-14" means scenario AS-14 of the S32 spec. Visible copy is in the *Copy catalogue* (FR-170..FR-176).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Land on Home and start shopping (Priority: P1)

A visitor opens the site and, within one screen, can search, jump to a category, or open a trending product.

**Why this priority**: it is the front door; a broken rail or slow shell is the first impression and the most visited page.

**Independent Test**: open `/` against the seeded stack, with the trending endpoint healthy, then forced empty, then forced to fail.

**Acceptance Scenarios**:

1. **AS-01** — **Given** a visitor on `/`, **Then** the first response contains the static shell (hero with `h1`, the search box, the showcase blocks) and, inside a boundary with a same-size skeleton, the category shortcuts and the **Trending now** rail, which stream in; the page is usable before they arrive. **Category shortcuts** are the first eight category facets of a browse search (S32 AS-15), shown as links to `/search?category=<key>`; when that call fails, the row is omitted without any message. (P0902; S32 AS-15.)
2. **AS-02** — **Given** the trending endpoint answers `200` with items, **Then** the rail titled "Trending now" shows at most eight cards in the given order (rank ascending), each a single link to `/products/<productId>` whose accessible name is its title and price; each shows the rank badge ("1", "2", …), the title as text, the category and the price formatted from `priceMinor` and `currency`; the section shows no implementation note; a "View all" link goes to `/search`. (S35 AS-41, FR-027; S35 AS-01.)
3. **AS-03** — **Given** the trending endpoint answers `200` with empty `items`, `429`, `503` (`trending_unavailable`), an invalid body, or cannot be reached, **Then** the rail is replaced by the first eight products of a browse search (same card as AS-10) under the same heading, with no error text; **Given** that browse search also fails or returns nothing, **Then** the section shows "No products yet." and the page is otherwise intact; a failed rail load is never reused for the next visitor. (S35 AS-41, FR-027; S32 AS-04, AS-13.)
4. **AS-04** — **Given** `/` at ≥ 1024 px and at ≤ 640 px, **Then** the page has the structure of FR-180 and the focus order: skip link, navbar, search box, category shortcuts, "Trending now" cards in rank order, "View all", showcase links, footer.

### User Story 2 — Type, get suggestions, search (Priority: P1)

A shopper types in the search box, sees suggestions that keep up with typing, and searches by picking one or pressing Enter.

**Why this priority**: it is the main way to find a product.

**Independent Test**: type `iph` against a seeded index; pick a suggestion; observe the URL. A component test with a stubbed network proves the races.

**Acceptance Scenarios**:

1. **AS-05** — **Given** the published index and visible products (S33 dataset S), **When** a visitor types `iph` in the search box, **Then** a list shows `iphone 17`, `iphone charger`, `iphone 17 pro max case`, `Apple iPhone 17 Pro 256GB`, `iPhone 17 Silicone Case` in the order the API gave; choosing `iphone 17` runs a search and the address becomes `/search?q=iphone+17`. (S33 AS-55, FR-042.)
2. **AS-06** — **Given** the list is open, **Then** the box follows the combobox pattern: the input has role `combobox` named "Search products", `aria-expanded`, `aria-controls` the listbox, `aria-autocomplete="list"` and `aria-activedescendant`; options have role `option`; **Down** opens the list and moves to the next option (wrapping), **Up** to the previous, **Enter** on an active option searches for it, **Enter** with none active searches the typed text, **Escape** closes the list (a second **Escape** clears the text), **Tab** closes the list and moves on; focus never leaves the input; a polite status line announces "{n} suggestions available" or "No suggestions" after each settled request. (S33 FR-042.)
3. **AS-07** — **Given** the visitor types `iph` then `ipho`, **When** the answer for `iph` arrives after the answer for `ipho`, **Then** the list shows the suggestions of `ipho`; superseded requests are cancelled; at most one request is sent per 150 ms of typing; a prefix seen in the last 60 seconds is shown from the cache without a request; no request is sent for an empty or whitespace-only box. (S33 AS-56, FR-042.)
4. **AS-08** — **Given** the suggestions request answers `429`, `400`, `5xx`, an invalid body, or fails to connect, or answers `200` with an empty list (also with `degraded` reasons), **Then** the list simply stays closed (or shows "No suggestions" for an empty `200`), the typed text and the ability to submit are untouched, no toast or alert appears, and the next keystroke tries again. (S33 AS-16..AS-19, AS-09, AS-10, FR-009.)
5. **AS-09** — **Given** the box, **Then** the text is trimmed before use; submitting an empty or whitespace-only box on `/search` shows browse results (`q` removed), on any other page it goes to `/search`; the box accepts up to 100 characters (`maxLength`) and a longer paste is cut to 100 with a visible "Search is limited to 100 characters." hint; a **Clear** button (named "Clear search") appears when text is present, empties the box, keeps focus in it and closes the list; suggestion text is rendered as text, never as HTML. (S32 FR-002; S33 FR-002.)

### User Story 3 — Browse and narrow search results (Priority: P1)

A shopper sees results, narrows them with facets and filters, sorts, pages, and can send the exact view to someone by copying the address bar.

**Why this priority**: it is where the purchase decision is narrowed; every state must be reachable and recoverable.

**Independent Test**: open `/search?q=espresso`, apply a category facet, a price range and a sort, page forward, reload, go back; then force each error.

**Acceptance Scenarios**:

1. **AS-10** — **Given** `/search?q=espresso`, **Then** the first response already contains the results (rendered on the server), an `h1` "Results for “espresso”", a count line ("{n} results", "1 result", or "10,000+ results" when `total.exact` is false), and a grid of cards in API order; each card is one link to the product with its image (or the neutral placeholder when `imageUrl` is `null`), title, brand, rating ("Rated 4.5 out of 5"; nothing when 0), price from `priceMinor` and `currency`, "Out of stock" when `inStock` is false, and the "Sponsored" label when `sponsored` is true. (S32 AS-01, FR-009.)
2. **AS-11** — **Given** any combination of search, filters, sort and page, **Then** it is fully described by the address bar: loading that address in a new tab, reloading, and the browser's back and forward buttons restore exactly that view (inputs, selected facets, sort, page); changing a control updates the address without a full page load; changing anything but the page removes `cursor`; the scroll position is kept on filter changes and reset to the top of the results on a page change. (P0901; constitution VI.4.)
3. **AS-12** — **Given** an address with unknown parameters, the legacy names (`priceMin`, `priceMax`, `rating`, `nearMe`, `size`, `from`), repeated parameters, values out of range (`minRating=9`, `sort=popular`, `inStock=maybe`, `q` over 100 characters), a price range with min above max, or a `cursor` that is not an opaque token, **Then** the page never shows an error for them: it renders the view with the invalid or unknown parts dropped (the first value of a repeated parameter wins; a `q` over 100 characters is cut to 100) and replaces the address with the cleaned one without adding a history entry; the API is never sent a parameter it would answer `400` for. (S32 AS-10, FR-001.)
4. **AS-13** — **Given** the results, **Then** a control named "Sort by" offers **Relevance** (shown only when `q` is present; default), **Price: low to high**, **Price: high to low**, **Newest**; choosing one sets `sort` (omitted for the default) and shows the first page in that order; without `q` the default order is the API's browse order and the control reads "Featured". (S32 AS-08, FR-007.)
5. **AS-14** — **Given** the response carries `facets`, **Then** the filter panel shows, with the counts the API gave and nothing computed locally: **Category** and **Brand** (top 20 each; the key is displayed with hyphens as spaces and a capital first letter, the exact key is what is sent), **Price** with the four bands "Under $25", "$25 to $50", "$50 to $100", "Over $100" (band amounts follow the response currency), and **Rating** with the average ("Average rating 4.3"); choosing a category or brand keeps its sibling values visible with their counts (S32 AS-16), choosing another value of the same group replaces the first (single choice per group), and choosing the selected value again removes it; a facet group with no values is not rendered. (S32 AS-15..AS-17, FR-010.)
6. **AS-15** — **Given** active filters, **Then** each appears as a removable chip above the grid ("Category: shoes ✕", "Brand: Acme ✕", "Price: $10 – $50 ✕", "4 stars & up ✕", "In stock ✕") whose remove button is named "Remove filter {label}"; **Clear all filters** removes every filter but keeps `q` and `sort`; removing a filter returns focus to the results heading.
7. **AS-16** — **Given** the **Price** group, **Then** it has two fields "Minimum price" and "Maximum price" in the response currency's major units (not minor units); applying (**Apply** or Enter in a field) writes `minPriceMinor` / `maxPriceMinor`; a minimum above the maximum shows "The minimum price can't be higher than the maximum." under the fields and sends nothing; non-numeric, negative or more-than-two-decimals input shows "Enter a price like 25 or 25.50."; empty fields remove the bound; choosing a band fills both fields. (S32 AS-10 `invalid_price_range` is never reached from the UI.)
8. **AS-17** — **Given** the filter panel, **Then** **Rating** offers "4 stars & up", "3 stars & up", "2 stars & up", "1 star & up" (sets `minRating`), and an **In stock only** switch (sets `inStock=true`); both are plain filters (S32 AS-14).
9. **AS-18** — **Given** a result with a `nextCursor`, **Then** a **Next page** link below the grid keeps every parameter and sets `cursor`; the first page has no previous link; later pages show **Back to first page** (removes `cursor`) and the browser's back button returns to the previous page; the page size is 24; the count line is the same on every page (the cursor carries no page number, so no "page n of m" is shown); an item that appears on two pages (the index moved between fetches) is shown once per page and not duplicated within a page. (S32 AS-09, FR-008.)
10. **AS-19** — **Given** a search that matches nothing (also a filter value matching nothing), **Then** the grid is replaced by "No products match your search." with the active chips, a **Clear all filters** button when filters are on, and, with `q` present, "Try a different spelling or fewer words." — never an error, never an infinite skeleton. (S32 AS-14, AS-02.)
11. **AS-20** — **Given** `/search` with no `q`, **Then** the page is in browse mode: `h1` "All products", the sort control reads "Featured" (S32 AS-04, AS-08), and no meaning-search switch is offered.
12. **AS-21** — **Given** `q` is present, **Then** a switch named "Match by meaning" is offered; turning it on sets `semantic=true`, shows at most one page of the closest matches with the line "Showing the closest matches" and no **Next page**, hides facet counts and the Category/Brand lists with "Counts aren't available for meaning search." (active filters stay removable), and keeps price, rating and stock filters; **Given** the response is `mode: "lexical"` with `degraded: ["semantic_unavailable"]`, **Then** a status notice reads "Meaning search is unavailable right now. Showing keyword results." and the switch stays on; turning it off restores the keyword view. (S32 AS-18..AS-20, FR-014, FR-015.)
13. **AS-22** — **Given** an item with `sponsored: true`, **Then** its card carries the visible label "Sponsored" (not colour-only, announced before the title) in the same grid position the API gave; sponsored items are never moved or de-duplicated by the UI. (S32 AS-05, FR-024; S36 obligations.)
14. **AS-23** — **Given** results with a `searchId`, **When** the shopper opens a result (click, Enter, or middle-click), **Then** exactly one click record `{searchId, productId, position}` is sent (a keep-alive background request that never delays or blocks the navigation); an invalid, expired or rate-limited record (`422 invalid_search_id`, `429`, network) is ignored silently; the position is the API's `position`. (S32 AS-70, AS-71, FR-053.)
15. **AS-24** — **Given** a search request fails, **Then** the results area shows exactly one alert (never an empty grid, never the previous results as if current): `422 invalid_cursor` — the page restarts from the first page and a status notice reads "That page is no longer available. Showing the first page."; `429 rate_limited` — "Too many searches. Try again in {wait}." with **Try again** enabled when the wait has passed; `503 search_unavailable`, `5xx`, no body — "Search is temporarily unavailable. Try again." with **Try again** and "Reference: {requestId}" when the body has one; no network — "You appear to be offline. Check your connection and try again." and an automatic retry when the browser comes back online; `422 invalid_price_range`, `semantic_requires_query`, `unsupported_combination` (not reachable from the UI) fall back to the cleaned view of AS-12. The search box and filters stay usable in every case. (S32 AS-09, AS-10, AS-12, AS-13, AS-19; constitution V.3.)
16. **AS-25** — **Given** the first view of `/search?…`, **Then** the server-rendered results appear with no skeleton flash; **Given** a filter, sort or page change, **Then** the previous results stay on screen at reduced emphasis with `aria-busy="true"` on the region until the new ones arrive (no empty flash, no layout jump), and a polite status announces "{n} results" when they do; **Given** a view visited in the last 60 seconds, **Then** it appears immediately from the cache and is refreshed in the background. (P0902: transitions keep typing and clicking responsive.)
17. **AS-26** — **Given** `/search` at ≥ 1024 px and at ≤ 640 px, **Then** the structure is FR-181: desktop has a left filter column (sticky) beside the grid; mobile has a **Filters** button (showing the active-filter count) that opens the same panel as a bottom sheet with **Show {n} results** and **Clear all**, the sort control stays in the toolbar, and the grid is two columns.
18. **AS-27** — **Given** `/search`, **Then** there is exactly one `main` landmark (the site layout's), one `h1`, the filter panel is a labelled `form` landmark ("Filters"), the results region is labelled "Search results", the count line and "Showing the closest matches" are in the region, focus is never moved by a filter change (the control keeps focus) except after removing a chip (AS-15) and after page change (focus goes to the results heading), and everything is operable by keyboard alone (FR-186).

### User Story 4 — Find pickup availability near me in search (Priority: P2)

A shopper switches to "available for pickup near me" and sees products that a nearby pickup point holds, with the distance.

**Why this priority**: it is the local-commerce differentiator, but search works without it.

**Independent Test**: grant a fake location in the browser, switch it on, observe the list; then deny it.

**Acceptance Scenarios**:

1. **AS-28** — **Given** a shopper on `/search`, **When** they turn on **Available for pickup near me** and allow location sharing, **Then** the address gains `near=1&radiusKm=5`, the grid shows products with a visible in-stock offer within the radius, one card per product, each adding "{distance} away · {pickup point name} · {quantity} available" (distance as "850 m" under 1 km and "2.4 km" otherwise), ordered as the API gave them, with a **Radius** control (1, 2, 5, 10, 20, 50 km) that changes `radiusKm`; **Next page** follows `nextCursor` as in AS-18. (S19 AS-01, AS-05, FR-020.)
2. **AS-29** — **Given** the location request is denied, unsupported, insecure, or times out (10 seconds), **Then** the switch returns to off with the status message "Location is off. Allow location access in your browser to find pickup near you." (denied), "Your browser can't share its location." (unsupported or insecure), or "We couldn't get your location. Try again." (timeout or unavailable) and a **Try again** button where retry can help; no request is sent to the API and the address is left without `near`.
3. **AS-30** — **Given** near-me mode is on, **Then** price, brand, category, rating, stock, sort and meaning controls are disabled with the note "Not available together with pickup search." (their values are kept and return when the mode is turned off), the heading is "Pickup near you" with `q` when present, and the count line is omitted (the API returns no total); errors follow AS-24 (`429`, `503 search_unavailable`, network) with the pickup wording "Pickup search is temporarily unavailable. Try again."; an empty answer shows "No pickup points near you have these products. Try a larger radius." with the radius control. (S19 AS-08, AS-09, FR-022, FR-024, FR-027.)
4. **AS-31** — **Given** near-me mode, **Then** the coordinates exist only in memory of the open page (never in the address, storage, cookies, logs, analytics or a `Referer`), are rounded to three decimals before sending, are requested again after a reload (the browser remembers the permission), and the API call is made directly by the browser to the same-origin endpoint with no caching. (S19 FR-052.)

### User Story 5 — Read the product page (Priority: P1)

A shopper opens a product and sees what it is, what it costs, whether it is available, who sells it, and what else to look at — even if some optional parts are down.

**Why this priority**: this is where the purchase happens; partial responses are the reason the BFF exists.

**Independent Test**: open a seeded product; then stub each optional section to fail, one at a time, and all at once.

**Acceptance Scenarios**:

1. **AS-32** — **Given** a visible product, **Then** the page shows: a breadcrumb "Home › {category} › {title}" (category links to `/search?category=<category>`), the `h1` title, the brand (a link to `/search?brand=<brand>`), the rating ("Rated 4.5 out of 5" or "Not rated yet" when 0), the price from `priceMinor` and `currency`, "In stock" or "Out of stock", the shop line (AS-35), the description as plain text with line breaks kept (never interpreted as HTML), tags as links to `/search?q=<tag>`; the document title is "{title} · Marketplace"; the description, canonical URL, Open Graph data and structured data (`Product` with `priceCurrency` from the response, `availability`, `brand`, `image`, `url`) describe the same product, with `<` escaped in the structured data. The page shows no stock count (the public view has none). (S05 AS-23; S48 FR-001.)
2. **AS-33** — **Given** the product cannot be shown, **Then** exactly one full-page state replaces the product area (navbar and footer stay): a malformed id, or `404 not_found` (unknown, archived, sandbox or hidden — the same page for all, S05/S48 FR-006) — "We couldn't find that product." with a link "Search products"; `503 upstream_unavailable` or `503 overloaded` — "This product page couldn't be loaded right now. Try again." with **Try again** and "Reference: {requestId}"; `502 upstream_invalid` and other `5xx` — the same copy; `429 rate_limited` — "Too many requests. Try again in {wait}."; no network — "You appear to be offline. Check your connection and try again."; an unknown id is marked `noindex`. (S48 AS-07..AS-11, FR-006.)
3. **AS-34** — **Given** the aggregate answers `200` with some sections `null` and entries in `errors`, **Then** the page renders everything it has and only the missing part is replaced: a missing `shop` hides the shop line; missing `recommendations`, `trending` or `videos` hides that section entirely (no heading, no message); a missing `gallery` shows the placeholder image; the product summary, price, purchase area and tabs are never blocked by any optional section; the `errors` codes are never shown to the visitor; a response with a non-empty `errors` is reused for no more than 5 seconds. (P0402; S48 AS-12..AS-15, FR-005, FR-008; S34 FR-030; S35 FR-027.)
4. **AS-35** — **Given** the `shop` section `{id, name, slug}`, **Then** the shop line reads "Sold by {name}" as text; with `shop: null` the line is omitted; the shop name is rendered as text; there is no link until a shop page exists. (S48 FR-001; S05 questions.)
5. **AS-36** — **Given** the gallery, **Then** the main image shows the first gallery item at its `feed` size with the product title as alt text, thumbnails (when there is more than one) switch the main image and are buttons named "Show image {n} of {total}" with `aria-current` on the shown one, **Full** size opens in a lightbox dialog that closes with **Escape** and returns focus to the thumbnail; with no gallery or a failing image, a neutral placeholder block of the same size is shown (no third-party placeholder service); the first image is loaded eagerly and the others lazily; image boxes reserve their aspect ratio so nothing shifts. (S29 AS-38.)
6. **AS-37** — **Given** the purchase area, **Then** it holds, in order: price, stock line, **Add to cart** (W03's control; disabled and labelled "Out of stock" when `inStock` is false), **Chat with seller** (link to `/chat?product=<id>`), **Share** (AS-60); at ≤ 640 px a bar fixed to the bottom of the screen repeats the price and the **Add to cart** control while the main purchase area is out of view, and never covers the focused element or the tab content. (W03, W05 own the controls' behaviour.)
7. **AS-38** — **Given** the product page at ≥ 1024 px and at ≤ 640 px, **Then** the structure is FR-182 and the focus order: skip link, navbar, breadcrumb, gallery thumbnails, title links, **Add to cart**, **Chat with seller**, **Share**, tab list, active tab panel, rails, footer.
8. **AS-39** — **Given** `recommendations` with items, **Then** a section "Frequently bought together" shows the cards in the given order (direct before indirect, S34 FR-007), each linking to its page with title as text and price from `priceMinor`/`currency`; **Given** `trending` with items for the product's category, **Then** a section "Trending in {category}" shows at most eight cards without the product itself; **Given** empty `items`, `404`, `429`, `503` or an invalid body, **Then** the section is not rendered at all (no empty heading). (S34 AS-48, FR-030; S35 FR-027.)
9. **AS-40** — **Given** the tab list, **Then** the tabs are **Details**, **Pickup near me**, **Ask about this product**, **Discussions** in that order; the selected tab is in the address (`tab`, default `details` omitted), is restored on reload and back/forward, and a deep link `?tab=discussions` opens that panel; the tabs follow the ARIA tab pattern (roving focus with Left/Right, Home/End; only the active panel in the accessibility tree); a tab's content loads only when it is first opened (nothing for Pickup, Ask or Discussions is requested by the initial page view).

### User Story 6 — Find a pickup point near me on the product page (Priority: P2)

A shopper opens "Pickup near me" on a product, shares their location, and sees which nearby pickup points hold it, how far they are and when they are open; they can also see them on a map.

**Why this priority**: it turns discovery into a same-day visit, but the page is complete without it.

**Independent Test**: grant a fake location in the browser, open `?tab=pickup` on a product that a seeded point stocks; then deny the location; then force empty and error answers.

**Acceptance Scenarios**:

### Edge Cases

Each is covered by the scenario shown; none is left to implementation judgement.

- Rapid typing, out-of-order suggestion answers, hostile or very long text → AS-07, AS-09, AS-72.
- Address-bar tampering (legacy, unknown, repeated, out-of-range parameters; forged `cursor`) → AS-12, AS-24; filters that match nothing → AS-19.
- Facet selection that would collapse its siblings; semantic mode without facets; degraded semantic answer → AS-14, AS-21.
- Index moves between page fetches (duplicates across pages) → AS-18; stale result click records → AS-23.
- Location denied, unsupported, timed out, rounded and kept out of the address → AS-29, AS-31, AS-43.
- Product hidden, unknown, malformed, archived; every optional section failing at once; slow aggregate → AS-33, AS-34, AS-64.
- Out of stock; no image; unrated; very long title or description; description containing markup → AS-32, AS-36, AS-37.
- Empty trending and recommendations; same product appearing in its own trending rail → AS-03, AS-39.
- Hostile markdown and links in discussions; self-voting; voting while another vote is in flight; deleted parents; depth limit; content deleted elsewhere → AS-47..AS-52.
- Signed-out writes; session ending mid-compose; double submit; offline writes → AS-46, AS-51, AS-74.
- Questions with nothing to retrieve, refused, moderated mid-answer, cut off, ungrounded; stop and navigate away → AS-55..AS-58.
- Share without a session, at the link limit, with a key still in flight; invalid or replayed `ref` → AS-61..AS-63.
- Privacy signals set; unload during a flush; retry of a failed batch → AS-68.
- Layout: 320 px width, long titles and brand names (wrap, clamp to three lines in cards, full text in the accessible name), 200 % zoom, reduced motion → AS-75.

**Home**

- **FR-001**: `/` prerenders a static shell: the hero (with the single `h1`, the search box in its `hero` variant and the "Browse products" link), the showcase blocks ("What this showcases", "Built with") and the footer; the category shortcuts and the trending rail are separate async sections under `<Suspense>` with fallbacks of their final height (AS-01, AS-04, AS-69).
- **FR-002**: The trending rail reads `GET /api/trending?limit=8` (category `all`) on the server through a server-only module, validates it with `trendingResponseSchema`, and renders at most eight text cards (the response carries no image): rank, title, formatted category, price; each card is one link; the response is cached for 30 seconds without any visitor identity; no implementation note is shown (AS-02, AS-69; S35 FR-027).
- **FR-003**: Fallback chain: empty `items`, `429`, `503 trending_unavailable`, `400`, an invalid body, a timeout (2 s) or a network failure → the first eight items of `GET /api/products/search?limit=8` (browse), rendered with the search card; that failing too → "No products yet." Neither failure is cached beyond 5 seconds (AS-03).
- **FR-004**: Category shortcuts are the first eight `facets.categories` of `GET /api/products/search?facets=true&limit=1`, cached 60 seconds, shown as links `/search?category=<key>` with the label of FR-027; any failure omits the row (AS-01).
- **FR-005**: The showcase blocks are static content: no request at render, no third-party host, every link resolves to a route that exists (AS-01).

**Search box and autocomplete**

- **FR-010**: One `SearchBox` component (variants `hero`, `page`, `navbar`) serves every page. On `/search` its initial text is the `q` of the address and it follows back/forward; the `navbar` variant renders nothing on `/` and `/search`, so at most one search combobox is on a page (AS-05, AS-06).
- **FR-011**: A suggestion request is `GET /api/suggest?q=<trimmed text>&limit=8`, sent only when the trimmed text has at least one character and at most 100, through `lib/api/suggest.ts`, parsed with `suggestResponseSchema` (AS-05, AS-07).
- **FR-012**: Timing: the request starts 150 ms after the last keystroke; a newer request aborts the older one (the abort signal reaches the network call); an answer for a prefix other than the current text is ignored; answers are cached per normalised prefix (lower case, whitespace collapsed) for 60 seconds under `queryKeys.suggest.prefix(prefix)`; `degraded` reasons are ignored (AS-07).
- **FR-013**: Up to eight suggestions are shown in the order given, as plain text; `source` is not shown; duplicates are not removed by the UI (the API guarantees none) (AS-05).
- **FR-014**: The combobox follows the ARIA pattern of AS-06; the listbox is named "Search suggestions"; the status line is a visually hidden polite region; pointer hover highlights but does not select; **click** on an option selects it.
- **FR-015**: Submitting (Enter, the **Search** button, or choosing a suggestion) navigates to `/search?q=<trimmed text>` keeping nothing else when it comes from another page and keeping the current filters and sort when it comes from `/search` (the cursor is removed); an empty text removes `q` (AS-05, AS-09).
- **FR-016**: Any failed or invalid suggestion answer closes the list silently (AS-08).
- **FR-017**: The input has `maxLength` 100, a pasted longer text is cut to 100 with the hint "Search is limited to 100 characters.", and the **Clear search** button of AS-09 (AS-09).

**Search results**

- **FR-020**: The view state of `/search` is the parsed address: `q` (≤ 100), `category`, `brand` (≤ 100 each, exact), `minPriceMinor`, `maxPriceMinor` (integers ≥ 0, min ≤ max), `minRating` (integer 1–5), `inStock` (`true` only), `sort` (`relevance`, `price-asc`, `price-desc`, `newest`; `relevance` is the default and is omitted; without `q` only the non-default values are kept), `semantic` (`true` only, requires `q`), `near` (`1` only), `radiusKm` (one of the choices, default 5 omitted), `cursor` (opaque, ≤ 2,048 characters, dropped when `near` or `semantic` changes). Parsing is strict and total: invalid parts are dropped, never rejected, and the canonical address (fixed parameter order, defaults omitted) replaces the current entry when it differs (AS-11, AS-12).
- **FR-021**: The results request is `GET /api/products/search` with exactly the canonical parameters, `limit=24`, and `facets=true` (omitted when `semantic=true`); money is sent in minor units; the response is parsed with `productSearchResponseSchema`; an unparsable answer is treated as `502` (AS-10, AS-24).
- **FR-022**: First view: the server reads the address, fetches the results (no shared caching; the response is `private, no-store`), renders them and puts the answer in the query cache under `queryKeys.search.results(params)` so the client shows it without a second request; later changes are fetched by the browser from the same-origin endpoint through `lib/api/search.ts` (AS-10, AS-25, AS-71).
- **FR-023**: A change of a control updates the address through the router's history integration (no server round trip for the page, no full reload): filter, sort, `q` and radius changes push a history entry; the cleaning of AS-12 replaces; the back and forward buttons re-read the address and show the cached or freshly fetched view (AS-11).
- **FR-024**: A result card shows the fields of AS-10 from the item; the image is `imageUrl` (when it is an allowed `https` URL) with empty alt text because the title is in the same link, else a neutral placeholder; the link target is `/products/<id>`; the brand line shows `brand` (no shop name exists in the response); no review count is shown (the API has none) (AS-10).
- **FR-025**: Heading and title: `q` present → `h1` "Results for “{q}”" and document title "{q} – Search · Marketplace"; browse → "All products" and "Search · Marketplace"; pickup mode → "Pickup near you". Any address with `q`, a filter, `semantic`, `near` or `cursor` carries `noindex, follow`; plain `/search` is indexable. The count line is `{n} results` (`1 result`), `10,000+ results` when `total.exact` is false (AS-10, AS-19, AS-20).
- **FR-026**: The sort control offers the four sorts of AS-13; **Relevance** is hidden without `q` and the default label then reads "Featured"; a `sort=relevance` without `q` is cleaned by FR-020 (AS-13).
- **FR-027**: The filter panel renders `facets` exactly as the API gave them (order, counts), labels keys as "Home & living"-style text (hyphens to spaces, first letter capitalised, nothing else), and never invents a category, a brand or a count; a hard-coded list is not allowed (AS-14).
- **FR-028**: Active filters are chips (AS-15); **Clear all filters** keeps `q` and `sort`; chips and the panel always agree because both read the address.
- **FR-029**: Price fields take major units with up to two decimals (`^\d+(\.\d{1,2})?$`), convert to minor units with the response currency's decimals, validate min ≤ max on the client before any request, and show the messages of AS-16 (AS-16).
- **FR-030**: **Rating** and **In stock only** are described in AS-17; selecting the active rating again clears it.
- **FR-031**: Paging is by `cursor` in the address: **Next page** is a link; **Back to first page** removes `cursor`; there is no offset, no page number, no "load more" that hides the cursor, and no previous-page link beyond the browser's back button (AS-18).
- **FR-032**: The empty state is AS-19; it shows no skeleton and no error.
- **FR-033**: Meaning search is AS-21: `semantic=true` implies no `cursor`, no `facets`, `limit=24`, and a disabled **Next page**.
- **FR-034**: Sponsored items are labelled (AS-22) and otherwise rendered like any other item in the given position.
- **FR-035**: Click logging: on the first activation of a result link per page view and result, `POST /api/search/clicks {searchId, productId, position}` is sent with `keepalive` through `lib/api/search.ts`; the `searchId` is the one of the response that produced the card; failures are ignored (AS-23).
- **FR-036**: Error forms of the search page are the ones listed in AS-24 and FR-171; the alert is a single `role="alert"` region inside the results area (AS-24).
- **FR-037**: Transition states: first view from the server shows no skeleton; a client change keeps the previous results (`placeholderData`), marks the region busy and dims it; a view visited within the stale time shows from the cache and refreshes silently; skeletons of the grid have the final card size (AS-25).

**Near me (search)**

- **FR-040**: Pickup mode request: `GET /api/search/near?lat&lng&radiusKm&q&limit=24&cursor` through `lib/api/pickup.ts`, parsed with the near-search response schema; no other search parameter is sent (AS-28, AS-30).
- **FR-041**: Location comes from the browser's geolocation (`timeout` 10 s, `maximumAge` 5 minutes, no high accuracy) through one shared hook with states `idle`, `asking`, `granted`, `denied`, `unsupported`, `timeout`, `unavailable`; asking happens only after the shopper turns the mode on or presses **Use my location**, never on page load (AS-28, AS-29, AS-41).

- **FR-043**: Coordinates are kept in memory only, rounded to three decimals before each request, never written to the address, storage, cookies, logs or events, and the pickup requests are sent with `cache: "no-store"` (AS-31).
- **FR-044**: Errors and the empty state of pickup mode are AS-30; radius choices are the Defaults (AS-30).

**Product page**

- **FR-050**: The page's data is one server-side read of `GET {BFF}/api/bff/product-page/{productId}` made **without any visitor credential** (no cookie, no `Authorization`, no `X-Anonymous-Id`), validated with `productPageResponseSchema`, cached for 15 seconds under the tag `product:{productId}`; the cache key contains the product id only (AS-32, AS-34, AS-69; S48 FR-001, FR-008, FR-012 apply to shared caches, and nothing per-visitor is requested).
- **FR-051**: `productId` is validated as a UUID before any request; a malformed id renders the not-found page. The aggregate's problems map to AS-33: `404` → not found; `503`, `502`, other `5xx` → temporarily unavailable; `429` → wait text (AS-33, AS-64).
- **FR-052**: Summary content is AS-32: money from `priceMinor`/`currency`; rating "Rated {n} out of 5" with the value to one decimal, "Not rated yet" for 0; stock from `inStock` only; description as text with `white-space: pre-line`; tags as links; no field that the public view does not carry (no stock count, no seller id, no view count) is shown (AS-32).
- **FR-053**: Metadata is generated from the same cached read: title, description (first 160 characters of the description), canonical `{SITE_URL}/products/{id}`, Open Graph (title, description, image when a gallery item exists, `url`); structured data `Product` is emitted as one `application/ld+json` script whose JSON has `<` replaced by `<` (AS-32).
- **FR-054**: Optional-section rule: `shop`, `gallery` (when the S48 section exists), `recommendations`, `trending`, `videos` are each read independently; a `null` section or an unparsable one is treated as missing: its place is empty (no heading, no message) except the gallery (placeholder image). `errors` entries are used only for diagnostics (never shown); sections the page does not use (`flags`, `chatUnread`, `discussions`, `pickup`, `flashSale`, `auction`) are ignored (AS-34).
- **FR-055**: Shop line "Sold by {name}" as text (AS-35).
- **FR-056**: Gallery behaviour is AS-36: `feed` size for the main image, `thumb` for thumbnails, `full` for the lightbox; sizes and aspect ratios are declared so images do not shift the layout.
- **FR-057**: The purchase area order, the stock states and the mobile bottom bar are AS-37; the add-to-cart control receives `productId`, the product's `category` and `disabled`.
- **FR-058**: Rails use the rail card (text card with price, optional rank and category); the product itself is removed from "Trending in {category}"; at most eight cards each (AS-39).
- **FR-059**: Tabs are AS-40; the panels of Pickup, Ask and Discussions are client islands mounted when first selected and kept mounted afterwards within the page visit (their state survives a tab switch); the `tab` value is validated (anything else is `details`) and written with a history entry.
- **FR-060**: Breadcrumb "Home › {category} › {title}" is a `nav` named "Breadcrumb" with `aria-current="page"` on the last item.
- **FR-061**: The page's loading state is one skeleton with the same grid as the final page (gallery block, title lines, price, buttons, tab bar); no content jumps when it is replaced (CLS ≤ 0.1).

**Pickup near me (product page)**

- **FR-070**: List request: `GET /api/pickup-points/near?lat&lng&radiusKm&productId&limit=10&cursor` through `lib/api/pickup.ts`, parsed with the pickup-points response schema; `quantity` is shown only when present (AS-41).
- **FR-071**: Location handling is FR-041 and FR-043, shared with the search page.

**Discussions**

- **FR-080**: The board id is the product UUID. Calls (all through `lib/api/discussions.ts`, schemas from `packages/contracts`): `GET /api/boards/{productId}/posts?sort=hot|top|new&window=day|week|month|year|all&limit=20&cursor`; `POST /api/boards/{productId}/posts {title, body}`; `GET /api/posts/{postId}/comments?sort=best|new|old&limit=25&cursor`; `GET /api/comments/{commentId}/replies?limit&cursor`; `POST /api/posts/{postId}/comments {body, parentId?}`; `PUT /api/votes/{targetId} {value}`; `DELETE /api/posts/{postId}`; `DELETE /api/comments/{commentId}` (AS-45..AS-50).
- **FR-081**: List reads: `window` is sent only with `sort=top`; items are merged across pages and de-duplicated by `postId` (comments by `commentId`); a changed sort or window starts again at the first page; the list is a query under `queryKeys.discussions.board(productId, {sort, window})` (AS-45).
- **FR-082**: A post shows title (text), body excerpt (the sanitised rendition clamped to four lines with **Show discussion**), author label ("You" when `authorId` equals the signed-in user's id, otherwise "Community member": no identity is derived from the opaque id), `<time>` with `datetime`, score, comment count (AS-45).
- **FR-083**: Composer rules are AS-46: title 3–300 and body ≤ 40,000 code points counted by code point; trimmed before sending; unknown fields never sent; the `Idempotency-Key` is a fresh UUID per attempt, kept for retries of an unchanged form and replaced after success or edit; on `201` the board's lists are invalidated, the sort becomes `new`, and the new post is focused (AS-46).
- **FR-084**: One `sanitizeBodyHtml(html)` function (an allow-list sanitiser run in the browser) implements AS-47 and is the only way `bodyHtml` reaches the DOM; it is applied on every render of a body and is unit-tested with the hostile inputs of S25's table (`<script>`, `<img onerror>`, `javascript:` links, images, nested quotes) (AS-47).
- **FR-085**: Votes are AS-48: the optimistic update changes the post or comment inside the query cache, the response replaces it, a failure restores the snapshot taken before the optimistic update; at most one vote request per target is in flight (a second press while pending is queued as the final value).
- **FR-086**: Comments are AS-49; replies are loaded by cursor; the thread is a query under `queryKeys.discussions.thread(postId, sort)`; a created comment is inserted into the cached thread at the right place instead of refetching the thread.
- **FR-087**: Delete is AS-50; the control is shown from the `authorId` and the `useAuth()` role only as a convenience (the server decides, constitution VI.5).
- **FR-088**: Signed-out and session-ended behaviour is AS-51; the sign-in links carry `returnTo` through W01's `loginHref` and the page address including `tab`, `sort`, `window` and `post`.
- **FR-089**: Degraded and failure forms are AS-52 and FR-176.
- **FR-090**: The expanded post is in the address as `post=<postId>` (validated as a UUID; an unknown id is dropped after the list loads without it), is restored on reload and back, and is scrolled into view with focus on its title (AS-49).
- **FR-091**: Times: `<time datetime>` ISO instant; visible text "just now", "{n} minutes ago", "{n} hours ago", "{n} days ago" up to 30 days, then "{Mon D, YYYY}"; the exact time is in the `title`.

**Ask this product**

- **FR-100**: `POST /api/products/{productId}/ask {question}` through `lib/api/ask.ts`, which owns the streaming read (the component never calls the network): it sends `Accept: text/event-stream`, the shared CSRF header when its cookie exists, no credentials from JavaScript, and exposes `{start(question, signal), onEvent}`; the abort signal ends the request (AS-54, AS-58).
- **FR-101**: Event handling: `sources {mode, items}` → remember `items` by `n`; `text {t}` → append; `done {citations, grounded}` → finish, show cited sources, apply the `grounded` notice; `not_found` → AS-55; `refusal` → AS-55; `error {code}` → AS-57; an unknown event name is ignored; an event whose data is not valid JSON ends the answer as AS-57; every event is validated with `ragStreamEventSchema` (AS-54..AS-57).
- **FR-102**: The answer is plain text; the sources list shows `title`, `headingPath` joined with " › " and `page` when not `null`; nothing is a link (documents have no public address) (AS-54).
- **FR-103**: States: `idle`, `asking`, `streaming`, `answered`, `not_found`, `refused`, `stopped`, `failed`, `blocked` (the `404` tab replacement); one status string per state as in AS-54..AS-58 and FR-174.
- **FR-104**: Abort rules are AS-58; unmounting the panel (page leave) aborts too; a panel kept mounted across tab switches keeps streaming (the tab switch is not a leave).
- **FR-105**: Announcements are AS-59: a hidden polite status for state changes, `role="alert"` only for request errors, no token-by-token live region.
- **FR-106**: Client validation: the trimmed question must have 3–500 characters (counted by code point) before **Ask** is enabled; a violation the server reports (`400`) is shown as in AS-56.
- **FR-107**: Question and answer text never go into the address, storage, an analytics event, an error report or the console (AS-77).

**Rendering, data flow and safety**

- **FR-150**: Rendering model of AS-69: static shell first; runtime data (`searchParams`, `params`, cookies) is read only inside `<Suspense>`; shared public data uses `use cache` with `cacheLife` and `cacheTag`; no cached function takes or reads visitor identity; data that depends on `searchParams` is not cached across requests (AS-69).
- **FR-151**: Cache table. Trending rail: 30 s, tag `trending`. Category shortcuts: 60 s, tag `search-facets`. Product aggregate: 15 s, tag `product:{id}`; degraded (non-empty `errors`) or failed: not kept beyond 5 s. Search results and everything per-visitor: not cached on the server (AS-69).
- **FR-152**: Server-only configuration (`API_URL`, `BFF_URL`, `SITE_URL`) is read in server-only modules that import `server-only`; client code receives only the values it renders (`NEXT_PUBLIC_MAP_TILE_URL` is public by nature); a missing `SITE_URL` fails the build in production (AS-70).
- **FR-153**: Every response is parsed with its `packages/contracts` schema inside `lib/api/*`; a parse failure is an error of that call (`UPSTREAM_INVALID`-like) and follows the section's failure rule; hand-written duplicate response types are not allowed (AS-70; constitution V.2).
- **FR-154**: Query keys come only from `lib/query-keys.ts` with these roots: `search.results(params)`, `search.near(params)`, `suggest.prefix(prefix)`, `rails.trending(category)`, `rails.recommendations(productId)`, `product.page(productId)`, `pickup.near(productId, {radiusKm, coords3dp})`, `pickup.clusters(productId, bbox, zoom)`, `discussions.board(productId, {sort, window})`, `discussions.thread(postId, sort)`, `discussions.replies(commentId)`, `share.link(productId)`, `video.playback(videoId)`, `ads.sponsored(category)`; an ask session is local state, not a query (AS-71).
- **FR-155**: The query client defaults of the app (`staleTime` 60 s, `retry` 1, no refetch on focus) are overridden per query only as the Defaults say; mutations never retry automatically except the idempotent ones named (`409 idempotency_in_flight`, `409 vote_in_progress`) (AS-71).
- **FR-156**: Client components are leaves: `SearchBox`, the filter panel, the sort control, the results region (for the cache and transitions), `LocationButton`, the pickup panel and map, the discussions panel and its parts, the ask panel, the share popover, the gallery lightbox, the tab list, the tracker, the attribution trigger and the video player; everything else is a Server Component (AS-70).
- **FR-157**: Images: only the hosts of the media delivery origin (and none by default for placeholders) are allowed; every image has dimensions or an aspect ratio; decorative images have empty alt text; a failing image is replaced by the placeholder (AS-36, AS-72).
- **FR-158**: Content safety is AS-72; the only HTML sinks are `sanitizeBodyHtml` output and the escaped structured data.
- **FR-159**: Session interplay: write actions read `useAuth()` (W01) and send the shared CSRF header; a `401` from any W02 request while signed in runs W01's session-ended flow exactly once; W02 never reads a token and never redirects to login except through `loginHref(returnTo)` (AS-51).
- **FR-160**: Money: `formatMoney(minor, currency)` divides by `10^fractionDigits(currency)` and uses the English locale; the helper's old default (`"USD"`, cents) is removed so a missing currency is a compile error (AS-10, AS-32).
- **FR-161**: Every W02 route segment has a `loading` fallback of final size and an error boundary that shows the FR-170 generic error with **Try again**; every optional section on the home and product pages is additionally wrapped in its own boundary so a rendering fault in one section never blanks the page (AS-34).
- **FR-162**: Wait text for `Retry-After` is W01 FR-041 (seconds below 60, minutes below 3,600, then hours; "Try again later." when the header is missing); a control disabled by a wait is re-enabled by a timer without a reload.

### Key Entities

- **Search view (URL state)**: the parsed, canonical set of FR-020; the only copy of what the shopper selected.
- **Result item**: `{id, shopId, title, brand, category, priceMinor, currency, rating, inStock, imageUrl | null, sponsored, position}` plus `searchId` of its response.
- **Facets**: `{categories, brands, priceRanges, avgRating}` as returned.
- **Suggestion**: `{text, source}`; only `text` is displayed.
- **Rail item**: trending `{rank, productId, title, priceMinor, currency, category, score}` and recommendation `{productId, title, priceMinor, currency, score, hops}`.
- **Product page**: the aggregate `{product, shop | null, gallery | null, recommendations | null, trending | null, videos | null, errors}` as used by W02.
- **Pickup point (near)**: `{id, shopId, name, address, lat, lng, distanceM, openingHours, quantity?}`; **cluster cell**: `{cellId, offers, pickupPoints, lat, lng, pickupPointId?}`.
- **Post / Comment views**: as S25 defines (`PostView`, `CommentView`, `CommentNode`); **vote result** `{targetId, targetType, ups, downs, score, myVote}`.
- **Ask session**: local state of one question: status, answer text, `sources.items`, citations, notice; never persisted.
- **Short link**: `{code, shortUrl, destination, status}`; **Referral cookie**: `__Host-ref`, the code.
- **Visitor event**: `{event_id, name, anonymous_id, ts, page?, props?}`; **anonymous id**: first-party cookie value.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A first-time visitor can go from the home page to a product page in no more than three interactions and 15 seconds, by search, category shortcut or trending card, with no instruction.
- **SC-002**: Suggestions are visible within 400 ms of the shopper pausing typing for 95% of keystroke pauses on a typical broadband connection, and typing is never blocked or delayed by suggestions.
- **SC-003**: On a mid-range phone over a fast mobile connection, 75% of visits show the main content of Home and of a product page within 2.5 seconds, respond to input within 200 ms, and shift layout by no more than 0.1 while rails and images load.
- **SC-004**: After a filter, sort or page change, new results appear within 1 second for 95% of changes, the previous results stay visible meanwhile, and the scroll position is kept on filter changes.
- **SC-005**: 100% of search views (search text, filters, sort, page) and product-page views (tab, discussion sort, open post) restore exactly from a pasted address.
- **SC-006**: When any one, several or all optional sections fail, 100% of product pages still show the product, its price, stock and the purchase actions, and no section shows a technical error code.
- **SC-007**: No credential, token, coordinate, question text or discussion text is present in browser storage, a URL, the console or an analytics event in any tested flow, and no third-party host is requested by default.
- **SC-008**: Each journey in the test plan can be completed using only the keyboard, and an automated accessibility scan reports no serious or critical issue on every layout state at 390 and 1280 px width.
- **SC-009**: A posted discussion, vote or comment is visible within 1 second of the shopper's action, and the first words of an answer appear as soon as the assistant sends them (no waiting for the full answer).
- **SC-010**: 100% of the error forms listed in the Copy catalogue are produced by a single shared mapping, and no server `detail` text is shown to a shopper.

## Assumptions

Each default below is also one line in [`questions.md`](questions.md), tagged and sorted by impact.

- Decision policy: production-grade over cheapest; there are no external clients, so routes, parameters, props and tests change freely, with `[BREAKING]` tags for the implementation.
- **URL parameter names follow the API's** (`minPriceMinor`, `maxPriceMinor`, `minRating`, `inStock`, `sort`, `semantic`, `cursor`) so the address, the request and the query key describe the same thing; the old names (`priceMin`, `priceMax`, `rating`, `nearMe`) are not kept `[BREAKING]`.
- **One category and one brand at a time**: the API takes a single exact value for each; the multi-select checkboxes are replaced `[BREAKING]`.
- **Paging is a "Next page" link driven by the cursor in the address**, not an infinite list: the cursor is view state (constitution VI.4) and cannot be rebuilt from a list of pages; the dead "Load More" button is removed `[BREAKING]`.
- **First view of search is rendered on the server and handed to the query cache**; later changes are client-side with history integration. Search answers are never cached on the server.
- **The product page reads the S48 aggregate anonymously on the server and caches it 15 seconds**; everything per-visitor (discussion votes, ask, share, add to cart) is a client island. The aggregate's per-visitor sections (`flags`, `chatUnread`) are not used. Price and stock on the page can therefore be up to 15 seconds old; the cart and checkout re-price (S32 assumptions, S10).
- **Routes**: `/products/[productId]` replaces `[slug]` (the "slug" was always the id); `/p/{productId}` redirects so that S36's click redirect and S37's examples hold `[CONTRACT]`.
- **Tabs in the address**: Pickup near me and Ask become tabs (today Ask sits in the buy column and Pickup does not exist).
- **Rails are text cards** because S34 and S35 items carry no image; an additive `imageUrl` is requested from them `[CONTRACT]`.
- **No shop page exists**: the shop name is text.
- **Location privacy**: coordinates stay in memory, are rounded to three decimals (about 100 m) and are never in the address.
- **Author labels**: the API exposes only an opaque `authorId`, so authors are "Community member" or "You"; a display-name composition is a later S48 section `[CONTRACT]`.
- **Ask answers are plain text**; sources are not links because documents have no public address.
- **Share destination is built from `SITE_URL`**, which must equal S37's configured storefront origin; the short link domain and `/l/{code}` belong to S37 and the edge.
- **The referral cookie is HttpOnly, set by a same-origin web endpoint, last click wins, 30 days**; the order must read it on the server (W03/S10) `[CONTRACT]`.
- **Analytics**: only `product_view` and `video_view` are emitted by W02; `page_view` belongs to W07; the anonymous-id cookie is first party and is not created when Global Privacy Control or Do Not Track is set; no consent banner exists in this version.
- **Map tiles**: no third-party tile host by default; a configured tile address enables the map, otherwise the list view is the only view.
- **Not-found for a product is a streamed page with `noindex` and status 200**, as the framework documents for content under a boundary; a real `404` status would need an existence check before streaming and is not built `[LOCAL]`.
- **The sponsored slot and product videos are conditional** (P3) and their absence never changes the rest of the page.
- Interface language is English only; money is shown in the product's currency.
