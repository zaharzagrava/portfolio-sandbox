# Open Decisions for W05 (answered unattended)

Format: `[TAG] question → default taken → why`. BREAKING first, then CONTRACT, then LOCAL. The human reviews BREAKING and CONTRACT lines first. Decision policy: most production-grade option the Interview-Prep notes and the constitution support; a `[BREAKING]` tag tells the implementation to update existing tests and callers.

## BREAKING (changes behaviour or a UI/API contract that exists today)

- [BREAKING] How does the chat page learn about new messages? → a live hint on the shared stream triggers a sync; a 15 s safety sync while visible, 5 s while the stream is down, nothing while hidden or offline; today a fixed 3 s `setInterval` sync of every channel, always (`app/chat/chat-view.tsx:16,86-90`) → the notes: "push is best-effort, sync is the guarantee"; P0406 push instead of poll; constant polling of all chats is a reconnect-storm generator (S24 SC-004).
- [BREAKING] Initial load of a conversation → newest 50 messages from the history endpoint, "Load earlier messages" for scroll-back, sync only moves forward; today the page syncs from cursor 0, shows at most the first 200 messages and ignores `hasMore` (`chat-view.tsx:72-83`) → S24 AS-22/AS-27: a long chat showed its oldest 200 messages and never the newest.
- [BREAKING] Where does the inbox come from? → one call `GET /chat/channels/mine` (new, S24) with title, unread, last time; today `GET /chat/unread` (a bare array, soon `{items, nextCursor}`) plus one `GET /chat/channels/:id` per row from the browser (`chat-view.tsx:56-58`, `lib/api/chat.ts:42`) → N+1 from the client is forbidden (VI.9, IX.7); the unread shape change is S24's own BREAKING line.
- [BREAKING] Which chat is open → the URL (`/chat?channel=<id>`), the `?product=` resolver replaces itself with it; today `useState` `active` and the address keeps `?product=` (`chat-view.tsx:41`) → VI.4: shareable view state lives in the URL; Back and reload keep the place.
- [BREAKING] Who may create a chat and how → an explicit button "Open chat for this product" shown to `SELLER`/`ADMIN` roles, the backend decides; today the page silently creates the chat when `GET /api/products/:id` says `sellerId === user.id` (`chat-view.tsx:19-31`) → a navigation must not create data; ownership is the shop's (S24 AS-01/AS-02), and the page must not read a catalogue field to decide authority.
- [BREAKING] Sending → one `clientMessageId` per user action reused on every retry, optimistic bubble, "Not sent" with Retry/Discard, auto-retry once after reconnect; today a new UUID per call (`lib/api/chat.ts:48-49`), nothing optimistic, a failure is a toast and the text stays in the field → S24 FR-011 only protects retries that reuse the id (S24 `questions.md` CONTRACT); P0414 at the browser.
- [BREAKING] Marking read → only what is rendered in view while the tab is visible and focused, debounced, badge set from the response; today every change of the last message marks read immediately and zeroes the badge locally even in a hidden tab (`chat-view.tsx:96-100`) → a read receipt is a statement to other people (S24 FR-033); false "Seen" is worse than a late one.
- [BREAKING] Composer → multi-line, Enter sends, Shift+Enter newline, code-point counter, Send named "Send message"; today a single-line `Input` and an icon-only unnamed button with `aria-label="Send"` (`chat-view.tsx:176-179`) → S24 allows multi-line 4,000-character bodies; accessible names.
- [BREAKING] Assistant send is idempotent, resumable and stoppable → `Idempotency-Key` per action, attach to `messageId` on `idempotency_in_flight`, resume with `Last-Event-ID`, reload recovery from a per-tab pointer; today a send without key and a dropped connection ends the stream silently with a half answer (`hooks/use-assistant-chat.ts:30-62`, `lib/api/sse-reader.ts:41-70`) → S46 FR-034 makes the key mandatory (`422` without); S46 FR-003/FR-004 exist for exactly this reader; the notes: "if the user refreshes mid-answer … resume from a buffer".
- [BREAKING] Assistant errors are inline, not toasts → one inline alert per problem/stream error with the copy catalogue; `refusal` replaces streamed text; today a `toast.error(data.message ?? …)` that reads a `message` field the stream never sends and shows "Rate limit exceeded" for every `429` (`use-assistant-chat.ts:53,56`) → S46 has ten distinct 4xx/5xx codes with different next steps (quota resets at a date; busy retries in seconds; sensitive data needs editing).
- [BREAKING] Stream auth → same-origin cookie session, no `Authorization` from JavaScript; `streamSse` stops calling `getAccessToken()`; `createEventStream` loses `NEXT_PUBLIC_SSE_URL` cross-origin default → VI.2 and W01 (the token handler is the BFF); `lib/api/sse-reader.ts:1,51-59`, `lib/api/sse.ts:6-8`.
- [BREAKING] The launcher replaces the `toggle-assistant` window event and the layout-level `<AssistantSheet />` → `<AssistantLauncher />` owns its trigger and sheet; mounted by W07 in the persistent navbar; today the navbar dispatches `window.dispatchEvent(new Event('toggle-assistant'))` and `app/layout.tsx:40` mounts the sheet for every page, including anonymous ones (`components/layout/navbar.tsx:35-37`) → a global DOM event bus is an untyped dependency between two components; owning the trigger gives focus-return and removes the layout-level mount from the shared shell.
- [BREAKING] The assistant remembers the open conversation per tab and offers a conversation list, new chat, delete; today every page load starts a fresh conversation created on the first message and there is no way back (`use-assistant-chat.ts:30,41`) → S46 FR-010 gives the shopper their conversations; reload recovery needs the pointer.
- [BREAKING] The stream query keys → `queryKeys.chat.*` and `queryKeys.assistant.*` replace `chat.channels` / `chat.messages`; chat and assistant data move into TanStack Query; today both features hold server data in `useState` / refs (`chat-view.tsx:37-44`, `use-assistant-chat.ts:23-30`) → VI.4.
- [BREAKING] Presence and "Seen by" are shown (seller online; "Seen by n" under my last message) and a heartbeat runs while the chat page is visible; today neither exists → S24 US4/US5 are otherwise unused by any client.

## LOCAL (this capability's internals)

- [LOCAL] Joining on `?product=` → automatic (the link press is the consent); `?channel=` never joins → "Chat with seller" is the explicit action; a join confirmation would add a click to the main journey.
- [LOCAL] "Seller online" shown only for non-sellers and only when online → presence of arbitrary buyers is not useful in a public room and "offline"/"last seen" would be surveillance (S24 US5 title).
- [LOCAL] Message list library → implementer's choice (react-virtuoso is installed); the behaviour of AS-13 (no jump on prepend) is the requirement.
- [LOCAL] Topic cap → open chat + 8 latest others (10 topics per connection incl. `user:<id>`).
- [LOCAL] Heartbeat every 30 s, presence read every 30 s → under the 6/min and 30/min limits with margin.
- [LOCAL] Stop does not abort the local read for 5 s → the server's `CANCELLED` is the authoritative end and carries the tokens charge.
- [LOCAL] Resume schedule 0/1/2/4/8 s then every 10 s up to 2 min → first attempts inside the server's 10 s grace.
- [LOCAL] Pending question text kept in per-tab session storage for reload recovery only → it is the user's own text, removed when the reply ends; no token, no location.
- [LOCAL] Allowance shown as a percentage → tokens are meaningless to shoppers.
- [LOCAL] Delete-message confirmation dialog, delete-conversation confirmation dialog → both are irreversible server actions.
- [LOCAL] Markdown allow-list (paragraph, emphasis, lists, tables, code, links) with no images or HTML → VI.7; product images come from tool data in a later release.
- [LOCAL] Existing `data-testid` hooks (`chat-title`, `chat-message`, `chat-channel`, `assistant-message`, `user-message`) stay; new tests prefer roles and names.
- [LOCAL] Unread divider text "{n} new messages" and the jump pill use the server's `unread` at open time → no guessing.
- [LOCAL] Tablet widths (641–1023 px) use the mobile single-pane layout → the two-pane layout needs ≥ 1024 px for a usable message width.
