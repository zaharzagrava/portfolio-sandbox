# QA report: buy
Tried: home -> search -> product page -> add to cart as guest -> cart quantity + (1->2) -> "Sign in to check out" -> register -> sign in (guest cart merge) -> checkout review -> Place order (single and double click) -> pay with Visa test card (normal, double click on Pay, page reload 300 ms after Pay) -> success page -> "View order" -> order history. After each step I checked the API answers, the BisOrder/Payment/Outbox rows, ElasticMQ and the API log; doctor-live was run at start, after the flows and at the end (healthy each time).
## Defects
DEFECT D1 CONFIRMED high: "View order" on the confirmation page and the `/orders` and `/orders/{id}` pages answer 404, so the buyer cannot reach order detail
- oracle: W03 entry points (`/orders` order history, `/orders/{orderId}` order detail, `/dashboard/orders` redirects to `/orders`); W03.B-18 flow; link that leads to an error page
- steps: 1. Sign in as a buyer with a PAID order. 2. Open http://localhost:3000/checkout/success/01a13485-1245-70c6-b278-0205f7e9a9eb. 3. Click "View order" (href /orders/01a13485-...). 4. Open http://localhost:3000/orders directly.
- expected: order detail page (and an order history at /orders); /dashboard/orders redirects to /orders.
- actual: both /orders/{id} and /orders answer HTTP 404 "Page not found" (document response 404, console "Failed to load resource 404"). /dashboard/orders does not redirect: it renders the history itself (3 rows, correct status/totals), and the rows are not links to a detail page.
- evidence: scripts/orders.js, scripts/orders2.js output ("DOC 404 http://localhost:3000/orders/01a13485-..."); screenshots /tmp/tmp.8jkDSSNS4j/shots/vieworder.png, orders.png. API side is fine: GET /api/orders?limit=20 -> 200 and DB has the 3 orders PAID/COMPLETED.
DEFECT D2 CONFIRMED medium: clicking a product in the search results fires POST /api/search/clicks that always fails with 400 (browser console error)
- oracle: browser console error / API 4xx on a normal action (contract mismatch web vs API)
- steps: 1. Open http://localhost:3000/search. 2. Click any product card (e.g. "Mechanical Keyboard Cherry MX Brown").
- expected: click event accepted (2xx), no console error.
- actual: web sends body {"searchId":"v1.eyJ...","productId":"...","position":1}; API answers 400 validation_failed with errors [{field:searchId, code:unknown_property},{field:query, code:maxLength},{field:query, code:isString}], i.e. the API wants `query` and rejects `searchId`. Happens on every click, so search-click analytics are never recorded.
- evidence: curl POST localhost:8000/api/search/clicks with the same body reproduces it; API log "HTTP 400 validation_failed /api/search/clicks" at 11:06:19 and earlier; scripts/flow3.js prints CLICKREQ and the 400.
DEFECT D3 SUSPICIOUS low: browser analytics event posts get 403 csrf_invalid
- oracle: judgment (API log warning on a normal flow)
- steps: 1. Sign in. 2. Add to cart / pay / reach /checkout/success (scripts/pay.js).
- expected: no CSRF rejection on the app's own calls.
- actual: API log shows `HTTP 403 csrf_invalid /api/bff/f/events - The CSRF token is missing or invalid` right after the pay page loads, once per order flow (11:06:50, 11:07:40, 11:08:16, 11:08:25). The later `POST /api/events` returns 202, so some events are lost, some delivered.
- evidence: /tmp/tmp.g0a9rMz3f8/api.log lines ~9130, 9297, 9458, 9546.
DEFECT D4 SUSPICIOUS low: every page logs dozens of CSP console errors; plus `<main>` nested inside `<main>` on dashboard
- oracle: judgment (may be dev-server related)
- steps: open http://localhost:3000/ with console collection (scripts/explore.js).
- expected: no console errors.
- actual: about 40 "Applying inline style violates ... style-src 'self' 'nonce-...'" errors per page load; the dashboard page has two <main> elements (strict-mode locator('main') fails). Also 401 on GET /api/bff/session for every anonymous page view (logged as an error by the browser).
- evidence: scripts/explore.js output.
DEFECT D5 SUSPICIOUS low: short order number "#01A13485" is the timestamp prefix of a UUIDv7, so orders created in the same ~minute show the same number
- oracle: judgment
- steps: place two orders within a minute; compare "Order #..." on success pages / history.
- expected: a number that tells orders apart.
- actual: the 8-char prefix of a UUIDv7 only changes about every 65 s; my three orders (01A13483/84/85) were minutes apart so they differed, but two quick orders will collide. Not reproduced as a collision, so low confidence.
- evidence: order ids 01a13483-c1b0..., 01a13484-82a4..., 01a13485-1245... in BisOrder.
