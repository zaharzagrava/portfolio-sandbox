# Questions and decisions: J01 — Buy to payout

Decisions taken unattended under the decision policy (production-grade, constitution and Interview-Prep notes first; no external client to keep compatible). BREAKING first, then CONTRACT, then LOCAL. The human reviews BREAKING and CONTRACT lines first.

## BREAKING

- [BREAKING] How does a payment start? → `POST /payments/intents` over HTTP (S13); the Kafka edge topic `payments.requests` and the `payment-processor` message consumer are retired (today there is no HTTP route; `payment.controller.ts:24-36`) → one authenticated, idempotent entry with the amount taken from the order (10/07 §19: idempotency key = order id); the local monolith must serve it.
- [BREAKING] Can the provider's webhook alone mark an order paid? → No: orders marks `PAID` only after `PaymentQueryService.getPaymentStatus` says `COMPLETED`; a webhook for an unknown payment stays `RECEIVED` and is retried (today the webhook handler looks up a `Payment` row by `metadata.idempotencyKey`, ignores the event when there is none, and calls `markPaid` directly: `stripe-webhook.controller.ts:56-65`) → the webhook is a hint, the payments record is the truth; also stops "paid with no sale journal".
- [BREAKING] The outbox relay envelope → the poller publishes the bare envelope exactly as the CDC connector does (today the poller wraps it as `{payload: envelope, extra, error}`, so `parseEnvelope` turns every event into `<aggregate>.legacy` and `order.paid`/`ledger.journal_posted` consumers skip it: `outbox-publisher.service.ts:90-94`, `envelope-parser.ts:27-49`) → both relay modes must be indistinguishable to consumers; blocks every hand-off of this journey on the default mode.
- [BREAKING] Payment results and their stream → typed events `payments.payment_succeeded|failed|refunded` on `payments.events` (key `paymentId`) and a `payment.status` event on `user:<id>`; the legacy `payments.responses` / `payments.dlq` topics, the `order-payment-listener` group and `GET /payment/stream` are removed → typed, versioned, one envelope (IV.4); S13 spec.
- [BREAKING] `order.paid` payload `{userId, total, currency?, paymentId, lines[{productId, shopId|null, quantity, price}]}` → `{orderId, userId, totalMinor, currency, paymentRef, paidAt, lines[{lineId, productId, shopId, category, title, quantity, unitPriceMinor, discountMinor, lineTotalMinor}], shopOrders[], orderVersion}` → settlement, statements and notifications need the shop split and per-line facts without a query (IX.8); `shopId` is never null.
- [BREAKING] Where the platform commission is booked → at settlement from S16's rates (`getRatesAsOf`); the sale journal books the full captured amount to clearing (today and in S14's draft: flat 50 minor units at capture, `payment.service.ts:251-262`, S14 AS-11) → ledger credit == statement net, so reconciliation shows no `fee_mismatch`; S14's AS-11, AS-14, AS-15 and the refund path change accordingly (the refund returns the commission at the settlement that booked it).
- [BREAKING] Statements source → events (R3: `order.paid`, `payout.paid`, `ledger.journal_posted`) with a watermark, not SQL over `BisOrder`/`BisOrderItem` and the rate table (today `statements.jobs.ts`, `statements.service`) → IX.4, S16 spec; the close needs a complete watermark.
- [BREAKING] A payment that completes for a cancelled or expired order → automatic refund through `orders.refund_requested` (today only a log line "needs a refund": `order-payment.listener.ts`) → money never stays with the platform without an order (10/07 §19 saga compensation).
- [BREAKING] Settlement without a sale journal → deferred and retried, then dead-lettered (today it debits `MARKETPLACE_CLEARING` regardless, so a webhook-only path credits shops while clearing goes negative: `settlement.listener.ts:64`) → S14 AS-20.
- [BREAKING] The local monolith composes every process the chain needs (payment processor, realtime gateway, payment-result consumers) → today `LocalMonolithModule` lacks `PaymentProcessor` and the sse payment consumer, so the chain cannot run end to end locally.
- [BREAKING] Provider fakes → provider doubles chosen by `paymentMethodId` and `providerAccountId` through a port adapter in the local profile (today a global `IS_LOAD_TEST=true` flag fakes Stripe calls and hard-codes `usd`: `stripe.service.ts:87,100,120,223`) → deterministic failure scenarios without a global switch; the charge currency is the order's currency.
- [BREAKING] Seller notifications → shop owners are notified on a sale (`shop.order_received`) and on `payout.paid` / `payout.failed` (today the router maps only `order.paid` to the buyer, `order.cancelled`, auctions, billing: `notification-router.projector.ts:35-62`) → "buyer and sellers notified" is the journey's outcome; S28 spec.
- [BREAKING] `GET /shops/:id/balance` `{available, source}` → `{shopId, currency, availableMinor, asOf, source}` (and a stale non-null hot entry must not hide a newer ledger state) → S14 spec; `asOf` is the freshness observable.
- [BREAKING] Payout creation and statements close have no event or API → `payout.*` and `statements.*` events through the outbox, run-on-demand through the job control surface (today neither exists) → S15 and S16 specs; the journey cannot observe or trigger them otherwise.

## CONTRACT

- [CONTRACT] S13 says payments keeps an order copy and never calls orders; S10 says S13 calls `OrderQueryService.getPayableOrder` → S13 wins (events only; no module cycle, D-11, IV.2); S10 keeps `getPayableOrder` for S42 and others; J01 proves it with AS-04 and AS-19.
- [CONTRACT] Journey control surface → `POST /api/admin/jobs` + `GET /api/admin/jobs/:jobId` (S49 service, S01 routes); `GET /api/admin/consumers/:group`, `…/pause`, `…/resume`, `…/replay {since}` (S53); `GET|PUT /api/admin/clock` (S54), enabled only by `CLOCK_CONTROL=enabled`, refused at startup in production; consumers' pause/resume/replay are operator tools behind the admin role and a sensitive session, available in every profile → no HTTP trigger exists today and the journey is black-box; an operator needs the same tools in production.
- [CONTRACT] Canonical consumer-group names → `payments-order-copy` (S13), `orders-payment-results` (S10), `ledger-settlement` and `ledger-balances` (S14), `statements-facts` (S16), `notification-router` (S28, the existing name) → tests and the control surface address groups by name.
- [CONTRACT] `order.paid` adds `lineId` and `category` per line (asked by S16) and `shopOrders` (S10 already lists it) → statements and settlement need them; S10 must carry them.
- [CONTRACT] `payments.payment_failed` reasons that notify the buyer → all but `order_not_payable` and `order_cancelled` (S28 catalog); `order.cancelled` with `payment_failed` notifies nobody (avoid a second notice) → S28 AS-13; J01 asserts one `payment.failed` notice.
- [CONTRACT] Verified, payout-enabled shop fixture → through S04's public onboarding and admin decision routes with the extractor test double auto-approving; a destination set through S15's operator route; no database seeding (today `Shop.stripeAccountId` can only be set in the database) → black-box rule; S04 and S15 must make this possible in the local profile.
- [CONTRACT] UI journey file → `packages/web/tests/buy-to-payout.spec.ts` (S15, S16) rather than `packages/web/e2e` (S14) → one path; S14's test plan row AS-32 should point to it.
- [CONTRACT] Time budgets → the hop table H1–H13 is the contract; S14 keeps its 5 s p99 projector staleness (H4 allows 10 s end to end including settlement), S28's 2 s p99 inbox target stays its own and H5 uses 5 s for the test → one table the tests wait on.
- [CONTRACT] Topics created explicitly at stack set-up (`orders.events`, `payments.events`, `ledger.events`, `payouts.events`, `statements.events`) → today only the payment and product topics are created and the rest rely on broker auto-create (`scripts/init-kafka-topics.sh`).
- [CONTRACT] Statement-ready notices → not part of J01; S16's optional `statements.period_closed` consumer in S28 stays optional → S28 states finance alerts have no recipient directory.
- [CONTRACT] Consumers of `orders.events` outside the journey (`order-baskets`, `analytics-purchases`, `webhook-router`, `shop-live-dashboard`, `shop-sales-olap`) → J01 does not assert them, but the replay in AS-25 touches their topic; each owning capability must make its consumer idempotent (S34, S39, S43, S40) → replay must not corrupt them.

## LOCAL

- [LOCAL] Two shops plus a third (`S3`) for the rejected transfer → separate fixtures per scenario → isolation.
- [LOCAL] Poll interval 250 ms, deadline = 2 × the hop's maximum, `JOURNEY_TIME_FACTOR` scales it → CI variance.
- [LOCAL] SSE is asserted only in AS-01 and AS-08; everything else polls REST → fewer moving parts.
- [LOCAL] Assertions are relational (sums, equalities with `commission(s)`), not literal commission numbers → rates are configurable.
- [LOCAL] The journey suite resets the clock and resumes consumers in `afterAll` and in a global `finally` → a failed run must not poison the stack.
- [LOCAL] Journey file layout: one `describe` per user story inside `buy-to-payout.journey-spec.ts`, helpers in `test/journeys/support/` → traceability to the test plan.
