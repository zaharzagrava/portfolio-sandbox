## CONTRACT

- [CONTRACT] Who owns the conversion (affiliate credit)? → **S37 (marketing)** owns the record, the consumer `marketing-affiliate-conversions`, `GET /links/:code/conversions`, stats fields `conversions`/`convertedMinor`, and the events `link.converted` / `link.conversion_reversed` → S37 states commission is "not specified anywhere" and no spec asks for it; the link owner's data lives in marketing; orders only freezes the attribution (S37 and S10 specs must adopt these; they currently name neither).
- [CONTRACT] Is commission (amount, ledger entry, payout) part of J05? → no; the conversion carries `amountMinor` of the order and the events are the interface for a future commission capability (S16's rates) → keeps J05 about hand-offs; the ledger is J01's domain; raised so S16 knows it may subscribe to `links.events`.
- [CONTRACT] Where does the order learn the owner? → at checkout through `LinkAttributionService.resolveAttributions([ref])` (S37 R1 export) and a frozen copy `attribution: {code, ownerId}` in `order.paid`; the consumer never reads orders or marketing tables of another domain → IX.7 R1 then R3; S37 spec Provides already exports the lookup.
- [CONTRACT] Status handling → `ACTIVE` and `EXPIRED` attribute; `DISABLED`, unknown, self-owned do not → a cookie lasts 30 days and may outlive the link's expiry (S37 keeps the ref resolvable); a disabled link is a takedown.
- [CONTRACT] Refund semantics → a full `order.refunded` (`amountMinor` ≥ conversion amount) marks `REVERSED`; a partial one keeps `CONFIRMED` and raises `refundedMinor` → S34 notes that `order.refunded` carries an amount, not lines; amount is enough for money.
- [CONTRACT] Does trending count purchases? → no, honouring S35; the journey proves `product_view`/`add_to_cart` and asserts a paid order alone changes nothing (AS-27). A purchase signal would need `category` on `order.paid` (J01 already asks for it for S16) and a decision by S35 → not overriding an approved spec silently; if S35 adds a weight, AS-27 flips to an assertion of that weight.
- [CONTRACT] Recommendations after one purchase → impossible by S34 design (3 orders / 3 buyers, nightly build); the journey makes three real purchases and runs the job through the control surface; it never lowers a threshold → black box over real rules.
- [CONTRACT] `order.paid` also gains `category` and `lineId` (J01 asks) → nothing new for J05, listed so S35/S34 do not diverge; `paidAt` is the J05 addition.
- [CONTRACT] Control surface additions → job allow-list gets `recommendations.build-bought-together`; the event tap covers `links.events` and `feed.events` → AS-03, AS-13, AS-19 prove "exactly once" for events with no other observer (J03 introduced the tap).
- [CONTRACT] Feed visibility of posts → R1 `DiscussionQueryService.getPostsByIds` on every read (S25 export, S26 consumer) so a deletion is immediate (H5 = 0 s) → matches both specs; J05 only asserts the effect.
- [CONTRACT] Notification of a comment → S28 adds `discussions` type `discussion.comment` for `postAuthorId` and subscribes to `discussion.events` (S28's table lists it; its router does not subscribe today) → AS-09.
- [CONTRACT] Storefront emitters → W02/W03 must emit `product_view`, `add_to_cart`, `exposure` and send `ref` in the checkout body; the test plays the storefront until then (S35 and S39 already list the emitters as `[CONTRACT]` on W02/W03).
- [CONTRACT] Home-feed page and follow button have no web owner (S26 questions) → AS-34 is specified and marked pending; a web capability (W02 for the follow button, one for the feed page) must claim it.
- [CONTRACT] Experiment unit for J05 → `user` with metric `purchase`; a `visitor` experiment cannot count purchases (S39) → AS-30, AS-33.
- [CONTRACT] H7 and H14 keep the specs' 60 s (S37 SC-004, S39 FR-044) rather than a tighter local figure → no capability is asked for more than it promised; tests poll, so a faster stack is not penalised.
- [CONTRACT] Group names above are contracts of S26, S37, S34, S35, S39 and S28 (`notification-router`) → the capability specs do not name most of them; this journey fixes them (J03 did the same for `auctions-order-results`).
