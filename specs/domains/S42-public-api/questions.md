# Questions and decisions: S42 — Seller public API (domain `developer-platform`)

Decisions taken unattended (policy: the most production-grade option the notes and the constitution support). One line each: `- [TAG] question → default → why`. BREAKING first (changes behaviour or a contract that exists today: update existing tests and callers), then CONTRACT (another capability must provide or consume it), then LOCAL.

## BREAKING

- [BREAKING] Stock write `POST /v1/stock/bulk {items:[{productId, stock}]}` sets absolute values and overwrites sales made meanwhile (`public-catalog.service.ts:180`) → deltas with an `operationId` (`{operationId, productId, delta}`), applied through S05's `applyStockDelta` (all-or-nothing ≤ 100, idempotent per operation, never below zero), result per item, job chunks of 100 → absolute "set to N" is a lost-update bug on a live inventory; the delta contract is the one S05 offers and proves.
- [BREAKING] Missing `Idempotency-Key` on a creating POST is accepted today → `422 idempotency_key_required` on `POST /v1/products`, `/v1/stock/bulk`, `/v1/batch` (and per `POST` batch operation `idempotencyKey`) → constitution V.6 (key required, replay / in flight 409 / different body 422 / TTL).
- [BREAKING] Money in requests: `price` is a bare integer today but a `{amount, currency}` object in responses → latest version takes `price: {amount, currency}`; the old version `2026-01-15` keeps the bare integer through a request transformer; `price: 0` is refused (S05: free products are not a concept); currency must equal the platform currency, never hard-coded `usd` (`public-catalog.service.ts:56`) → symmetric, P0103, one shape per version.
- [BREAKING] Product update has no concurrency control (`UPDATE … coalesce(…)` at `public-catalog.service.ts:133`) → `PATCH` requires `If-Match: "<version>"` (`428` absent, `412 version_conflict` stale), responses carry `ETag` and `version`, batch PATCH uses `ifMatch` → lost-update prevention; matches S05's `expectedVersion`.
- [BREAKING] Today the product handlers, catalog and orders services run raw SQL on `Product`, `Shop`, `ShopOrder`, `BisOrder`, `BisOrderItem` → R1 only: S05 `ProductQueryService` / `ProductCommandService` / `ProductStockService`, S10 `OrderQueryService`, S03 `ShopQueryService` → constitution IX.4; debt D-7, D-12.
- [BREAKING] Sandbox shop is created with raw `INSERT INTO "Shop"` using a `sandboxOf` column that is not in the model (`api-keys.service.ts:124`) → S03 `ShopProvisioningService.ensureSandboxShop` (matches S03's own BREAKING line); sandbox responses carry `livemode: false` → one owner for `Shop`; the flag makes mode visible in every resource.
- [BREAKING] Batch per-operation scope failure is `400 insufficient_scope` (`v1.controller.ts:171`) and unsupported operations throw `400` → per-operation `403 insufficient_scope` and `422 unsupported_operation`, tenant misses `404`, failures are problem bodies, a 10 s budget leaves later operations unrun with `503 batch_deadline_exceeded` → the status an operation would have had as a request; budget protects the process.
- [BREAKING] `limit` is silently clamped, `fields`/`expand` are loose (`public-catalog.service.ts:92`, `pickFields`) → `limit` `1…100` strict (`400`), invalid cursor `400 invalid_cursor`, `expand` accepts only `shop`, depth 1, ≤ 3 (`400 invalid_expand`), `fields` and `expand` speak the requested version's names → P0403 depth limits; predictable clients; tolerant-reader applies to clients, not to our input.
- [BREAKING] Validation errors and not-found bodies use ad-hoc `{type, message}` objects (`api-key.guard.ts:30`, `public-catalog.service.ts:117`) → RFC 9457 problem+json with `type` URL, `title`, `status`, `detail`, `instance`, `requestId`, `code`, `errors[]` for validation, generic detail on 5xx → constitution V.3.
- [BREAKING] The client's `X-Request-Id` becomes the request ID (`public-api.interceptor.ts:38`) → server always generates `Request-Id`; a valid client value is echoed as `X-Client-Request-Id` and stored as `clientRequestId` → a client can otherwise collide or poison the log IDs.
- [BREAKING] Unpinned shops get "latest at every call" (`public-api.interceptor.ts:84-95`) → the shop is pinned to the latest version when its **first key** is created (atomic, once); the header still overrides per request; unknown version `400 invalid_version` → Stripe model; a new version never changes an existing integration.
- [BREAKING] Deprecation covers one route only and never ends → registry of routes **and versions** with sunset, `410 endpoint_retired` / `version_retired` after sunset, brownout windows (`410 endpoint_brownout` + `Retry-After`), a registry rule "sunset ≥ 6 months after deprecation", version `2026-01-15` deprecated on 2026-10-01 with sunset 2027-04-01 → notes 04/02 §3–5 (policy, timeline, brownouts, `410`).
- [BREAKING] Key management routes need only `shop.manage` → create/rotate/revoke and `PUT api-version` are `Firewall({sensitive:true})`, and creating or rotating a **live** key needs `amr` ∋ `mfa` (`403 mfa_required`); revoke is never blocked → S01/S02 contracts; a stolen session must not mint live credentials.
- [BREAKING] Key-hash pepper falls back to the JWT secret (`api-keys.service.ts:46`) → a dedicated `api_key_pepper` is required, startup fails without it, a previous pepper is accepted for rotation → one secret, one purpose (VIII.5); blast-radius separation.
- [BREAKING] Rotation always overlaps 24 h and can be repeated on the same key, and a revoked key can be rotated (`api-keys.service.ts:66-75`: `find` ignores status) → rotate allowed only from `active`; `409 key_revoked | key_expired | key_already_rotating`, conditional update with one winner; `overlapHours` `0…168`; revoke idempotent `204` → constitution III.7 (state transitions are conditional updates, illegal ones `409`).
- [BREAKING] Key creation has no per-shop limit → at most 25 active-or-rotating keys, enforced by the store under concurrency (`422 key_limit_reached`) → III.6; prevents runaway key sprawl (OWASP API6).
- [BREAKING] `GET /logs` runs raw ClickHouse SQL inside the controller, returns a fixed latest-100 with `status >= n` meaning (`api-keys.controller.ts:76-86`) → an application service behind a port; filters `status` class, `route`, `keyId`, `livemode`, `from/to`, keyset cursor, `limit 1…100`; `GET /usage` gains `days`, `livemode`, `deprecated` and per-key rows → II.1 (controllers hold no queries), III.10.
- [BREAKING] The request log is produced from the interceptor with a fire-and-forget producer that swallows errors (`public-api.interceptor.ts:79`) → bounded in-memory buffer with retry and a counted drop; and records for `401`s are not written → no silent loss; failed auth is a metric, not a log row.
- [BREAKING] `ApiKey`, `ShopApiSettings` have foreign keys to `Shop` and `User` (migration `20261001290000-public-api.js`) → expand/contract migration removes them (plain ID columns); `Shop.sandboxOf` and its index move to S03 → IX.4 (no FK across owners).
- [BREAKING] Bulk job state is a Redis hash with a 24 h TTL (`bulkstock:<id>`) → a durable table owned by this domain with one completion marker per chunk and 7-day retention → the cache is never the source of truth (III.9); idempotent chunk accounting.
- [BREAKING] `usage.recorded` is not emitted by developer-platform at all today (nothing calls billing's `UsageService` for API calls) → emitted per shop per UTC minute from the deduplicated request stream with deterministic event IDs; sandbox excluded → S18's required contract (`usage.recorded` v1) — metering is the point of the quota.
- [BREAKING] `GET /v1/orders` / `GET /v1/orders/:id` expose today's `ShopOrder` join and `unit_price` as a bare number → money objects (`{amount, currency}`) at latest, bare integers in the old version through the transformer; no buyer data; orders come from S10's R1 service → P0516 (property-level), IX.7.
- [BREAKING] `Cache-Control` is unset and CORS is the shared bootstrap's → `no-store` on every authenticated response, no CORS headers → OWASP API8; server-to-server API.

## CONTRACT

- [CONTRACT] S10 exports `getOrdersForShop` and `getOrderLines` but no single-order lookup → ask S10 to add `getShopOrder(shopId, shopOrderId): Promise<ShopOrderDto | null>` (shop-scoped; `null` for another shop's order, never a model) → `GET /v1/orders/:id` needs a scoped lookup; "load by ID then check" is forbidden (III.4) and listing and filtering client-side is wrong.
- [CONTRACT] S03 `ensureSandboxShop` must be safe under concurrent first calls and return `ShopSummaryDto` with `isSandbox: true`; sandbox shops have no members → AS-23 (exactly one sandbox shop under 10 parallel first calls); S03's own line says the same.
- [CONTRACT] S05 `ProductQueryService.getProductsByIds(ids, {shopId})` returns only the shop's products (foreign ids are absent, not an error) and `ProductCommandService.listByShop(shopId, {limit, cursor})` has an opaque keyset cursor and a unique tiebreaker; product `version` is exposed as `ETag` → AS-16 and AS-37; the bulk stock pre-filter is one statement.
- [CONTRACT] S18 `usage.recorded` v1 `{metric: "api.calls", quantity ≥ 1, ts}`, `aggregateId = shopId`, deterministic event ID per `(shop, metric, minute, sequence)`; late records emit a new sequence, never a total or a negative → S18's questions ask for a stable eventId per recorded batch; this is that identity.
- [CONTRACT] S18 `checkQuota` failure policy: S42 **fails open** on `usage_unavailable` (counter `public_api_quota_degraded_total`), caches the answer 60 s per shop, never applies it to test keys, and returns `429 quota_exceeded` with `Retry-After` ≤ 3,600 s → S18 leaves the decision to the caller; availability of seller integrations beats a billing-store outage; abuse is bounded by the per-key rate limit.
- [CONTRACT] S50 policy `public-api.default` must support a per-request **cost** (batch = operation count, bulk = ⌈items ÷ 100⌉) and emit `RateLimit-Limit/Remaining/Reset` and `Retry-After`; add `public-api.auth-failure.ip` (30/min, fail closed) → without cost, a 50-operation batch is a 50× bypass of the limit (OWASP API4).
- [CONTRACT] Shared idempotency store (P0414, specified first in S10) must scope a key by an explicit scope string (acting shop + route), expose claim / stored response / fingerprint / release-on-5xx / TTL, and be usable per batch operation → AS-47, AS-53; sandbox and live use different acting shops, so keys never collide.
- [CONTRACT] S01 `Firewall({sensitive:true})` and S02 `amr` ∋ `mfa` are used by key routes; `SecretBox` (S01 lists S42 as a consumer) is **not used** by S42 → key secrets are hashed, never decrypted; S43 will use `SecretBox` for webhook signing secrets, not this capability. S01's consumer note for S42 can be dropped.
- [CONTRACT] S43 reads `ApiVersionService` (supported versions, latest, shop pins by IDs) from this capability for webhook endpoint payload versions → keeps one version registry; webhooks, like the API, evolve additively with pinned versions (notes 04/02 §8).
- [CONTRACT] S03 events `tenancy.shop_status_changed` and `tenancy.shop_deleted` are consumed (this capability reacts to its shop's lifecycle) → the status staleness bound is 60 s without events; `shop_deleted` revokes keys once.
- [CONTRACT] W04 renders keys, version pin, logs and usage from the dashboard contract in `spec.md` and shows the full key once with a copy action, never storing it → the UI journey row for AS-01, AS-06, AS-08, AS-30 lives in W04.
- [CONTRACT] The `packages/contracts` package gets one schema set per supported version for products, orders, lists, batch results, bulk jobs, key DTOs, log rows and the problem document → constitution V.2 and VII.6; AS-67.

## LOCAL

- [LOCAL] Keys survive the creator leaving the shop → yes, `createdBy` is audit only → shop-owned machine credentials; manual revoke exists.
- [LOCAL] Key cache holds hash + metadata and revoke writes a short-lived tombstone with an atomic fill-if-absent → closes the "racing fill revives a revoked key" window (AS-09).
- [LOCAL] Product list order → the catalog's deterministic keyset order; orders newest first → whatever S05/S10 provide, ending in a unique tiebreaker.
- [LOCAL] Shop status staleness without events → 60 s → same as the key cache; events make it immediate.
- [LOCAL] Request logs are best-effort (bounded buffer 10,000 + counted drop); usage is exact from the deduplicated stream → logs are for people; usage is money.
- [LOCAL] Usage bucket is the UTC minute with sequence numbers → bounded event rate (≤ 1/min/shop plus late corrections).
- [LOCAL] Per-key deprecation telemetry lives in the usage report, not in metric labels → label cardinality (client ID as a Prometheus label is unbounded).
- [LOCAL] Sandbox has no orders, no reset, no webhooks → smallest honest sandbox; orders in sandbox need a checkout simulation, which is another capability.
- [LOCAL] Products and orders read through R1 (database), not an R3 read model → lists are scoped to one shop, so R1 is allowed; revisit only if the 30k RPS load test fails.
- [LOCAL] Brownout windows and deprecations are code-registered → no new table; changes ship with a release and its changelog.
- [LOCAL] OpenAPI 3.1 is generated from the code and published at the documentation route; the OWASP mapping lives in the developer docs and a test checks the scenario IDs exist → docs stay true.
- [LOCAL] 2 MiB body limit and 10,000-item bulk limit → one bulk request of 10,000 items is about 700 KB.
- [LOCAL] `HEAD` is `GET` without a body; `OPTIONS` is not served → no CORS.
- [LOCAL] Rotation of the pepper is a one-way re-hash on next successful use → no bulk re-hash job.
