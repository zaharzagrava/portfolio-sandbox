# Test Plan: S13 — Payment Intents, Idempotency, Unknown Outcomes, PSP Circuit Breaker, Outbox, Saga with Orders (domain `payments`)

Constitution VII.8 table: one row per acceptance scenario in [`spec.md`](spec.md) (66 rows), each proven at the lowest layer that can prove it. A dash means the layer does not test that scenario.

- API e2e files live in `packages/backend/libs/domains/payments/`. Each file's top-level `describe` names its feature (VII.8). They boot the real `PaymentModule` and `PaymentProcessorModule` (the processor, the consumers and the jobs are invoked through their handlers, as other specs do) with the production prefix, `ValidationPipe`, problem+json filter and interceptors, against real Postgres, Redis and the outbox, with real migrations, and call HTTP through `supertest`:
  - `payment-intent.e2e-spec.ts` — describe "Payment intents: accept, idempotency, validation and access"
  - `payment-charge.e2e-spec.ts` — describe "Payments: charge processing and outcomes"
  - `payment-unknown.e2e-spec.ts` — describe "Payments: unknown outcomes and resolution"
  - `payment-breaker.e2e-spec.ts` — describe "Payments: provider circuit breaker, timeouts and degradation"
  - `payment-transitions.e2e-spec.ts` — describe "Payments: guarded transitions and races"
  - `payment-order-events.e2e-spec.ts` — describe "Payments: order facts and order-driven compensation" (VII.4 duplicate and invalid-payload tests for the `orders.events` consumer)
  - `payment-refund.e2e-spec.ts` — describe "Payments: refund commands" (VII.4 tests for the `orders.refund_requested` consumer)
  - `payment-status-service.e2e-spec.ts` — describe "Payments: exported status service and provider refresh"
  - `payment-events.e2e-spec.ts` — describe "Payments: events, outbox atomicity and realtime"
  - `payment-read.e2e-spec.ts` — describe "Payments: reads, list and tenant isolation"
  - `payment-ops.e2e-spec.ts` — describe "Payments: observability, secrets, configuration and shutdown"
- The order copy is fed in tests by publishing S10-shaped order events (contract-valid fixtures from `packages/contracts`) to the consumer's handler; the ledger is S14's real exported service on the real tables (no spec injects `ProductModel`, `BisOrderModel`, `UserModel` or `PaymentModel`; payments and users are seeded through the shared fixture helpers, D-7). Every test asserts the response body **and** persisted state (payment, history, order copy, ledger journals, outbox rows, jobs, idempotency record, provider-call log) and parses responses with the `packages/contracts` schemas `paymentAcceptedSchema`, `paymentSchema`, `paymentPageSchema` and the event schemas (VII.6). Users come from the S01 fixture.
- Only system edges are faked: identity token verification, the payment provider (one scriptable test double behind the provider port: answers per call, delays, timeouts, `5xx`, declines, customer-action, lookup results, refund results, with a call log), the realtime hub (a spy), the rate limiter's store (forced down in two scenarios) and the clock (frozen and advanced by the test). The breaker, retries, backoff and state machine run for real.
- Consumers (`orders.events`, `orders.refund_requested`, the charge command) have the duplicate-delivery and invalid-payload tests of VII.4 (AS-20, AS-44, AS-51, AS-53).
- Unit specs sit beside the code under `domain/`, are table-driven (`it.each`), and exist only for pure logic (VII.5): `payment-status.spec.ts` (transition table), `provider-outcome.spec.ts` (classification of provider answers and validation of their fields), `payment-amount.spec.ts` (range and currency rules), `backoff.spec.ts` (full-jitter bounds with an injected random source). Money rules also get one `fast-check` property (any amount in range, in any supported currency, is accepted and any outside is refused). Controllers, repositories, jobs and glue get no unit tests.
- UI journey (Playwright): owned by W03, `packages/web/tests/cart-checkout.spec.ts` — one happy path: a signed-in buyer checks out, presses "Pay" with the provider's test card, and the order page shows `PAID` (the provider double returns "succeeded"). It never repeats an edge case from this plan; rows below mark the steps it covers; the API column still holds the deep proof.
- Static gates (VII.1): `tsc --noEmit` and ESLint for `packages/backend` and `packages/contracts`; `pnpm check:boundaries`; `pnpm --dir packages/backend check:table-ownership --strict` for payment-intent files (AS-64).
- Gate 9 (VII.9): AS-14 (limiter store down), AS-22 (invalid provider answer), AS-23 (timeout), AS-27 (provider unreachable while resolving), AS-29 (lost job), AS-30 (crash), AS-31–AS-38 (breaker, timeouts, outage), AS-45 (ledger and transaction failure), AS-54 (refund failures), AS-56 (provider down during refresh), AS-61 (hub down), AS-66 (shutdown) each force their fault.
- Concurrency tests use `Promise.all` and assert that exactly one succeeds and the invariant holds (VII.3): AS-05, AS-06, AS-20, AS-40, AS-43, AS-51, AS-56.
