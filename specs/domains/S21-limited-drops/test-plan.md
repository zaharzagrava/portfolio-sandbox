# Test Plan: S21 — Limited-Drop Auctions (domain `auctions`)

Constitution VII.8 table: one row per acceptance scenario in [`spec.md`](spec.md) (54 rows), each proven at the lowest layer that can prove it. A dash means the layer does not test that scenario.

- API e2e files live in `packages/backend/libs/domains/auctions/`. Each file's top-level `describe` names its feature (VII.8). They boot the real `AuctionsModule` and `AuctionsWorkerModule` (jobs and the `orders.events` consumer are invoked through their handlers, as other specs do) with the production prefix, `ValidationPipe`, problem+json filter and interceptors, against real Postgres (real migrations, real monthly partitions), real Redis (the same major version as production; cache, limiter and realtime only), the outbox, the inbox and the job table, and call HTTP through `supertest`:
  - `auction-schedule.e2e-spec.ts` — describe "Auctions: scheduling, authorization, listing and cancel"
  - `auction-bidding.e2e-spec.ts` — describe "Auctions: proxy bidding, server clock, idempotency and concurrency"
  - `auction-shill-guard.e2e-spec.ts` — describe "Auctions: shill-bid guard"
  - `auction-anti-sniping.e2e-spec.ts` — describe "Auctions: anti-sniping extension"
  - `auction-close.e2e-spec.ts` — describe "Auctions: exactly-once close, winner order and second chance" (includes the VII.4 duplicate-delivery and invalid-payload tests of the jobs and of the `orders.events` consumer)
  - `auction-public.e2e-spec.ts` — describe "Auctions: public view, bid history, my bid and live price push"
  - `auction-operations.e2e-spec.ts` — describe "Auctions: events, bid partitions, metrics and domain isolation"
- Products, shops, memberships, stock and orders are seeded and read in tests only through the shared fixture helpers and the exported services (`ProductQueryService`, `ProductStockService`, `ShopAccessService`, `OrderQueryService`); no spec injects `ProductModel`, `BisOrderModel`, `ShopModel`, `ShopMembershipModel` or `UserModel` (D-7). Auctions are created through the schedule route and closed by invoking the `auctions.close` handler; no spec calls a service class of the domain. Every test asserts the response body **and** persisted state (auction, bids, history, outbox rows, jobs, inbox rows, catalog stock, S10 orders through its exported reads, cache keys where relevant) and parses responses with the `packages/contracts` schema (VII.6).
- Only system edges are faked: identity token verification, S10's payment confirmation (order paid and cancelled events are delivered by S10's own handlers or by a contract-valid fixture of its events), the realtime transport, the entitlement lookup of S18 where a plan must be forced, and the clock (frozen and advanced; every window, anti-sniping and close decision uses the injected clock). Faults use real mechanisms: a store rule making the cache/limiter store refuse commands (AS-21, AS-22, AS-45), a flush of the whole fast store (AS-22), a refused outbox append (AS-23), a tenancy lookup that times out (AS-41), a crash switch between two steps of a job (AS-06, AS-33), a gate (latch) inside the bid decision (AS-32) and a deleted close job (AS-31).
- Unit specs sit beside the code under `domain/`, are table-driven (`it.each`), and exist only for pure logic (VII.5): `proxy-bid.spec.ts` (with `fast-check` for the resolution invariants), `auction-state.spec.ts` (state machine, bidding window, extension, alias, runner-up selection). Controllers, repositories, jobs, adapters and glue get no unit tests; nothing mocks Redis or the ORM (the current Lua and relay code is deleted, with nothing to unit-test).
- UI journey (Playwright): `packages/web/e2e/auctions.spec.ts` (owned by the web capability for auction pages) — one happy path: the seller's auction (created through the API fixture) is `OPEN` with a countdown anchored on server time, bidder 1 bids a maximum and sees "you are leading", bidder 2 (API fixture) outbids and bidder 1's page updates without reload, the clock reaches the end, the page shows closed, and the winner's account shows a reserved order at the final price. It never repeats an edge case from this plan.
- Static gates (VII.1): `tsc --noEmit` and ESLint for `packages/backend`, `packages/contracts`, `packages/web`; `pnpm check:boundaries`; `pnpm --dir packages/backend check:table-ownership --strict` (AS-52).
- Gate 9 (VII.9): AS-21 (limiter down), AS-22 (store wiped, realtime down), AS-23 (outbox failure), AS-31 (lost close job), AS-33 (crash between close and order request, S10 failure), AS-41 (tenancy down), AS-45 (cache down), AS-50 (missing partition) each force their fault.
- Concurrency tests use `Promise.all` and assert that exactly the allowed number succeed and the invariant holds (VII.3): AS-04, AS-05, AS-09, AS-18, AS-19, AS-20, AS-28, AS-31, AS-32, AS-33, AS-35, AS-39, AS-50.
- Consumers (VII.4): the `orders.events` consumer is covered by AS-34 (duplicate and invalid payload) and AS-39 (duplicate, late, out of order); the jobs by AS-28, AS-31, AS-33, AS-35, AS-50.
