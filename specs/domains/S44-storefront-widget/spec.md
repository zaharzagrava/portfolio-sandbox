## Overview

A shop puts a **"Buy on Marketplace" button on its own website** with two lines of HTML: a script tag that carries a public **site key**. A visitor clicks the button, and our checkout opens in an iframe on top of the shop's page. The shop's page is not ours: it can be anyone's domain, anyone can copy the public key out of its HTML, and the shop may want to tell us who its logged-in customer is. This capability makes that safe and controllable:

- **A copied key is useless on someone else's website.** Every site key is bound to a short list of exact origins. A request from any other origin gets nothing, not even the shop's name.
- **Only the shop's own pages can frame our checkout.** The iframe document is allowed to be framed by exactly the origins registered for that key; every other page of ours refuses to be framed at all (clickjacking). The iframe document runs under a strict script policy with a fresh nonce on every response.
- **The shop can say who its customer is, without cookies and without trust in the browser.** The shop's own backend signs a short-lived, single-use hand-off token with a secret only the shop holds; we exchange it for a short-lived widget session that lives in the iframe's memory. We never create or link a marketplace account from it.
- **The shop (or we) can switch a site off at once.** A kill switch makes the button disappear, the checkout refuse to load and every session stop working, without a deploy. Shops that are suspended or deleted switch their sites off automatically.
- **The page is never harmed by us.** The loader is tiny, async, one global, and every failure ends in "render nothing".

### Scope

In scope: site management by shop managers (create, list, read, update origins / featured products / theme, rotate the identity secret with an overlap, delete, kill switch, change history); the public widget API under `/api/widget/v1` (`config`, `identify`, `session`, `embed`, plus CORS preflight); exact-origin binding and per-site CORS; the framing policy and strict CSP of the embed document and the `frame-ancestors 'none'` default everywhere else; the identity hand-off and the widget session token and its verifier; the CSRF stance of widget and dashboard mutations (P0504); the edge loader and its `postMessage` contract; reaction to shop rename, suspension and deletion; abuse limits; events, metrics and logs of all of that.

Out of scope (owners named):

- The iframe checkout application itself (cart, address, payment screens, its use of the widget session) → **W07** (app shell, CSP and security headers of the web app); the checkout domain behaviour → **S10**, **S13**. This capability delivers the document, the policy and the token contract that application runs under.
- The dashboard screens for site management → **W04**. This capability defines the API they call.
- Public API keys (`sk_`), request logs, versions → **S42**; webhooks → **S43** (same domain). The widget's identity secret is not an API key and is never accepted by the public API.
- Who may do what in a shop and the shop status machine → **S03**; this capability uses the permission `widget.manage` that S03 is asked to define and reacts to S03's events.
- Rate-limit engine, cache toolkit, outbox/consumer runtime, request context, problem+json filter → **S50 / S52 / S53 / S54**; secret sealing and the CSRF guard for cookie sessions → **S01**.
- Per-site partitioned cookies (CHIPS) as a session transport: not built; the in-memory token is the only transport (see Assumptions). Wildcard origins, a platform-wide switch for a whole widget version (done by CDN purge or deploy, or later through S38 flags), analytics events from the widget (S39), custom domains for the embed host, and mobile-app (non-browser) embedding: not in this release.

Cross-domain data used (constitution IX.7): product title, price and stock by **R1** (S05 `ProductQueryService.getProductsByIds`, called with the shop filter, never a table read); shop name and status by **R3** (this capability keeps a version-guarded copy on its own site record, fed by S03's `tenancy.shop_updated` and `tenancy.shop_status_changed`, seeded once through **R1** `ShopQueryService.getShopsByIds` when a site is created); shop deletion by an **event** (`tenancy.shop_deleted`); membership and permission by **R1** (S03 `ShopScoped`). The widget configuration is assembled inside the domain (it owns the site table; per the runbook it is a domain, not a composition lib), so R2 is not used. This capability reads and writes no table owned by another domain.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — A shop registers and manages a widget site (Priority: P1)

A shop owner or admin registers a site: the list of exact origins where the button will appear, and optionally which products to feature. They get a public key for the page and a secret for their server, shown once. They can later change origins, products and look, rotate the secret without breaking running checkouts, and delete the site.

**Why this priority**: nothing else exists without a site; the origin list is the root of every later check.

**Independent Test**: create a site through the dashboard API with an admin session, read it back, change its origins, rotate its secret, delete it, with every other role and shop refused.

**Acceptance Scenarios**:

1. **AS-01 (create)** — **Given** an `ADMIN` of an `ACTIVE` shop `S` with two products, **When** `POST /api/shops/S/widget/sites {name: "Main blog", origins: ["https://www.my-shop.com", "https://shop.example:8443"], featuredProductIds: [P1, P2]}`, **Then** `201` with `{id, shopId, name, publishableKey, identitySecret, allowedOrigins, featuredProductIds, theme: {}, killSwitch: false, hasPreviousSecret: false, previousSecretExpiresAt: null, version: 1, createdAt, updatedAt}` where `publishableKey` matches `^pk_live_[A-Za-z0-9_-]{24}$` and `identitySecret` matches `^wis_[A-Za-z0-9_-]{43}$`; the stored row holds the secret only in sealed form (the plaintext appears nowhere in the database, the outbox row, the logs or any later response); the site's copy of the shop (name, status `ACTIVE`, `shopVersion`) is stored; one `developer_platform.widget_site_changed {change: "created"}` is in the outbox; a following `GET` of the site has no `identitySecret`; the response parses with `widgetSiteCreatedSchema`.
2. **AS-02 (origin rules, pure)** — **Given** the origin rule, **When** it is given the table below, **Then** the outcomes match: accepted (stored normalised) — `https://www.my-shop.com`, `HTTPS://WWW.My-Shop.COM` → `https://www.my-shop.com`, `https://shop.example:8443`, `https://shop.com:443` → `https://shop.com`, `https://bücher.example` → `https://xn--bcher-kva.example`; rejected with a reason — `http://shop.com` (`not_https`), `https://shop.com/path`, `https://shop.com/?q=1`, `https://shop.com/#x` (`not_an_origin`), `https://user:pw@shop.com` (`userinfo`), `https://*.shop.com` (`wildcard`), `https://192.168.1.1`, `https://[::1]`, `https://8.8.8.8` (`ip_literal`), `https://localhost`, `https://intranet` (`single_label_host`), `https://shop.com.` (`trailing_dot`), `shop.com`, `""`, `"null"`, `ftp://shop.com`, a string over 253 characters (`malformed`), a port of `0` or above `65535` (`bad_port`). Over the API a rejected origin is `422 origin_invalid` with `details: {origin, reason}` and nothing is stored (one wired case proves the status and body; the table is proven once, by the pure rule).
3. **AS-03 (validation)** — **Given** a manager, **When** the create or update body has: no `origins`, an empty list, more than 10 origins, a non-array, a non-string element, more than 12 `featuredProductIds`, a non-UUID product ID, a `name` over 60 characters or empty, an unknown property (for example `killSwitch` or `publishableKey`), or a non-object `theme`, **Then** each answers `400 validation_failed` with the failing field, and nothing is stored. Duplicate origins after normalisation (`https://Shop.com` and `https://shop.com:443`) collapse to one entry, and an update whose origins collapse to the same set as before is not a change.
4. **AS-04 (theme)** — **Given** a manager updates `theme`, **When** it contains only the allowed keys with valid values (`primaryColor`, `textColor`, `backgroundColor`: `#rrggbb`; `borderRadius`: integer 0–24 followed by `px`; `fontFamily`: one of `system`, `serif`, `mono`; `buttonLabel`: 1–40 characters, text only), **Then** `200` and the values are stored as given; **When** it contains an unknown key, a colour such as `red` or `url(javascript:…)`, a radius of `25px`, a label with `<` or control characters, or a value that is not a string, **Then** `400 validation_failed` and the theme is unchanged. The theme is rendered by the loader as text and as validated style values only (AS-47).
5. **AS-05 (site limit)** — **Given** a shop with 9 sites, **When** 20 `POST` create requests run at once, **Then** exactly one answers `201`, the other 19 answer `422 site_limit_reached`, and the shop has 10 sites; **Given** 10 sites, **When** one more is created, **Then** `422 site_limit_reached` and nothing is stored. Deleting a site frees a slot.
6. **AS-06 (list and read)** — **Given** a shop with 5 sites and another shop with 2, **When** `GET /api/shops/S/widget/sites?limit=2`, **Then** `200 {items: [≤2 WidgetSiteDto], nextCursor}` ordered by `createdAt` descending then `id` descending with an opaque cursor; following the cursor yields every site of `S` exactly once and none of the other shop's; no item has `identitySecret`; a `limit` of 0, 101 or a tampered cursor is `400 validation_failed`; `GET …/sites/:siteId` returns the one `WidgetSiteDto`.
7. **AS-07 (update and lost updates)** — **Given** site `X` at `version: 3`, **When** `PATCH …/sites/X {allowedOrigins, expectedVersion: 3}`, **Then** `200` with `version: 4`, the new origins and `updatedAt` advanced, and `widget_site_changed {change: "origins_changed"}` in the outbox (one change type per changed field group: `origins_changed`, `products_changed`, `theme_changed`; a rename emits none); **When** two `PATCH` requests with `expectedVersion: 4` run at once, **Then** exactly one answers `200` and the other `409 site_version_conflict`, and no change of the loser is stored; **When** `expectedVersion` is missing or stale, **Then** `400 validation_failed` / `409 site_version_conflict` respectively.
8. **AS-08 (featured products belong to the shop)** — **Given** products `P1` of shop `S`, `Q1` of shop `T`, an archived `P2` of `S`, and an unknown ID, **When** a manager of `S` sets `featuredProductIds` to each, **Then** `P1` is accepted; `Q1`, the unknown ID and a deleted product are all `422 featured_product_invalid` with identical bodies except the echoed ID (a foreign product is indistinguishable from an unknown one); an archived `P2` is accepted (it simply is not shown, AS-19); the check is one batch lookup through R1 with the shop filter, never one call per product.
9. **AS-09 (permission, IDOR, authentication)** — **Given** users OWNER, ADMIN, STAFF, VIEWER of shop `A`, a member of shop `B` only, and an anonymous caller, **When** each calls every dashboard route of this capability (create, list, read, update, rotate secret, expire previous secret, delete, kill switch, history) for `A`, **Then** OWNER and ADMIN succeed, STAFF and VIEWER get `403 permission_denied`, the member of `B` gets `404 shop_not_found`, the anonymous caller gets `401`; **When** an OWNER of `A` calls any of those routes with `A`'s shop ID and a site ID that belongs to `B`, or an unknown site ID, **Then** both answer the same `404 widget_site_not_found` body and `B`'s site is unchanged (the lookup carries the shop in its predicate).
10. **AS-10 (identity secret rotation with overlap)** — **Given** site `X`, **When** `POST …/sites/X/rotate-secret {overlapHours: 24}`, **Then** `201 {identitySecret, previousSecretExpiresAt}` (new secret `wis_…`, shown once; expiry = now + 24 h, frozen clock), the new secret is valid at once, the old secret stays valid until `previousSecretExpiresAt` (proven at the expiry instant by AS-28), `hasPreviousSecret` is `true`, and `widget_site_changed {change: "secret_rotated"}` is in the outbox; `overlapHours` defaults to 24, accepts `0` (the old secret stops at once) to `72`, and refuses anything else with `400 validation_failed`.
11. **AS-11 (rotation conflicts)** — **Given** a previous secret that is still valid, **When** `POST …/rotate-secret` is called again, **Then** `409 rotation_in_progress` and no secret changes; **When** `POST …/expire-previous-secret` is called, **Then** `200` with `hasPreviousSecret: false` and `widget_site_changed {change: "previous_secret_expired"}`; calling it again when there is no previous secret is `409 rotation_not_in_progress`; **When** two rotations run at once on a site without a previous secret, **Then** exactly one answers `201` and the other `409 rotation_in_progress`, and the site holds exactly one current and one previous secret.
12. **AS-12 (delete)** — **Given** a site with a warm cache, **When** `DELETE …/sites/X`, **Then** `204`, the row is gone, `widget_site_changed {change: "deleted"}` is in the outbox, the very next `config`, `identify`, `embed` and `session` calls with its key (any instance) answer `404 widget_site_not_found`, and deleting again answers `404 widget_site_not_found`.
13. **AS-13 (CSRF on the dashboard, P0504)** — **Given** a manager signed in with a **cookie** session (S01), **When** `POST …/widget/sites` is sent without the `X-CSRF-Token` header, **Then** `403 csrf_invalid` and nothing is created; **When** it carries the valid token and an allowed `Origin`, **Then** `201`; **When** the same request is authenticated by `Authorization: Bearer` and carries no CSRF header, **Then** `201` (no ambient credential, nothing to forge). The same holds for every mutation route of this capability (update, rotate, expire, delete, kill switch).

### User Story 2 — A visitor's browser gets the widget configuration only from a registered origin (Priority: P1)

The loader on the shop's page asks for the site's configuration. Only a page whose origin is registered for that key gets an answer; the answer is cheap to serve at huge volume and never leaks anything private.

**Why this priority**: this is the origin binding the whole capability is named after; the config route is also the hottest.

**Independent Test**: call the config route with a registered origin and with each wrong variant and check body, headers and that nothing leaks.

**Acceptance Scenarios**:

1. **AS-14 (config)** — **Given** an active site for shop "My Shop" registered for `https://www.my-shop.com` with featured products `P1` (price 12900, stock 3) and `P2` (stock 0), **When** `GET /api/widget/v1/config?key=<pk>` with `Origin: https://www.my-shop.com`, **Then** `200 {version: "v1", shop: {name: "My Shop"}, theme, products: [{id, title, price: {amountMinor: 12900, currency}, inStock: true}, {…, inStock: false}], checkoutUrl}` (integer minor units, never a float), parsed by `widgetConfigSchema`; headers `Access-Control-Allow-Origin: https://www.my-shop.com`, `Vary: Origin`, `Cache-Control: public, max-age=60, s-maxage=60`, `X-Content-Type-Options: nosniff`, and **no** `Access-Control-Allow-Credentials`, no `Set-Cookie`; the product data came from exactly one R1 batch call and no table of another domain was read; the body contains no `shopId`, no origin list, no secret and no internal ID other than product IDs.
2. **AS-15 (origin matching, pure)** — **Given** a site registered for `https://www.my-shop.com` and `https://shop.example:8443`, **When** the matcher is given: `https://www.my-shop.com` ✔, `https://WWW.MY-SHOP.COM` ✔, `https://www.my-shop.com:443` ✔ (default port), `https://shop.example:8443` ✔; and ✘ for `http://www.my-shop.com` (scheme), `https://my-shop.com`, `https://evil-www.my-shop.com`, `https://www.my-shop.com.evil.com`, `https://www.my-shop.com@evil.com`, `https://evilwww.my-shop.com`, `https://shop.example` (port missing), `https://shop.example:8444`, `https://sub.www.my-shop.com`, `null`, the empty string, a value with a path or trailing slash, a list `a, b`, and non-ASCII look-alikes (`https://wwш.my-shop.com`), **Then** only the ✔ rows match, by whole-origin equality after normalisation and never by prefix, suffix or substring.
3. **AS-16 (refusals, wired)** — **Given** the site of AS-14, **When** `config` is called with an unregistered origin, with the registered host over `http`, with no `Origin` header, with `Origin: null`, and with two `Origin` headers, **Then** each answers `403 origin_not_allowed` with the same body, **no** `Access-Control-Allow-Origin` header, `Cache-Control: no-store`, and no shop data; the order of checks is key (404) → origin (403) → switch/shop status (410) → data, so an unregistered origin cannot learn whether a site is switched off.
4. **AS-17 (unknown and malformed keys)** — **Given** no site with key `K`, **When** `config` is called with `K`, with a malformed key (`""`, `pk_live_x`, 500 characters, `pk_test_…`, `pk_live_` plus characters outside the alphabet, or no `key` at all), **Then** every case answers `404 widget_site_not_found` with the same body and `Cache-Control: no-store`; a malformed key is refused before any lookup and never becomes a cache key; a well-formed unknown key is looked up once and remembered as unknown for at most 30 seconds (never longer than the time a new site needs to become visible, AS-20).
5. **AS-18 (preflight)** — **Given** the site of AS-14, **When** `OPTIONS /api/widget/v1/identify` (and `…/config`, `…/session`) is sent with `Origin: https://www.my-shop.com`, `Access-Control-Request-Method: POST` and `Access-Control-Request-Headers: content-type`, **Then** `204` with `Access-Control-Allow-Origin` equal to that origin, `Access-Control-Allow-Methods: GET, POST` (never more), `Access-Control-Allow-Headers: Content-Type, Authorization`, `Access-Control-Max-Age: 600`, `Vary: Origin`, no credentials header; **When** the origin is unregistered or the key cannot be resolved (the key comes from the `key` query parameter of the preflight URL), **Then** `403 origin_not_allowed`, no `Access-Control-*` header; the global application CORS policy does not apply to these routes.
6. **AS-19 (product shaping)** — **Given** featured products `[P3, P1, P2]` where `P2` is archived and `P4` was deleted since, **When** `config` is called, **Then** `products` lists exactly the live, non-archived products of this shop in the configured order (`P3`, `P1`), an out-of-stock product has `inStock: false`, a product of another shop that somehow sits in the list is never shown, and when none remain `products` is `[]` with `200`; price and stock are the current database values (never an older cached copy than the config cache of AS-21).
7. **AS-20 (changes are visible at once, on every instance)** — **Given** a warm cache for site `X` on two application instances, **When** a manager removes origin `O` (AS-07), **Then** the very next `config`, `identify`, `session` and `embed` call from `O` on **either** instance is refused (`403 origin_not_allowed`; `embed` answers `frame-ancestors` without `O`); likewise a kill switch (AS-39), a delete (AS-12) and a shop status change (AS-43) apply on the very next request; **Given** a request for a key that was looked up and not found a moment ago, **When** a site with that key is created, **Then** the next request resolves it (the unknown-key memory is cleared by the creation). Intermediary (CDN) copies of a successful `config` are bounded by `s-maxage=60`.
8. **AS-21 (degradation: stale on error)** — **Given** a `config` response produced less than 600 seconds ago and a failing product lookup (R1 raising or timing out after its deadline), **When** `config` is requested after the 60-second fresh window, **Then** the last good response is served (`200`, `Cache-Control: public, max-age=0, s-maxage=15`, header `Warning: 110 - "Response is Stale"`); **Given** no last good copy, **Then** `503 service_unavailable` (generic detail, `Cache-Control: no-store`) and the failure is counted and logged with the request ID but not the key owner's data; after recovery the next request is fresh again. A failed lookup is never cached as success.
9. **AS-22 (rate limits and fail modes)** — **Given** the policies `widget.config.ip` (600 per minute, fail-open: a public read must stay up), `widget.identify.ip` (30 per minute) and `widget.identify.site` (1,200 per minute per key, both fail-closed), **When** a caller exceeds one, **Then** `429` problem+json with `Retry-After` and `RateLimit` headers, and the counter of another key or another IP is untouched; **When** the limiter's store is unavailable, **Then** `config` is still served (`200`), `identify` answers `503 service_unavailable` and mints no token, and a fallback counter increases. Identify never consumes the login policies of S01.

### User Story 3 — The shop tells us who its customer is, and nobody else can (Priority: P1)

The shop's page asks its own backend for a hand-off token (its server signs it with the secret from AS-01). The page passes the token to our iframe; we check it and hand the iframe a short-lived session kept in memory. A stolen, forged, replayed or over-long token never works.

**Why this priority**: it is the only place a third party's claim about a person enters our system; the notes call out the attack (account takeover by e-mail) explicitly.

**Independent Test**: sign tokens with the site's secret in a test, exchange them, and try every tampered variant.

**Acceptance Scenarios**:

1. **AS-23 (exchange)** — **Given** site `X` and a hand-off token signed with HS256 and the site's secret, `aud: "marketplace-widget"`, `iss: <pk>`, `sub: "cust-42"`, `email: "buyer@example.com"`, a fresh `jti` and `exp` 120 s ahead, **When** `POST /api/widget/v1/identify {key, token}` with the registered `Origin`, **Then** `200 {widgetToken, expiresIn: 900, customer: {id: "cust-42", email: "buyer@example.com"}}` (`email: null` when the token has none), `Cache-Control: no-store`, the registered origin echoed, no `Set-Cookie`; the widget token is a signed token with `typ: widget+jwt`, `aud: marketplace-widget-session`, `iss: marketplace`, `site`, `shop`, `ext` (the shop's customer ID), `email`, `jti`, `iat` and `exp` = `iat` + 900, and it is signed with a key that no access-token verifier accepts (AS-33); the single-use marker of the hand-off `jti` is stored for the site; the response parses with `widgetIdentifySchema`.
2. **AS-24 (claims policy, pure)** — **Given** the claims policy and a frozen clock, **When** given the table: valid; `sub` missing, empty, 129 characters or a non-string; `jti` missing, shorter than 8 or longer than 128 characters; `exp` missing, non-integer, equal to now (expired at the instant), 301 s ahead (too long), exactly 300 s ahead (accepted); `aud` different, an array, or missing; `iss` different or missing; `nbf` 31 s in the future (rejected) and 30 s (accepted); `iat` 61 s in the future (rejected) and 60 s (accepted); `email` present but not an address, over 254 characters or not a string; extra unknown claims (ignored), **Then** exactly the accepting rows pass and every rejection is one closed reason (`bad_subject`, `bad_jti`, `expired`, `too_long_lived`, `bad_audience`, `bad_issuer`, `not_yet_valid`, `bad_issued_at`, `bad_email`, `missing_exp`).
3. **AS-25 (forgeries, wired)** — **Given** the site, **When** `identify` receives: a token signed with another secret; with the right secret but a foreign `iss`; an `alg: none` token; an HS384 token; an RS256 token whose "key" is our own public text (algorithm confusion); a token with `exp` 1 h ahead; an expired token; a token signed for a different site of the same shop; a non-JWT string; **Then** every case answers `401 identity_token_invalid` with a byte-identical body (the reason goes to the log and a metric label only), no widget token, no single-use marker stored, and nothing about the secret leaks through timing-visible differences between "wrong secret" and "wrong claims" beyond one signature check.
4. **AS-26 (replay and concurrent replay)** — **Given** a valid hand-off token, **When** it is exchanged a second time, **Then** `401 identity_token_invalid` (single use); **When** 20 identical exchanges run at once, **Then** exactly one answers `200` and 19 answer `401`; **When** the same `jti` is used on a different site, **Then** it is independent (accepted once there); the marker lives until the token's `exp` plus 60 seconds.
5. **AS-27 (marker store down, fail closed)** — **Given** the single-use store is unreachable, **When** a valid token is exchanged, **Then** `503 service_unavailable`, no widget token is minted, a fallback counter increases, and the same token works once the store is back (it was not consumed).
6. **AS-28 (secret overlap boundary)** — **Given** a rotation with a 24-hour overlap at frozen time `T`, **When** tokens signed with the previous secret are exchanged at `T + 24 h − 1 s` and at `T + 24 h`, **Then** the first is accepted and the second is `401`; tokens signed with the new secret are accepted at both times; after `expire-previous-secret` the previous secret is refused at once; with `overlapHours: 0` it is refused at once.
7. **AS-29 (no account linking)** — **Given** a marketplace user with the e-mail `buyer@example.com`, **When** a valid hand-off token carrying that e-mail is exchanged, **Then** the response and widget token carry the shop's `ext` and the e-mail as claimed, **no** marketplace session, user, link or account is created, read or changed (user and session counts equal before and after), and the widget token is refused by every marketplace route (AS-33). Linking a shop's customer to a marketplace account is not available in this capability.
8. **AS-30 (order of checks)** — **Given** a switched-off site, an unregistered origin, and an unknown key, **When** `identify` is called with a valid token in each case, **Then** the answers are `410 widget_disabled` (registered origin, switched off), `403 origin_not_allowed`, and `404 widget_site_not_found`, in the order key → origin → switch/shop status → token; the token is not opened (no signature check) before the first three pass.
9. **AS-31 (no ambient credentials, P0504)** — **Given** the widget routes, **When** `identify` is sent with `Content-Type: application/x-www-form-urlencoded` or `text/plain`, **Then** `415 unsupported_media_type` and nothing is evaluated (a cross-site HTML form can send nothing else without a preflight); **When** it carries a valid marketplace session cookie but no token, **Then** `401 identity_token_invalid` (cookies are never read as credentials by any widget route, and the marketplace session is not used); **When** the body is over 8 KiB, **Then** `413 payload_too_large`; **When** the `token` is over 4 KiB, **Then** `400 validation_failed`; **When** any widget route succeeds or fails, **Then** the response has no `Set-Cookie` header. Because widget requests are authenticated only by an explicit value in the body or the `Authorization` header and gated by the origin list, a page on another site cannot cause a state change by making the visitor's browser send a request.
10. **AS-32 (session check and verifier)** — **Given** a widget token minted by AS-23, **When** `GET /api/widget/v1/session` with `Authorization: Bearer <widgetToken>` and the registered `Origin`, **Then** `200 {site: {id}, customer: {id, email}, expiresAt}`; **When** the token is expired (frozen clock +900 s), malformed, has another `aud` or `typ`, was signed by another key, or its site was deleted, switched off or belongs to a shop that is no longer `ACTIVE`, or the `Origin` is no longer registered, **Then** `401 widget_token_invalid` (token problems) or `410 widget_disabled` (site switched off or shop inactive) or `403 origin_not_allowed`; no header means `401`. The same decision is what the exported `WidgetSessionService.verify(token, origin?)` returns: the principal or `null`, never an exception.
11. **AS-33 (token isolation)** — **Given** a valid widget token, **When** it is sent as `Authorization: Bearer` to a marketplace API route that requires a user (for example `GET /api/auth/me`) and to the public API, **Then** both answer `401` (different key, audience and `typ`); **Given** a valid marketplace access token and a valid S42 `sk_` key, **When** either is sent to `GET /api/widget/v1/session`, **Then** `401 widget_token_invalid`; a hand-off token is never accepted as a widget token and the reverse.

### User Story 4 — Only the shop's own pages can frame our checkout (Priority: P1)

The iframe document tells the browser which pages may display it: exactly the origins registered for the key. Everything else we serve refuses to be framed. The document itself runs only scripts we marked with a fresh nonce.

**Why this priority**: without it anyone can overlay our checkout on a hostile page (clickjacking); it is pattern P0502.

**Independent Test**: fetch the embed document for two sites and read the headers; fetch other routes and read theirs.

**Acceptance Scenarios**:

1. **AS-34 (embed document and strict CSP)** — **Given** an active site, **When** `GET /api/widget/v1/embed?key=<pk>`, **Then** `200 text/html; charset=utf-8` and a `Content-Security-Policy` header that has `default-src 'none'`, `script-src 'nonce-<N>' 'strict-dynamic'`, `object-src 'none'`, `base-uri 'none'`, `form-action 'self'`, `frame-ancestors <origins>`, and no `unsafe-inline`, `unsafe-eval`, `*`, `data:` or bare scheme source in `script-src`; `<N>` is at least 128 bits, base64, and different on every response (50 consecutive responses are all different); the document's only script element carries `nonce="<N>"`, the document has no inline event handler and no other script; headers `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and **no** `X-Frame-Options` (a conflicting value would override the allowlist in older browsers); the site key appears in the document only as a URL-encoded attribute value.
2. **AS-35 (frame-ancestors is exactly the site's list)** — **Given** site `X` registered for `https://www.my-shop.com` and `https://shop.example:8443` and site `Y` for `https://other.example`, **When** the embed document of each is fetched, **Then** `X`'s header has `frame-ancestors https://shop.example:8443 https://www.my-shop.com` (the exact normalised origins, sorted, no duplicates, no wildcard, no `https:` scheme source, no `'self'`) and `Y`'s has only `https://other.example`; after an origin edit (AS-07) the next fetch reflects it (AS-20).
3. **AS-36 (everything else refuses framing)** — **Given** the application, **When** each of these is requested: `config` (success and every error), `identify`, `session`, a dashboard route, a 404 page, a 500 response, `embed` for an unknown key, `embed` for a malformed key, `embed` for a switched-off site, **Then** every response carries `Content-Security-Policy` with `frame-ancestors 'none'` (and the platform's `X-Frame-Options`); only the success response of `embed` differs.
4. **AS-37 (embed refusals and reflection)** — **Given** a switched-off site, an unknown key, a malformed key, and the key `"><script>alert(1)</script>`, **When** `embed` is requested, **Then** `410 widget_disabled`, `404 widget_site_not_found`, `404 widget_site_not_found` and `404 widget_site_not_found` respectively, each with `frame-ancestors 'none'`, no HTML body containing the submitted key (the error body is problem+json), and no stored or reflected markup; **Given** a site whose shop is `SUSPENDED`, **Then** `410 widget_disabled`.
5. **AS-38 (policy builder, pure)** — **Given** the framing-policy function, **When** given origin lists (one origin; ten origins in random order; duplicates; an origin with a port), **Then** the output lists each exactly once, sorted, space-separated, and the function throws for an empty list, a non-normalised origin, or any value containing whitespace, `;`, `,`, a quote or a control character (these can never reach a header because registration refuses them, AS-02, but the builder refuses them as well).

### User Story 5 — The kill switch (Priority: P1)

If a site misbehaves (a compromised shop page, a bad theme, an incident), the shop or an operator-acting manager flips one switch and the widget stops everywhere, without a deploy. Flipping it back restores service.

**Why this priority**: the notes name the kill switch as the answer to "breaking the loader breaks thousands of sites".

**Independent Test**: switch a site off, call every public route, switch it on again.

**Acceptance Scenarios**:

1. **AS-39 (switch off, effects, audit)** — **Given** an active site with a warm cache on two instances, **When** a manager calls `PUT …/sites/X/kill-switch {on: true}`, **Then** `200` with the `WidgetSiteDto` (`killSwitch: true`, `version` +1), one history row `{change: "kill_switch_on", from: false, to: true, actorId, at}` and one `widget_site_changed {change: "kill_switch_on"}` are stored in the same transaction, and the very next call (any instance) to `config`, `identify`, `session` and `embed` with a registered origin answers `410 widget_disabled` with `Cache-Control: public, s-maxage=30` on `config` (so the load of a switched-off site on the origin stays bounded, and a restore reaches the edge within 30 seconds) and `no-store` on the others; widget tokens issued earlier stop verifying (AS-32); `GET …/sites/X/history?limit&cursor` lists the change (newest first, opaque cursor, shop-scoped).
2. **AS-40 (idempotent and race-safe)** — **Given** a site that is already switched off, **When** `PUT … {on: true}` is repeated, **Then** `200`, no new history row, no new event, `version` unchanged; **When** 10 `PUT {on: true}` run at once on a switched-on site, **Then** all answer `200`, exactly one history row and one event exist; **When** `{on: true}` and `{on: false}` run at once, **Then** both answer `200`, the final state equals the last committed change, and the history rows form an unbroken chain (each row's `from` equals the previous row's `to`).
3. **AS-41 (restore)** — **Given** a switched-off site, **When** `PUT … {on: false}`, **Then** `200`, `widget_site_changed {change: "kill_switch_off"}`, and the next `config` from a registered origin answers `200` again; a malformed body (`{on: "yes"}`, no body, extra properties) is `400 validation_failed`.

### User Story 6 — Sites follow the shop they belong to (Priority: P2)

A site shows its shop's current name, stops working while the shop is suspended or being deleted, and disappears with the shop. All of it happens from events: this capability never reads the shop's table.

**Why this priority**: it prevents widgets of closed shops from taking orders, and removes orphaned public keys.

**Independent Test**: publish the shop events through the consumer entry points and read the public routes.

**Acceptance Scenarios**:

1. **AS-42 (rename, version guard)** — **Given** a site whose copy holds `shopName: "My Shop"`, `shopVersion: 5`, **When** `tenancy.shop_updated {shopId, name: "My Shop 2", slug, shopVersion: 6}` arrives, **Then** the copy becomes `"My Shop 2"`, `shopVersion: 6` and the next `config` shows it (AS-20); **When** an older event (`shopVersion: 4`, name "Old") arrives afterwards, or version 6 again (duplicate), **Then** nothing changes (out-of-order and duplicate events leave exactly one effect); all sites of the shop are updated, sites of other shops are not.
2. **AS-43 (suspension switches sites off)** — **Given** an active site, **When** `tenancy.shop_status_changed {shopId, from: "ACTIVE", to: "SUSPENDED", shopVersion: 7}` arrives, **Then** the next `config`, `identify`, `session`, `embed` answer `410 widget_disabled` (the manager's kill switch is untouched and stays `false`); **When** `{to: "ACTIVE", shopVersion: 8}` arrives, **Then** the site works again; **When** the events arrive in the reverse order (`ACTIVE` v8 first, then `SUSPENDED` v7), **Then** the final state is `ACTIVE` (the higher version wins); `DELETING` and `DELETED` also disable. Staleness bound: a status change reaches the public routes within 60 seconds of being published (consumer lag).
3. **AS-44 (shop deleted)** — **Given** a shop with 3 sites, **When** `tenancy.shop_deleted {shopId}` arrives, **Then** all 3 sites and their history are removed, their keys answer `404 widget_site_not_found` on the next request, one `widget_site_changed {change: "deleted"}` per site is in the outbox; **When** the event arrives again or for a shop without sites, **Then** nothing changes and nothing fails.
4. **AS-45 (invalid events)** — **Given** each consumer (`shop_updated`, `shop_status_changed`, `shop_deleted`), **When** it receives a payload that fails its schema (missing `shopId`, non-UUID, unknown status, non-integer `shopVersion`, wrong envelope version) and, separately, the same valid message twice, **Then** the invalid one is dead-lettered without any change to any site, and the valid one has a single effect.
5. **AS-46 (creation seeds the copy)** — **Given** a shop at `shopVersion: 12`, **When** a site is created, **Then** the shop's name, status and version are read once through `ShopQueryService.getShopsByIds([S])` (R1, before the site transaction opens, no network call inside it) and stored on the site; an event with `shopVersion` ≤ 12 arriving later is ignored and a higher one applies; **When** the lookup fails or the shop is not found, **Then** `503 service_unavailable` / `404 shop_not_found` and no site is created.

### User Story 7 — The loader never harms the host page (Priority: P2)

The script tag on the shop's page loads a tiny script that draws the button and opens the iframe. It talks to the iframe only with checked messages. If anything is wrong it silently does nothing.

**Why this priority**: it runs on other people's pages at very large volume; a mistake here breaks thousands of sites or opens a hole in them.

**Independent Test**: load the loader in a test page against a stub of the public routes; send it foreign messages; make every call fail.

**Acceptance Scenarios**:

1. **AS-47 (loader contract, pure)** — **Given** the generated loader script, **When** inspected, **Then** it is at most 5,120 bytes, a single self-invoking function, creates exactly one global (`MarketplaceWidget`) and does nothing when it already exists, reads the key only from its own script tag's `data-site-key`, calls `config` with `credentials: "omit"`, builds all DOM with `createElement`/`textContent`/`setAttribute` (no `innerHTML`, `outerHTML`, `document.write`, `eval`, `new Function`, string timers), applies only theme values that pass the same rules as AS-04 (re-checked in the loader), uses a stylesheet-free inline style set limited to the validated theme keys, and contains no `postMessage` call whose target origin is `"*"` and no use of `localStorage`, `sessionStorage` or `document.cookie`; it is served at `GET /widget/v1/loader.js` with `Cache-Control: public, max-age=300, s-maxage=300` and `X-Content-Type-Options: nosniff`.
2. **AS-48 (postMessage contract)** — **Given** the loader with an open iframe, **When** a message arrives from a foreign origin, from the right origin but a different window, from the iframe after it was closed, or with an unknown `type`, a non-object body, or `marketplace:close` with extra fields, **Then** it is ignored (no effect, no error); **When** the iframe posts `{type: "marketplace:close"}` from the API origin, **Then** the iframe is removed; **When** it posts `{type: "marketplace:need-identity"}` and the host has set `MarketplaceWidget.identify`, **Then** the loader awaits it (5-second deadline) and posts `{type: "marketplace:identity", token}` to the iframe with the explicit API origin as target; the token travels only in that message, never in a URL, storage or cookie. The message types are exactly `marketplace:close`, `marketplace:need-identity`, `marketplace:identity` in this release.
3. **AS-49 (failure isolation)** — **Given** the loader on a page, **When** the config call fails at the network, answers `403`, `404`, `410` or `503`, returns invalid JSON or a body that fails the shape check (products not an array, a title that is not text, more than 12 products), or the page has no `data-site-key`, or `MarketplaceWidget.identify` rejects or times out, **Then** nothing is drawn (or, for identify, the iframe proceeds without a customer), no exception reaches the host page, and no button for an out-of-stock product is clickable.
4. **AS-50 (happy journey)** — **Given** a test shop page on a registered origin with the loader tag, **When** a visitor opens it and clicks the button of an in-stock product, **Then** the iframe opens over the page, the shop's page supplies a hand-off token when asked, the iframe reaches its checkout screen with the customer recognised, and closing it removes the iframe (one real-browser journey, W07/W04 specs own the browser file).

### Edge Cases

- A site key copied to a hostile page: that page's requests carry its own origin and are refused (AS-16). A non-browser client can send any `Origin` header it likes; it still receives only public data (`config`) and cannot obtain a widget token without the secret (AS-25). The origin list is a browser-side control, not authentication.
- A site with several origins: each is independent and exact; a port or scheme difference is a different origin (AS-15).
- Unicode look-alike and punycode hosts: normalised to ASCII before comparison and storage (AS-02, AS-15).
- A shop that registers an origin it does not control: not detectable by this capability; the damage is limited to that origin's visitors using that shop's public data and a checkout that still needs the visitor's own credentials (Assumptions).
- Concurrent site creation near the limit (AS-05), concurrent edits (AS-07), concurrent rotation (AS-11), concurrent kill-switch flips (AS-40), concurrent token replay (AS-26): exactly the allowed outcome, enforced by the store.
- Illegal transitions: rotating while an overlap is open, expiring a previous secret that does not exist (AS-11).
- Events out of order or duplicated (AS-42, AS-43, AS-44, AS-45); event arriving before the site's seed copy (AS-46).
- A kill switch flipped while CDN copies exist: bounded by `s-maxage` (AS-20, AS-39).
- Dependencies down: product lookup (AS-21), single-use store (AS-27), limiter store (AS-22), shop lookup at creation (AS-46).
- A very large number of loads of a switched-off site: the 410 is edge-cacheable for 30 seconds (AS-39).
- Cross-tenant: any dashboard call with another shop's site ID is `404 widget_site_not_found` (AS-09); featured products of other shops are refused (AS-08) and never shown (AS-19).

## Requirements *(mandatory)*

### Functional Requirements

**Sites and origins**

- **FR-001**: A member with the permission `widget.manage` (OWNER, ADMIN) MUST be able to create, list, read, update, rotate the identity secret of, expire the previous secret of, delete, switch off/on, and read the history of widget sites of their shop; every other role gets `403`, non-members `404 shop_not_found`, anonymous callers `401` (AS-09). Every lookup of a site carries the shop in its predicate; an ID of another shop is indistinguishable from an unknown ID (`404 widget_site_not_found`).
- **FR-002**: A site MUST have a name (1–60 characters, default "Storefront widget"), 1–10 allowed origins, 0–12 featured product IDs, a theme, a kill switch, a version number, and a public key `pk_live_` + 24 URL-safe random characters from a cryptographically secure source; the key is immutable and unique (AS-01, AS-03).
- **FR-003**: Origins MUST be validated and normalised by one rule: `https` only; a bare origin (no path, query, fragment, user info); host lower-cased and converted to ASCII (punycode), at least two labels, no trailing dot, no wildcard, no IP literal, not `localhost`; default port 443 removed; at most 253 characters; duplicates collapsed. A rejected origin is `422 origin_invalid` with the closed reason list of AS-02.
- **FR-004**: A shop MUST NOT hold more than 10 sites; the limit is enforced by the store so concurrent creations cannot exceed it (`422 site_limit_reached`, AS-05).
- **FR-005**: Updates MUST be optimistic: `PATCH` carries `expectedVersion`; a stale value is `409 site_version_conflict`, and two concurrent updates cannot both win (AS-07). Only `name`, `allowedOrigins`, `featuredProductIds` and `theme` can be updated; the key and the kill switch cannot.
- **FR-006**: Featured product IDs MUST be checked against the shop's own products in one batch through R1 (S05) at update time; foreign and unknown IDs are the same `422 featured_product_invalid` (AS-08).
- **FR-007**: The theme MUST accept only the allowed keys and value formats of AS-04; anything else is rejected at write time and, defensively, ignored by the loader.
- **FR-008**: Deleting a site MUST remove it and its history, take effect on every instance on the next request, and free its slot (AS-12).

**Identity secret**

- **FR-009**: The identity secret MUST be `wis_` + 256 random bits, returned only in the create and rotate responses, stored only sealed with `SecretBox` bound to the site (context `widget-site:<siteId>`), and never present in a log line, metric, event or later response (AS-01, AS-52).
- **FR-010**: Rotation MUST keep at most two secrets: the new current one and an optional previous one valid until an expiry set by `overlapHours` (0–72, default 24); a rotation while a previous secret is valid is `409 rotation_in_progress`; early end is `POST …/expire-previous-secret`; the validity of the previous secret is decided from the injected clock at the moment of use (AS-10, AS-11, AS-28).

**Public widget API and origin binding**

- **FR-011**: The public routes `GET /api/widget/v1/config`, `POST /api/widget/v1/identify`, `GET /api/widget/v1/session`, `GET /api/widget/v1/embed` and the preflight `OPTIONS` of the first three MUST resolve the site by key, then check the origin, then the switch and the shop status, in that order, before doing any other work (AS-16, AS-30). Origin matching is whole-origin equality after normalisation (AS-15). A missing, `null`, repeated or unregistered `Origin` is `403 origin_not_allowed`.
- **FR-012**: A key that is malformed or unknown MUST answer `404 widget_site_not_found` with identical bodies; a malformed key is never used as a cache key or in a query (AS-17).
- **FR-013**: Cross-origin access MUST be granted per site: the registered origin is echoed in `Access-Control-Allow-Origin`, `Vary: Origin` is always present, credentials are never allowed, preflights are answered only for registered origins with exactly the methods and headers of AS-18, and the application-wide CORS policy does not apply to these routes.
- **FR-014**: `config` MUST return the shape of AS-14 with integer minor-unit prices, live non-archived products of the site's shop in the configured order, current stock, the shop's name from the site's copy, and a configured HTTPS `checkoutUrl`; it MUST be edge-cacheable per key and origin (`public, max-age=60, s-maxage=60`, `Vary: Origin`) and it MUST contain nothing private (AS-14, AS-19).
- **FR-015**: Product data MUST come only from S05's exported batch lookup with the shop filter (R1); no table of another domain is read by this capability (AS-14, AS-54).
- **FR-016**: When the lookup fails, `config` MUST serve the last good response for up to 600 seconds (stale-on-error), otherwise `503`; failures MUST NOT be cached as success (AS-21).
- **FR-017**: Changes to a site (origins, kill switch, deletion, creation, shop status) MUST be visible on every instance on the next request; no per-process copy of a site record may outlive a change (AS-20).

**Identity hand-off**

- **FR-018**: `identify` MUST accept a hand-off token only if it passes every rule of AS-24: HS256 pinned (any other algorithm, including `none`, refused), signature by the current secret or an unexpired previous secret, `aud = "marketplace-widget"`, `iss` = the site's key, `sub` and `jti` present and within length, `exp` present, in the future and at most 300 seconds ahead, `nbf`/`iat` within 30/60 seconds of the clock, optional `email` well-formed. All rejections are the same `401 identity_token_invalid` (AS-25).
- **FR-019**: A hand-off token MUST be single use per site, enforced by one atomic set-if-absent in a store with expiry (token `exp` + 60 seconds); when the store is unavailable the exchange fails closed with `503` and the token is not consumed (AS-26, AS-27).
- **FR-020**: A successful exchange MUST mint a widget token valid for 900 seconds with the claims of AS-23, signed with a key dedicated to widget tokens (startup fails without it), with `typ: widget+jwt` and `aud: marketplace-widget-session`, so that it can be verified by this capability only and is refused by every other verifier and vice versa (AS-23, AS-33).
- **FR-021**: A shop's customer claim MUST NOT create, link, authenticate or modify any marketplace account, session or user record (AS-29).
- **FR-022**: `GET /api/widget/v1/session` and the exported `WidgetSessionService.verify` MUST apply the same decision: signature, `typ`, `aud`, expiry, site existing, site not switched off, shop `ACTIVE`, origin still registered (AS-32).
- **FR-023**: The widget token MUST live only in the iframe's memory; no widget route sets or reads a cookie, and a partitioned or any other cookie is never issued (AS-31).

**Framing and CSP (P0502)**

- **FR-024**: The embed document MUST be the only response of the application that allows framing, and then only by the exact origins of the site (sorted, deduplicated, no wildcard); every other response, including every error of the widget routes, MUST carry `frame-ancestors 'none'` (AS-35, AS-36, AS-37).
- **FR-025**: The embed document MUST carry a CSP with a fresh unpredictable nonce on every response (at least 128 bits), `script-src` limited to that nonce and `'strict-dynamic'`, `default-src 'none'`, `object-src 'none'`, `base-uri 'none'`, `form-action 'self'`, no `unsafe-inline`/`unsafe-eval`/wildcard in `script-src`, no `X-Frame-Options`, `Cache-Control: no-store`, `nosniff`; its one script element carries the nonce, and the document has no inline handler or other script (AS-34). The URL of the checkout application bundle comes from configuration (owned by W07) and is HTTPS.
- **FR-026**: Nothing the requester submitted (the key) MUST be reflected into markup without encoding, and only well-formed keys are ever echoed (AS-34, AS-37).

**Kill switch**

- **FR-027**: The kill switch MUST be a boolean per site, settable by `PUT …/kill-switch {on}`, idempotent, race-safe (a conditional update that records a history row and an event in the same transaction only when the value changes), and effective for `config`, `identify`, `session`, `embed` and issued widget tokens on the next request on every instance (AS-39, AS-40, AS-41).
- **FR-028**: A shop whose status is not `ACTIVE` MUST make all its sites answer `410 widget_disabled` without touching their kill switches; the status is taken from the site's copy, kept current by `tenancy.shop_status_changed` with a version guard (AS-43).
- **FR-029**: A 410 from `config` MUST be cacheable for 30 seconds at intermediaries; every other error MUST be `no-store`.

**Request-forgery stance (P0504)**

- **FR-030**: Dashboard mutations authenticated by a cookie session MUST be protected by the platform's CSRF check (S01: header token bound to the session, plus an allowed `Origin`); bearer-authenticated calls need none (AS-13).
- **FR-031**: Widget routes MUST never treat a cookie as a credential, MUST accept state-changing bodies only as `application/json` (`415` otherwise), MUST bound body size (8 KiB) and token size (4 KiB), and MUST be gated by the origin list; they never set cookies (AS-31). Should a cookie-based widget session ever be added, it must be `Partitioned; Secure; SameSite=None` with a `__Host-` name and its own CSRF token, which requires a new capability revision.

**Loader**

- **FR-032**: The loader MUST satisfy AS-47 (size, single global, no unsafe sinks, `credentials: "omit"`, explicit target origins) and AS-48 (message checks, closed message set, identity deadline) and AS-49 (every failure renders nothing and throws nothing into the host page). It is versioned by path (`/v1/`); within `v1` changes are additive.

**Lifecycle**

- **FR-033**: The domain MUST keep, on each site, a copy of the shop's name, status and `shopVersion`, seeded when the site is created (R1 `getShopsByIds`, outside the transaction) and updated only by `tenancy.shop_updated` and `tenancy.shop_status_changed` events through a version-guarded update that ignores older and duplicate versions (AS-42, AS-43, AS-46).
- **FR-034**: On `tenancy.shop_deleted` the domain MUST delete every site and history row of the shop and emit one deleted event per site; the handler is idempotent (AS-44).
- **FR-035**: Every consumer MUST validate its payload against a schema, record the event identity for idempotency, and dead-letter invalid messages without effect (AS-45).

**Limits, events, errors, observability**

- **FR-036**: Rate limits MUST be the named policies of AS-22 with their fail modes; identify never uses another capability's policy.
- **FR-037**: Every site change MUST write one `developer_platform.widget_site_changed` event through the outbox in the same transaction as the change, and a history row for kill-switch changes (AS-39, AS-51).
- **FR-038**: Errors MUST be problem+json with the codes named in this document; contracts MUST be defined in `packages/contracts` and used by every spec (AS-53).
- **FR-039**: Metrics and logs MUST be as in AS-52 and MUST NOT contain secrets, tokens or customer e-mails.
- **FR-040**: The capability MUST read and write only tables it owns (`WidgetSite`, `WidgetSiteChange`), declare them in the ownership registry, and hold no foreign key to another domain's table (AS-54).

### Key Entities

- **Widget site**: one embedding configuration of a shop: name, public key, allowed origins, featured products, theme, kill switch, sealed identity secret (and an optional sealed previous one with an expiry), a version number, and a copy of the shop's name, status and version.
- **Site change**: an append-only history record of a site change (kind, before and after for the kill switch, actor, time); removed with the site.
- **Hand-off token**: a short-lived, single-use signed claim produced by the shop's backend (`sub`, optional `email`, `jti`, `exp`); never stored, only its single-use marker is, until expiry.
- **Widget session token**: our 15-minute signed token held in the iframe's memory, bound to one site and one shop customer ID.
- **Allowed origin**: a normalised `https://host[:port]` string that is the unit of trust of a site.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: In a matrix of at least 30 wrong-origin variants (wrong scheme, port, host, look-alike, missing, repeated) across every public route, 100% are refused, and none of the refusals contains any shop data.
- **SC-002**: After a kill switch, a deletion, an origin removal or a shop suspension, 100% of requests that reach the application are refused from the next request on every instance; copies held by intermediaries stop being served within 60 seconds.
- **SC-003**: Of 1,000 simultaneous exchanges of one hand-off token, exactly one succeeds; of the whole forged-token matrix (at least 15 tampered variants), none yields a session.
- **SC-004**: In a real browser, a page on an origin that is not registered cannot display the embed document, while a page on a registered origin can, for 100% of attempts over 20 registered/unregistered pairs.
- **SC-005**: A shop owner can register a site and see a working button on a test page in under 5 minutes of interaction, with no support help.
- **SC-006**: The loader is at most 5 KiB and, in a failure drill (every upstream call failing in turn), the host page records zero uncaught errors and zero layout changes.
- **SC-007**: Under a load of 50,000 configuration requests per second for a mix of 10,000 sites, at least 99% are answered by intermediaries without reaching the application (ops artifact, not a test row).
- **SC-008**: A shop rename or suspension is reflected in the widget within 60 seconds of the shop's change in 99% of cases.
- **SC-009**: Across the full e2e run, secrets, tokens and customer e-mails appear in logs, metrics, events and error bodies 0 times.

## Assumptions

Each is also a line in `questions.md`.

- **Origin binding is a browser-side control.** The `Origin` header is set by browsers and cannot be forged by a page, but any server-side client can send any value. The public key therefore unlocks only public data; everything privileged needs the identity secret (hand-off) or the visitor's own credentials (checkout). Registering an origin the shop does not control cannot be detected here.
- **Permission** is a new `widget.manage` (OWNER, ADMIN) for every dashboard route; today's `shop.manage` is replaced because the routes mint secrets. S03 is asked to define it.
- **Origins** are strict bare `https` origins: no wildcards, no IP literals, no `localhost`, no `http` (developers test through an HTTPS tunnel). Today's silent stripping of paths and queries and the `403` for malformed input are replaced by `422 origin_invalid`.
- **Shop data** (name, status) is a copy on the site, fed by S03 events (R3), seeded by R1 at creation. Maximum accepted staleness: 60 seconds (to be restated in `plan.md`). Reading the shop on every request would put tenancy on the hottest public path.
- **Config assembly** stays in the domain with R1 for products (not a composition lib), because the domain owns the site table and the runbook classifies the widget as a domain.
- **Prices** are returned as `{amountMinor, currency}` (integer minor units), replacing today's float `price`.
- **Kill switch** responds `200` with the site (not `204`), is idempotent, and records history and an event only on change. A shop that is not `ACTIVE` disables its sites regardless of the switch.
- **Identity hand-off** accepts only HS256 with at most 300 s lifetime, single use, and never links accounts. The widget token is signed with a **dedicated key** and carries `typ: widget+jwt` and `aud: marketplace-widget-session`, replacing today's reuse of the general JWT secret with `aud: widget`.
- **No cookies.** CHIPS (partitioned cookies) from the notes is an alternative transport that is deliberately not built; the in-memory token is the transport. Mutations are JSON-only and origin-gated, which is the "custom header / JSON only plus strict CORS allowlist plus Origin check" control the notes give for token-authenticated JSON APIs; the dashboard's cookie sessions use S01's CSRF check.
- **CSP**: the embed document uses a per-response nonce with `strict-dynamic`, as the notes recommend, instead of a host allowlist; the checkout bundle URL is configuration owned by W07. Report-only rollout and violation reporting are not part of this release.
- **Caching**: `config` fresh 60 s, stale-on-error 600 s, 410 cacheable 30 s, unknown-key memory at most 30 s; identity single-use marker until `exp` + 60 s. Numbers are configuration, not contract.
- **Limits** (configuration): 10 sites per shop, 10 origins per site, 12 featured products, hand-off lifetime 300 s, widget token 900 s, secret overlap default 24 h (max 72 h), request body 8 KiB, token 4 KiB.
- **Sandbox shops** may create sites; no special behaviour.
- **Platform-wide kill** of the whole widget version is an operational action (CDN purge or deploy), not an API of this capability.
- **Load test** of the edge-cached config route is an ops artifact (`scripts/load-tests/widget-config.test.js`), not a row of the test plan.
