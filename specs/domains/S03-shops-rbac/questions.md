# Open Decisions for S03 (answered unattended)

Format: `[TAG] question → default taken → why`. BREAKING first, then CONTRACT, then LOCAL. The human reviews BREAKING and CONTRACT lines first. Decision policy: most production-grade option the Interview-Prep notes and the constitution support.

## BREAKING (changes behaviour or an API/UI contract that exists today)

- [BREAKING] Invite creation (today `POST /shops/:id/invites` returns `{inviteUrl}` containing the token to the inviter; S01 never proves e-mail ownership, so the inviter can register the invitee's address and accept as them) → response is invite metadata only; the token leaves only in the single-consumer message `tenancy.invite_requested` to S28 → notes 05/02 (single-use signed tokens), 05/02 §10 (broken authentication); the same pattern as S01's reset token.
- [BREAKING] Invite acceptance compares `user.email` from the request (S01 access tokens carry no e-mail, so this cannot work) → the address comes from R1 `UserDirectoryService`; a missing address or a mismatch is the same `404 invite_not_found` → S01 FR-021; no oracle for token guessing.
- [BREAKING] Accepting an invite as an existing member (today `upsert` overwrites the role, so an owner who accepts a VIEWER invite is demoted) → role kept, `200 {alreadyMember:true}`, invite consumed → privilege never decreases or increases by accident; constitution III.6.
- [BREAKING] Role management (today any holder of `members.manage`, i.e. ADMIN, can promote anyone to OWNER and demote or remove owners) → only OWNER manages OWNER/ADMIN; ADMIN manages STAFF/VIEWER; `403 insufficient_role` → notes 05/02 §6 (ABAC on top of RBAC); privilege-escalation hole.
- [BREAKING] Permission matrix (today VIEWER has `payouts.read`, ADMIN has `sso.manage`, there is no `orders.read`/`shop.export`) → VIEWER loses `payouts.read`; ADMIN loses `sso.manage`; added `orders.read` (all roles) and `shop.export` (OWNER) → least privilege: finance data and identity federation are owner decisions; viewers must be able to read orders. Other domains' `ShopScoped('payouts.read')` routes are retested.
- [BREAKING] Last-owner violation (today `422`) → `409 last_owner` → state conflict per constitution V.4; retry exhaustion `503 serialization_failure` with `Retry-After`.
- [BREAKING] Authorization cache (today 60 s positive, in-process L1 `hot` layer on top of Redis, so a removal can stay valid on other instances for the L1 lifetime) → shared store only, 15 s, delete-on-write after commit, sensitive permissions read the database → notes 10/04 §2 ("membership resolved from a Redis cache, invalidated via events") but revocation must be immediate for destructive actions; III.9 (cache never the source of truth).
- [BREAKING] Shop status in the guard (today `status` is stored but never checked; a suspended shop works normally) → `SUSPENDED` read-only (`403 shop_suspended`), `DELETING` read/export/cancel only (`409 shop_offboarding`), `DELETED` 404 → every domain using `ShopScoped` inherits the gate; they must retest write routes.
- [BREAKING] Platform role promotion (today `ShopService.create` runs `UPDATE "User" SET role = 'SELLER'` and clears an identity cache key) → tenancy writes nothing of identity's; S01 consumes `tenancy.shop_created` and promotes; the new role reaches the token at the next refresh as before → IX.4 (D-7/D-12), IV.1.
- [BREAKING] List shapes (today `mine`, `members`, `invites` return bare arrays, unbounded, via raw SQL joins on `User`) → cursor pages `{items, nextCursor}`, default 50, max 100; e-mails resolved by R1 batch → III.10, IX.4; the web client and every caller change.
- [BREAKING] `GET /shops/:id` and `POST /shops` (today return the ORM model spread, including the payment-provider account id) → explicit DTO without it, plus `myRole`/`myPermissions` → V.1; S14/S15 own that column from now on (see CONTRACT line).
- [BREAKING] SSO configuration (today `PUT /shops/:id/sso` accepts any https URL with no discovery check, seals the secret without a context, forces `enabled: true`, returns a GET-style `loginUrl`, ADMIN allowed; there is no read or disable) → OWNER only; issuer must pass the SSRF guard and discovery with matching `issuer` within 3 s; secret sealed with context `shop-sso:<shopId>` (existing rows are re-sealed by a one-off migration step); response `{providerId, secretSet, …}`, no URL; `GET` and `DELETE` added; `defaultRole` ∈ {STAFF, VIEWER} → notes 05/02 §4, §8 and §9 (envelope encryption with context, validate third-party endpoints); S02 made the start route a POST.
- [BREAKING] Shop-IdP users (today they get an account but no membership, so they can sign in and reach nothing) → membership provisioned from `identity.federated_identity_linked` with the shop's default role → notes 10/04 §2 ("SSO per tenant plus provisioning"); S02's contract anticipates it.
- [BREAKING] Unknown or unconfigured cell (today `connectionFor` silently returns the pooled connection) → `503 cell_unavailable`, fail closed; per-cell pool with 2 s acquire timeout → a shop bought as "dedicated" must never write into the shared database; notes 10/04 §2.
- [BREAKING] Row-level security (today only `ShopInvite` and `ShopSsoConfig`; bypass is free text; nothing checks the app role) → also `ShopMembership` (visible by shop or by owning user), bypass reasons from an allowlist with counter and log, startup refuses a superuser/bypass role in production → notes 05/02 §7 ("app role must not have BYPASSRLS"), constitution VIII.5.
- [BREAKING] Foreign key `ShopMembership.userId → User` (and `Product.shopId`, `ChatChannel.shopId → Shop`) → dropped by an expand/contract migration with `lock_timeout`; cross-domain references are plain IDs → IX.4 (the last two belong to S05 and the chat domain's migrations, listed in `gaps.md`).
- [BREAKING] Backfill job `tenancy.backfill-shops` (today tenancy runs raw `UPDATE "Product"` / `"ChatChannel"` and owns the NOT NULL contract constraint on `Product`) → removed from tenancy; owning domains run their own batched backfill and contract step using R1 `ShopProvisioningService.ensureShopsForLegacySellers` (≤ 200, idempotent) → IX.4 (D-12), P0315 stays proven by the idempotent batch plus the migration scenario.
- [BREAKING] Sandbox shops (today developer-platform inserts `Shop` rows with raw SQL and a `sandboxOf` column that is not in the model) → R1 `ShopProvisioningService.ensureSandboxShop`; `sandboxOf` becomes a modelled column → IX.4 (D-12).
- [BREAKING] Verification fields (today seller-onboarding runs `UPDATE "Shop" SET "verificationStatus"…`) → tenancy consumes `shop.onboarding_submitted` / `shop.verified` / `shop.rejected` through a state machine → domain-map §2 ("tenancy consumes `shop.verified`"); IX.4.
- [BREAKING] Public batch read `GET /batch/shops` (today raw SQL in a controller, shows suspended shops) → via repository; suspended, closing, deleted and sandbox shops answer `null`; max 100 ids → II.1, IX.4.
- [BREAKING] New limits (today none): 10 owned shops per user, plan seat limits 5/25/250 (members + pending invites), 20 invites per shop per hour, reserved slugs → notes 10/04 §2 ("plan limits", "per-tenant quotas", pitfalls "no per-tenant limits").
- [BREAKING] Realtime topic `shop:<id>:live` (today any membership row; no status rule) → members of `ACTIVE`/`SUSPENDED` shops only; open subscriptions are closed on `member_removed` (S51) → removal must end access, not only new access.
- [BREAKING] Barrel `@app/domains/tenancy` (today exports five models and `MembershipService`) → exports only the module, `ShopScoped`, the R1 services and DTOs/event contracts; models are removed after consumers migrate → X.4, D-7, D-8.

## CONTRACT (decides something another capability must provide or consume)

- [CONTRACT] Who promotes a shop owner to `SELLER`? → S01 consumes `tenancy.shop_created` v1 `{shopId, ownerId, …}` with a conditional `USER → SELLER` update (idempotent); S01's spec lists no such consumer, so S01 must add one → IX.4 forbids tenancy writing `User`; S01 FR-004 already treats `SELLER` as an account role.
- [CONTRACT] Is the e-mail available at invite acceptance? → no; S03 calls S01 `UserDirectoryService.getUsersByIds([userId])` and `findByEmail(email)` (already in S01's Provides) → S01 access tokens carry no personal data.
- [CONTRACT] Sessions on offboarding → S03 calls S01 `SessionRevocationService.revokeAllForUser(userId, 'shop_membership_removed')` only for `source: sso` members (removal and purge), after commit → S01's Provides names S03 as consumer; ordinary users keep sessions, shop access ends by the membership check.
- [CONTRACT] Sealing the SSO secret → S01 `SecretBox` with context `shop-sso:<shopId>` → S01 FR-066 supports contexts; pre-existing context-less values are re-sealed once.
- [CONTRACT] Provider seam → S03 uses S02 `OidcProviderRegistry.registerResolver('shop:', resolver)` and `invalidate('shop:<id>')`, passes a plain secret, and stops using `OidcService` → exactly S02's Provides.
- [CONTRACT] Membership provisioning trigger → S02 must emit `identity.federated_identity_linked` (provider `shop:<uuid>`) on the first login through a shop provider, including when the login created the account → S02's FR-066 creates the account; its event list names this event; S03 relies on `provider` and `userId` only.
- [CONTRACT] Verification events → S04 emits `shop.onboarding_submitted {shopId}`, `shop.verified {shopId}` and, for a rejection, `shop.rejected {shopId}` (not in domain-map §2, which lists the first two) → `REJECTED` exists in today's model; S04 may differ, then `REJECTED` is simply unreachable.
- [CONTRACT] Plan events → S17 emits `billing.subscription_plan_changed {shopId, plan, version}` with a per-shop monotonic `version` → no S17 spec exists yet; tenancy needs a version for out-of-order protection (P0610); S17 may rename it, S03 adapts the consumer.
- [CONTRACT] Invite and offboarding mails → S28 consumes `tenancy.invite_requested` (contains the token) and builds the link `<front>/invites/<token>`; offboarding events go to owners resolved with `MembershipQueryService.getMembersByShopIds(shopIds, ['OWNER'])` → S03 never sends mail (IV.3); token only in a single-consumer message like S01's reset token.
- [CONTRACT] Payment-provider account id on `Shop` (`stripeAccountId`) → not exposed by any DTO; S14/S15 move the value into a table they own (expand/contract); tenancy drops the column afterwards; `payments/infra/payout.jobs.ts` reads it today → it is payments' data, not tenancy's.
- [CONTRACT] Read models of shop name and slug (stories, leaderboards, public catalog, widget, review queue today `JOIN "Shop"`) → R1 `getShopsByIds` for lookups; for lists and search each consumer projects `tenancy.shop_created`/`shop_updated` (with `shopVersion`) into its own table or index (R3) → IX.7; each consumer states its staleness in its `plan.md`.
- [CONTRACT] Shop-scoped data deletion → every shop-owning domain consumes `tenancy.shop_offboarding_started` (export) and `tenancy.shop_deleted` (purge); no ack is awaited → saga by events (IV.4); tenancy does not veto deletion (open balances are the owning domains' retention duty).
- [CONTRACT] Backfills → S05 and the chat domain call `ensureShopsForLegacySellers` in batches ≤ 200 and own their NOT NULL contract step → replaces D-12 SQL in `tenancy-backfill.jobs.ts`.
- [CONTRACT] Sandbox shops → S42 calls `ensureSandboxShop`; sandbox shops carry no members and are hidden from public reads → replaces raw INSERT in `api-keys.service.ts`.
- [CONTRACT] Replacing direct `ShopMembership` reads (collab drafts, notifications router, live stream, crawler, webhook deliverer) → R1 `ShopAccessService.assertMember/getRole` and `MembershipQueryService.getMembersByShopIds`; notifications routing that needs "all members of shop X" uses the batch method or a projection of `tenancy.member_*` events (R3) → domain-map §3.
- [CONTRACT] Realtime → S51 closes open subscriptions to `shop:<id>:*` for the user on `tenancy.member_removed` → access must end when membership ends.
- [CONTRACT] Rate-limit policies → S50 registry gets `tenancy.shop-create.user`, `tenancy.invite.shop`, `tenancy.invite-accept.user`, `tenancy.invite-accept.ip`, `tenancy.sso-lookup.ip`, `tenancy.shop-write.shop`, all fail-closed → per-shop and per-user keys give the bulkhead of P0618.

- [CONTRACT] Web → W04 owns `/invites/<token>` (post, then replace the URL), shop switcher, team and roles screens from `GET /shop-roles` and `myPermissions` (display only; the server decides) → VI.5.

## LOCAL (internal to this capability)

- [LOCAL] Seat limits 5/25/250; plan lowering removes nobody → fits the "95% under 5 members" target; enforced by a per-shop row lock on seat-changing writes.
- [LOCAL] Invite lifetime 7 days, 192-bit token, SHA-256 digest, one pending invite per `(shop, lower(email))` → partial unique index; expired ones are revoked when re-inviting; purge after 30 days.
- [LOCAL] Offboarding grace 30 days, confirmation by slug, cancel allowed until purge → GDPR "within N days" with a regret window.
- [LOCAL] Slugs immutable, 3–40 chars, reserved list → avoids a rename saga for read models.
- [LOCAL] Shop limit 10 per user, enforced with a transaction-scoped advisory lock keyed by the user (the user's row belongs to identity).
- [LOCAL] Authorization cache 15 s positive / 10 s negative; sensitive permission set listed in FR-015.
- [LOCAL] Serializable isolation with 3 attempts, full-jitter back-off, only for last-owner-sensitive writes; other writes use row locks or conditional updates.
- [LOCAL] SSO discovery check timeout 3 s, one attempt, outside any transaction.
- [LOCAL] Consumer inbox retention ≥ topic retention (30 days) so redelivered provisioning events cannot re-add removed members.
- [LOCAL] `ShopSsoConfig` row is deleted (not flagged) on disable, so no secret remains.
- [LOCAL] Purge keeps a tombstone `{id, status DELETED, slug deleted-<id>, name [deleted]}` so other domains' stale IDs resolve to "deleted", not to a reused ID.
- [LOCAL] Page size default 50, max 100; `GET /batch/shops` max 100 ids.
- [LOCAL] Status history table records `from`, `to`, actor, reason, time.
- [LOCAL] Membership `source` values `owner|invite|sso|provisioned` (`provisioned` = legacy backfill).
