# Research: S35 — Trending Products

- **R-1 Consumer shape.** The S53 `Projector` framework gives validated `EventEnvelope`s and owns offsets, so a window that stays open for up to 3 minutes cannot hold the commit back; `analytics.events` also carries the raw S39 stored event, not an envelope. Decision: keep a dedicated kafkajs `eachBatch` loop in `infra/trending.consumer.ts` (`autoCommit: false`), delegating each message to `TrendingIngestService`. It reuses `createKafka`, `DeadLetterWriter` (`discovery-trending-topk.dlq`, code `INVALID_PAYLOAD`), `ReadinessService.register`, `ShutdownRegistry` (phase `drain`), `MetricsRegistry`. Alternatives rejected: a `Projector` with `idempotency: 'natural'` (cannot hold offsets; would re-create at-most-once); a second topic of pre-windowed counts (new infrastructure for an approximate feature).
- **R-2 Commit floor.** Per partition, floor = smallest first-offset of any window not yet merged (open, closed-pending, or merge-failed); if none, last consumed offset + 1. After each batch the loop commits `floor` per partition via `consumer.commitOffsets`. A restart replays from the floor and rebuilds the same windows deterministically from the log (watermark rules depend only on message content, except the idle advance, R-5). Event-id and visitor-cap state is rebuilt by the replay, which is why duplicates inside the replay are harmless. `lastConsumedOffset` is held when a partition is paused for backpressure.
- **R-3 Idempotent merge (FR-019).** One `EVAL` per closed (partition, window): `KEYS = [mergeRecordKey, aggregateKey₁…ₙ]`, `ARGV = [ttl, firstOffset-lastOffset, (member, score)…]`. Script: `SET mergeRecordKey <offsets> NX EX ttl` → if it exists return `0` (replayed, counted `merge_replayed`); else `ZINCRBY` every pair, `EXPIRE` each aggregate to the retention, return `1`. Atomic, so a partial failure leaves nothing (all-or-nothing, AS-35) and two concurrent owners of one (partition, window) apply it once (AS-33). Two different partitions have different record keys, so their sums both apply. The primary merge identity is (partition, window), the covered offsets are stored as the record's value for audit; a **correction merge** uses a record `…:c:{first}-{last}` of its own. Consequence, accepted and documented: if an idle close made a window merge with fewer events than a later replay would rebuild, the replayed superset is skipped (an undercount, never a double count). The script touches several keys, which is fine on the single-node client in use; Redis Cluster would need a hash tag per window (noted in `trending-keys.ts`). Alternative rejected: `ZINCRBY` pipeline plus a separate "merged" flag (not atomic, T26).
- **R-4 Event time and watermark (FR-012).** `eventTime = min(ts, received_at)`; both parsed from `YYYY-MM-DD HH:mm:ss.SSS` UTC by a strict parser (invalid → dead letter, T21). Per partition, `maxEventTime` and `maxReceivedAt`; `watermark = min(maxEventTime, maxReceivedAt) − lateness`. Since `eventTime ≤ received_at`, `maxEventTime ≤ maxReceivedAt` already, so a forged future `ts` cannot pass `received_at`. Windows whose end ≤ watermark close. All pure in `tumbling-windows.ts` with `now` injected.
- **R-5 Idle advance (FR-013).** The loop calls `windows.tick(now)` on a 5 s timer; a partition with no message for `idleMs` gets `watermark = max(watermark, now − lateness)`. A partition receiving messages is never advanced by the clock. The timer is cleared on shutdown; tests drive `tick` through the injected clock rather than waiting.
- **R-6 Classification (FR-014).** For an event with window `w`: `open` (w not closed) → count; `late_corrected` (w closed, `w.start ≥ horizonStart(now)`) → count into a **correction buffer** keyed by (partition, window), flushed as a correction merge at the next cycle after `SET trending:seen:{event_id} NX EX retention`; `late_dropped` (older) → counter. Closed windows never reopen. The correction buffer's offsets also hold back the commit floor until merged.
- **R-7 Visitor cap and duplicates (FR-015, AS-29).** Per open window, two Bloom filters (bit arrays, `k` hashes from `murmur3` in `libs/common/core/murmur3.ts`): `visitorSeen` keyed `(anonymous_id, name, product_id)` and `eventSeen` keyed `event_id`. Sized from the expected distinct entries per window per partition (config, default 2^24 bits ≈ 2 MB each) so the false-"seen" rate stays ≤ 1% at the design load; no false "unseen". The window's filters are dropped when it merges. Identifiers are hashed in memory only. A false "seen" undercounts slightly (accepted by the notes). The check order is `eventSeen` (→ `duplicate`) then `visitorSeen` (→ `visitor_capped`). Correction-path duplicates are caught by the Redis `trending:seen` key.
- **R-8 Sketch sizing and memory (FR-016, FR-017).** `all`: 2^16 × 4 × 4 B = 1 MiB; tracked category: 2^14 × 4 × 4 B = 256 KiB plus a heap of 50 entries. Per partition-window ≤ 1 MiB + 100 × 256 KiB ≈ 26 MiB worst case; with 4 partitions per consumer and 3 open windows the worst case is ~300 MiB, inside the 512 MB budget. The ingest service keeps a running `trackedBytes` gauge; at 80% of the budget it stops opening new category sketches (counted `category_capped`); at 100% it pauses the partition (`consumer.pause`) until a merge frees memory (backpressure, FR-022). Cells are `Uint32Array`, `add` saturates at `0xFFFFFFFF` (T40). Heap tie order by code-unit comparison (`a < b`), never `localeCompare` (T41). `merge(other)` adds cell by cell with saturation (T42).
- **R-9 Aggregate read (FR-004, AS-18, AS-39).** The serving window set is the 60 one-minute windows ending at the latest minute boundary: `boundary = floor(now / 60 s) × 60 s`, starts `boundary − 60 min … boundary − 1 min`. Check against AS-18: at 11:59:20 the boundary is 11:59:00 and the set starts at 10:59, so the 11:00 window counts; at 12:01:05 the set starts at 11:01, so it does not, while 11:01 still counts and stops at 12:02:05. The still-open current minute is excluded (T13); U4 pins these instants. Keys are computed (`trending-keys.ts`), read with `ZUNION numkeys … WITHSCORES` under a 100 ms budget, never `KEYS`/`SCAN`. Merge records and aggregates share one TTL = `retentionSeconds` (default 3 h; validated ≥ 60 min + lateness + correction horizon, ≤ 3 h). A window older than the horizon is never in the key list even if the key still exists.
- **R-10 Ranking cache (FR-007, AS-15).** `CacheService.getOrLoad` (single flight) under key `trending:rank:{category}:{boundaryMs}`, value = the first 60 `{productId, score}` pairs, TTL 30 s, L1 off (the existing 10 s L1 added staleness). The key includes the boundary so a new minute never serves the previous minute's set. `limit` is applied after the cache, so `limit=2` and `limit=20` share one read. The loader runs under the 100 ms budget; any throw (including a cache/Redis failure) becomes `TrendingUnavailableError` (T10: the `?? []` is deleted). Product facts and visibility are never cached.
- **R-11 Visibility (FR-006, AS-10, AS-11).** Pool = first `min(3 × limit, 60)` entries of the cached ranking. `TrendingCatalogFacts.lookup(ids)` (adapter in `infra/`, same two-call shape as S34's `CatalogFactsAdapter`: product batch first, shop batch for the distinct `shopId`s found; budgets 100 ms and 50 ms; any throw/timeout → `TrendingUnavailableError`). Pure `selectVisible(pool, facts, category, limit)`: `status === 'ACTIVE'`, `!isSandbox`, `inStock`, shop `ACTIVE`, and `category === 'all' || facts.category === category`; unknown ids dropped; ranks assigned after filtering, no padding. The S34 adapter is not reused because it lacks `category`, depends on S34's settings token, and S34 owns its port; a shared extraction is a later refactor, not this capability's scope.
- **R-12 Errors and headers (FR-008–FR-010).** Controller sets `Cache-Control: no-store` first and replaces it with `public, max-age=30, s-maxage=30` only after the service returned a body, so every problem keeps `no-store`. `400` from a strict Zod parse (`.strict()`, unknown key → error, `limit` parsed with a regex-guarded integer coercion so `2.5`, `''`, `abc` fail); `TrendingUnavailableError` carries `Retry-After: 5` through the global filter; `429` comes from the rate-limit guard with its `Retry-After`. No `Vary`, no cookie, `@Firewall({ anonymous: true })`; whether an invalid bearer is ignored is asserted in AS-07 against the firewall and, if it rejects, the route opts out of token parsing (as S34 R-11).
- **R-13 Config (FR-026, AS-37).** Keys in `common/config/trending-config.ts` (joi, fail at startup naming the key), defaults: `TRENDING_WEIGHT_VIEW` 1, `_WEIGHT_CART` 5 (integers ≥ 1), `_WINDOW_SECONDS` 60 (fixed 60 in this version, validated), `_LATENESS_SECONDS` 120 (0–600), `_IDLE_SECONDS` 30 (≥ 1), `_HEAP_K` 50 (≥ 40), `_ALL_WIDTH` 65536 and `_CATEGORY_WIDTH` 16384 (powers of two), `_DEPTH` 4 (1–8), `_CATEGORY_CAP` 100 (≥ 1), `_MEMORY_BUDGET_MB` 512 (≥ 1), `_RETENTION_SECONDS` 10800, `_AGGREGATE_BUDGET_MS` 100, `_PRODUCT_BUDGET_MS` 100, `_SHOP_BUDGET_MS` 50, `_MERGE_BUDGET_MS` 100 (each ≥ 1), `_CONNECT_TIMEOUT_MS`, `_SHUTDOWN_DEADLINE_MS`. The pure rules live in `domain/trending-config.ts` (U6); the adapter only maps env to the settings object.
- **R-14 Readiness and liveness (FR-023, AS-40).** `ReadinessService.register({name:'trending-consumer', ...})` reports ready only after `subscribe` resolved and `run` started. Connect/subscribe run in a retry loop (timeout per call, exponential backoff with full jitter, each failure logged without payload and counted `trending_consumer_connect_failures_total`) that no longer swallows errors. If `run()` rejects or the consumer crashes (`consumer.on(CRASH)` with `restart: false`), the check turns not-ready and the process exits through an injectable `ProcessExit` (tests pass a spy; production calls `process.exit(1)`). Liveness is untouched.
- **R-15 Shutdown (FR-020, AS-34).** `ShutdownRegistry` task, phase `drain`, deadline from config: stop fetching (`consumer.pause` all, stop the tick timer), force-close every open window of owned partitions, merge them (one attempt cycle), commit the floor (which now equals last consumed + 1 for merged partitions), disconnect. A merge that fails at shutdown leaves the floor behind that window, so the next instance replays it (no loss) and the merge record prevents a double count.
- **R-16 Backoff.** Merge cycle: attempts 1–3 with `delay = random(0, min(cap, base·2^n))` (full jitter), implemented once in the ingest service; the Redis client is configured without extra retries for these calls so retry stays at one layer. After 3 failures the window stays closed-pending (`merge_failed`), the floor does not move, and the next tick retries.
- **R-17 Metrics.** `trending_events_total{outcome}`, `trending_windows_closed_total`, `trending_merges_total{outcome}`, `trending_last_merge_timestamp_seconds`, `trending_oldest_unmerged_window_age_seconds`, `trending_consumer_lag`, `trending_tracked_bytes`, `trending_requests_total{outcome}`, `trending_dependency_failures_total{dependency}`, `trending_ranking_cache_total{result}`, `trending_consumer_connect_failures_total`, `trending_ratelimit_fail_open_total` reuses S50's counter. Outcomes and dependencies are fixed enums; lag is per consumer, not per partition label. The alert on "no merge for 10 minutes while events flow" is an ops artifact.
- **R-18 Transactions.** The trending files hold no `sequelize.transaction` and no `// S54 T037 audit` comment (baseline `.tx.baseline` = 0). The injected `Sequelize` is deleted with the raw SQL.
- **R-19 Sibling files.** BFF, web, Playwright, S39 emitters, S50 registry: see `gaps.md` "Sibling-spec follow-ups". S33 gets no trending source (decision in `questions.md`); S36 shares no code.
