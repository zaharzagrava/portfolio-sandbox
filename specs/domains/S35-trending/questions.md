# Questions and defaults: S35 — Trending Products

Each line is a choice made unattended, with the default taken and why. Sorted by impact: BREAKING first (changes behaviour or a contract that exists today, so existing tests and callers need updating), then CONTRACT (another capability must provide or consume it), then LOCAL.

- [BREAKING] Response is a bare array `[{id, title, price, category, score}]` → envelope `{category, windowMinutes: 60, generatedAt, items: [{rank, productId, title, priceMinor, currency, category, score}]}` → `price` is a float today (`trending.service.ts:43`), which breaks III.8 (money is integer minor units); an envelope leaves room to grow additively (V.7). Callers to update: `packages/web/app/page.tsx:185-203`, `libs/composition/bff/product-page.service.ts:15,41,69`, `bff.e2e-spec.ts:32`.
- [BREAKING] `category` is silently cut to 40 characters (`trending.controller.ts:15`) and has no alphabet → `400 validation_failed` for anything outside 1–40 of `[a-z0-9-]`, plus `400` for unknown parameters and for `limit` outside the integer 1–20 (a new parameter, default 20) → a silent cut answers a question the caller did not ask, and `{`, `}` or `*` in a category would reach the aggregate key names (V.3, `forbidNonWhitelisted`).
- [BREAKING] Visibility is `quantity > 0` on a raw SQL read of the catalog table (`trending.service.ts:37`) → product `ACTIVE`, not sandbox, `inStock`, shop `ACTIVE`, via batched R1 calls (`getProductsByIds`, `getShopsByIds`) → today archived, sandbox and suspended-shop products can trend (S32 hides them); IX.4 forbids the direct read (D-7, D-12).
- [BREAKING] The whole hydrated list is cached for 30 s (`trending.service.ts:23-45`) → only the ranking is cached; facts and visibility are looked up on every origin request → a product that sold out must not be shown for up to 40 s at origin (10 s L1 + 30 s); same rule as S34 (SC-003); the CDN keeps the 30 s `s-maxage`.
- [BREAKING] The category of an event decides the ranking it appears in, with no check → the catalog category is authoritative at read time; a product whose catalog category differs is dropped from that category's list → event props are client claims; without the check anybody can place any product in any category's trending list.
- [BREAKING] Delivery is "commit as consumed, lose the open windows on a crash" (`trending.consumer.ts:23-27, 60-63`) → at-least-once with offsets committed only up to the earliest unmerged window and an idempotent merge keyed by (partition, window, covered offsets) → the notes call for idempotent sinks and event-time correctness; losing up to 3 minutes of counts on every deploy makes the ranking dip at each release, and `ZINCRBY` replays would double count, so the merge must be made idempotent in the same change.
- [BREAKING] Late events (beyond the lateness) are dropped (`count-min-sketch.ts:121-124`) → a correction path adds them to the window's aggregate when the window is still inside the 60-minute horizon, and drops (counted) only older ones → the notes (SD-32 table, 10/09 #32) say "late events → correction path"; the code's own comment says it dropped them on purpose.
- [BREAKING] Rate limit is switched off (`@Firewall({skipThrottle: true})`, `trending.controller.ts:11`) → policy `discovery.trending`, 300/minute per address, fail open → the endpoint is anonymous and every miss costs two lookups; the CDN is not a limiter.
- [BREAKING] Redis or lookup failure surfaces as `500` → `503 trending_unavailable` with `Retry-After: 5`, `no-store`, never an unfiltered list; explicit budgets (aggregate 100 ms, product lookup 100 ms, shop lookup 50 ms) → IV.6 and V.3; the BFF's 200 ms optional-section budget stays intact.
- [BREAKING] Malformed or unexpected messages are swallowed (`trending.consumer.ts:56-59`) → zod validation of the stored analytics event, invalid payloads dead-lettered with a reason, unrelated event names ignored and counted → IV.5 and VII.4. Also today `ts` is parsed as a string only (`:71`) and an unparsable value becomes `NaN` and a bogus window.
- [BREAKING] Event time is the client's `ts` and the watermark follows the largest `ts` seen → event time is the earlier of `ts` and `received_at`, the watermark never passes `received_at − lateness`, and an idle partition's watermark follows the wall clock → one forged future timestamp closes every open window and makes real events late today; a quiet partition never closes anything today.
- [BREAKING] Every event counts → one visitor counts at most once per event name, product and window → anyone can post `product_view` events anonymously (S39 ingestion is public), so without a cap one script makes any product trend; scores change for existing data accordingly (SC-005).
- [BREAKING] Unbounded categories (every `props.category` string gets a sketch, `trending.consumer.ts:73-78`) → only valid slugs, capped at 100 per partition-window, the rest in `all` only, counted → memory and key-space attack through a client-controlled string.
- [BREAKING] Equal scores sort in the order Redis returned them (`trending.service.ts:32`, no tiebreak) and the heap tie order uses `localeCompare` (`count-min-sketch.ts:68`) → score descending, then `productId` ascending, compared by code unit → the same data must give the same body (cache and replay stability).
- [BREAKING] Barrel exports `TrendingService`, `TrendingConsumer`, `TrendingConsumerModule` (`index.ts:13-19`) and apps wire `TrendingConsumerModule` (`apps/projector/src/projector.module.ts:3,51`) → apps import `TrendingProjectorModule` and `TrendingModule` only; the other classes leave the barrel (D-8, X.4) → the existing e2e that imports `TrendingConsumer` and `TrendingService` from the barrel (`libs/domains/marketing/ads.e2e-spec.ts:19-21,114-129`) moves into this capability's e2e specs (it calls `ingest` and `flush(true)` directly and never touches the stream or HTTP).
- [BREAKING] The consumer's connect and subscribe failures are swallowed (`trending.consumer.ts:43-44`), so the process runs with no consumer → readiness reflects "subscribed", failed connect retries with backoff and a timeout, a dead loop ends the process → a silently dead consumer serves an ever staler ranking (VIII.3).
- [BREAKING] Sketch width in code is `1 << 14` (`trending.consumer.ts:76`), the notes say 2^16 × 4 ≈ 1 MB → `all` uses 2^16, tracked categories 2^14, both configuration; the per-category total is bounded by the category cap and a memory budget → the notes' memory arithmetic only holds for one sketch per window; per-partition and per-category sketches multiply it.
- [CONTRACT] S39 provides the message shape `{event_id, name, anonymous_id, user_id, ts, received_at, props}` on `analytics.events` keyed by `anonymous_id`, and a zod schema `storedAnalyticsEventSchema` in `packages/contracts` → the consumer validates against it; the key must stay `anonymous_id` because the per-visitor cap relies on one partition per visitor.
- [CONTRACT] W02 / W03 emit `product_view` and `add_to_cart` with `props.product_id` and `props.category` (catalog slug) → today nothing in `packages/web` emits them (the feature only works for synthetic events) → without emitters trending never fills; W02 and W03 add the emission through S39's ingestion.
- [CONTRACT] Endpoint contract and schemas in `packages/contracts` (`trendingQuerySchema`, `trendingResponseSchema`) → W02 and S48 adopt the new envelope and treat the section as optional with a 200 ms budget in the composition; the home page copy "Powered by Count-Min Sketch…" is removed → implementation notes do not belong in buyer-facing text.
- [CONTRACT] Product facts via `ProductQueryService.getProductsByIds` (S05) with fields `id, title, priceMinor, currency, category, status, isSandbox, inStock, shopId`, and shop status via `ShopQueryService.getShopsByIds` (S03) → S05 already names S35 a consumer; shop status is not in `ProductDto`, so a second batched R1 call is needed (an R3 product read model rejected: S05 provides no trending-friendly snapshot and the pool is at most 60 products).
- [CONTRACT] Rate-limit policy `discovery.trending` for S50's registry → name must match exactly.
- [CONTRACT] S33 deferred a trending blend to S35 → not built; trending products are not search terms, and a `trending` autocomplete source would be a new contract on S33's response → S33 keeps `source` values as they are.
- [CONTRACT] S36 shares nothing with this capability: exact deduplicated click counting, hot-key salting and billing belong to S36; trending code is not reused for money → keeps the approximate and exact paths separate, as the notes require.
- [LOCAL] Purchases are not a signal → views 1 and add-to-carts 5 only (the notes' implementation) → `order.paid` lines carry no category and S34 already consumes that topic for baskets.
- [LOCAL] Window, lateness, idle timeout, K, widths, depth, weights, category cap, memory budget, retention are configuration with defaults 60 s, 2 min, 30 s, 50, 2^16 / 2^14, 4, 1 / 5, 100, 512 MB, 3 h; validated at startup (AS-37).
- [LOCAL] The per-visitor membership check is a Bloom-style filter sized per window with a 1% false-"seen" bound → bounded memory at 500k events per second; a false "seen" slightly undercounts, which approximate counting tolerates.
- [LOCAL] Merge identity is (partition, window, first and last covered offset) kept as long as the window's aggregate → makes replays and concurrent owners safe without a lock.
- [LOCAL] While the aggregate store is down the consumer buffers to its memory budget, then pauses the partitions → backpressure over dropping.
- [LOCAL] No `404` for an empty or unknown category → a category is a label, not a resource; `200` with empty `items`.
- [LOCAL] Candidate pool is `min(3 × limit, 60)` → enough to replace hidden items while keeping both lookups far below the 500-id limit.
- [LOCAL] The seeded generator replaces `Math.random` in the unit tests (`count-min-sketch.spec.ts:10,23`) → a flaky precision test cannot gate a PR; the existing "≥ 9 of 10" threshold stays.
- [LOCAL] Wall clock reaches pure logic only as an injected `now` → I.3 and frozen-time tests.
