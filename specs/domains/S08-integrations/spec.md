# Feature Specification: S08 — Shopify/WooCommerce Catalog and Stock Sync: Incremental Pulls, Bidirectional Stock, Reconciliation, Quarantine (domain `catalog-sync`)

**Feature Branch**: `S08-integrations` (spec directory `specs/domains/S08-integrations`)

**Created**: 2026-10-05

**Status**: Draft

**Input**: Capability S08 of `scripts/sdd/capabilities.tsv`. Sources: `docs/showcase/sections/SD-36-shop-integrations-sync.md`, `06-Distributed-Systems/02-consistency-sagas-and-data-sync.md` (§3 bidirectional sync, §4 incremental ETL, §5 reconciliation), `04-API-Design/03-idempotency-pagination-rate-limiting-webhooks.md` (§4 consuming rate-limited APIs, §5 webhooks as consumer). Pattern-map rows covered: **P0112** (runtime validation at boundaries), **P0417** (consuming rate-limited APIs: token bucket per credential, `Retry-After`), **P0419** (webhooks as consumer: verify raw body, fast 2xx, dedupe on event ID), **P0518** (secrets: envelope-encrypted fields), **P0612** (bidirectional sync, echo suppression, conflict queue), **P0613** (incremental ETL with watermark and overlap, backfill separation), **P0614** (reconciliation and period close).

## Scope

A shop that already sells through **Shopify** or **WooCommerce** connects that store to the marketplace. Its catalog appears here and stays current without anyone keying anything, and its **stock is shared**: a sale on either side lowers the one number both sides show. This capability owns the connection (credentials, OAuth hand-shake, lifecycle), the schedule and queues that pull changes, the webhook receiver, the mapping between provider items and marketplace products, the stock merge between the two systems, the quarantine for items that cannot be understood, the conflict queue for stock that cannot be reconciled automatically, the nightly reconciliation, and the operator-facing status of all of it.

In scope:

- Connecting a store: Shopify through the OAuth install flow, WooCommerce through API keys; sealed credentials; webhook registration; the integration life cycle (`ACTIVE`, `PAUSED`, `NEEDS_REAUTH`, `DISCONNECTED`).
- **Incremental pulls**: a watermark with an overlap window, a checkpoint per page, a single runner per integration, a time budget per run, a separate queue for backfills so an initial import never delays other shops' day-to-day syncs, and a scheduled pull as the guarantee when webhooks are lost.
- **Webhooks as a fast path**: signature check over the raw body, replay and duplicate protection, acknowledge first, fetch the current state afterwards.
- **Anti-corruption layer**: provider payloads are validated and normalised before anything else sees them; the raw payload is kept; one provider variant becomes one marketplace product, and money is parsed from decimal strings, never through floating point.
- **Writes to the catalog only through the catalog's exported commands** (never to the product table, never to product events).
- **Bidirectional stock**: field ownership (the provider owns catalog fields, stock is shared), a three-way merge on a recorded common base, echo suppression, stale-read protection, a conditional write to the provider, and a conflict queue for what cannot be merged safely.
- **Quarantine** of malformed or unacceptable provider items with an alert, never a crash, plus its review routes.
- **Provider etiquette and resilience**: a fleet-wide token bucket per credential, `Retry-After`, bounded retries with jitter, timeouts, a circuit breaker, token refresh, a re-authorisation state.
- **Nightly reconciliation** (compare, classify, report, auto-fix only what is clear, mass-deletion guard) with immutable reports.
- Management routes for the shop's members, the lifecycle events other capabilities may use, shop-lifecycle reactions (suspension, offboarding, deletion), retention, observability.

Out of scope (owned elsewhere):

- Product validation rules, the product record, product events, change detection, stock arithmetic and the `(shopId, externalSku)` uniqueness → **S05** (this capability calls `ProductImportService.upsertFromExternal` and `ProductStockService.applyStockDelta`, reads with `ProductQueryService.getProductsByIds`, and consumes S05's product events; it writes no product row and no product event).
- Bulk file import → **S07**; offline device sync (operations, deltas, per-field clocks) → **S09**. They share the domain, not these tables or routes. S09's stock changes reach the provider through S05's events like any other local stock change (AS-36).
- Shop membership, permissions, status → **S03**. Sealing primitives → **S01**. Rate-limit engine, scheduler, outbox and consumer framework, resilient HTTP client, error filter, metrics → **S50**, **S49**, **S53**, **S54**.
- The seller dashboard screens (connect button, status, quarantine and conflict lists) → **W04**. The OAuth redirect lands on a W04 page.
- Pushing catalog fields (title, price, description) from the marketplace to the provider: the provider owns them (FR-040). Order import from providers is not part of this capability.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — A seller connects a store and the catalog appears (Priority: P1)

A seller with a Shopify store clicks "Connect Shopify", approves the app on Shopify, and returns to the dashboard. A few minutes later every variant of every active product is in the marketplace with its price and stock, linked to the original. A WooCommerce seller pastes API keys instead. Nobody can point the connection at an internal address, connect someone else's store, or read the keys back.

**Why this priority**: it is the entry point; nothing else matters before a store can be connected safely.

**Independent Test**: drive the real routes with a seeded shop and a member against a fake provider server that speaks the real API shapes; run the worker entry for the backfill; read the products back through the catalog's exported query.

**Acceptance Scenarios**:

1. **AS-01** (install start) — **Given** an `ACTIVE` shop `S` and a member with `integrations.manage`, **When** they `POST /shops/S/integrations/shopify/install {shopDomain: "Acme.myshopify.com"}`, **Then** `200 {authorizeUrl, expiresAt}` parsed by `integrationInstallResponseSchema`; the URL host is `acme.myshopify.com` (lower-cased), its path is `/admin/oauth/authorize`, and it carries the app's client ID, the scopes `read_products,read_inventory,write_inventory,read_locations`, the platform callback as `redirect_uri` and an opaque `state` of at least 128 random bits; one install record exists for `(S, member, acme.myshopify.com)` that holds only a digest of `state` and expires 10 minutes after the frozen clock.
2. **AS-02** (install validation) — **Given** a member of `S`, **When** `shopDomain` is `acme.com`, `acme.myshopify.com.evil.io`, `evil.com/.myshopify.com`, `https://acme.myshopify.com`, `10.0.0.1`, `acme.myshopify.com:8443`, `-acme.myshopify.com`, an empty string, 256 characters, or the body has an unknown extra field or is empty, **Then** each is `400 validation_failed` with `errors:[{field, code}]`, no install record and no URL; a viewer or staff member gets `403 permission_denied`; a request without credentials gets `401`.
3. **AS-03** (callback success) — **Given** an open install record for `(S, member, acme.myshopify.com)` and a Shopify callback whose `hmac` is valid over its other parameters with the app secret and whose `state` matches, **When** the browser follows it to `GET /integrations/shopify/callback?…`, **Then** the code is exchanged for a token (one call to the fake provider), the store's currency equals the platform currency, and the answer is `302` to the web app's integrations page with `?connected=<integrationId>`; the integration is `ACTIVE` with `provider: "shopify"`, `externalShop: "acme.myshopify.com"`, `connectedBy` the member, a history row, and exactly one `catalog_sync.integration_connected` outbox row; the credentials are stored sealed (the ciphertext contains no part of the token and opens only with this integration's context, AS-79); four webhook subscriptions (`products/update`, `products/delete`, `inventory_levels/update`, `app/uninstalled`) exist at the provider pointing to this integration's webhook URL; exactly one message `{integrationId, kind: "backfill"}` is on the backfill queue; the install record is consumed.
4. **AS-04** (callback rejections) — **Given** a callback, **When** its `hmac` is wrong, a parameter was altered, the `timestamp` is older than 5 minutes, the `state` is unknown, expired or already used, the `shop` differs from the install record's domain, or a required parameter is missing, **Then** each answers `400 invalid_oauth_callback` with the same body whatever the cause (the cause is only logged), no token exchange is attempted, no integration exists and no message is enqueued; **When** the signature and state are valid but the provider rejects the code exchange, **Then** `302` to the web app with `?error=oauth_exchange_failed` and nothing is stored.
5. **AS-05** (callback replay and race) — **Given** a valid callback, **When** it is delivered twice at the same moment (`Promise.all`) and once more afterwards, **Then** exactly one answers the success `302`, the others answer `400 invalid_oauth_callback`; one integration, one `integration_connected` row and one backfill message exist.
6. **AS-06** (WooCommerce connect) — **Given** a member of `S`, **When** they `POST /shops/S/integrations {provider: "woocommerce", storeUrl: "https://shop.example.com", consumerKey, consumerSecret}`, **Then** the server verifies the keys with one authenticated call and reads the store currency (equal to the platform currency), generates a webhook secret, registers the product webhooks with it, and answers `201 integrationSchema` (`status: "ACTIVE"`, `credentialsSet: true`, no key or secret anywhere in the body); one backfill message is enqueued; **When** the provider rejects the keys, **Then** `422 provider_credentials_rejected` and nothing is stored; **When** the provider does not answer within 15 s or answers 5xx, **Then** `503 provider_unavailable` with a generic detail and nothing is stored; **When** the same store is posted again for the same shop, **Then** `200` with the same integration (credentials replaced, `status: "ACTIVE"`, AS-09), not a second one.
7. **AS-07** (store URL guard) — **Given** a WooCommerce connect request, **When** `storeUrl` is `http://…`, has user-info, a port other than 443, an IP literal (v4 or v6), `localhost`, a name that resolves to loopback, private (`10/8`, `172.16/12`, `192.168/16`), link-local (`169.254/16`, including the cloud metadata address), unique-local or multicast addresses, or answers with a redirect, **Then** `422 invalid_store_url` and no outbound call is made to the blocked address; **Given** a hostname that resolved to a public address at validation and resolves to a private one when the call is made (DNS rebinding), **Then** the call is refused, the connect fails `422 invalid_store_url`, and the same guard applies to every later sync call, webhook registration and `Link`/redirect target.
8. **AS-08** (currency) — **Given** a store whose currency differs from the platform currency, **When** it is connected (either provider), **Then** `422 currency_mismatch` (WooCommerce) or `302 …?error=currency_mismatch` (Shopify), no integration is created and the Shopify token is discarded unused beyond that check.
9. **AS-09** (reconnect) — **Given** an integration for `(S, shopify, acme)` in `NEEDS_REAUTH` or `DISCONNECTED`, **When** the OAuth flow completes again for the same shop, **Then** the same `integrationId` is reused, credentials are replaced, `status` is `ACTIVE` with a history row, the cursor is reset, one backfill message is enqueued, and its links are kept so no product is duplicated afterwards (a backfill finds every variant `unchanged` or `updated`).
10. **AS-10** (one connection per store) — **Given** shop `A` has a non-`DISCONNECTED` integration for `acme.myshopify.com`, **When** shop `B` completes the OAuth flow for the same store, **Then** `302 …?error=store_already_connected` and nothing is created; **When** `A` and `B` complete callbacks for a store nobody has connected at the same moment (`Promise.all`), **Then** exactly one integration exists (the other answers `store_already_connected`), whatever the interleaving.
11. **AS-11** (integration limit) — **Given** shop `S` with 5 non-`DISCONNECTED` integrations, **When** a sixth is connected, **Then** `409 integration_limit_reached` (or `302 …?error=integration_limit_reached`) and nothing is created; **Given** `S` with 4, **When** two different stores are connected at the same moment, **Then** exactly one succeeds and the count never exceeds 5.

### User Story 2 — Changes flow in incrementally, once, and never lost (Priority: P1)

After the first pull, only what changed is read. A product changed at the provider shows up here within minutes (seconds with webhooks), a crash mid-run costs at most one page of work, two workers never run the same store, a huge store never starves a small one, and a replay changes nothing.

**Why this priority**: the sync must be correct and cheap on the provider's API budget before stock is layered on it.

**Independent Test**: a fake provider server with page size 2 holding variants with controllable `updatedAt`; run the worker entry directly with a frozen clock; assert product state through S05's query and the persisted links, cursors and runs.

**Acceptance Scenarios**:

1. **AS-12** (backfill) — **Given** an integration whose store has 5 products of which 2 have 2 variants each (7 variants, 1 draft product that is ignored), page size 2, **When** the backfill message is handled, **Then** the catalog's import command is called with `source: "shopify"` in batches of at most 500 items; 7 products exist for the shop with `quantity` equal to the provider's stock; 7 links exist with `externalId` `<productId>:<variantId>`, a deterministic `externalSku` `<provider>:<integrationId>:<externalId>`, the content digest, `syncedStock` equal to the provider's stock, `remoteUpdatedAt` and the raw payload; the watermark equals the largest `updatedAt` fetched (not "now") and no page cursor remains; one run record shows `kind: "backfill"`, `outcome: "completed"`, counters `{fetched: 7, created: 7, updated: 0, unchanged: 0, quarantined: 0}`; the incremental queue received nothing; the provider received no stock write (AS-36 covers why).
2. **AS-13** (idempotent replay) — **Given** AS-12 done, **When** the same backfill message is handled again, **Then** counters are `{fetched: 7, created: 0, updated: 0, unchanged: 7}`, the catalog wrote no row and no event, the 7 links are unchanged and no product was duplicated.
3. **AS-14** (normalisation, pure) — **Given** the Shopify and WooCommerce mapping rules, **When** table-driven over provider JSON, **Then** each yields the stated normalised item or the stated rejection code: a one-variant product (title as is), a multi-variant product (`"<title> — <variant title>"`, the default variant title `Default Title` omitted), HTML in the description stripped and whitespace collapsed, a missing product type → category `uncategorized`, vendor → brand (empty allowed), tags split on commas and trimmed, a title longer than 200 characters → `title_too_long`, missing title → `missing_title`, a draft or archived provider product → `unlisted` (not a product), variant without an inventory item → `no_inventory_item`, `externalId` over 64 characters → `external_id_too_long`; every output carries `updatedAt`, a content digest over exactly the provider-owned fields (title, description, price, category, brand, tags), and never any credential.
4. **AS-15** (money parsing, pure) — **Given** the price rule, **When** table-driven in the platform currency (2 decimals): `"19.99"→1999`, `"19"→1900`, `"0.5"→50`, `"0.50"→50`, `" 12.99 "→1299`, `"1234567.89"→123456789`; `"12.999"`, `"-1"`, `"1e3"`, `"1,99"`, `""`, `"abc"`, `"0"`, `"0.00"`, a 12-digit whole part, a JSON number `19.99` where a string is required, **Then** each yields the stated minor-unit integer or `invalid_price`; no step uses floating-point arithmetic, and a currency with another number of decimals yields its own exponent (`"1999"` in a 0-decimal currency → `1999`).
5. **AS-16** (incremental with overlap) — **Given** a stored watermark `W`, an item changed at `W+1 min` and an unchanged item at `W−3 min`, an old item at `W−2 h`, **When** the incremental message is handled, **Then** the provider is asked for changes since exactly `W − 5 min`; the item at `W−2 h` is not requested; the changed item is `updated`, the `W−3 min` item is `unchanged` (its digest and stock equal the link), and the new watermark is the largest fetched `updatedAt`; a second run with nothing new asks since `W' − 5 min`, applies nothing and keeps the watermark.
6. **AS-17** (checkpoints, resume) — **Given** a run over 5 pages that is killed (the fake provider drops the connection and the worker process is terminated) after page 3 was applied, **When** the message is redelivered, **Then** the run resumes at page 4 from the stored page cursor (the provider sees no new request for pages 1–3), finishes with counters that add up to the whole set, and only then moves the watermark; **Given** the run is killed before finishing, **Then** the stored watermark is unchanged (only the page cursor moved); **Given** a provider item whose `updatedAt` is in the future, **Then** it is applied but the watermark never exceeds the frozen "now" (it is clamped), so one bad clock cannot hide later changes.
7. **AS-18** (single runner) — **Given** two messages for the same integration (a scheduled one and a redelivery), **When** both are handled at the same moment (`Promise.all`), **Then** exactly one run executes and the other ends `skipped_locked` without calling the provider or writing; **Given** the lease holder stalls and the clock passes the lease expiry, **When** another worker claims the run, **Then** the stalled holder's later checkpoint or watermark write is refused (fencing) and the stored watermark never moves backwards.
8. **AS-19** (run budget yields) — **Given** a store with 12 pages and a run budget of 3 pages (configured), **When** the backfill is handled, **Then** the run ends `yielded` after page 3 with its checkpoint stored, exactly one continuation message is enqueued (not 12), and the continuation finishes the remaining pages; **When** the time budget (4 minutes incremental, 12 minutes backfill) is reached by the frozen clock, **Then** the same happens.
9. **AS-20** (scheduled pull) — **Given** 3 `ACTIVE` integrations due, one `PAUSED`, one `NEEDS_REAUTH`, one `DISCONNECTED`, one in a shop that is not `ACTIVE`, and one with an open breaker (AS-59), **When** the scheduled job `catalog-sync.sync-all` runs, **Then** exactly 3 incremental messages are enqueued, each integration's next-due time moves by 5 minutes plus a deterministic per-integration jitter in `[0, 60 s)`; **When** it runs again at the same instant, **Then** nothing is enqueued.
10. **AS-21** (backfills do not starve incrementals) — **Given** a backfill for shop `A` blocked mid-run (the fake provider holds a page), **When** an incremental message for shop `B` arrives, **Then** it runs to completion while `A`'s backfill is still blocked; backfills run on their own queue with their own concurrency (4) and the incremental queue has its own (20).
11. **AS-22** (out-of-order snapshot) — **Given** a link whose `remoteUpdatedAt` is `T2`, **When** a snapshot of the same variant with `updatedAt` `T1 < T2` is applied (a delayed page or a replayed message), **Then** it is skipped as `stale`: the product, the link and the stock are unchanged and no catalog call is made.
12. **AS-23** (concurrent apply) — **Given** a variant changed at the provider, **When** a webhook-triggered fetch and an incremental page apply it at the same moment (`Promise.all`), **Then** exactly one reports `updated` and the other `unchanged`; the product's version rose by exactly 1 and one `catalog.product_updated` exists.
13. **AS-24** (crash between catalog write and link write) — **Given** a fault that makes the link write fail once (a database trigger raising), **When** the run is retried, **Then** it completes; exactly one product exists for the variant's `externalSku`, one link exists, the stock equals the provider's (not doubled), and no unique-violation error reached any caller.
14. **AS-25** (queue messages) — **Given** the sync queues, **When** the identical `{integrationId, kind: "one", externalId}` message is delivered twice (and a duplicate `incremental`), **Then** the second delivery changes nothing (AS-13 semantics); **When** a message with an invalid payload (not a UUID, unknown `kind`, extra field, empty `externalId`) arrives, **Then** it is rejected without side effects and ends in the dead-letter queue after the configured receive count; a message for an unknown or `DISCONNECTED` integration is acknowledged and does nothing.

### User Story 3 — Webhooks are a fast path, never the guarantee (Priority: P1)

Providers call the marketplace when something changes. The call is verified against the raw bytes, acknowledged immediately, deduplicated, and the work is done afterwards from the provider's *current* state. Forged, replayed, stale and duplicate calls change nothing. If every webhook is lost, the scheduled pull still converges.

**Why this priority**: webhooks are an unauthenticated public entry point (a security boundary) and the main source of duplicates and reordering.

**Independent Test**: post raw bodies with computed signatures to the real route; assert the response, the enqueued message, the receipt record and, after running the worker, the resulting state.

**Acceptance Scenarios**:

1. **AS-26** (valid webhook) — **Given** a Shopify integration and a body `{"id": 1001}` with a correct `X-Shopify-Hmac-Sha256` over the raw bytes, `X-Shopify-Topic: products/update`, `X-Shopify-Webhook-Id: w1`, `X-Shopify-Triggered-At` equal to the frozen now, **When** it is posted to `POST /api/integrations/I/webhooks`, **Then** `200 {received: true}` is returned while the provider has received no call yet; one receipt for `w1` is stored; one message `{integrationId: I, kind: "one", externalId: …}` is enqueued; **When** the worker handles it, **Then** the provider's current state of that product is fetched and applied (AS-13 semantics for repeats). The route needs no credentials and is not subject to the per-user throttle.
2. **AS-27** (forged or malformed) — **Given** the same route, **When** the signature is wrong, absent, computed over a re-serialised body (whitespace changed), made with another integration's secret, or the body is not valid JSON, **Then** `401 invalid_webhook_signature` with identical bodies, nothing is enqueued and no receipt is stored; **When** the integration ID is unknown, malformed, or `DISCONNECTED`, **Then** the identical `401` (existence is not revealed); signature comparison is constant-time.
3. **AS-28** (duplicate delivery) — **Given** a valid webhook with ID `w1` already received, **When** the same ID is delivered again, also twice at the same moment, **Then** every response is `200 {received: true}`, exactly one message was enqueued in total and one receipt exists.
4. **AS-29** (stale timestamp) — **Given** a valid signature and `X-Shopify-Triggered-At` older than 5 minutes (frozen clock), **When** posted, **Then** `401 webhook_stale`, nothing enqueued; at exactly 5 minutes it is accepted, at 5 minutes 1 second it is rejected; a provider that sends no timestamp (WooCommerce) is protected by the ID dedupe of AS-28 instead.
5. **AS-30** (delete and uninstall topics) — **Given** `products/delete` for variant `X`, **When** processed, **Then** the worker re-checks with the provider (a `404` confirms), marks the link `DELETED_AT_PROVIDER`, lowers local stock to zero through the catalog's stock command (operation `sync:<I>:<digest>`, reason `sync-deleted`), and writes nothing else; if the provider still returns the item, nothing is deleted (AS-62 semantics); **Given** `app/uninstalled`, **When** received with a valid signature, **Then** the integration becomes `DISCONNECTED` (history row, status event), its credentials are erased, links are kept, and no further provider call is made for it.
6. **AS-31** (enqueue failure) — **Given** a queue outage (the enqueue call fails), **When** a valid webhook arrives, **Then** `503` with a generic body and **no** receipt stored, so the provider's retry is not mistaken for a duplicate; once the queue is back the redelivery answers `200` and enqueues one message.
7. **AS-32** (limits) — **Given** the route, **When** a body exceeds 1 MiB, **Then** `413`; **When** more than 1,200 requests per minute arrive for one integration, or 600 per minute from one address before the signature is verified, **Then** `429 rate_limited` with `Retry-After`; below the limits nothing is refused; a limiter outage fails open (a webhook is never refused only because the limiter store is down; the signature check still applies).
8. **AS-33** (WooCommerce variant) — **Given** a WooCommerce integration with its own per-integration webhook secret, **When** a delivery carries a correct base64 `X-WC-Webhook-Signature` over the raw body and a delivery ID, **Then** it behaves as AS-26 (deduped by delivery ID); **When** the registration ping (a form-encoded body with only `webhook_id`) arrives, **Then** `200` and nothing is enqueued; a wrong signature is `401 invalid_webhook_signature`.
9. **AS-34** (paused integration) — **Given** a `PAUSED` integration, **When** a valid webhook arrives, **Then** `200 {received: true}` and nothing is enqueued or recorded (the resume catch-up of AS-68 converges); **Given** `NEEDS_REAUTH`, the same.

### User Story 4 — Stock stays right on both sides, without ping-pong (Priority: P1)

A sale on the marketplace lowers the provider's stock, a sale at the provider lowers ours, a sale on both sides at once lowers both by both, and the provider's echo of our own write is recognised and ignored. When both sides sold the same last unit, nobody's order is silently lost: the overselling is clamped to zero and queued for a human.

**Why this priority**: shared stock is the invariant sellers care about (an oversold item is a refunded order and a bad review). Catalog fields are simple by comparison.

**Independent Test**: fake provider with a writable stock, per-write preconditions and an `updatedAt` that moves on every write (like real providers); drive local changes through S05's stock command and the real product events; assert the provider's write log and both quantities.

**Acceptance Scenarios**:

1. **AS-35** (inbound stock merge) — **Given** a link with `syncedStock: 10`, local quantity `10`, **When** the provider shows `7`, **Then** the catalog's stock command is called once with delta `-3`, `reason: "sync-inbound"` and the deterministic operation `sync:<I>:<digest of externalId, base, remote, remoteUpdatedAt>`; local quantity is `7`, `syncedStock` is `7`, and the provider receives no write.
2. **AS-36** (outbound push, echo ignored) — **Given** a linked product with local quantity `10` and `syncedStock: 10`, **When** a local sale (any capability, through the catalog's stock command) lowers it to `8` and the product event arrives, **Then** one conditional write "set `8`, provided the provider still has `10`" is sent; `syncedStock` becomes `8`; the provider's write log is `[{externalId, set: 8, expected: 10}]`; **When** the provider's `updatedAt` moves because of that write and the next incremental pull returns the item, **Then** nothing is applied (stock `8` equals `syncedStock`, content digest equal) and no second write is sent; the same holds for a stock change made by S09, S10, S11, S21 or S42 (they all go through the catalog's stock command).
3. **AS-37** (both sides sold) — **Given** `syncedStock: 10`, local `8` (sold 2) and provider `7` (sold 3), **When** the pull and the push are processed in either order (table-driven, both orders), **Then** both sides end at `5` (= 8 + 7 − 10), `syncedStock` is `5`, no conflict is opened, and in the push-first order the provider's conditional write is refused (the provider holds `7`, not `10`), is abandoned without overwriting the provider's sale, and the merge then runs from the fresh remote state; the provider's write log holds exactly one accepted write (`5`).
4. **AS-38** (oversold → conflict queue) — **Given** `syncedStock: 3`, local `0` (sold 3), provider `1` (sold 2), **When** the merge runs, **Then** the merged value would be `-2`, so both sides are set to `0`, and one stock conflict `OPEN` is stored `{kind: "oversold", base: 3, local: 0, remote: 1, merged: -2, resolvedTo: 0}` with one `catalog_sync.stock_conflict_opened` outbox row and the open-conflict gauge incremented; running the same merge again changes nothing and opens no second conflict.
5. **AS-39** (conflict queue routes) — **Given** open conflicts of an integration of shop `S`, **When** a member with `integrations.manage` calls `GET /shops/S/integrations/I/conflicts?status=OPEN&limit&cursor`, **Then** `200 conflictPageSchema` ordered by creation time then ID descending with an opaque cursor (a tampered cursor is `400 invalid_cursor`); **When** they `POST …/conflicts/C/dismiss`, **Then** `200` with `status: "DISMISSED"`, a `dismissedBy` and time; dismissing again answers `409 conflict_not_open`; a conflict of another shop's integration, or an integration ID under the wrong shop, answers `404 conflict_not_found`; dismissing changes no stock.
6. **AS-40** (product-event consumer) — **Given** the consumer of S05's `catalog.product_*` events on `products.events`, **When** an event of a product with no link, a sandbox product (`isSandbox: true`), an event whose `changedFields` lacks `quantity`, or an event of a link whose integration is not `ACTIVE` arrives, **Then** nothing is sent to any provider; **When** the same event (same `eventId`) arrives twice, or an event with `productVersion` lower than the link's last seen version arrives after a newer one, **Then** a single push at most happens and the older one is ignored; **When** the event of our own inbound apply (AS-35: quantity equals `syncedStock`) arrives, **Then** no write is sent (no ping-pong); **When** the payload is invalid (missing `productId` or `quantity`, non-UUID, wrong `version`), **Then** it is dead-lettered with no side effects; links are looked up with the event's `shopId` in the predicate so an event cannot reach another shop's integration.
7. **AS-41** (stale read) — **Given** a page fetched from the provider before our latest stock write to the same variant completed (a gated fetch), **When** it is applied after that write, **Then** its stock is not used (the next pull, fetched after the write, decides), the local quantity is unchanged by it and no double counting happens; its catalog fields are applied normally.
8. **AS-42** (crash replay) — **Given** a crash after the catalog applied the delta of AS-35 but before `syncedStock` was saved, **When** the run is retried, **Then** the same operation ID is replayed (`replayed: true`), the local quantity changed once, and `syncedStock` is saved; a later genuine change from `10` to `7` again has a different remote `updatedAt`, hence a different operation ID, and is applied.
9. **AS-43** (push failure) — **Given** the provider answers 503 to the conditional write three times, **When** the push runs, **Then** it is retried at most 3 times in one run with backoff (AS-57) and ends failed; `syncedStock` is unchanged so the difference stays visible; the next product event, the next scheduled pull or the nightly reconciliation retries it; when the provider recovers the provider's stock equals the local quantity and `syncedStock` follows; a provider answer `404` for the variant marks the link `DELETED_AT_PROVIDER` (AS-62).
10. **AS-44** (coalescing) — **Given** three local changes `10→9→8→7` of one product within one consumer batch, **When** the batch is processed, **Then** one conditional write `set 7 expected 10` is sent.
11. **AS-45** (merge rule, pure) — **Given** the rule `merge(base B, local L, remote R)`, **When** table-driven, **Then**: `(10,10,10)` → nothing; `(10,10,7)` → pull, result `7`; `(10,8,10)` → push, result `8`; `(10,8,7)` → pull `-3` locally and push, result `5`; `(10,5,5)` → converged, base `5`, no operation; `(3,0,1)` → conflict `oversold`, result `0`; `(5, 1e9, 1e9)` (merged `2e9 − 5`) → conflict `quantity_limit`, result `1,000,000,000`; **Given** any generated `(B,L,R)` in `[0, 1e9]`, **Then** the result is always in `[0, 1e9]`, it equals `L + R − B` whenever that is in range, swapping `L` and `R` gives the same result (property-based), and the function reads no clock and no store.
12. **AS-46** (local deletion) — **Given** a linked product that is deleted in the catalog (`catalog.product_deleted`), **When** the provider later sends changes for the variant, **Then** the link is `IGNORED`, the product is not resurrected and nothing is pushed; a repeated event changes nothing.

### User Story 5 — Bad data and a bad provider never stop the sync (Priority: P1)

One malformed product among 100,000 is set aside with its reason and the rest carry on. A provider that rate-limits, hangs, fails or revokes access is handled politely and visibly: shared budgets, `Retry-After`, bounded retries, a breaker, and a clear "reconnect needed" state.

**Why this priority**: third-party data and third-party uptime are the reasons these syncs fail in production.

**Independent Test**: a fake provider that serves malformed items, 429s, slow answers and 401s on demand; frozen clock; assert quarantine rows, run outcomes and the provider's observed request log.

**Acceptance Scenarios**:

1. **AS-47** (quarantine, sync continues) — **Given** a store with 4 valid variants and one whose price is `"free"`, **When** a pull runs, **Then** counters are `{created: 4, quarantined: 1}`, the run ends `completed_with_quarantine`, the watermark moves past the bad item, one quarantine row `OPEN` exists `{entity: "product", externalId, reasonCode: "invalid_price", message (≤ 500 characters), payload (the raw item), occurrences: 1, firstSeenAt, lastSeenAt}`, a metric and a structured log line count it, and no log line contains the payload.
2. **AS-48** (no duplicate rows) — **Given** the bad item of AS-47 is read again by every overlap re-read for 12 consecutive runs, **Then** exactly one `OPEN` row exists with `occurrences: 13` and a new `lastSeenAt`; if its payload changes but is still bad, the same row is updated in place; an item with no readable ID is deduplicated by a digest of its payload.
3. **AS-49** (auto-resolution) — **Given** a quarantined variant, **When** it becomes valid at the provider and is pulled, **Then** it is applied normally and its quarantine row becomes `RESOLVED` with `resolution: "fixed_at_provider"`.
4. **AS-50** (review routes) — **Given** open quarantine rows, **When** a member with `integrations.manage` calls `GET /shops/S/integrations/I/quarantine?status&limit&cursor`, **Then** `200 quarantinePageSchema` (cursor pagination as AS-39, `status` filter, `limit` 1–100); `POST …/quarantine/Q/retry` re-fetches the item from the provider and answers `200 {outcome: "resolved" | "still_invalid", item}` (resolved applies it and marks the row `RESOLVED`; still invalid increments `occurrences`); `POST …/quarantine/Q/dismiss` answers `200` with `DISMISSED`; retry or dismiss on a row that is not `OPEN` answers `409 quarantine_not_open`; another shop's row or integration answers `404 quarantine_not_found`; two concurrent dismiss/retry calls leave exactly one transition.
5. **AS-51** (catalog refusal) — **Given** the catalog's import command returns `rejected` for one item (e.g. a title the catalog refuses) among 5, **When** the pull runs, **Then** the other 4 are applied, and the rejected one is quarantined with `reasonCode: "catalog_rejected"` and the catalog's `field` and `code` in its message.
6. **AS-52** (stock quirks) — **Given** provider stock values, **When** table-driven, **Then** `-3` is treated as `0` without quarantine, `2,000,000,000` → quarantine `stock_out_of_range`, `1.5` or `"abc"` → `invalid_stock`, a variant whose inventory is not tracked by the provider → quarantine `inventory_not_tracked` (the marketplace cannot sell unlimited stock safely), and a missing location level → `inventory_level_missing`.
7. **AS-53** (mass drift halts) — **Given** a provider that starts returning malformed items so that more than 1,000 are quarantined in one run, **When** the run reaches 1,000, **Then** it stops `halted_schema_drift`, the watermark is **not** advanced, one `catalog_sync.integration_attention_required {reason: "schema_drift"}` event is written, the integration's next pull is delayed by 1 hour, and the already-applied good items stay applied.
8. **AS-54** (response validation) — **Given** a provider page whose envelope is invalid (`products` is not an array, an HTML error page with status 200, a JSON body of the wrong type), **When** it is read, **Then** the run ends `failed` with `provider_schema_invalid`, nothing is quarantined or applied from it, the payload is not stored, and the breaker counts one failure; **Given** a `Link` header whose `next` target is another host, another scheme, or not the store's API path, **Then** it is not followed and the run ends `failed` with `provider_schema_invalid`.
9. **AS-55** (shared rate budget) — **Given** a credential whose bucket allows 5 calls per second (test configuration), **When** two worker instances make 12 calls for that integration at the same moment, **Then** the fake provider never sees more than 5 calls in any 1-second window and returns no `429`; another integration (another credential) is not slowed; **Given** the limiter store is down, **When** a run starts, **Then** it ends `yielded` with `rate_limiter_unavailable` and the provider received no call (the policy fails closed).
10. **AS-56** (`Retry-After`) — **Given** the provider answers `429` with `Retry-After: 3`, **When** a call is made, **Then** the credential's bucket is paused for 3 seconds for every worker, the call is retried once after at least 3 seconds and no other call to that credential is made meanwhile; **When** `Retry-After` is above 60 seconds, **Then** the run stops `yielded`, a continuation is enqueued with that delay (capped at 15 minutes) and nothing is retried inline.
11. **AS-57** (retry policy) — **Given** provider answers, **When** a read gets `503` twice then `200`, **Then** it succeeds on the third attempt with full-jitter exponential waits (base 500 ms, cap 8 s); **When** it gets `400`, `403` on a non-auth cause, `404` or `422`, **Then** it is not retried (`404` on a single-item read means "gone", AS-30); **When** the conditional stock write times out, **Then** it is retried (it is idempotent); **When** webhook registration (non-idempotent) times out, **Then** it is not retried automatically; at most 3 attempts are made in any call path, retries happen at this layer only (the queue redelivery is not a second retry layer for the same call within one run).
12. **AS-58** (timeouts) — **Given** a provider that never answers, **When** a call is made, **Then** it is aborted at 15 s (frozen/fake clock), counted as one failure towards the breaker, retried per AS-57, and finally the run ends `failed` retryable; the message is returned to the queue and the lease is released at the end of the run.
13. **AS-59** (circuit breaker) — **Given** 5 consecutive failed provider calls (after retries) for one integration, **When** the fifth fails, **Then** the breaker opens for 5 minutes: runs for that integration end `skipped_breaker_open` without any provider call, the scheduled job does not enqueue it, one `catalog_sync.integration_attention_required {reason: "breaker_open"}` event is written, the status stays `ACTIVE`; **When** the 5 minutes pass, **Then** exactly one probe call is made: success closes the breaker, failure reopens it for another 5 minutes (no second attention event until it has closed once).
14. **AS-60** (auth failure and token refresh) — **Given** the provider answers `401` to a call, **When** the integration holds a refresh token (expiring offline tokens), **Then** exactly one refresh is made, the new token is stored sealed, the call is retried once and succeeds; **When** two workers see the `401` at the same moment (`Promise.all`), **Then** exactly one refresh call reaches the provider and both continue with the new token; **When** there is no refresh token or the refresh is refused, **Then** the status becomes `NEEDS_REAUTH` (history row), `lastError` is `provider_auth_failed`, runs and pushes stop, exactly one `integration_status_changed` and one `integration_attention_required {reason: "needs_reauth"}` event are written, and the scheduled job skips it until the seller reconnects (AS-09).

### User Story 6 — Nightly reconciliation proves the two sides agree (Priority: P2)

Incremental sync and webhooks can still miss things: a deleted product, a missed webhook, a lost stock event. Every night the full set of provider IDs and hashes is compared with the links, drift is classified, only what is clearly safe is fixed automatically, and a report says what was found and done. Reports are never edited afterwards.

**Why this priority**: it turns "eventually consistent" into "provably consistent" (note 06/02 §3.5, §5).

**Independent Test**: seed links and a fake provider with each kind of drift; run the reconcile message; assert the classification counts, the fixes and the stored report.

**Acceptance Scenarios**:

1. **AS-61** (classification) — **Given** 8 links and a provider listing where: 3 match, 1 variant is missing at the provider, 1 provider variant has no link, 1 variant changed at the provider with an `updatedAt` older than the watermark (a missed update), 1 variant has `syncedStock: 6`, provider `6` and local `4` (a lost stock event), **When** the reconcile message runs, **Then** the report counts are `{linked: 8, remote: 8, matched: 3, missingAtProvider: 1, missingLocally: 1, contentDrift: 1, stockDrift: 1, autoFixed: 4, needsReview: 0}`; the missing-locally variant is queued for a normal pull (not applied inline), the content drift is applied through the normal inbound path, the stock drift is fixed by pushing `4` (exactly one side differs from the base: AS-45), the deletion is handled per AS-62; a drift where both sides differ from the base is merged by the same rule as live sync (AS-37) and, if it cannot be, becomes a conflict (AS-38); the local quantities are read with one batch call to the catalog's query, never one call per link.
2. **AS-62** (deletion check) — **Given** a variant absent from the provider's listing, **When** reconciliation handles it, **Then** it asks the provider for that variant directly: a `404` confirms and the link becomes `DELETED_AT_PROVIDER`, local stock is lowered to zero by one stock command (operation `sync:<I>:<digest>`, reason `sync-deleted`), the finding `missing_at_provider` is reported and the product is **not** archived or deleted; a second run applies nothing more; if the provider returns the variant, the finding is `list_inconsistent` and nothing is changed; a variant that is relisted later (active again) returns the link to `ACTIVE`, and its stock is merged from base `0` (AS-45).
3. **AS-63** (mass-deletion guard) — **Given** 100 links and a listing that returns only 3 of them (a partial or failed listing), **When** reconciliation runs, **Then** no link or product is changed, the run ends `aborted_mass_delete` (guard: at least 10 links missing and more than 20% of all), one `integration_attention_required {reason: "reconcile_mass_delete"}` event is written; **Given** a listing that fails midway (a page returns `500` after retries), **Then** the run ends `failed`, nothing is deleted (no set difference is ever computed from a partial listing).
4. **AS-64** (immutable reports, adjustments) — **Given** a finished reconciliation run `R1` with its report, **When** the store is asked to change any of its fields (a direct update by a fixture), **Then** it refuses; **When** the next run `R2` finds that an item flagged in `R1` is now fixed or still open, **Then** `R2`'s report lists it with `previousRunId: R1` and its outcome (`fixed`, `still_open`), and `R1`'s stored report is byte-for-byte unchanged; a run in progress is the only one that can be updated.
5. **AS-65** (report routes) — **Given** finished runs, **When** a member with `integrations.manage` calls `GET /shops/S/integrations/I/reconciliations?limit&cursor` or `…/reconciliations/R`, **Then** `200` pages / `reconciliationReportSchema` (counts plus up to 1,000 findings; further findings are only counted, with `truncated: true`); `POST …/reconcile` enqueues one on-demand run (`202 {enqueued}`; one per hour per integration, otherwise `429`); a run on a `PAUSED` or `DISCONNECTED` integration is `409`; another shop's integration or run is `404`.
6. **AS-66** (lag alert) — **Given** an `ACTIVE` integration whose watermark is more than 30 minutes behind the frozen now, **When** the scheduled job evaluates it, **Then** one `integration_attention_required {reason: "sync_lag"}` event is written and the lag gauge shows the seconds; evaluating again while still lagging writes nothing; once a run succeeds (lag below 30 minutes) and the lag later recurs, one new event is written.

A suspended shop stops syncing, an offboarding shop pauses and a deleted shop leaves nothing behind. Old operational data expires. Every important change is announced once. Secrets stay secret. The code respects the ownership boundaries.

**Why this priority**: lifecycle completeness and the constitution's gates; not needed for the first sync, needed before it is trusted.

**Independent Test**: publish the tenancy events with the real consumer framework; run the retention job with a frozen clock; scrape logs, metrics and the outbox; run the ownership check.

**Acceptance Scenarios**:

1. **AS-73** (shop not active) — **Given** a shop that is not `ACTIVE` (the tenancy query says so), **When** its integration's run starts, **Then** it ends `skipped_shop_not_active` with no provider call and no failure counted; **Given** the shop is suspended between the start and the first catalog write (the catalog throws `ShopNotActiveError`), **Then** the run ends `skipped_shop_not_active` and the page is retried later; when the shop is `ACTIVE` again the next scheduled pull continues from the checkpoint.

### Edge Cases

- **Echo of our own write** returns with a newer `updatedAt`: stock equals `syncedStock` and the digest is equal, so nothing is applied and nothing is pushed (AS-36, AS-40).
- **Overlap re-reads** are not duplicates: they are cheap `unchanged` results (AS-16).
- **Webhook payloads are never trusted**: the handler fetches the current state; a delayed or reordered webhook cannot apply an old value (AS-22, AS-26).
- **Provider clock skew and late commits**: the overlap covers 5 minutes; a missed older update is caught by the nightly content-drift check (AS-61); a future timestamp cannot push the watermark past now (AS-17).
- **Provider variants and multiple locations**: stock is the quantity at the one location chosen at connect time (the primary location); products with several variants become several marketplace products (AS-12, AS-14).
- **A seller edits a provider-owned field on a linked product** in the marketplace: it is not pushed (FR-040) and is overwritten at the provider's next change of that variant; this is intended and documented, not a conflict.
- **A seller archives a linked product** in the marketplace: sync continues (stock keeps flowing, positive deltas are accepted by the catalog, negative ones on an archived product are refused as `unavailable`: such an inbound delta is left unapplied and retried; it is reported in the next reconciliation as `stock_drift`).
- **Two Shopify stores of one shop** are two integrations with disjoint link sets (`externalSku` embeds the integration ID).
- **Store disconnected then reconnected** keeps its links, so products are not duplicated (AS-09).
- **A provider re-sends a webhook after we answered 200**: deduplicated (AS-28).
- **An integration deleted during a run**: the run stops at the next checkpoint and writes nothing (AS-69, AS-75).
- **The catalog refuses a delta** (`insufficient_stock` on an inbound merge): that is the oversold case (AS-38); `not_found` (a product removed outside this capability) marks the link `IGNORED` (AS-46).

## Requirements *(mandatory)*

### Functional Requirements

**Connection and credentials**

- **FR-001**: A shop's `integrations.manage` members can connect Shopify only through the OAuth install flow whose `state` is single-use, bound to shop, member and domain, stored only as a digest and valid 10 minutes; the callback verifies the provider's HMAC and timestamp and the state before any token exchange and answers every verification failure with one identical response (AS-01–AS-05).
- **FR-002**: WooCommerce is connected with API keys that are verified with a live call before anything is stored; a per-integration webhook secret is generated by the platform (AS-06).
- **FR-003**: Only `shopify` and `woocommerce` are accepted providers. No test-only provider exists in the production wiring or the public contracts (AS-80).
- **FR-004**: Every outbound address (store URL, redirects, `Link` targets, webhook registration) passes an SSRF guard: HTTPS only, port 443, no IP literals or user-info, no loopback/private/link-local/metadata/unique-local/multicast targets, re-resolved and re-checked on every call and redirect (AS-07, AS-54).
- **FR-005**: The store's currency must equal the platform currency at connect time; otherwise nothing is created (AS-08).
- **FR-006**: One store belongs to at most one non-`DISCONNECTED` integration platform-wide and a shop has at most 5; both rules are enforced by the store, so concurrent connects cannot exceed them (AS-10, AS-11).
- **FR-007**: Credentials are sealed at rest with a context bound to the integration, never returned, logged, evented or stored in plaintext; they are erased on disconnect, uninstall and shop purge (AS-69, AS-75, AS-79).
- **FR-008**: The integration status is a closed machine `ACTIVE | PAUSED | NEEDS_REAUTH | DISCONNECTED` with a closed transition table; every transition is a conditional update plus a history row in one transaction and an outbox event; illegal moves answer `409 invalid_integration_transition` (AS-60, AS-68, AS-69).
- **FR-009**: Provider auth failure leads to at most one token refresh (single-flight across workers) and then to `NEEDS_REAUTH` with one alert (AS-60).

**Incremental pull and queues**

- **FR-010**: Pulls ask the provider for changes since `watermark − 5 minutes`, read pages in order, store a page checkpoint after each page, and move the watermark to the largest fetched `updatedAt` (clamped to now) only after the whole pass (AS-16, AS-17).
- **FR-011**: At most one run per integration executes at a time (a renewable lease with fencing on every checkpoint and watermark write); a second claim ends `skipped_locked` (AS-18).
- **FR-012**: Backfills (first pull, reconnect, requested rebuild) run on a queue separate from incremental pulls and webhook work, with their own concurrency; neither starves the other (AS-21).
- **FR-013**: A run yields at its page or time budget with a checkpoint and one continuation message, so a large store cannot hold a worker indefinitely or starve smaller shops (AS-19).
- **FR-014**: A scheduled job enqueues incremental pulls for integrations that are `ACTIVE`, due, in an `ACTIVE` shop and not breaker-open, with a deterministic jitter, never twice for one due time; it is the guarantee that webhooks are only an optimisation (AS-20).
- **FR-015**: Queue messages are validated before use; replays are idempotent; poison messages go to the dead-letter queue; messages for unknown, `DISCONNECTED`, `PAUSED` or `NEEDS_REAUTH` integrations do nothing (AS-25).
- **FR-016**: An older snapshot of a variant never overwrites a newer applied one (compared on the provider's `updatedAt` and the content digest), and concurrent applies of one variant produce exactly one effect (AS-22, AS-23).
- **FR-017**: A crash at any point between the catalog write and the link write is recoverable by re-running, with no duplicate product and no double-applied stock (AS-24, AS-42).

**Anti-corruption layer and catalog writes**

- **FR-020**: Provider payloads are validated and normalised by the adapter before use; the raw payload (capped at 256 KiB, otherwise quarantined `payload_too_large`) is kept per link; a response envelope that does not validate fails the page without quarantining or storing anything (AS-14, AS-54).
- **FR-021**: One provider variant is one marketplace product; its identity is `(integrationId, externalId)`; its catalog identity is the deterministic `externalSku` `<provider>:<integrationId>:<externalId>` (AS-12).
- **FR-022**: Money is parsed from decimal strings into integer minor units with the platform currency's exponent and never touches floating point (AS-15).
- **FR-023**: Products are created and updated only through the catalog's import command with `source` `shopify` or `woocommerce`, in batches of at most 500; initial stock is passed only when no link exists; per-item refusals are quarantined (AS-12, AS-51).
- **FR-024**: Draft or archived provider products, and variants the platform cannot sell safely (untracked inventory, no inventory level), are not imported; linked ones lose their stock without being deleted; the reason is visible in quarantine or on the link (AS-14, AS-52, AS-62).

**Webhooks**

- **FR-030**: The webhook route verifies the provider's signature over the raw bytes in constant time, rejects timestamps older than 5 minutes where the provider supplies one, deduplicates on the provider's delivery ID, acknowledges before processing, and enqueues thin work whose handler fetches the current state (AS-26–AS-29).
- **FR-031**: Unknown, malformed and disconnected integration IDs answer exactly like a bad signature (AS-27); paused and re-auth integrations acknowledge and do nothing (AS-34).
- **FR-032**: A failed enqueue is `503` with no receipt recorded (AS-31); the route is size- and rate-limited with a fail-open limiter (AS-32).
- **FR-033**: `products/delete` and `app/uninstalled` are handled as AS-30 describes, always confirming deletions with the provider before acting.

**Stock**

- **FR-040**: Field ownership: provider-owned fields (title, description, price, category, brand, tags) flow only inbound; stock is the one shared field. Local edits of provider-owned fields are never pushed.
- **FR-041**: Each link records the stock both sides last agreed on (`syncedStock`). Inbound and outbound changes are decided by one pure three-way merge of (base, local, remote); results are clamped to `[0, 1,000,000,000]`; a clamp or a negative merge opens a conflict (AS-35–AS-38, AS-45).
- **FR-042**: Inbound stock is applied to the catalog only as a delta through its stock command with a deterministic operation ID and reason `sync-inbound`/`sync-deleted`; the catalog's refusal to go below zero is the oversell detector (AS-35, AS-38, AS-42).
- **FR-043**: Outbound stock is an absolute, idempotent write that is conditional on the provider still holding the quantity we last saw, where the provider supports a precondition; on a refused precondition the write is abandoned and the merge re-runs from fresh state (AS-37).
- **FR-044**: Echoes are suppressed by comparing with `syncedStock` and the content digest, by ignoring our own inbound apply's product event, by version guards on product events, by coalescing, and by ignoring snapshots fetched before our latest write (AS-36, AS-40, AS-41, AS-44).
- **FR-045**: The consumer of the catalog's product events reads quantities from the event copy (IX.8) and never from the product table; it ignores unlinked, sandbox, non-quantity, stale and duplicate events and dead-letters invalid ones (AS-40).
- **FR-046**: A conflict queue holds oversell and range conflicts with the numbers involved; members list and dismiss them; conflicts never change stock by themselves (AS-38, AS-39).

**Quarantine and resilience**

- **FR-050**: Items that cannot be understood or accepted are quarantined with a reason code, message, payload and counters, deduplicated per integration and item, auto-resolved when fixed, reviewable and dismissable; the sync always continues (AS-47–AS-51).
- **FR-051**: More than 1,000 quarantined items in one run halts the run without advancing the watermark and raises one alert (AS-53).
- **FR-052**: Every call to a provider goes through one token bucket per credential shared by all workers and instances; `Retry-After` pauses that bucket for everyone; bounded retries with exponential backoff and full jitter, at most 3 attempts, on transient failures of idempotent operations only; a 15-second timeout; a per-integration circuit breaker (5 failures, 5 minutes, one probe) (AS-55–AS-59).
- **FR-053**: When the limiter store is unavailable the sync fails closed and yields; webhook receipt fails open (AS-55, AS-32).

**Reconciliation**

- **FR-060**: Every night, and on demand, each `ACTIVE` integration is reconciled: the full provider ID and digest listing is compared with the links; findings are classified `matched`, `missing_at_provider`, `missing_locally`, `content_drift`, `stock_drift`, `list_inconsistent`; only clearly safe fixes are applied automatically (AS-61).
- **FR-061**: Deletions are confirmed by a direct provider read, never inferred from a partial listing, and are guarded by the mass-deletion rule (AS-62, AS-63).
- **FR-062**: A finished reconciliation report is immutable; later corrections appear in the current run referencing the earlier one (AS-64).
- **FR-063**: Sync lag beyond 30 minutes raises one alert per episode (AS-66).

**Management, lifecycle, operations**

- **FR-070**: All routes need `integrations.manage` (owner, admin); lookups put the shop and integration IDs together in the predicate, so cross-tenant access is indistinguishable from not found (AS-71).
- **FR-071**: Lists use keyset pagination with an opaque, tamper-evident cursor and a deterministic order ending in the ID (AS-39, AS-50, AS-65, AS-67).
- **FR-072**: Pause, resume, disconnect and sync-now are sub-resource actions with the rules of AS-68–AS-70; `GET` never changes state.
- **FR-073**: Errors are problem+json with stable codes: `validation_failed` 400, `invalid_cursor` 400, `invalid_oauth_callback` 400, `permission_denied` 403, `shop_suspended` 403, `shop_not_found` 404, `integration_not_found` 404, `quarantine_not_found` 404, `conflict_not_found` 404, `report_not_found` 404, `invalid_integration_transition` 409, `quarantine_not_open` 409, `conflict_not_open` 409, `integration_limit_reached` 409, `store_already_connected` 409, `shop_offboarding` 409, `invalid_store_url` 422, `provider_credentials_rejected` 422, `currency_mismatch` 422, `invalid_webhook_signature` 401, `webhook_stale` 401, `rate_limited` 429, `provider_unavailable` 503.
- **FR-080**: Shop lifecycle: a non-`ACTIVE` shop does not sync; offboarding pauses and cancelled-offboarding resumes only its own pauses; shop deletion purges all of the shop's data in resumable batches (AS-73–AS-75).
- **FR-081**: Operational data has the retention of AS-76; open items older than 90 days are closed, not silently deleted.
- **FR-082**: Lifecycle changes are announced once on `catalog-sync.events` through the outbox in the same transaction (AS-77).
- **FR-090**: Consumers (tenancy events, product events, queue messages) validate payloads, are idempotent and dead-letter poison messages; each documents its mechanism (inbox record for events, version guards for product events, lease and conditional state for queue work).
- **FR-091**: No network call happens inside a database transaction (provider calls, queue sends, catalog commands are outside; outbox rows are inside).
- **FR-100**: Every statement and model of this capability touches only tables it owns; cross-domain data is obtained by R1 calls (catalog commands and queries, tenancy queries); the capability never joins or reads product, shop or membership tables (AS-80).
- **FR-101**: Configuration is validated at startup: Shopify app credentials (mandatory in production), the pinned provider API version, public base URLs, queue names, limits listed in Assumptions.
- **FR-102**: Metrics: `catalog_sync_runs_total{provider,kind,outcome}`, `catalog_sync_lag_seconds{provider}` (gauge, per integration bucketed), `catalog_sync_items_total{provider,result}`, `catalog_sync_provider_calls_total{provider,status}`, `catalog_sync_provider_429_total{provider}`, `catalog_sync_echo_suppressed_total`, `catalog_sync_quarantine_open`, `catalog_sync_conflicts_open`, `catalog_sync_webhooks_total{provider,result}`, `catalog_sync_breaker_open{provider}`, `catalog_sync_reconcile_findings_total{kind}`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A store with 50,000 variants is fully visible in the marketplace within 15 minutes of connecting, while a small shop's day-to-day sync running at the same time is never delayed by more than one minute.
- **SC-002**: A change at the provider is visible in the marketplace within 30 seconds at the 99th percentile when webhooks arrive, and within 6 minutes in 100% of cases when every webhook is lost.
- **SC-003**: A marketplace stock change reaches the provider within 30 seconds at the 99th percentile; after 1,000 randomly interleaved stock changes on both sides, both systems end with identical stock, with no more provider writes than local changes (no ping-pong) and no sale lost except those reported as conflicts.
- **SC-004**: Killing the worker at 50 random points during a 20,000-variant sync and restarting it each time ends with products, links and counters identical to an uninterrupted run in 100% of runs.
- **SC-005**: One malformed item among 100,000 never reduces the number of applied good items; 100% of malformed items appear in quarantine with a reason, exactly once each however many times they are re-read.
- **SC-006**: Under a provider limit of N calls per window, the provider never sees more than N calls in any window from this platform, for any number of workers, and 0 requests are rejected with `429` in normal operation.
- **SC-007**: 100% of forged, stale and duplicate webhooks (matrix of the three) have zero effect on any product, stock value or queue, and every valid webhook is acknowledged before any provider call is made.
- **SC-008**: In a matrix over every route against every role of the same shop, every role of another shop and no credentials, 100% of cross-shop attempts answer the identical "not found" and change nothing.
- **SC-009**: Nightly reconciliation detects 100% of seeded drift (deleted, missed update, lost stock event, unknown remote item) and auto-fixes only the classes listed as safe; a listing that returns under 80% of known items deletes nothing.
- **SC-010**: A seller connects a Shopify store and sees the first products within 5 minutes of returning to the dashboard (benchmark with a 1,000-variant store).
- **SC-011**: Delivering any webhook, queue message, product event or tenancy event a second time changes nothing in 100% of the cases tested; two simultaneous connects, pauses, dismissals or claims always yield exactly one winner per rule.
- **SC-012**: A full-database scan, every log line, every metric label and every API, event and error body of the test run contains 0 occurrences of any provider token or secret.
- **SC-013**: The ownership check reports 0 cross-domain queries, models, associations or foreign keys for this capability's files and 0 writes of the product table from this domain.

## Assumptions

- Decisions behind every default are in `questions.md`; the ones that change behaviour that exists today are tagged `[BREAKING]` there.
- **Providers**: Shopify Admin REST at a pinned API version (configuration), cursor pagination through the `Link` header, `updated_at_min` for increments, inventory levels for stock; WooCommerce REST v3 with `modified_after`, page-number pagination (the adapter hides it behind the same port), per-integration webhook secret. Both adapters implement one provider port; the sync engine never sees a provider shape.
- **Variants**: one variant → one product; the product's stock is the quantity at the one location chosen at connect time (the provider's primary location). Multi-location aggregation is not offered.
- **One platform currency** (S05); a store in another currency cannot be connected. No currency conversion.
- **Field ownership**: the provider owns catalog fields; the marketplace owns nothing but shares stock. Product images, media and variants as a concept are not synced in this release.
- **Not-sellable items** (draft/archived at the provider, inventory not tracked, no inventory level) are not imported; this is shown in quarantine or on the link rather than guessed at.
- **Deletion at the provider** means "zero stock and mark the link"; this capability never archives or deletes marketplace products (it would need an actor and is the seller's decision). The reconciliation report lists them so the seller can archive them.
- **Archived local products** keep syncing; a refused negative inbound delta is retried and shows as drift.
- **Locally deleted products** are ignored by sync from then on (never resurrected).
- **Webhook timestamps**: Shopify supplies `X-Shopify-Triggered-At`; a webhook older than 5 minutes is rejected and the scheduled pull covers it. WooCommerce supplies none; dedupe by delivery ID and a fresh fetch cover it.
- **Time budgets and numbers** are configuration, not contract: overlap 5 min, pull interval 5 min plus up to 60 s jitter, run budget 4 min (incremental) / 12 min (backfill) or 40 pages, provider call timeout 15 s, retries 3 (base 500 ms, cap 8 s), `Retry-After` inline limit 60 s (continuation cap 15 min), breaker 5 failures / 5 min, quarantine halt 1,000 per run, raw payload cap 256 KiB, webhook body cap 1 MiB, lag alert 30 min, mass-deletion guard 10 links and 20%, integrations per shop 5, install state 10 min, sync-now 1 per minute, backfill and reconcile on demand 1 per hour, bucket per credential from the provider's documented limit (Shopify 40 per 20 s as `integrations.shopify`, WooCommerce 20 burst at 5 per second as `integrations.woocommerce`), retention 7 / 30 / 90 days (AS-76), lease 5 min renewed each 60 s.
- **No polling UI contract**: W04 polls `GET …/integrations/:id`; no live channel is introduced (a progress push can be added later without changing this contract).
- **Conflict resolution** is by the seller changing stock through the normal product routes (which then flows outbound) and dismissing the conflict; no resolve-with-value route exists.
- **Idempotency-Key** is not used on these routes: connect is naturally idempotent per store, and pause/resume/disconnect/dismiss are conditional state changes (V.6 applies to money- and order-creating routes only).
- **Validation errors** are `400 validation_failed`, as in the sibling specs of S03, S05 and S06.
- **Tests** replace only system edges: third-party HTTP (a fake Shopify and a fake WooCommerce server speaking the real shapes, with injectable delays, 429s, 401s and drops), DNS resolution (for the SSRF cases), the clock; everything else is real.
