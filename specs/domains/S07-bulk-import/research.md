## Decisions

**D-01 Spec first, contracts second.** The living-spec page `docs/spec/capabilities/S07-bulk-import.md` does not exist (only S08's page names the domain). It is created before code, following S08's front matter (`scope: libs/domains/catalog-sync/**` is shared with S08/S09, so S07's scope lists only the import files and `packages/contracts/src/catalog-sync/imports.ts`). Every rule carries `[proof: S07 AS-nn]` and `[code: …#Symbol]`; `python3 scripts/livespec/check.py` must pass. No `*.reviewed.json` is created or edited.

**D-02 Lease and fencing.** `ImportJob.leaseHolder` (a fresh UUID per run, never the host name) and `leaseExpiresAt`. Claim: one conditional `UPDATE … SET leaseHolder, leaseExpiresAt = :now+5min WHERE id AND status IN ('UPLOADED','SCANNING','PROCESSING') AND (leaseHolder IS NULL OR leaseExpiresAt <= :now)`; zero rows ⇒ another runner (return, ack). Renewal every 60 s: `… WHERE leaseHolder = :me AND leaseExpiresAt > :now`. Every checkpoint commit has the same fence in its `WHERE`; zero rows ⇒ `LeaseLostError`, the runner aborts without touching counters (AS-37). `:now` is the injected `Clock` value passed as a bind parameter, never `now()` in SQL (so frozen-clock tests and clock jumps behave: spec Edge case). Release on shutdown/finish sets both columns NULL (conditional on holder).

**D-03 One running import per shop, in creation order.** Store-enforced: partial unique index on `("shopId") WHERE status IN ('SCANNING','PROCESSING')`. The `UPLOADED→SCANNING` transition therefore fails with a unique violation when the shop already runs a job ⇒ `ShopBusy`; the consumer hands the message back with `delaySeconds = 60 ± 20%` (jitter from an injected random) and acknowledges the original (new message, fresh `receiveCount`, AS-60). Creation order: the claim also requires `NOT EXISTS` an earlier (`createdAt, id`) non-final `UPLOADED|SCANNING|PROCESSING` job of the same shop. A lease takeover of a stalled job keeps its status, so the index keeps the shop blocked until that job is final.

**D-04 Active-import cap by the store.** `ImportJob.slot SMALLINT` 1..3 and a partial unique index `("shopId","slot") WHERE status IN ('PENDING_UPLOAD','UPLOADED','SCANNING','PROCESSING')`. `start` inserts with the lowest free slot (`INSERT … SELECT` of the first free slot) and retries on `unique_violation` up to 3 times, then answers `409 too_many_active_imports` (AS-61; five concurrent starts ⇒ exactly three win). No check-then-write, no advisory lock (III.6). Final jobs leave the index automatically.

**D-05 Scanner.** Use the shared `MalwareScanner` port (`AntivirusModule`); extend `scan` options additively with `inactivityMs` (default none) and keep `timeoutMs` as the total deadline; the clamd adapter destroys the socket on every path (extend its spec for the stalled-quiet-socket and size-limit-reply cases of AS-25). Import config: `totalMs = 30 min`, `inactivityMs = 60 s`. Fail-closed mapping: `ScannerUnavailableError` and any unexpected reply ⇒ delivery fails (stay `SCANNING`), third delivery ⇒ `FAILED scan_unavailable`; `{clean:false}` ⇒ `FAILED malware_detected` (signature to logs only). Production without a scanner already fails startup (media rule); outside production, `media_scanner_disabled` ⇒ `DisabledMalwareScanner`, job `scan: 'skipped'` with one warning per job (the runner asks the port whether it is the disabled one through a `kind` property added additively: `MalwareScanner.mode: 'active' | 'disabled'`). Alternative rejected: keep a domain-private clamd adapter (questions.md LOCAL line) — superseded by the S29 follow-up.

**D-06 Pipeline.** One `stream.pipeline` over: storage `getStream(key, {start: nextByteOffset})` → parse stage (CSV via `csv-parse` with explicit `columns` from the stored header on resume; JSONL via a Buffer line splitter) → object-mode transform producing `{row, byteEnd, data}` → async-iterator batcher/writer in `application/` driving one batch at a time. Backpressure bound AS-43 (500 + 16): batcher accumulates ≤ 500 records and does not pull while a batch is being written (`for await` over the readable with `highWaterMark: 16` objects). `AbortSignal` is passed to `pipeline`; on any error or abort every stage is destroyed (observed `destroyed` in AS-42). Record limit 1 MiB: JSONL line splitter drops an oversized line (`row_too_large`) and resynchronises at the next `\n`; for CSV, `csv-parse` `max_record_size: 1 MiB` ⇒ `malformed_file` with the record's start ordinal. The pure parts (splitter, sniff, batcher, report writer) live in `domain/`; the Node stream wiring is `infra/import-parse-stage.ts` (domain may not import `node:stream`? I.3 forbids only Nest/ORM/clients, but the stage is infra to keep `domain/` free of I/O types).

**D-07 Byte offsets.** The checkpoint stores `nextByteOffset` = byte where the next record starts. For JSONL the splitter counts exactly. For CSV, `csv-parse` with `info: true` reports `info.bytes` (cumulative bytes consumed); it must be verified with a property test (generate CSV with BOM/CRLF/quoted newlines/multibyte; for every record `i`, parsing from `offset_i` with the stored header must yield exactly records `i+1…`). If `info.bytes` proves unreliable with a BOM or `trim`, fall back to the project's own 120-line RFC 4180 tokenizer (`domain/import-csv.ts`). This is the one genuinely uncertain piece (R-01); it is the first task of step 2 and gates the rest of the pipeline.

**D-08 Header and format are stored once.** After the sniff and first record, `format`, `headerColumns` (normalised: trimmed, lower-cased), `ignoredColumns` are committed with the first checkpoint (or, for a file with a valid header but no rows, with the terminal transition). Resume never re-reads the header or re-sniffs.

**D-09 Upload parts.** Use `startMultipartUpload` + `presignUploadPart(key, uploadId, n, exactLength, 6 h)`: the signature covers the part length, so a client cannot upload more bytes than declared; the last part is `size − (n−1)·64 MiB`. `GET …/upload` re-signs only missing parts (from `listParts`). Consequence: a *short* object cannot occur through honest signed URLs, so AS-09 (`size_mismatch`) is exercised by the e2e altering the declared `sizeBytes` in the row (or uploading through the storage port directly); the complete-time `head` size check stays as defence in depth.

**D-10 Complete = transition first.** Order: (1) read job by `(id, shopId)`; non-`PENDING_UPLOAD` ⇒ replay `200` (UPLOADED…DONE/FAILED) or `409 import_not_completable` (CANCELLED/EXPIRED); (2) validate the body against `listParts` (every part 1..n once, in order, ETag equal) ⇒ `422 invalid_parts`, nothing changes; (3) conditional transition `PENDING_UPLOAD→UPLOADED` + history in one transaction — the store picks one winner (AS-11, AS-57); (4) winner calls `completeMultipartUpload` then `head`; size ≠ declared ⇒ transition `UPLOADED→FAILED size_mismatch` (+finished event), delete object, answer `422 size_mismatch` (AS-09); (5) enqueue `{importId}` after commit. A transient storage failure in (4) transitions `UPLOADED→FAILED internal_error` and answers `503` (documented risk R-02: the seller starts again; the alternative, a hidden `COMPLETING` state, would break the closed 13-pair table of AS-58). A crash between (3) and (5) is covered by the recovery job (AS-40). The loser of a complete/complete race gets the winner's status body with `200`.

**D-11 Start sequence.** (1) `limiter.check('catalog-sync.import-start.shop', shopId)` fail-closed (`429` with `Retry-After`; limiter down ⇒ `503`), called in code so it holds in every app (S50: `@RateLimit` is metadata only); (2) one transaction: insert job (slot, server-generated key `imports/<shopId>/<importId>/source`, sanitised name) + first history row; (3) outside any transaction `startMultipartUpload`, then conditional `UPDATE uploadHandle WHERE status='PENDING_UPLOAD' AND uploadHandle IS NULL`; (4) sign `partCount` URLs. If (3) fails, compensate `PENDING_UPLOAD→CANCELLED` (reason `upload_init_failed`) and answer `503`; a crash before (3) leaves a handle-less `PENDING_UPLOAD` that the expiry job cleans after 24 h (it tolerates a null handle and an unknown upload — L-016). The Idempotency interceptor wraps the whole route (replay returns the stored body; `GET …/upload` re-signs, AS-06). Rate-limit consumption happens after the idempotency lookup so a replay does not spend a token (interceptor runs before the handler).

**D-12 Controller shape (II.1).** Services return a value object `{ job, created }` for `complete` and `{ job }` for the rest; the controller calls the service once and sets `Location` / status through a small route-level response interceptor `ImportCompleteResponse` that maps `created ? 202 + Location : 200`. This keeps the controller free of state branching. Alternative rejected: `@Res({passthrough:true})` with an `if` in the controller (fails II.1).

**D-13 Error report storage.** One object per batch with problems: `imports/<shopId>/<importId>/report/<batch 8-digit>.csv`, written with `put` (replace on redo, so a redone batch never duplicates lines — AS-49). The header line is added when serving. `GET …/error-report` needs one URL for the whole report: at finish the runner concatenates parts server-side into `…/report/errors.csv` through a streamed `put` (`inactivityTimeoutMs`) and deletes the parts (the final concatenation is idempotent: if `errors.csv` exists and no parts remain, nothing to do; a crash mid-concatenation re-concatenates from the parts, which are deleted only after the object is stored). For `FAILED`/`CANCELLED` jobs the same finalisation runs on the way out. Report rows and `errorReportRows` are counted from the lines written (committed with the batch counters). Lines are CSV-escaped and formula-guarded (`'` prefix for `=+-@\t\r`). The sanitised download name `errors-<name>.csv` (≤ 120) is passed to `presignGet`.

**D-14 Routes and guards.** `ShopScoped('products.write'|'products.read')` as today (guard supplies the identical not-found for non-members, the shop status gate, and AS-53 roles). No `@RateLimit` decorator and no `Firewall` options are needed on import routes; nothing to migrate from `throttle`/`skipThrottle`. The start route stays non-"sensitive": it changes no credential or session. The boundary e2e greps the import files to prove no `throttle`/`skipThrottle`/`SessionNotRevokedGuard`.

**D-15 Status codes (S54 follow-up vs spec).** DTO/query/cursor failures are `400 validation_failed` (house `ZodPipe`); `422` remains for `invalid_parts`, `size_mismatch`, `idempotency_key_required|invalid|reuse`. Spec AS-02, AS-54 say `422 validation_failed`; recorded under Spec changes. The AS-53 line "malformed id ⇒ `400`" already agrees.

**D-16 Failure mapping and retry budget.** Domain errors carry a `failureCode`: `unsupported_file_type`, `invalid_header`, `malformed_file`, `too_many_errors`, `shop_not_active` (S05 `ShopNotActiveError`), `source_missing` (storage 404), `malware_detected` ⇒ terminal at once (no retry, ack). Retryable (`ScannerUnavailableError`, DB timeout, storage 5xx, lease contention): rethrow; if `receiveCount >= 3` the runner records the terminal failure (`scan_unavailable` or `internal_error`) with the finished event and rethrows so the queue dead-letters. No in-process retry loop (one layer, IV.6). `failure.message` is a fixed table keyed by code; the raw error goes to logs only.

**D-17 Terminal transition + event + report finalisation.** One `TransactionRunner.run`: conditional status update (from the expected state, lease-fenced when a runner), history row, `outbox.append(catalog_sync.import_finished)`, lease release. Storage side effects (delete source, concatenate/delete report parts, abort upload) happen **after** commit and are idempotent; the retention/purge job cleans any leftover. A fault on the outbox insert rolls the transition back (AS-64). Realtime `done|failed|cancelled` is published after commit with `replay: true`; `progress` with `replay: false`, after the checkpoint commit.

**D-18 Realtime policy.** `ImportJobTopicsModule` imports `TenancyModule` and defines `import` with an async policy calling `ShopAccessService.assertMember(shopId, viewer.userId, 'products.read')`. The shop id comes from the job: one primary-key read through the repository port, scoped by nothing but id (the policy decides on membership of that row's shop); `NotFound`/`Forbidden`/missing job ⇒ `false`. A removed member is refused (S03 SC-002) because membership is read at subscribe time.

**D-19 Lifecycle consumers.** `tenancy.shop_offboarding_started` ⇒ cancel the shop's non-final jobs (`PENDING_UPLOAD|UPLOADED` immediately, running via `cancelRequestedAt`), `inbox` idempotency (pattern of `TenancyOffboardingConsumer`); `tenancy.shop_deleted` ⇒ objects first (`deletePrefix imports/<shopId>/`, repeated while it returns the limit), then rows (history first), `natural` idempotency; `shop_offboarding_cancelled` ignored. Uses the same `Projector` framework and `PermanentError` for bad payloads. Both live in `CatalogImportProjectorModule`; `apps/projector` imports it and its wiring e2e (like `integrations-wiring.e2e-spec.ts`) lists the two consumers.

**D-20 Scheduled jobs.** `catalog-sync.recover-stalled-imports` (`0 * * * * *`), `catalog-sync.expire-pending-imports` (`0 */5 * * * *`), `catalog-sync.purge-imports` (`0 20 3 * * *`), `@JobHandler(..., {concurrency:1, fleetConcurrency:1})`, declared with `declareJobType` and `{}` payload contracts; schedules registered on bootstrap catching `InvalidScheduleError`. Recovery re-enqueues with a `recoveredAt` stamp to guarantee at most once per window: `UPDATE … SET "lastEnqueuedAt" = :now WHERE (… stalled …) AND ("lastEnqueuedAt" IS NULL OR "lastEnqueuedAt" <= :now − 2 min) RETURNING id`, enqueue after, so two instances cannot both re-enqueue (AS-40). Purge handles ≤ 500 per run, oldest first, objects before rows.

**D-21 Rows: file rules vs S05.** `domain/import-row.ts` keeps only structural rules: required cells present, price text `^\d{1,9}(\.\d{1,2})?$` after trim (exact integer arithmetic, `BigInt` or digit split, no floats), stock `^\d{1,7}$` ≤ 1,000,000 (empty = absent), tags split on `|`, trimmed, empties dropped. Everything else (lengths, price > 0, tag counts) is S05's. S05 rejections are passed through with `code` unchanged and `field` mapped back (`priceMinor→price`, `quantity→stock`, `externalSku→sku`). The S05 contract of a closed code list per field: the message table covers the codes S05 currently emits (read from `libs/domains/catalog/domain/product-input.ts` at task time and pinned by a unit test that fails when S05 adds a code without a message — a generic fallback still prints), per the `[CONTRACT]` line. **Sibling follow-up** recorded for S05.

**D-22 Batch write and counters.** Per batch of ≤ 500 valid rows: `ImportCatalogGateway.upsert(shopId, items)` (outside a transaction) → results mapped to created/updated/unchanged/rejected; rejected items and file-rule failures become report lines; then **one** transaction: fenced counters+checkpoint update (`rowsProcessed += batch records`, per-outcome counters, `lastRow`, `nextByteOffset`, `bytesProcessed`, `errorReportRows`, lease extension), cancel-request check, optional terminal transition when cancel requested. Report part for the batch is stored **before** the commit (idempotent key) so a committed counter always has its lines (AS-49). Progress publish after the commit.

**D-23 Failure cap.** `errorReportRows` (counter of report lines) vs `rowsFailed` (rows). The cap compares `rowsFailed` (100,000, configurable; test sets 5) at each batch boundary: when the batch that passes the cap commits, the terminal `FAILED too_many_errors` follows in the same transaction (AS-46: "report holds every failed row up to that batch exactly once").

**D-24 Metrics and logs.** A small `import-metrics.ts` registering counters/histograms on the existing registry (`rows_total{outcome}`, `jobs_total{status}`, `batch_seconds`, `scan_seconds`, `bytes_read_total`, `checkpoint_age_seconds` gauge from the repository's oldest running checkpoint, `queue_to_start_seconds`). Logs go through the Nest `Logger` with object fields `{importId, shopId, action}`; the request context adds `requestId`. A log-scrubbing unit test is not needed; the e2e (AS-68) captures log output and asserts the absence of row values, SKUs, URLs.

**D-25 Config.** Defaults live in `domain/import-limits.ts` (`resolveImportConfig(get)`), validated when the module is built (S54, same approach as `resolveSyncConfig`): batch 500 (bounded 1–500), part size 64 MiB, max size, record limit, error cap, lease/renew/recovery, caps, report link, retentions, scan deadlines, busy-shop delay. Environment keys (all optional): `IMPORT_ERROR_CAP`, `IMPORT_BUSY_DELAY_SECONDS`, `IMPORT_SCAN_*`; `USERCONTENT_ORIGIN` already exists in config; `CLAMAV_HOST`, `MEDIA_SCANNER_DISABLED` reused.

**D-26 Tests.** Nine e2e files from `test-plan.md`, plus unit specs: `import-row`, `import-sniff`, `import-batcher`, `import-status`, `error-report`, `file-name`, `import-pipeline` (infra), `import-csv-offsets` (the R-01 property test), and `fake-clamd` as the TCP fake. Contract tests: each schema parses a representative payload.
