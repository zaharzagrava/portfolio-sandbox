# Feature Specification: S07 — Bulk Catalog Import: Multipart Upload, Malware Scan, Streamed Parse, Checkpoints, Error Report (domain `catalog-sync`)

**Feature Branch**: `S07-bulk-import` (spec directory `specs/domains/S07-bulk-import`)

**Created**: 2026-10-05

**Status**: Draft

**Input**: Capability S07 of `scripts/sdd/capabilities.tsv`. Sources: `docs/showcase/sections/SD-27-bulk-catalog-import.md`, `02-Node.js/02-streams-and-backpressure.md`, `10-System-Design/08-media-and-files.md` (design 27). Pattern-map rows covered: **P0207** (streams, backpressure, `pipeline`, object-mode transform), **P0407** (async request-reply: 202 + status + live events), **P0509** (upload security: separate user-content domain, `nosniff`, attachment, malware scan, magic bytes).

## Scope

A **bulk import** lets a shop replace hand-keyed listing with a file: the seller uploads a CSV or JSON-lines catalog of up to 5 GiB (about a million products), watches it progress live, and downloads a report of the rows that were refused. This capability owns the import job, the upload handshake, the safety checks on the file, the streamed read of the file, the resumable progress record, and the error report.

In scope:

- The upload handshake: a job is created, the client sends the file straight to object storage in parts (parallel, individually retryable, resumable), then tells the API it is done. The API never carries the file's bytes.
- File safety: size and shape limits, content sniffing instead of trusting names, a malware scan before any row is read, and delivery of results as downloads from a separate user-content origin.
- Streaming parse in constant memory with backpressure, row-by-row validation, and batched writes of products **through the catalog's exported import command** (never to the product table).
- The job state machine (`PENDING_UPLOAD → UPLOADED → SCANNING → PROCESSING → DONE | FAILED`, plus `CANCELLED` and `EXPIRED`), checkpoints, resume after a crash, single-runner leases, recovery of lost work, and graceful shutdown.
- The error report (one downloadable CSV per job), status and history reads, live progress, cancel, fairness between shops, limits, retention, and the shop-lifecycle reactions (offboarding, deletion).
- The terminal import event other capabilities may react to.

Out of scope (owned elsewhere):

- Product validation rules, the product record, product events, change detection, and the `(shopId, externalSku)` uniqueness → **S05** (this capability calls `ProductImportService.upsertFromExternal` and writes no product row and no product event).
- Order export (its routes, job, and queue leave `catalog-sync`; debt D-10) → **S12**.
- Shopify/WooCommerce sync → **S08**; offline device sync → **S09** (they share the domain, not these tables or routes).
- Search indexing of imported products → **S32** (it consumes S05's product events). Product-page caching → S05/S52.
- The import screens in the seller dashboard → **W04** (calls the routes and the live channel named below).
- The generic realtime hub, rate limiter, job scheduler, outbox, consumer framework, and error filter → **S51**, **S50**, **S49**, **S53**, **S54**.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — A seller imports a catalog from a file (Priority: P1)

A seller with 40,000 products in a spreadsheet exports it as CSV, starts an import, the browser sends the file in parts directly to storage, and the shop's products appear (or are updated) without the seller keying anything. Running the same file again changes nothing.

**Why this priority**: it is the capability. Everything else protects or explains this path.

**Independent Test**: drive the real routes with a seeded shop and a member, upload through the real storage engine, run the worker entry, and read the products back through the catalog's exported services.

**Acceptance Scenarios**:

1. **AS-01** (start) — **Given** an `ACTIVE` shop `S`, a member with `products.write`, and `Idempotency-Key: k1`, **When** they `POST /shops/S/imports {fileName: "catalog.csv", sizeBytes: 200_000_000}`, **Then** `201` with `{importId, status: "PENDING_UPLOAD", partSize: 67_108_864, partCount: 3, parts: [{partNumber: 1..3, url}], uploadExpiresAt}` parsed by `importStartResponseSchema`; one job row exists for `(S, creator)` in `PENDING_UPLOAD` with a first history row; the storage key is generated by the server and contains neither the file name nor any request text; a multipart upload is open in storage; every part URL expires at `uploadExpiresAt` (6 hours after creation); no part URL contains the file name.
2. **AS-02** (start validation) — **Given** a member of `S`, **When** the body has any of: `sizeBytes` `0`, `-1`, `1.5`, `"10"`, `5_368_709_121`; `fileName` empty, 201 characters, or containing a control character; an unknown extra field; no body, **Then** each is `422 validation_failed` with `errors:[{field, code}]` naming the offending field, no job row, no storage upload, and no part URL; **When** `sizeBytes` is exactly `1` or exactly `5_368_709_120`, **Then** `201` (the boundaries are inclusive; `partCount` is `1` and `80`).
3. **AS-03** (idempotent start) — **Given** a completed `POST /shops/S/imports` with key `k1`, **When** the same body is sent again with `k1` within 24 hours, **Then** the stored status and body are returned (same `importId`), exactly one job and one open upload exist.
4. **AS-04** (start in flight) — **Given** two identical `POST /shops/S/imports` requests with the same key sent at the same moment (`Promise.all`), **Then** exactly one creates the job (`201`) and the other is `409 idempotency_in_flight`; one job row exists.
5. **AS-05** (key misuse) — **Given** key `k1` already used with `{fileName: "a.csv", sizeBytes: 10}`, **When** it is reused with `{fileName: "b.csv", sizeBytes: 10}`, **Then** `422 idempotency_key_reuse` and nothing is created; **When** a start request has no `Idempotency-Key` header, **Then** `422 idempotency_key_required`.
6. **AS-06** (resume the upload) — **Given** a `PENDING_UPLOAD` job of 3 parts of which parts 1 and 3 reached storage, **When** the creator calls `GET /shops/S/imports/J/upload`, **Then** `200 {importId, partSize, partCount: 3, uploaded: [{partNumber: 1, etag, sizeBytes}, {partNumber: 3, etag, sizeBytes}], missing: [{partNumber: 2, url}], uploadExpiresAt}` (fresh URLs only for missing parts); **Given** the job is in any other state, **Then** `409 import_not_uploadable`.
7. **AS-07** (complete = async request-reply) — **Given** a `PENDING_UPLOAD` job whose parts are all uploaded, **When** the member `POST /shops/S/imports/J/complete {parts: [{partNumber, etag}…]}`, **Then** `202` with header `Location: /api/shops/S/imports/J` and the status body (`status: "UPLOADED"`); the stored object's size equals the declared `sizeBytes`; the job is `UPLOADED` with a history row; exactly one message `{importId: J}` is on the import queue; the response does not wait for scanning or parsing.
8. **AS-08** (invalid parts) — **Given** a `PENDING_UPLOAD` job of 3 parts, **When** `complete` lists parts `[1,2]`, `[1,2,2]`, `[1,3,2]`, `[0,1,2]`, `[1,2,3,4]`, an empty list, or a part with an empty `etag`, or an ETag that storage does not recognise, **Then** each is `422 invalid_parts`; the job stays `PENDING_UPLOAD` (the client may retry), nothing is enqueued, and the stored object is not assembled.
9. **AS-09** (size mismatch) — **Given** a job declared as 200,000,000 bytes whose uploaded parts add up to 199,999,999 bytes, **When** `complete` is called with the valid parts, **Then** `422 size_mismatch`; the job is `FAILED` with `failure.code: "size_mismatch"`; the assembled object is deleted; nothing is enqueued; a `catalog_sync.import_finished` event (status `FAILED`) is written.
10. **AS-10** (complete replay) — **Given** a job already `UPLOADED` (or later), **When** `complete` is called again with any parts, **Then** `200` with the current status body, no storage call, and still exactly one queue message for the job.
11. **AS-11** (complete race) — **Given** a `PENDING_UPLOAD` job with all parts uploaded, **When** two `complete` calls arrive at the same moment (`Promise.all`), **Then** exactly one answers `202` and the other `200`; one queue message exists; the history has exactly one `PENDING_UPLOAD → UPLOADED` row.
12. **AS-12** (complete in a dead state) — **Given** a job `CANCELLED` or `EXPIRED`, **When** `complete` is called, **Then** `409 import_not_completable`, and nothing changes.
13. **AS-13** (import happy path) — **Given** an `UPLOADED` job holding a valid 1,200-row CSV for shop `S` (all products new), a clean scan, **When** the worker handles the job's message, **Then** the job passes `SCANNING` and `PROCESSING` to `DONE`; the catalog's import command was called 3 times with 500, 500 and 200 items, source `"import"`; the job shows `rowsProcessed: 1200, rowsCreated: 1200, rowsUpdated: 0, rowsUnchanged: 0, rowsFailed: 0`, `bytesProcessed` equal to the file size, `startedAt` and `finishedAt`; reading the shop's products through the catalog's exported query shows 1,200 products with `externalSku` equal to the file's `sku`, and prices in minor units; the uploaded file is deleted from storage; no error report exists; one `catalog_sync.import_finished` event is in the outbox and one `done` live event was published. (This scenario is the UI happy path: upload → progress bar → done → open the report link.)
14. **AS-14** (dialects) — **Given** a CSV with a byte-order mark, CRLF line ends, a header written ` SKU , Title ,PRICE,Category` (any case, spaces), a quoted title containing a comma, a quoted description containing a newline and doubled quotes, an extra unknown column `colour`, and a blank line, **When** imported, **Then** every record is read as the author meant, the unknown column is ignored and named in the job's `ignoredColumns: ["colour"]`, and the blank line is skipped without counting as a row; **Given** the same catalog as JSON lines (one object per line, a leading BOM allowed), **Then** the products written are identical.
15. **AS-15** (value coercion, pure) — **Given** the row-parsing rules, **When** table-driven over: price `"12.99"→1299`, `"0.1"→10`, `"19"→1900`, `" 12.99 "→1299`, `"0.00"→0` (accepted here; the catalog refuses it, AS-48), `"12.999"`, `"-5"`, `"12,99"`, `"1e3"`, `"1 299.00"`, `""`, `"abc"`, a 10-digit whole part, a JSON number `19.99`; stock `"3"→3`, `""→absent`, `"-1"`, `"1.5"`, `"1e3"`, `"abc"`, `"1000001"`; tags `"a|b| c "→["a","b","c"]` and `""→[]`, **Then** each yields the stated minor-unit value or the stated per-field error (`invalid_price`, `invalid_stock`, `missing_required`, `invalid_type`), with no floating-point arithmetic (property: for any whole `w` ≤ 999,999,999 and cents `c` in 0–99, the text `w.cc` parses to exactly `w*100+c`).
16. **AS-16** (header check) — **Given** a CSV whose header lacks `sku`, `title`, `price` or `category`, or repeats a column, **When** the job runs, **Then** it ends `FAILED` with `failure.code: "invalid_header"` and the missing or repeated column names in `failure.detail`, zero rows processed, zero calls to the catalog, and the uploaded file deleted; a header with only optional columns missing (`description`, `brand`, `stock`, `tags`) is accepted.
17. **AS-17** (re-import is idempotent) — **Given** the AS-13 file imported once, **When** the same file is uploaded as a new job and imported, **Then** the job is `DONE` with `rowsUnchanged: 1200` and `rowsCreated: 0`, the shop still has exactly 1,200 products, every product's `version` is unchanged, and the catalog emitted no further product events.
18. **AS-18** (changed rows) — **Given** the products of AS-13, **When** a second file repeats them with 3 changed prices and 2 new SKUs, **Then** `rowsUpdated: 3`, `rowsCreated: 2`, `rowsUnchanged: 1197`, the three products' `version` is +1 and their new prices are readable, and counters add up (`rowsProcessed = created + updated + unchanged + failed`).
19. **AS-19** (same SKU twice in a file) — **Given** a file where SKU `A1` appears at rows 2 and 7 with different prices, **When** imported, **Then** the product ends with row 7's price (file order wins), both rows count as processed (`rowsUpdated`/`rowsCreated` totals match what the catalog reported), no error line is written, and the two rows never travel in the same call to the catalog (the pending batch is sent first when a repeated SKU arrives; pure rule, table-driven in the unit layer).
20. **AS-20** (empty stock cell) — **Given** product `A1` with stock 5 from an earlier import, **When** a file row for `A1` has an empty `stock` cell (or the file has no `stock` column), **Then** the item carries no quantity and stock stays 5; **When** the cell is `0`, **Then** stock becomes 0.

### User Story 2 — Uploaded files are untrusted (Priority: P1)

A seller (or someone with a seller's stolen session) uploads something that is not a catalog: a renamed archive, a file with malware, a 5 GiB file of nothing, an HTML page. The system refuses it before it can do harm, and never serves an uploaded file back as part of the application.

**Why this priority**: bulk upload is the largest untrusted input the system accepts (note 05/01 §1, design 27 "Security").

**Independent Test**: upload the EICAR string, a zip renamed `.csv`, an HTML page, an unterminated quote; stop the scanner; read the download URL.

**Acceptance Scenarios**:

1. **AS-21** (clean scan) — **Given** an `UPLOADED` job and a scanner that answers "clean", **When** the worker runs, **Then** the job is `SCANNING`, then `PROCESSING`; the scan verdict `clean` and its time are recorded on the job; the whole file was streamed to the scanner without being held in memory (peak buffered bytes stay under 2 MiB).
2. **AS-22** (malware) — **Given** an `UPLOADED` job whose file the scanner reports as infected (`Eicar-Test-Signature`), **When** the worker runs, **Then** the job is `FAILED` with `failure.code: "malware_detected"` and a generic message (the signature name is in the logs and nowhere in the API); the file is deleted from storage; the catalog was never called; one `failed` live event and one `catalog_sync.import_finished` (status `FAILED`, `failureCode: "malware_detected"`) were produced.
3. **AS-23** (scanner unavailable fails closed) — **Given** an `UPLOADED` job and a scanner that refuses connections, **When** the message is delivered, **Then** the job stays `SCANNING`, no row is read, and the message is retried by the queue's redelivery; **When** the third delivery also finds the scanner down, **Then** the job is `FAILED` with `failure.code: "scan_unavailable"` (never `PROCESSING`), the file is deleted, and the message is dead-lettered with no further retries.
4. **AS-24** (scanner stalls) — **Given** a scanner that accepts the connection and then stops reading and answering for longer than the 60 s inactivity limit (frozen clock advanced), **When** the worker scans, **Then** the scan is abandoned, its connection is closed, and the delivery is treated as AS-23 (`scan_unavailable` after the third failed delivery); a scan that is still making progress is never cut off before the overall 30-minute deadline.
5. **AS-25** (scanner protocol, adapter) — **Given** a fake scanner server that speaks the real streaming protocol (command, length-prefixed chunks of at most 64 KiB, zero-length terminator), **When** the adapter scans, **Then** it returns clean for `stream: OK`, infected with the signature for `stream: <sig> FOUND`, and throws (so the job fails closed) for `INSTREAM size limit exceeded ERROR`, an empty reply, a half-written reply, and any other text; it honours the sink's backpressure (never more than one chunk in flight while the socket reports a full buffer) and destroys the socket on every exit path.
6. **AS-26** (content sniffing) — **Given** the first 4 KiB of a file, **When** classified, **Then** `jsonl` when the first non-blank byte after an optional BOM is `{`; `csv` for other UTF-8 text; **unsupported** (`failure.code: "unsupported_file_type"`, file deleted, zero rows) for any NUL byte, the signatures of zip, gzip, PDF, PNG/JPEG/GIF, ELF, Windows executable and OLE documents, UTF-16 or UTF-32 byte-order marks, and invalid UTF-8 in the sniffed window (table-driven; the unit layer proves the table, the API layer proves one disguised zip ends `FAILED`). A compressed catalog is therefore refused rather than expanded (no decompression bomb is possible).
7. **AS-27** (names are not trusted) — **Given** JSON-lines content uploaded as `catalog.csv`, and CSV content uploaded as `catalog.jsonl`, **When** imported, **Then** each is parsed by what it contains and both end `DONE`; **Given** a file name with path separators or traversal (`../../etc/passwd.csv`), **Then** the job is created, the stored key and all later keys are unaffected, and the shown name is sanitised (AS-31).
8. **AS-28** (oversize record) — **Given** a JSON-lines file with one 2 MiB line among valid lines, **When** imported, **Then** that line becomes one error row `{row, field: "", code: "row_too_large"}`, parsing continues at the next line, and the others import; **Given** a CSV with an unterminated quote that would swallow the rest of the file, **When** a record passes 1 MiB, **Then** the job is `FAILED` with `failure.code: "malformed_file"` and the row ordinal where the record started, memory stays flat (the oversized record is never fully buffered), and batches already committed are kept.
9. **AS-29** (delivery of the report) — **Given** a `DONE` job with an error report, **When** the creator calls `GET /shops/S/imports/J/error-report`, **Then** `200 {url, expiresAt, rows}` parsed by `importErrorReportSchema`, where `url` points at the **user-content origin** (a different site from the application's origin), expires after 10 minutes, and instructs the storage to answer with `Content-Disposition: attachment; filename="errors-<sanitised name>.csv"` and `Content-Type: text/csv; charset=utf-8`; no route anywhere returns a link to the uploaded source file; the user-content origin answers every object with `X-Content-Type-Options: nosniff` (an operations artifact, proven by its own test, not by this API).
10. **AS-30** (spreadsheet formula injection, pure) — **Given** an error line whose echoed values begin with `=`, `+`, `-`, `@`, a tab, or a carriage return (e.g. sku `=HYPERLINK("http://x","y")`), **When** the report line is written, **Then** the cell is written with a leading `'` so that no spreadsheet application evaluates it; values that merely contain those characters later are unchanged; quotes, commas and newlines in values are CSV-escaped (round-trip property: parsing the written report gives back the original values, apart from the guard).
11. **AS-31** (display names, pure) — **Given** a client file name, **When** it is stored for display and used in the download name, **Then** control characters, path separators, quotes and anything beyond 120 characters are removed or cut, an empty result becomes `catalog`, and the download header can never contain a line break or a second header (table-driven, including `"a\r\nSet-Cookie: x"`, `"..\\..\\x.csv"`, a 300-character name and a name of only dots).
12. **AS-32** (scanner is mandatory in production) — **Given** the production environment and no scanner configured, **When** the application starts, **Then** startup fails with a configuration error naming the setting; **Given** a non-production environment with scanning explicitly disabled, **Then** startup succeeds, jobs record `scan: "skipped"`, and a warning is logged once per job.

### User Story 3 — A 5 GiB import survives crashes, restarts and doubled workers (Priority: P1)

A worker dies halfway through a 3 GiB file. Another picks the job up where it stopped, nothing is written twice, no row is lost, and the seller's progress bar keeps its place.

**Why this priority**: at this size a restart is certain, not rare (design 27 "checkpointing for very long jobs", "idempotent processing per upload ID", "visibility timeout > processing time or heartbeat").

**Independent Test**: stop the worker at a chosen batch (shutdown signal and a killed lease), restart, compare the stored state with a clean run of the same file.

**Acceptance Scenarios**:

1. **AS-33** (checkpoint per batch) — **Given** a 3,000-row file (six batches of 500), **When** processing is stopped right after batch 3 commits, **Then** the job is still `PROCESSING` and stores, committed together as one unit with that batch's counters: `rowsProcessed: 1500`, `nextByteOffset` (the byte where record 1,501 starts), `lastRow: 1500`, the header columns and the detected format; a progress event `{processed, failed, bytesProcessed, sizeBytes}` was published after the commit, never before.
2. **AS-34** (resume) — **Given** the job of AS-33, **When** the message is redelivered to a worker, **Then** the worker reads the file starting at `nextByteOffset` (the storage call asks for that range, not the whole file) and does not re-scan; the catalog is never sent a row with `row ≤ 1500` in this run; the final state has `rowsProcessed: 3000`, the same counters and the same products as an uninterrupted run, and `bytesProcessed` equals the file size.
3. **AS-35** (crash between write and checkpoint) — **Given** a fault after the catalog has applied batch 4 and before its checkpoint commits (the worker is killed in that window), **When** the message is redelivered, **Then** batch 4 is sent again and the catalog answers `unchanged` for its items; the final `rowsProcessed` and `rowsFailed` equal an uninterrupted run exactly, `created + updated + unchanged + failed = rowsProcessed`, and at most the 500 rows of that one batch moved from `created`/`updated` to `unchanged` (documented bound); the products are identical to an uninterrupted run.
4. **AS-36** (one runner per job) — **Given** an `UPLOADED` job and two workers handed its message at the same moment (`Promise.all`), **Then** exactly one claims the job and runs it, the other returns without reading the file, writing anything or publishing anything; the job's lease names one runner; final counters equal one clean run.
5. **AS-37** (stalled worker is fenced) — **Given** worker A holds the job's lease and stalls (no renewal for more than the 5-minute lease; frozen clock advanced), and worker B takes the job over from the checkpoint and commits batch 5, **When** A wakes and tries to commit its own batch, **Then** A's commit is refused (it no longer holds the lease), A stops without touching the counters, and the final state equals B's alone (counters never decrease; no batch counted twice).
6. **AS-38** (redelivery of finished work) — **Given** jobs in `DONE`, `FAILED`, `CANCELLED` and `EXPIRED`, **When** a message for each is delivered again (a duplicate, a late retry), **Then** each is acknowledged with no storage read, no call to the catalog, no status change, no event and no outbox row.
7. **AS-39** (graceful shutdown) — **Given** a worker in the middle of batch 2 of 6, **When** it receives the shutdown signal, **Then** it finishes or abandons the current batch at a consistent point, commits a checkpoint that matches what the catalog applied (or the previous checkpoint), destroys the source stream and any scanner socket (no stream or socket stays open), releases its lease, leaves the job `PROCESSING`, and returns control so the message is redelivered; the stop completes within 10 seconds for a 500-row batch.
8. **AS-40** (lost work is recovered) — **Given** (a) a job `UPLOADED` for more than 2 minutes with no live lease (its message was lost), (b) a `PROCESSING` or `SCANNING` job whose lease expired, (c) a job `UPLOADED` for 30 seconds, and (d) a job with a live lease, **When** the recovery job runs (and runs again, and runs on two instances at once), **Then** (a) and (b) are re-enqueued exactly once per run window, (c) and (d) are not touched, and no job ever has two live runners.
9. **AS-41** (bad message) — **Given** import-queue messages that are not JSON, miss `importId`, carry a non-UUID `importId`, an unknown job's ID, or extra fields, **When** delivered, **Then** each is rejected (dead-lettered after the retry budget for the unknown-job case, immediately for the malformed ones) with no job changed, nothing read from storage, no event, and one structured log line with the `messageId`.
10. **AS-42** (a broken file stops the pipeline cleanly) — **Given** a CSV that becomes malformed after 700 rows (a bare quote inside an unquoted field the parser cannot recover from), **When** processed, **Then** the job is `FAILED` with `failure.code: "malformed_file"` and the failing row ordinal; the source stream, parser and writer are all destroyed (none stays open: observable as `destroyed` on the stream handed out by storage); the one full batch before the break (500 rows) stays applied and checkpointed; the error report holds the rows refused so far.
11. **AS-43** (backpressure, pure) — **Given** a generated source of 1,000,000 records and a sink that never finishes its first batch, **When** the parse pipeline runs, **Then** no more than 500 + 16 records are ever pulled from the source (the batch plus the object-mode queue's high-water mark; the source is paused, not buffered); **When** the sink resumes, **Then** every record is delivered exactly once in order, and an abort signal fired while the sink is blocked ends the pipeline with an error and destroys every stage.
12. **AS-44** (transient failure) — **Given** a database statement timeout while committing batch 2's checkpoint, **When** the first delivery fails, **Then** the job stays `PROCESSING`, the delivery is retried by the queue (no in-process retry: one retry layer), the second delivery resumes from the last checkpoint and ends `DONE` with exact counters; **Given** the same fault persists through the third delivery, **Then** the job is `FAILED` with `failure.code: "internal_error"` and a generic message (no SQL or stack in the API), the message is dead-lettered, and the checkpoint is kept.
13. **AS-45** (shop stops being active) — **Given** a job `UPLOADED` for a shop that has become `SUSPENDED` or `DELETING`, or a shop that turns `SUSPENDED` after batch 2, **When** the catalog throws `ShopNotActiveError` for a batch, **Then** the job is `FAILED` with `failure.code: "shop_not_active"` (not retried), nothing from that batch is written, the checkpoint stays at the last good batch, and the file is deleted.
14. **AS-46** (error cap) — **Given** the failure cap set to 5 for the test (default 100,000) and a file where every row is invalid, **When** processed, **Then** the job stops at the batch in which the cap is passed, ends `FAILED` with `failure.code: "too_many_errors"`, the report holds every failed row up to that batch exactly once, and rows after it are neither read nor reported.
15. **AS-71** (file missing) — **Given** an `UPLOADED` job whose stored file no longer exists (removed by the backstop rule or by hand), **When** the worker starts it, **Then** the job is `FAILED` with `failure.code: "source_missing"`, nothing is written, no retry is attempted, and one `catalog_sync.import_finished` event (status `FAILED`) is produced.

### User Story 4 — The seller learns exactly which rows were refused and why (Priority: P2)

After an import with problems, the seller downloads one CSV listing each refused row, the column, a stable code and a readable message, fixes the file, and re-imports only what matters.

**Why this priority**: an import that silently skips rows is worse than none; the report is how a seller trusts the result.

**Independent Test**: import 10,000 rows with 3 bad rows (and one with two problems) and compare the report with the expected lines; kill the worker mid-file and compare again.

**Acceptance Scenarios**:

1. **AS-47** (report content) — **Given** a 10,000-row file with rows 17, 5,001 and 9,999 invalid (blank title; price `abc`; stock `-1`), **When** imported, **Then** the job is `DONE` with `rowsProcessed: 10000, rowsFailed: 3`, 9,997 products exist, and the report is a CSV with the header `row,sku,field,code,message`, in file order, one line per problem: `17,SKU-17,title,missing_required,…`; `5001,SKU-5001,price,invalid_price,…`; `9999,SKU-9999,stock,invalid_stock,…` (`row` is the record's ordinal, `1` = the first record after the header, so a spreadsheet user finds it at row+1); a row with two problems yields two lines; progress events were published after each of the 20 batches.
2. **AS-48** (refusals from the catalog) — **Given** rows whose values pass the file rules but are refused by the catalog (price `0`; a 201-character title; a SKU longer than 128 characters), **When** imported, **Then** each appears in the report with the catalog's `code` unchanged and `field` mapped back to the file's column name (`priceMinor→price`, `quantity→stock`, `externalSku→sku`, others unchanged), counts in `rowsFailed`, and does not block the valid rows of its batch (pure mapping and message table in the unit layer; the API layer proves one catalog refusal end to end).
3. **AS-49** (report after a crash) — **Given** a 3,000-row file with bad rows at 100, 1,200 and 2,800 and a crash after batch 3 (rows 1–1,500 done), **When** the job resumes and finishes, **Then** the report holds all three lines exactly once, in file order, and `rowsFailed: 3` (so the report is complete across a resume, including failures that happened before the crash, and a batch redone after a crash does not duplicate its lines).
4. **AS-50** (when a report exists) — **Given** a job `PROCESSING`, **When** `GET …/error-report` is called, **Then** `409 error_report_not_ready`; **Given** a `DONE` job with `rowsFailed: 0`, **Then** `404 import_error_report_not_found`; **Given** a job `FAILED` or `CANCELLED` after some rows had been refused, **Then** `200` with the lines found so far; **Given** a report older than its 30-day retention (AS-67), **Then** `404 import_error_report_not_found`; status shows `errorReport: {available, rows}` in every case.

### User Story 5 — Seller and team follow, list and cancel imports (Priority: P2)

Anyone on the shop's team with read access can see what is being imported and how far along it is; the person who started it, or a writer, can cancel it. Nobody sees another shop's imports.

**Why this priority**: it turns a long job into something a person can trust, and the isolation rules are what make the feature safe to expose.

**Independent Test**: a route-by-role-by-shop matrix; a subscribed live channel; cancel at each state.

**Acceptance Scenarios**:

1. **AS-51** (status shape) — **Given** any job of shop `S`, **When** a member with `products.read` calls `GET /shops/S/imports/J`, **Then** `200` parsed by `importJobSchema`: `{id, shopId, status, fileName (sanitised), sizeBytes, rowsProcessed, rowsCreated, rowsUpdated, rowsUnchanged, rowsFailed, bytesProcessed, ignoredColumns, scan: "clean"|"skipped"|null, failure: {code, message}|null, errorReport: {available, rows}, createdBy, createdAt, startedAt, finishedAt, history: [{status, at}]}`; it never contains the storage key, the upload handle, a presigned URL, a lease, or a signature name; `failure.message` is generic text chosen by the code.
2. **AS-52** (cross-shop access) — **Given** shops `A` and `B`, a job `JA` of `A`, and a member of `B` (and, separately, a person who belongs to no shop), **When** they call every import route (`GET` job, `GET` upload, `POST` complete, `POST` cancel, `GET` error-report, `GET` list) with `JA`, either on `/shops/A/…` or on `/shops/B/…`, **Then** every answer is the same `404` (for `JA` on `B`'s path: `import_not_found`; on `A`'s path by a non-member: the tenancy's not-found) with an identical body to the answer for a job that does not exist, and nothing changes; `GET /shops/B/imports` lists none of `A`'s jobs.
3. **AS-53** (authentication and roles) — **Given** no credentials, **When** any import route is called, **Then** `401`; **Given** a member whose role has `products.read` but not `products.write`, **Then** `GET` routes answer `200` and start, complete and cancel answer `403` with nothing changed; **Given** a malformed `shopId` or `importId` (not a UUID), **Then** `400 validation_failed` with no database statement.
4. **AS-54** (list) — **Given** 45 jobs of shop `S` in mixed states created at distinct and equal instants, **When** `GET /shops/S/imports?limit=20` is followed through `nextCursor`, **Then** pages hold 20, 20, 5 jobs, ordered newest first with the job id as tiebreaker, no job repeated or skipped, each item parsed by `importJobSchema` (without `history`); `?status=DONE` filters; `limit` of `0`, `101` or `abc`, an unknown `status`, or a tampered cursor is `422 validation_failed`; the default limit is 20.
5. **AS-55** (live progress) — **Given** a member of `S` subscribed to the live channel `import:J`, **When** the job runs, **Then** they receive `progress {processed, failed, bytesProcessed, sizeBytes}` after each checkpoint and a final `done {rowsProcessed, rowsFailed}` (or `failed {code}` or `cancelled`); terminal events are replayable (a subscriber who connects after the job ended, with `Last-Event-ID` or none, still receives the terminal event) and progress events are not; **Given** a viewer who is not a current member of `S` with `products.read` (another shop's member, or the creator after being removed from `S`), **Then** the subscription is refused exactly as for an unknown topic; the same facts remain readable by polling `GET …/imports/J` (live events are a convenience, never the only source).
6. **AS-56** (cancel) — **Given** a job in `PENDING_UPLOAD`, `UPLOADED`, `SCANNING` or `PROCESSING`, **When** a member with `products.write` calls `POST /shops/S/imports/J/cancel`, **Then** `200` with status `CANCELLED` at once for the first two (the open upload is aborted; a queued message becomes a no-op, AS-38) and, for the last two, the job becomes `CANCELLED` at the running worker's next safe point (a batch boundary, or the next chunk while scanning) (the lease holder commits the transition together with its checkpoint, closes its streams and deletes the file); products already written stay (nothing is rolled back) and are reflected in the counters; **Given** `DONE`, `FAILED`, `EXPIRED`, **Then** `409 import_not_cancellable`; **Given** a repeat on `CANCELLED`, **Then** `200` unchanged.
7. **AS-57** (cancel races complete) — **Given** a `PENDING_UPLOAD` job, **When** `complete` and `cancel` arrive together (`Promise.all`), **Then** exactly one transition happens (history has one row), the loser answers `409 import_not_completable` or `409 import_not_cancellable` respectively, and the job is either `UPLOADED` (with one message) or `CANCELLED` (with the upload aborted and no message), never both.
8. **AS-58** (state machine, pure) — **Given** the transition table, **When** table-driven over every ordered pair of the 8 states, **Then** exactly these 13 pairs are allowed: `PENDING_UPLOAD→UPLOADED|CANCELLED|EXPIRED|FAILED`, `UPLOADED→SCANNING|CANCELLED|FAILED`, `SCANNING→PROCESSING|CANCELLED|FAILED`, `PROCESSING→DONE|CANCELLED|FAILED`; `DONE`, `FAILED`, `CANCELLED`, `EXPIRED` are final; every other pair is refused (the path is always `UPLOADED→SCANNING→PROCESSING`, also when the scan is skipped); a `switch` over the states is exhaustive; and a storage-level conditional transition (`from` must match) refuses a stale `from`: a second writer applying `UPLOADED→SCANNING` to a job already in `PROCESSING` changes zero rows.
9. **AS-59** (abandoned uploads expire) — **Given** jobs `PENDING_UPLOAD` created 25 hours and 23 hours ago (frozen clock), **When** the expiry job runs (twice, and on two instances at once), **Then** the 25-hour job becomes `EXPIRED` with its open upload aborted and one `catalog_sync.import_finished` event of status `EXPIRED` (AS-64); the 23-hour job is untouched; a second run changes nothing; `complete` on the expired job is `409 import_not_completable`.

### User Story 6 — One shop's huge import never starves the others (Priority: P2)

Many shops import at once, and one shop uploads three big files in a row. Each shop's imports run one at a time; other shops are not delayed; nobody can flood the queue.

**Why this priority**: design 27 and SD-27 ("fair scheduling per shop") — a shared worker pool is only fair if one tenant cannot hold it.

**Independent Test**: block one shop's job on a gated file stream and observe another shop's job completing; fire concurrent starts at the cap.

**Acceptance Scenarios**:

1. **AS-60** (one run per shop) — **Given** shop `A` with two `UPLOADED` jobs `J1` and `J2` and shop `B` with `J3`, **When** `J1` is running (gated) and workers are handed `J2` and `J3`, **Then** `J3` runs to `DONE` at once; `J2` is handed back with a delay of 60 s ± 20% (a new message; it does not count against `J2`'s three-delivery budget), `J2` stays `UPLOADED`, nothing of `J2` is read; when `J1` finishes, `J2` runs next; imports of one shop run in creation order.
2. **AS-61** (active-import cap) — **Given** the cap of 3 non-final imports per shop, **When** 5 `POST /shops/S/imports` with distinct keys arrive together (`Promise.all`), **Then** exactly 3 are `201` and 2 are `409 too_many_active_imports`; exactly 3 job rows exist; **When** one job reaches a final state, **Then** a new start succeeds; final jobs never count.
3. **AS-62** (start rate limit) — **Given** the policy of 10 starts per hour per shop, **When** the 11th `POST /shops/S/imports` (valid, below the active cap) arrives within the hour, **Then** `429 rate_limited` with `Retry-After`, nothing created; reads of the same shop still succeed; **Given** the limiter's store is down, **Then** starts are refused `503` (fail closed) and reads are unaffected.
4. **AS-63** (shop status) — **Given** shop `S` `SUSPENDED`, **When** a member starts, completes or cancels an import, **Then** `403 shop_suspended`; **Given** `DELETING`, **Then** `409 shop_offboarding`; reads (`GET`) still answer `200`; nothing changes.

### User Story 7 — Imports follow the life of the shop, and say when they are done (Priority: P3)

When a shop leaves the platform its imports stop and its files disappear; old jobs and reports do not pile up; other capabilities can react to a finished import; operators can see what the pipeline is doing.

**Why this priority**: housekeeping and contracts. Needed for a clean boundary, not for the first demo.

**Independent Test**: deliver the shop events (twice, out of order, malformed); freeze time and run the purge; parse every event with its contracts schema.

**Acceptance Scenarios**:

1. **AS-64** (finished event) — **Given** a job that ends in `DONE`, `FAILED`, `CANCELLED` or `EXPIRED`, **Then** exactly one outbox row for topic `catalog-sync.events` is written in the same transaction as the status change, with `aggregateId = importId`, `type: "catalog_sync.import_finished"`, `version: 1`, `eventId`, `occurredAt`, and a payload that parses with `importEventSchemas`: `{importId, shopId, createdBy, status, failureCode, rowsProcessed, rowsCreated, rowsUpdated, rowsUnchanged, rowsFailed, startedAt, finishedAt}`; a redelivered message or a repeated cancel writes no second row; **Given** a fault that makes the outbox insert fail, **Then** the status change rolls back with it (the job is still `PROCESSING`, the message is retried), never a final job without its event.
2. **AS-65** (offboarding) — **Given** shop `S` with jobs in `PENDING_UPLOAD`, `PROCESSING` and `DONE`, **When** `tenancy.shop_offboarding_started {shopId: S, purgeAt}` is delivered, **Then** the two non-final jobs become `CANCELLED` (the running one at its next batch boundary), their open uploads are aborted, the `DONE` job is unchanged, and other shops' jobs are untouched; **When** the same envelope is delivered again, **Then** nothing changes (idempotent by `eventId`); **When** a payload fails its schema (no `shopId`, non-UUID, extra type) is delivered, **Then** it is rejected to the dead-letter queue with no change; **When** `tenancy.shop_offboarding_cancelled` arrives, **Then** nothing happens (cancelled imports are not revived).
3. **AS-66** (deletion purge) — **Given** shop `S` with jobs in several states, error reports and a leftover source file, **When** `tenancy.shop_deleted {shopId: S}` is delivered, **Then** every job row of `S`, its history and its stored objects (source, error report) are gone and other shops' data is untouched; **When** delivered again (or before any `shop_offboarding_started`, or after it), **Then** nothing fails and nothing else changes; **Given** storage fails halfway, **Then** the delivery fails and is retried, objects are removed before rows so the retry still finds what remains, and the end state is complete.
4. **AS-67** (retention) — **Given** (frozen clock) final jobs finished 31 days ago with a report, 91 days ago, and 10 days ago, plus a `PROCESSING` job created 100 days ago, **When** the purge job runs (twice; two instances at once), **Then** the 31-day job keeps its record but loses its report object (`errorReport.available: false`), the 91-day job's record, history and objects are deleted, the 10-day job is untouched, the `PROCESSING` job is never purged, at most 500 jobs are handled per run (oldest first), and a second run changes nothing.
5. **AS-68** (observability) — **Given** one full import, **Then** every log line carries `requestId` or `traceId`, plus `importId` and `shopId` on job lines; no log line contains a row's values, a SKU list, a file's content, a presigned URL, or a scanner signature outside the one `malware_detected` line (which names the signature only); metrics are exported for rows by outcome (`created|updated|unchanged|failed`), jobs by final status, batch duration, scan duration, bytes read, checkpoint age of running jobs, and queue-to-start delay.
6. **AS-69** (boundary, static) — **Given** the repository, **When** `pnpm --dir packages/backend check:table-ownership --strict` and `pnpm check:boundaries` run, **Then** they report zero findings for the import files: no query or model of any table other than the domain's own import tables (no product table, no outbox table, no shop or user table), no foreign key from the import tables to another owner's tables, no import of another domain except the entry points of `tenancy`, `identity` and `catalog`, and the domain's index exports no model.
7. **AS-70** (export routes are gone) — **Given** an application that loads only this capability's modules, **When** `POST /shops/S/exports/orders` or `GET /shops/S/exports/J` is requested, **Then** `404` (served by S12), and the import queue carries only `{importId}` messages (no `kind` field).

### Edge Cases

- Two imports of one shop touching the same SKUs run one after the other, never together (AS-60), so "file order wins" holds per job and the later job overwrites the earlier (AS-19, AS-18).
- A seller edits a product by hand while an import is running: the catalog's change detection and versions decide; the import never overrides a newer product silently beyond what its row says, and it never resurrects an archived product (S05 AS-63).
- A cancelled or failed import leaves earlier batches applied. That is intended (batches are independent and idempotent), and the counters and report say exactly how far it got (AS-56, AS-42, AS-46).
- The client declares a size and uploads a different amount (more or fewer bytes): the check at completion catches it (AS-09).
- The job's file is gone from storage when a worker starts (backstop lifecycle rule, manual deletion): the job fails `source_missing` and nothing is written (AS-71).
- An enormous number of progress events: one per 500 rows (about 40 per second at full speed); the live hub's fan-out limits are S51's concern; polling remains correct (AS-55).
- A clock jump does not shorten a lease: leases are compared with the injected application clock only.
- A scanner that is slow but alive is never mistaken for an unavailable one (AS-24).

## Requirements *(mandatory)*

### Functional Requirements

**Upload handshake (P0407 request, direct-to-storage upload)**

- **FR-001**: A job belongs to exactly one shop and records its creator; both come from the authenticated request and the path, never from the body. Starting needs `products.write`; every read needs `products.read`; an unknown or other-shop job always answers `404 import_not_found` with one identical body (AS-01, AS-52, AS-53).
- **FR-002**: Starting validates `fileName` (1–200 characters, no control characters) and `sizeBytes` (integer, 1 to 5,368,709,120 inclusive); extra fields are refused; the response lists one upload URL per part of 64 MiB (the last may be smaller), valid for 6 hours; the file's bytes never pass through the API (AS-01, AS-02).
- **FR-003**: Starting requires an `Idempotency-Key`: a replay returns the stored status and body for 24 hours, an in-flight duplicate is `409`, a different body under the same key is `422` (AS-03, AS-04, AS-05).
- **FR-004**: The storage key is generated by the server from the shop and job identifiers only; no client text enters a key, a header or a log field unsanitised (AS-01, AS-27, AS-31).
- **FR-005**: A client can resume an unfinished upload: the job reports which parts storage holds and gives new URLs for the rest (AS-06).
- **FR-006**: Completing validates the part list (every part `1..partCount` once, in order, with ETags storage recognises) and that the assembled size equals the declared size; success answers `202` with `Location` and the status body without waiting for processing; completing is idempotent and race-safe, with one queue message per job (AS-07–AS-11).
- **FR-007**: A job that was never completed (`CANCELLED`, `EXPIRED`) cannot be completed (AS-12); an unfinished upload expires 24 hours after creation and its storage upload is aborted (AS-59).

**Safety of the file (P0509)**

- **FR-008**: Before any row is read, the whole file is streamed through a malware scanner; an infected file fails the job, is deleted, and is never parsed (AS-21, AS-22).
- **FR-009**: The scan fails closed: an unreachable, stalled, erroring or confusing scanner never lets a file through; after three deliveries the job fails `scan_unavailable`; the scan has a 60-second inactivity limit and a 30-minute deadline (AS-23, AS-24, AS-25).
- **FR-010**: Scanning is mandatory in production (startup fails without it) and may be disabled only explicitly elsewhere, recording `scan: "skipped"` (AS-32).
- **FR-011**: The parser is chosen by sniffing the first 4 KiB, never by the name or declared type; binary, archive, document, executable, wrongly encoded and compressed files are refused `unsupported_file_type`; no decompression ever happens (AS-26, AS-27).
- **FR-012**: A record may be at most 1 MiB: an oversized JSON line is a row error; an oversized CSV record fails the job `malformed_file`; memory never holds more than one such bound (AS-28).
- **FR-013**: Results leave only as presigned, short-lived (10 minutes) downloads from the separate user-content origin with `attachment` disposition and a fixed `text/csv` type; the user-content origin sends `nosniff`; the uploaded source file is never linked to anyone (AS-29).
- **FR-014**: Values echoed into the error report are guarded against spreadsheet formula injection and CSV-escaped; display and download names are sanitised (AS-30, AS-31).

**Streaming parse and writes (P0207)**

- **FR-015**: The file is read as a stream through one cancellable pipeline (source → parser → batcher → writer); an error or cancellation at any stage destroys every stage and releases every handle; memory stays flat whatever the file size (AS-42, AS-43, AS-39).
- **FR-016**: Backpressure holds end to end: the source is paused while a batch is being written and never read further ahead than one batch plus the object queue's high-water mark (AS-43).
- **FR-017**: CSV (RFC 4180 with BOM, CRLF or LF, quoted newlines) and JSON-lines are both supported; headers are matched case-insensitively after trimming; `sku`, `title`, `price`, `category` are required columns; `description`, `brand`, `stock`, `tags` are optional; other columns are ignored and reported once (AS-14, AS-16).
- **FR-018**: Prices are decimal text in major units of the platform currency with at most two decimals, converted exactly to integer minor units; stock is a non-negative whole number up to 1,000,000; an empty stock cell means "do not touch stock" (AS-15, AS-20).
- **FR-019**: Records are validated one by one; a failing record is reported and skipped and never stops its neighbours; the catalog's own refusals are reported alike (AS-47, AS-48).
- **FR-020**: Valid records are written in batches of at most 500 through the catalog's exported import command with source `"import"`, in file order; the same SKU never appears twice in one batch (the pending batch is sent first); this capability never writes the product table or the product events (AS-13, AS-19, AS-69).
- **FR-021**: Re-importing identical data changes nothing (the catalog reports `unchanged`); changed data updates; the counters `rowsCreated`, `rowsUpdated`, `rowsUnchanged`, `rowsFailed` always sum to `rowsProcessed` (AS-17, AS-18).
- **FR-022**: At most 100,000 failed rows are tolerated; passing the cap fails the job `too_many_errors` (AS-46).

**Checkpoints and resume**

- **FR-023**: After every batch, the job's counters, `lastRow`, `nextByteOffset`, header columns and detected format are committed as one unit, then progress is published; a resumed run reads from `nextByteOffset` and never sends a row at or before `lastRow` (AS-33, AS-34).
- **FR-024**: A crash in any window loses no row and double-counts none beyond the one-batch bound of AS-35; the product result equals an uninterrupted run (AS-35).
- **FR-025**: One runner per job: a runner holds a renewable lease (5 minutes, renewed every 60 seconds); a second claim is refused; a runner that lost its lease cannot commit (fencing) (AS-36, AS-37).
- **FR-026**: Finished jobs ignore redelivered messages without any effect; malformed messages are rejected without effect (AS-38, AS-41).
- **FR-027**: Shutdown stops at a consistent point, closes every handle, keeps the job `PROCESSING` and releases the lease (AS-39).
- **FR-028**: A scheduled recovery job re-enqueues jobs whose message was lost or whose lease expired, at most once per window and never while a live lease exists (AS-40).
- **FR-029**: Failures are retried only by queue redelivery (one retry layer, at most 3 deliveries); on exhaustion the job fails with a code and a generic message and the message is dead-lettered (AS-23, AS-44).
- **FR-030**: A shop that is no longer active, or a source file that is gone, fails the job without retry and without writing the failing batch (AS-45, AS-71).

**Error report**

- **FR-031**: Each job has at most one error report: a CSV with header `row,sku,field,code,message`, one line per problem in file order, complete across resumes with each line exactly once; it is stored batch by batch so a crash neither loses nor repeats lines (AS-47, AS-49).
- **FR-032**: The report is available as soon as the job is final, is retained 30 days, and its availability is shown in the status (AS-50, AS-67).

**Status, progress, cancel, fairness, limits**

- **FR-033**: The status shows exact counters, byte progress, a generic failure `{code, message}`, report availability and the status history, and none of the internals (AS-51).
- **FR-034**: Jobs of a shop are listed with keyset pagination and an optional status filter (AS-54).
- **FR-035**: Live progress is published on `import:{importId}` to current shop members with `products.read`; terminal events are replayable and nothing depends on the live channel (AS-55).
- **FR-036**: Cancel works from every non-final state, takes effect at the next batch boundary for running jobs, keeps earlier writes, and never races a completion into two states (AS-56, AS-57).
- **FR-037**: Every status change is a conditional transition from the expected current state with a history row in the same transaction; the transition table is closed (AS-58).
- **FR-038**: A shop runs one import at a time, in creation order, without occupying worker capacity while it waits; other shops are not delayed (AS-60).
- **FR-039**: A shop may have at most 3 non-final imports and start at most 10 per hour; the cap is enforced by the store, not by check-then-write (AS-61, AS-62).
- **FR-040**: All mutating routes obey the shop status gate (`403 shop_suspended`, `409 shop_offboarding`) (AS-63).

**Lifecycle and contracts**

- **FR-041**: A final status and its `catalog_sync.import_finished` outbox row are written in one transaction (AS-64).
- **FR-042**: Offboarding cancels the shop's non-final imports; deletion purges all of the shop's jobs and objects; both consumers are idempotent, validate their payloads, and dead-letter bad ones (AS-65, AS-66).
- **FR-043**: Final jobs and their records are purged on a schedule (report after 30 days, record after 90), at most 500 per run, never a non-final job (AS-67).
- **FR-044**: The source file is deleted when a job becomes final (and by a storage lifecycle rule after 7 days as a backstop) (AS-13, AS-22, AS-56).
- **FR-045**: Logs and metrics follow AS-68; the import files satisfy the ownership and boundary checks; the order-export routes and queue use are not part of this domain (AS-68–AS-70).
- **FR-046**: Every request and response body is described by a schema in the shared contracts package; every error is problem+json with a stable `code` (AS-01, AS-51, AS-52, AS-53).

### Key Entities *(include if feature involves data)*

- **Import job**: `{id, shopId, createdBy, status (PENDING_UPLOAD|UPLOADED|SCANNING|PROCESSING|DONE|FAILED|CANCELLED|EXPIRED), fileName (sanitised, display only), sizeBytes, storageKey, uploadHandle, format (csv|jsonl)?, headerColumns?, ignoredColumns, scan (clean|skipped)?, scannedAt?, counters {rowsProcessed, rowsCreated, rowsUpdated, rowsUnchanged, rowsFailed}, checkpoint {lastRow, nextByteOffset}, failureCode?, failureDetail?, errorReportKey?, errorReportRows, lease {holder, expiresAt}?, createdAt, startedAt?, finishedAt?, updatedAt}`. Owned by `catalog-sync`; the shop and the creator are plain IDs with no foreign key (IX.4).
- **Import job history**: append-only `{importId, from, to, at, reason?}`, one row per transition, written with it.
- **Error report part**: one stored object per batch that had problems, keyed by job and batch number (rewriting a batch's part replaces it), combined into the one downloadable report.
- **Import message**: `{importId}` on the import queue (the only message kind).
- **Import event**: `catalog_sync.import_finished` (see Provides).
- **Consumed shop events**: `tenancy.shop_offboarding_started`, `tenancy.shop_deleted`, with a record of handled event IDs (idempotency).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A 1,000,000-row, 5 GiB-class file is imported to `DONE` by one worker in under 15 minutes while the worker's memory stays below 200 MB, for any file size up to 5 GiB (benchmark with a generated file).
- **SC-002**: Of 20 imports of 5 GiB-class files running at once across 20 shops, none is delayed by another shop's import, and each shop's own imports run one at a time.
- **SC-003**: Killing the worker at 50 random points of a 100,000-row import and restarting it each time ends with products and counters identical to an uninterrupted run in 100% of runs (counters may move at most one batch from `created`/`updated` to `unchanged`, never from `rowsFailed`, never in `rowsProcessed`).
- **SC-004**: 100% of files that are not plain-text CSV or JSON-lines, 100% of files the scanner flags, and 100% of files while the scanner is down end `FAILED` with zero products written.
- **SC-005**: In a matrix over every import route against every role of the same shop and every role of another shop, 100% of cross-shop attempts answer the identical "not found" and change nothing.
- **SC-006**: A seller sees progress move at least once per second on a 20,000 rows/second import, and learns the cause of 100% of refused rows from the report without contacting support.
- **SC-007**: Delivering any import message, shop event or recovery run a second time changes nothing in 100% of the cases tested; two simultaneous completions, cancels, claims or starts at the cap always yield exactly one winner per rule.
- **SC-008**: A seller can import a 10,000-row catalog and download the report of 3 bad rows in under 3 minutes of interaction.
- **SC-009**: The ownership check reports 0 cross-domain queries, models, associations or foreign keys for this capability's files, and 0 writes of the product table from this domain.

## Assumptions

- A seller's right to import is decided by shop membership and permission (S03); verification (S04) and plan limits (S18) do not gate imports in this release.
- One platform currency exists; file prices are in that currency's major units with a point as the decimal mark (a comma is refused as ambiguous). A currency column is not supported.
- Files are UTF-8 (with or without a byte-order mark); other encodings are refused rather than guessed. Files are plain text; compressed uploads are refused rather than expanded.
- The import is **additive and updating**: it creates and updates products by SKU and never archives or deletes products missing from the file.
- A row's `row` number counts records (not physical lines): quoted newlines do not shift it.
- Batch size (500), part size (64 MiB), size limit (5 GiB), record limit (1 MiB), error cap (100,000), lease (5 min, renewed each 60 s), unclaimed-job recovery (2 min), upload window (6 h presigned, 24 h to expiry), caps (3 active, 10 starts per hour), report link (10 min), report retention (30 days), record retention (90 days), source backstop (7 days), scan deadlines (60 s inactivity, 30 min total) and the busy-shop delay (60 s ± 20%) are defaults; they are configuration, not contract. The batch size is bound by the catalog's 500-item limit.
- Counters across a crash can reclassify at most one batch from created/updated to unchanged, because the catalog write and this capability's checkpoint live in different stores and cannot be one transaction (IX.4); processed and failed counts and the products themselves are exact.
- The live channel is a convenience on a backplane that may drop messages; the status route is the source of truth (IV.3).
- The malware scanner adapter stays inside this domain behind a domain port; if media (S29) needs the same adapter it can be moved to an infrastructure library later without changing any contract here.
- Import history is operational data and is not part of the shop's offboarding export; the seller already owns the files and the products.
- Terminal events are published for other capabilities (notifications, webhooks) to use; no consumer is required in this release.
- The decisions behind every default are listed in `questions.md`; the ones that change behaviour that exists today are tagged `[BREAKING]` there.

## Cross-capability contracts

Earlier specs searched (`grep -rl` over `specs/domains`, `specs/web`, `specs/journeys` for `S07` and `catalog-sync`; `specs/web` and `specs/journeys` do not exist yet): **S05** (spec, questions, gaps) requires from this capability that it writes products only through `ProductImportService.upsertFromExternal` and `applyStockDelta`, stops publishing `products.events`, keeps links, cursors, field clocks and quarantine to itself, and consumes the per-item `rejected` results for its error report (honoured: FR-020, FR-019, AS-48, AS-69); **S06** names S07 as another product writer (nothing required). **S03** requires every shop-owning domain to export on `tenancy.shop_offboarding_started` and purge on `tenancy.shop_deleted` (honoured: AS-65, AS-66; the export of import history is declined as a `[CONTRACT]` line in `questions.md`). Pattern map: P0207, P0407, P0509. Journey **J04** (`catalog-sync-to-search`) starts from this capability's `DONE` import.

**Provides** (exact names; exported from `@app/domains/catalog-sync` unless it is an HTTP endpoint or a message):
