## Decisions

### D-1 Layering and what is deleted

- **Decision**: rebuild `libs/domains/orders` into the four layers. `domain/` holds pure rules and ports (state machine, money allocation, stock-operation builder, cart merge, guest token, webhook signature, cursor codec, error classes, port tokens). `application/` holds `CartService`, `CheckoutService`, `OrderLifecycleService` (the only writer of order state), `OrderCancellationService`, `WebhookIntakeService`, `WebhookProcessorService`, `PaymentResultService`, `OrderQueryService`, `OrderFulfilmentService`, `ReservationRecoveryService`. `infra/` holds Sequelize repositories (order, reservation, history, shop-order), the Dynamo cart store, the Redis checkout lock, adapters for the catalog, tenancy, payments, discounts, realtime ports, the job handlers and the `payments.events` consumer.
- **Rationale**: closes D-6 (I.2), A32–A35; gives every other decision a place.
- **Alternatives**: keep `OrderService` and patch it. Rejected: it mixes cancel, pay, release and flash-sale code; the saga split (D-4) would not fit.
- **Barrel**: in-repo importers exist today (read 2026-10-10): `OrderExportService` (catalog-sync module, controller, worker), `OrderService` + `FlashStockService` (the auctions worker module provides both itself; `auction.jobs.ts` calls `OrderService.transition`), `CheckoutDiscounts`/`DiscountableLine` (shop-functions), `OrderPaid/OrderCancelled/OrderReserved` (notifications, experimentation, developer-platform, discovery, seller-insights, payments), `BisOrderModel` (auctions, payments, asset-library), `ExportJobTopicsModule` (sse-gateway), `CreateBisOrderDto` (test seeds). Removing any of them breaks another capability's build, which no spec asks for. So, as S03 and S05 did, `index.ts` gets a **marked TRANSITIONAL block** that keeps exactly these names (pinned by `orders-boundary.e2e-spec.ts` so the list can only shrink); the new names are added above it. Nothing new is added to the block.
- **`OrderService` (compat)**: kept with the **same constructor and the same `transition` signature**, because auctions instantiates it in its own module. Its internals shrink: the raw `UPDATE "Product"` release becomes "mark reservations `RELEASE_PENDING`" (the release job restores stock through `applyStockDelta`), it uses the shared state table of `domain/order-state.ts`, and it writes the new event payloads. New code never calls it; it is deleted when S21 moves to an order-creating command.
- `order-export.service.ts` stays untouched in the folder (S12). Its `Product` join is S12's finding, so `check:table-ownership --strict` for `orders` reaches 0 only after S12 (recorded in Complexity Tracking). Flash-sale files stay compiled in `FlashSaleLegacyModule` (D-9).

### D-2 Cart: DynamoDB, atomic idempotent merge, signed guest cookie

- **Decision**: keep `Carts` (one item per line, `PK = CART#<id>`, `SK = ITEM#<productId>`, `expiresAt` attribute, DynamoDB TTL as lagging cleanup). Reads filter `expiresAt <= now` (clock) — the store's TTL delete is only housekeeping (FR-006). `setLine` is an `UpdateItem` that keeps `addedAt` (`if_not_exists`) and refreshes `expiresAt`; the 50-line cap on a *new* line is a `TransactWriteItems` of the put plus a condition-check on a per-cart counter item `SK = META` (`lineCount < 50`, incremented with the put; decremented by delete). **Merge** is one `TransactWriteItems` per attempt (≤ 100 operations: ≤ 50 line writes on the user's cart, ≤ 50 deletes of guest lines): every guest line is deleted with `ConditionExpression: quantity = :readQuantity` and every changed user line is written with `quantity = :readQuantity` (or `attribute_not_exists`) as its condition. A concurrent merge of the same guest cart fails its conditions (`TransactionCanceledException`), re-reads (guest now empty) and returns the user's cart: the guest quantities are added exactly once in any interleaving (AS-06). Retries ≤ 3, then `503`. Merge rules (min 20, user's lines first, guest by `(addedAt, productId)`, `droppedLines`) are the pure `mergeCarts` function (AS-12).
- **Guest cookie**: `cart=guest:<uuid>.<base64url HMAC-SHA256(secret, "guest:<uuid>")>`; verification splits at the last dot, requires the `guest:` prefix and a UUID, compares with `timingSafeEqual` over equal-length buffers, and never throws (AS-11). Secret `cart_cookie_secret` (new config key, ≥ 32 bytes, required at startup, never `jwt_secret`); `Secure` outside local; `GET` never sets a cookie (FR-005).
- **Rationale**: Dynamo transactions give the all-or-nothing, race-safe merge the current 25-item batch cannot; keeping Dynamo keeps FR-002 and SC-004 (no relational access).
- **Alternatives**: Redis hash + Lua (cart store changes, loses TTL per line and the existing `dynamodb/Carts.json`); a "merged" marker item (a loser could read a half-merged cart). Rejected.
- **Risk**: DynamoDB Local must support `TransactWriteItems` (it does; the test stack's `test:stack:migrate` creates tables).

### D-3 Checkout idempotency: the S54 interceptor plus the order as the durable guard

- **Decision**: `POST /checkout` is `@Idempotent()` (required key, 24 h). The use case runs inside the interceptor; failures **before** an order exists throw ordinary `AppError`s (the interceptor releases the key: AS-20 first half). Failures **after** the order row exists are thrown with `idempotencyFinal: true` (`out_of_stock` → stored and replayed with `Idempotency-Replayed`, AS-20 second half). The order also stores `idempotencyKey` and `requestHash` (SHA-256 of the canonical body) under a unique `(userId, idempotencyKey)`; at the start of the use case an existing order for that pair is resolved first: `PENDING` → `409 idempotency_in_flight` (`Retry-After: 1`), `RESERVED` or later → rebuilt `202`, `CANCELLED(out_of_stock)` → the final `422`, different `requestHash` → `422 idempotency_key_reuse`. This is the guard after the interceptor's 24 h record is gone and the answer to AS-30 (stock call timed out → `503`, key released, retry sees the `PENDING` order and gets `409 in_flight` until recovery resolves it).
- **Fingerprint caveat**: the interceptor hashes the parsed body; an absent body and `{}` must hash alike, and `{expectedTotalMinor: 2500}` vs `{expectedTotalMinor: 3000}` must differ (AS-18). Verified by the first e2e (T-test in WP-8), not assumed.
- **Rationale**: uses the platform facility (cross-spec rule 4, V.6) without re-implementing a store; the order row covers the cases the facility cannot (key released but side effect started).
- **Alternatives**: own idempotency table (duplicate of S54, rejected by the follow-up list); store the 202 on the order only (loses `Idempotency-Replayed` semantics and fingerprint across 24 h).

### D-4 The checkout saga

- **Decision** (FR-025, gaps A5–A7): `CheckoutService.checkout(user, key, body)` =
  1. take the per-buyer Redis lock (`SET orders:checkout-lock:<userId> <token> NX PX 15000`, released by compare-and-delete Lua; busy → `409 checkout_in_progress`);
  2. read the cart; empty → `422 cart_empty`;
  3. `getProductsByIds` (1 s timeout) and `getShopsByIds` (batched ≤ 50) → validate (`product_unavailable {productIds}`, `mixed_currency`), compute gross money;
  4. `price_changed` check against `expectedTotalMinor` **after discounts** (the total the buyer is asked to pay);
  5. discounts through the port (250 ms), validated, allocated (`allocateLargestRemainder`), per-shop subtotals;
  6. **Tx 1** (`TransactionRunner.run`): insert order `PENDING` (version 1, key, requestHash, `reservedUntil = null`), items, shop orders `PENDING`, reservations `REQUESTED`, history `∅ → PENDING`;
  7. `ReservationSource.reserve` → `ProductStockService.applyStockDelta` with ops sorted by product id (2 s timeout), **outside any transaction**;
  8. `applied` → **Tx 2**: conditional `PENDING → RESERVED` (`reservedUntil = now + hold`), reservations `HELD`, history, `order.reserved` outbox row; enqueue `orders.expire-reservation` at `reservedUntil` (the job table insert is the same database, inside Tx 2 via the S49 transactional enqueue if supported by `JobsService`, otherwise right after commit with the sweeper as the backstop — see D-5); after commit: realtime push, cart cleanup (`consumedLines` only), `orders.clear-cart` job on failure;
  9. `rejected` → **Tx 2'**: `PENDING → CANCELLED(out_of_stock)`, reservations `RELEASED` (nothing was held), history; no `order.reserved`; the `out_of_stock` final problem.
  10. Timeout/unknown outcome of step 7 → leave `PENDING`, throw `503 checkout_unavailable` (non-final) — recovery (D-5) repeats the same operation ids.
  The lock is released in `finally`; it also expires on its own.
- **Rationale**: no transaction spans two domains (IX.4), the stock invariant stays in the catalog (III.6), replay of the same `operationId` is a no-op in S05 so recovery is safe.
- **Alternatives**: one transaction around the raw `UPDATE Product` (today): rejected by IX.4. Two-phase with a Redis counter: not needed for regular stock.

### D-5 Expiry, sweeper, recovery, release (jobs)

- **Decision**: seven job types registered with `declareJobType`: `orders.expire-reservation` (delayed per order, `runAt = reservedUntil`), `orders.sweep-expired-reservations` (60 s, `fleetConcurrency: 1`, `SELECT … WHERE status='RESERVED' AND reservedUntil <= now ORDER BY reservedUntil LIMIT 200 FOR UPDATE SKIP LOCKED`, each order cancelled through `OrderLifecycleService.cancel(hold_expired)` in its own transaction), `orders.recover-pending` (30 s, `fleetConcurrency: 1`, orders `PENDING` older than 60 s, `SKIP LOCKED`, repeats `reserve` with the same operation ids), `orders.release-stock` (30 s, per-row backoff, reservations `RELEASE_PENDING` → `applyStockDelta(+q)` with `orders:<orderId>:release:<productId>` → `RELEASED`), `orders.clear-cart` (≤ 5 attempts), `orders.process-webhook` (≤ 8 attempts, full-jitter backoff 5 s × 2ⁿ cap 10 min), `orders.purge-webhook-inbox` (daily, `InboxService.purge(now − 35 d)`). All handlers are idempotent by conditional state (a second run finds nothing to do).
- **Cancel** commits `HELD → RELEASE_PENDING` in the same transaction as the order move (FR-030). After commit the cancel path tries one immediate release; failure leaves `RELEASE_PENDING` and the gauge `orders_reservations_release_pending` is set by the release job from a `count(*)` per run.
- **Rationale**: SC-006 (16 min worst case = 15 min hold + 60 s sweeper); the sweeper is the backstop for a lost delayed job.
- **Open point resolved**: the delayed job is enqueued after commit of Tx 2 (a failed enqueue is logged and counted; the sweeper catches it within 60 s). This keeps no network I/O inside the transaction (III.3).

### D-6 Payments port while S13 is not built

- **Decision**: `PaymentStatusPort.getPaymentStatus(paymentRef)` in `domain/ports.ts` with the shape of the spec. The worker module binds `PaymentStatusAdapter` (`infra/`), which calls `PaymentQueryService` from `@app/domains/payments` **once S13 exports it**; until then the bound adapter is `PaymentStatusUnavailableAdapter`, which throws a retryable `PaymentStatusUnavailableError`. Effect today: a success event is stored, processed with retries, and after 8 failures becomes `FAILED` — never `PAID` without confirmation. Tests register a contract-valid fake through the same token (test plan, "Only system edges are faked").
- The `payments.events` consumer validates with `paymentEventSchemas` (zod, in `packages/contracts/src/orders/payment-events.ts` until S13 publishes its own; S13 may move it). It subscribes to the topic by name through the S53 consumer framework; with no producer yet it simply idles.
- **Alternatives**: wait for S13 (blocks the capability); read `PaymentModel` (D-7 violation). Rejected.

### D-7 Webhook intake and processing

- **Decision**: `POST /webhooks/stripe` (no session, raw body capped at 64 KiB via the S54 raw-body facility for this route, `413` above): `verifyStripeSignature(rawBody, header, secrets, now)` pure (AS-53) → parse `{id, type, data.object.metadata.orderId}` with zod (`400 invalid_payload`) → in one `TransactionRunner.run`: `InboxService.claim('stripe', id)` and, when `CLAIMED`, enqueue `orders.process-webhook {eventId}` with `idempotencyKey = stripe:<id>`; the stored payload needed for processing (type, orderId, amount, currency, paymentRef) is carried in the job payload (≤ 2 KiB, validated) — the raw body is **not** stored or logged. `DUPLICATE_*` → `200 {received: true, duplicate: true}`. Rate limit `orders.webhook.ip` (300/min, fail open, counts failed-signature traffic).
- Processing (`WebhookProcessorService`): type table → `payment_intent.succeeded` (`markPaid` path: order lookup by `orderId`; `getPaymentStatus` must be `COMPLETED` with equal amount and currency, else `REJECTED` with reason), `payment_intent.payment_failed` (`cancel(payment_failed)`), `charge.refunded` (full → `refund`, partial → history row), other types `IGNORED`. Results are written with `InboxService.markStatus`. A transient error rethrows (job retry); the 8th failure marks `FAILED` and the job dead-letters.
- **Late success after cancel/expiry**: `OrderLifecycleService.markPaid` returns `already_cancelled`; the processor appends exactly one `orders.refund_requested` (outbox, key = paymentRef so the unique outbox/idempotency key makes it once per payment; also the `orders_paid_after_cancel_total` counter).
- **Rationale**: V.8 (2xx after enqueue), D-7/D-11, A19–A23.

### D-8 Discounts and money

- **Decision**: internal port `ShopDiscountsPort.evaluate(cart) → { shopDiscounts: {shopId, discountMinor}[] }`. Today's exported `CheckoutDiscounts` (per-line unit prices, implemented by shop-functions) stays in the barrel's transitional block; the default adapter `LegacyCheckoutDiscountsAdapter` calls it when bound and converts its per-line unit prices to per-shop amounts (`Σ (gross − discounted unit) × quantity`, floored at 0), so S45 keeps working until it provides `shopDiscounts` natively (follow-up). The adapter has a 250 ms timeout (`Promise.race` + abort), validation (integer, ≥ 0, ≤ shop gross, known shop) and a fallback counter `orders_discount_fallback_total{reason: timeout|error|invalid}`. `allocateLargestRemainder(grossByLine[], discount)` pure, with `bigint`-free integer math (amounts stay below 2⁵³, spec Assumptions). All amounts `…Minor` integers; DB columns stay `BIGINT` only where they already are, new columns `BIGINT` mapped to JS numbers with a range check at the repository edge (III.8).
- **Rationale**: P1110, A9, A10.

### D-9 Flash sales stay compiled until S11

- **Decision**: the flash-sale model, jobs, `FlashStockService` and the `POST /shops/:shopId/flash-sales` route are **moved out of the checkout path** and into `FlashSaleLegacyModule` (same folder, `infra/flash-sale/`), keeping their behaviour and `flash-stock.service.spec.ts`, but: raw `UPDATE "Product"` in `flash-sale.jobs.ts` is replaced by `applyStockDelta` with operation ids `orders:flash:<saleId>:load|return` (gaps section C row 4 says S11 does this; S10 does the minimum so `check:table-ownership --strict` is 0 for `orders`), the `ProductModel` lookup in the controller by `getProductsByIds(ids, {shopId})`, and the direct `sequelize.transaction` becomes `TransactionRunner.run`. Checkout handles `CATALOG` reservations only; the `ReservationSource` port is in `domain/` for S11.
- **Rationale**: strict ownership check cannot stay at 12 findings if the flash files remain; deleting them early would break S11's starting point.
- **Alternative**: delete flash code now (breaking, spec says S11 takes it over). Rejected.

### D-10 Reads, cursors and the history index

- **Decision**: cursor = base64url of `{createdAt ISO, id}` plus an HMAC-less checksum bound to the `userId` (or `shopId`) it was issued for, so another buyer's cursor is `400 invalid_cursor` (AS-59). Query `WHERE "userId" = :u AND NOT (status='CANCELLED' AND cancelReason='out_of_stock') AND (createdAt, id) < (:c, :i) ORDER BY createdAt DESC, id DESC LIMIT :n+1`. The covering index `(userId, createdAt DESC, id DESC) INCLUDE (status, total, currency)`; the out-of-stock exclusion is a partial index predicate (`WHERE NOT (status = 'CANCELLED' AND "cancelReason" = 'out_of_stock')`) so the plan stays index-only (AS-60); `cancelReason` is added to the INCLUDE-free predicate only.
- **Seller list**: `ShopOrder` joined to its items inside the owned tables only (`ShopOrder ⟕ BisOrderItem ⟕ BisOrder` — all `domain:orders`), predicate `shopId = :shopId` on every joined table, keyset on `(ShopOrder.createdAt, ShopOrder.id)`; `buyerId` is the plain user id.

### D-11 Events, contracts and versions

- **Decision**: the three existing definitions keep their exported names and type strings (`OrderReserved`, `OrderPaid`, `OrderCancelled`) and get the spec's payload at envelope `version: 1` (the registry is keyed `type@version`, so a second definition of the same pair is refused); `OrderRefunded` and `OrderFulfilmentChanged` are new. Field renames (`total`→`totalMinor`, `price`→`unitPriceMinor`, `paymentId`→`paymentRef`) break the in-repo importers' compile, so WP-13 adapts **only their field reads** (projectors, listeners, and specs that build a payload) and lists each importer in `gaps.md` Sibling-spec follow-ups so its owner confirms. Five definitions on topic `orders.events` (key `orderId`) with `orderVersion` from the order's `version` after the move; payload schemas in `packages/contracts/src/orders/order-events.ts`, imported by both the definitions and the consumers' parity specs. `order.paid` carries lines and shop split (read inside Tx). `orders.refund_requested` is a single-consumer message through the S53 task producer.
- **Realtime**: after commit, `RealtimePublisher.publish('user:<userId>', 'order.status', …)`, catch + `orders_realtime_failed_total`.

### D-12 Rate limits and the Firewall

- **Decision**: add policies `orders.cart-write.identity` (120/min, key: user or client address, fail open), `orders.cancel.user` (20/min, fail closed), `orders.webhook.ip` (300/min, fail open) to `ordersRatePolicies`; keep `checkout.create`. Controllers carry `@RateLimit(...)`; enforcement is the global interceptor of `RateLimitModule.forRoot()` (core has it; the e2e kit imports it). `@SkipThrottle()` on the webhook is deleted. `Firewall({ anonymous: true })` on cart GET/PUT; `Firewall()` on merge, checkout, orders; `Firewall({ sensitive: true })` on `POST /orders/:id/cancel` and `POST /checkout` (money-moving).

### D-13 Static gates and the model clean-up

- `BisOrder`: drop `@BelongsTo(User)`, `@HasMany(Payment)` and the lazy accessors; `BisOrderItem`: drop `BelongsTo(Product)`; keep `BisOrderItem → BisOrder` (one-way) only. `ORDER_MODELS` loses `Product`, `Payment`. The barrel keeps the five `*Model` exports **last** (debt D-7) until S13, S16, S21, S31, S42, S43 migrate; the strict check then fails only on the consumers' findings, not on `orders` (the barrel is not a finding). `index.ts` adds `OrderQueryService`, `OrderFulfilmentService`, error classes, DTO types, the five event definitions and moves every legacy name listed in D-1 into the TRANSITIONAL block; it no longer exports any new `*Model`.
