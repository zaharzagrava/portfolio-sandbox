# Open Decisions for S10 (answered unattended)

Format: `[TAG] question → default taken → why`. BREAKING first, then CONTRACT, then LOCAL. The human reviews BREAKING and CONTRACT lines first. Decision policy: most production-grade option the Interview-Prep notes and the constitution support; no external clients to keep compatible, so correctness, security, observability and clean boundaries beat today's behaviour.

## BREAKING (changes behaviour or an API/UI contract that exists today)

- [BREAKING] `POST /checkout` answers `201` with `{orderId, status, total, currency, reservedUntil, paymentIdempotencyKey}` (`checkout.service.ts:216-223`, controller default status) → `202` with `Location` and `{orderId, status, totalMinor, currency, reservedUntil}`; `paymentIdempotencyKey` removed (S13 uses `orderId` through `getPayableOrder`) → note SD-19 API (`→ 202 + orderId`), pattern P0407, 04/03 §1; money fields get the `Minor` suffix (III.8).
- [BREAKING] Concurrent duplicates with one key today all get the same order (`checkout.service.ts:81,129-132`, unique-violation fallback) → exactly one runs, the others get `409 idempotency_in_flight` (`Retry-After: 1`), later ones replay the stored `202` → V.6 and note 04/03 §1 rule 3; existing "concurrent retries create one order" test changes from "all return one id" to "202 or 409, one order".
- [BREAKING] Missing or malformed `Idempotency-Key` answers `400` and a reused key with a different body is not detected (`orders.controller.ts:22,40`; the key is compared by user and key only) → `422 idempotency_key_required` / `idempotency_key_invalid` / `idempotency_key_reuse`, stored replay with `Idempotency-Replayed: true`, per-buyer scope, 24 h → V.4 (422 covers key misuse), V.6, S07's codes; the idempotency facility of S54 replaces the hand-written lookup.
- [BREAKING] Body: today no body → optional `{expectedTotalMinor}`, unknown properties rejected, `409 price_changed` when the server total differs → "confirm what the buyer saw" gives the idempotency fingerprint something to compare and protects against silent price changes; note 10/07 §19 "prices recalculated at checkout (never trust prices from the client)" is kept (the client never sends prices, only the total it saw, and it is optional).
- [BREAKING] Once an order exists for a key, the outcome (even `out_of_stock`) is final for that key; failures before an order exists release the key → keeps the stored replay simple and matches "key and side effects commit together" (note 04/03 §1); a buyer who wants another attempt uses a new key.
- [BREAKING] Stock is changed by raw `UPDATE "Product" SET quantity = quantity - :q …` in the order transaction (`checkout.service.ts:149`, `order.service.ts:97`, `order.jobs.ts:50,106`) → only S05's `applyStockDelta` with operation IDs `orders:<orderId>:reserve|release:<productId>`; the order is committed `PENDING` first, stock reserved second, `RESERVED` third, with a recovery job for crashes between steps → IX.4 (one transaction never spans two domains), III.6 (invariant stays in the catalog), pattern P0611 (saga with compensation); the "decrement inside the order transaction" design is gone.
- [BREAKING] Reservation lifecycle `HELD → CONVERTED | RELEASED` (today the release happens inside the cancel transaction and flash release after commit, `order.service.ts:89-115`) → `REQUESTED → HELD → CONVERTED | RELEASE_PENDING → RELEASED` with a retrying release job and a pending gauge → a release that fails after the cancel committed must not leak stock (the old code logs and forgets for flash units).
- [BREAKING] Webhook: today the event is inserted into the inbox and processed inline, with processing errors swallowed (`stripe-webhook.controller.ts:48-69`), so a failed `markPaid` is lost because the retry sees `duplicate` → acknowledge after store + enqueue, process asynchronously with retries, dead-letter, result states `PROCESSED | IGNORED | UNMATCHED | REJECTED | FAILED` → V.8 ("2xx after enqueueing, not after processing"), note 04/03 §5.
- [BREAKING] Webhook finds the payment through `PaymentModel` by `idempotencyKey` (`stripe-webhook.controller.ts:56`) → the order comes from the intent metadata `orderId`; the payment is confirmed through S13's `getPaymentStatus` (R1) and amount and currency are compared with the order → IX.4 / D-7 / D-11, note 04/03 §5 ("re-fetch the object for critical actions"); a mismatch is `REJECTED`, never paid.
- [BREAKING] Missing webhook secret fails each request with `400 Unsigned webhook` (`stripe-webhook.controller.ts:40`) → startup validation fails when the secret is missing; the previous secret is accepted during rotation; the 5-minute tolerance is explicit; body cap 64 KiB; `400 invalid_signature` problem+json → VIII.5, V.8.

## LOCAL (affects only this capability's internals)

- [LOCAL] Hold 15 min, sweeper 60 s (≤ 200 orders), recovery age 60 s, recovery every 30 s → note 10/07 §19 "10–15 min hold"; the worst unpaid hold is 16 min (SC-006).
- [LOCAL] Webhook job: 8 attempts, exponential backoff 5 s × 2ⁿ capped at 10 min with full jitter; inbox retention 35 days (provider retries last ≤ 3 days).
- [LOCAL] Cart: 50 lines, 20 per line, 30-day lifetime per line, filter expired lines on read (store deletion lags).
- [LOCAL] Merge overflow order: user's lines first, then guest lines by (`addedAt`, `productId`).
- [LOCAL] Timeouts: product read 1 s, stock call 2 s, discount call 250 ms, whole checkout 10 s.
- [LOCAL] Shop order status vocabulary `PENDING | PAID | CANCELLED | REFUNDED`; fulfilment progress per shop is out of scope.
- [LOCAL] `CANCELLED(out_of_stock)` orders are stored (they hold the key's final outcome) but hidden from the buyer's history.
- [LOCAL] Checkout lock per buyer is held for the duration of one checkout (≤ 10 s) and expires on its own.
- [LOCAL] Partial refunds only add a history row (`partial_refund`); the status changes only on a full refund.
- [LOCAL] `Idempotency-Replayed: true` header on replays.
- [LOCAL] History index stays `(userId, createdAt DESC, id DESC) INCLUDE (status, total, currency)` → index-only scan (P0303); the plan test runs after `VACUUM`.
- [LOCAL] Status values get a database CHECK constraint; `ShopOrder` gets a unique `(orderId, shopId)`; reservations a unique `(orderId, productId)`.
- [LOCAL] Metric names as in AS-66; logs carry `orderId`, never payload bodies.
- [LOCAL] Orders that predate the title snapshot get their item titles from a one-off resumable backfill (`"(removed product)"` when the product is gone); see `gaps.md` section E.
