## BREAKING (changes behaviour or an API/UI contract that exists today)

- [BREAKING] `confirm` and `hold` accept no `Idempotency-Key` today (`launch-events.controller.ts:61-79`; retries rely on a unique index) → both require the key with V.6 semantics (replay, in-flight 409, reuse 422, missing 422, 24 h TTL), and a new key on an already confirmed hold answers `200` with the same bookings → V.6 names bookings explicitly; a double-clicked hold would take quota twice.
- [BREAKING] Confirmation writes Postgres and then performs several DynamoDB and Redis calls, and has no outbox event (`seat-hold.service.ts:85-125`); a failure after the insert leaves ledger, lock and map disagreeing → booking rows, history rows, `booking_confirmed` and the voucher command in one transaction with no network call inside (III.3), the ledger is sealed before it and finalised after, and a 60 s reconciler repairs drift → III.3, IV.4, III.7; domain map says `launch-events` depends on orders "via command".
- [BREAKING] The confirm decision reads the hold from the ledger and compares `Date.now()` with `expiresAtMs`, then writes (`:86-89`); expiry job and takeover can interleave, so a stale holder may book a seat another hold now owns (the unique index only prevents a duplicate row, not a booking over a re-held seat) → per-seat fencing numbers, every confirm/release/expiry/rollback conditional on hold ID and fence, confirm and expiry mutually exclusive → P0326 (fencing tokens), III.6.
- [BREAKING] Release and expiry decrement the quota counter unconditionally after reading the hold (`:130-135`), so a release racing the expiry job credits twice and lets a buyer exceed the limit → the credit happens only for the transition `HELD → RELEASED|EXPIRED` that won a conditional update; counter rebuilt from bookings and active holds when missing, confirm re-checks the limit in the booking transaction (`TICKET_LIMIT_EXCEEDED`) → III.6 (the Redis counter is a cache, III.9).
- [BREAKING] `DELETE /launch-holds/:holdId` answers `200 {released: boolean}` and `403` for another user's hold (`:81-83`, `:131`); `confirm` answers `404` for another user → `204`; every cross-user access answers `404 HOLD_NOT_FOUND`; a confirmed hold answers `409 HOLD_ALREADY_CONFIRMED` → V.4 (`404` hides existence), VII.3 illegal-transition guard.
- [BREAKING] `GET /launch-events/:eventId/queue/:ticket` returns a ticket's status to anyone who has the ticket ID, and the SSE topic `queue:<ticket>` is `policy: () => true` (`launch-events.controller.ts:47`, `realtime-topics.ts:13`) → owner-only: the status call and the topic subscription check the ticket's owner; others get the same `404`/refusal as for an unknown ticket → the admission token is delivered over that channel; a leaked ticket ID must not leak a token.
- [BREAKING] Event creation returns the Sequelize row (`launch-events.controller.ts:25-26`) and the cached event page returns a raw row (`:87`) → response DTOs through `packages/contracts` schemas (`launchEventSchema`), no `createdAt/updatedAt` or admission rate on the public page → V.1, V.2.
- [BREAKING] Event status is stored but never changes (`SCHEDULED` forever) and holds are not gated by it; `salesOpenAt` is only compared in the admitter (`admission-ticker.service.ts:52`) → real state machine `SCHEDULED → ON_SALE → SOLD_OUT`, `→ CLOSED` (organizer or `startsAt`), holds only when `ON_SALE`, organizer `POST …/close`; new error codes `EVENT_NOT_ON_SALE`, `EVENT_SOLD_OUT`, `EVENT_CLOSED`, `EVENT_ALREADY_CLOSED` → P0110, III.7; the notes' "sales open at a fixed time" is otherwise unenforced at hold.
- [BREAKING] Join answers `201` always and uses the `search.query` rate-limit policy (`:38`) → `201` for a new ticket, `200` for an existing one; own policy `launch.queue.join.user` 10/min fail open → a shared search policy is the wrong budget; idempotent join is a stated behaviour.
- [BREAKING] Admission pops `ceil(N/8)` per shard, so up to `N + 7` users are admitted per tick, and a missing ticket still consumes capacity (`waiting-room.service.ts:75-83`); the existing e2e even asserts `≥ 10` → exactly `min(N, waiting)` per second, rotating start shard, abandoned tickets skipped without using capacity, bucket capacity one second → P0619 admission control.
- [BREAKING] Admitter leader election is `SET NX PX` then an unconditional `PEXPIRE` by whoever read the owner key (`admission-ticker.service.ts:41-44`), no fencing → Lua compare-and-extend plus a fencing epoch carried by every admission write → P0326; a paused leader must not admit.
- [BREAKING] No heartbeat: tickets live 1 h whether or not the buyer is still there (`waiting-room.service.ts:10`) → 120 s heartbeat refreshed by status polls; lapsed tickets are removed at admission → notes: "heartbeat to keep the spot"; otherwise the room admits ghosts and the real rate collapses.
- [BREAKING] Pre-sale joiners get `salesOpenAt + random(1 s)` but a post-open joiner gets `now`, which can land inside that second and jump ahead of pre-sale arrivals (`:52`) → post-open score is `max(now, salesOpenAt + 1 s)` → "randomised for pre-sale arrivals" must mean they are ahead.
- [BREAKING] `skipThrottle: true` on the public event page and seat map (`launch-events.controller.ts:30,53`) → policy `launch.seatmap.ip` 600/min fail open on the seat map, event page behind the CDN cache plus single-flight → an uncached public read of a hot event is a DoS lever; III.9.
- [BREAKING] Seat map is a Redis bitmap with no TTL and no `seq`; deltas carry no order (`seat-hold.service.ts:193-197`) and a Redis flush silently shows an empty room → every key has an expiry, deltas carry a `seq` assigned atomically with the bit, map rebuilt from bookings plus active holds when lost, reconciler clears stray bits → III.9 (cache is never the source of truth), the notes' "eventual consistency for the seat map display, authoritative check on hold".
- [BREAKING] Quota counter key lifetime is 30 days and the hold writes the counter before validating event state or seats (`:59,180-181`) → counter has an expiry tied to the event, claim happens after validation and token check; `422 TICKET_LIMIT_EXCEEDED {limit, remaining}` replaces the free-text 422 → stable machine-readable codes; no store effects on rejected input.
- [BREAKING] Admission token is verified with the algorithm from the key set and no `typ`/purpose isolation from access tokens (`waiting-room.service.ts:107-112`), signed by identity's `KeyStore` imported from the identity barrel → signing and verification through a purpose-token service owned by identity (R1) with a pinned algorithm; the token is refused as an access token and vice versa → VIII.7, S01 FR-027; `KeyStore` is not in S01's Provides.
- [BREAKING] `LaunchEvent.shopId` has `REFERENCES "Shop"("id")` (migration `20261001170000-launch-events.js:17`) → plain UUID, no foreign key, expand/contract migration with `lock_timeout` → IX.4 (no FK across owners).
- [BREAKING] `Booking` has no history table although `BookingEvent` is in the notes' data model, and `Booking.status` has an unreachable `CANCELLED` → a `BookingEvent` history row per booking state change in the confirm transaction; `CANCELLED` stays reserved and unreachable → III.7 (history row with every transition).
- [BREAKING] The barrel exports `BookingModel`, `LaunchEventModel`, `Reservoir` (S23), and the services are exported from `LaunchEventsModule` (`index.ts:7-8`, `launch-events.module.ts:16`) → export only the three Nest modules and DTO types; the e2e boots the module and goes through HTTP → X.4, D-7, D-8.
- [BREAKING] The existing e2e calls `SeatHoldService` and `WaitingRoomService` directly for holds, tests the 100-parallel case at service level, and has no HTTP, idempotency, IDOR, expiry-race, limit-race or consumer coverage (`launch-events.e2e-spec.ts`) → rewritten as HTTP e2e per `test-plan.md`; the service-level calls go away → VII.2/VII.3.

## CONTRACT (decides something another capability must provide or consume)

- [CONTRACT] Admission-token signing and verification → S22 asks S01 for an R1 `PurposeTokenService.sign/verify` (shape in `spec.md`) → S01's Provides has `SessionIssuer.createChallenge/verifyChallenge` (MFA only) and `ServiceTokenService` (service callers), neither fits a buyer-bound, event-audience token; the code today imports `KeyStore`, an identity internal. **If S01 declines, S22 would have to keep its own ES256 key pair and publish it in a JWKS of its own; not preferred.**
- [CONTRACT] Booking voucher → S22 emits SQS command `orders.booking_voucher_requested` v1 `{holdId, bookingIds, launchEventId, shopId, userId, seatCount}` (dedupe `booking-voucher:<holdId>`); S10 must consume it → the domain map says "orders (booking voucher via command)" and the notes say booking "includes a launch-day pre-order voucher", but S10's Provides has no such consumer; S22 treats the voucher as best-effort and never waits for it.
- [CONTRACT] Event vocabulary → new events `launch_events.event_created`, `booking_confirmed`, `event_sold_out`, `event_closed` on topic `launch-events.events` (domain map lists only `live.*` emits) → S28 needs `booking_confirmed` for the confirmation notice; J03 asserts it; `docs/architecture/domain-map.md` "Emits" must be extended by the implementer.
- [CONTRACT] Owner-only topic `queue:<ticket>` → S51's `TopicRegistry.define` policy must be async and receive the authenticated principal; the policy asks this domain's own ticket store → today's policy signature is `() => true`; a capability-by-unguessable-ID is not authorization (II.3 / VI.5 spirit).
- [CONTRACT] Permissions → event create/close use S03's existing `products.write`, bookings list uses `orders.manage`, no new permission asked → a "launch" permission would need S03 FR-020 to change; STAFF can run launches like they run products.
- [CONTRACT] Rate-limit policies `launch.queue.join.user`, `launch.hold.user`, `launch.seatmap.ip` → S50 declares them by these names with the failure modes in `spec.md` → keeps `search.query` free for search; hold fails closed because an unlimited hold path is a seat-hoarding bot's first target.
- [CONTRACT] `Idempotency-Key` facility → S54/S10 provide one shared implementation with V.6 semantics and the `idempotency_*` problem codes; S22 uses it as is (24 h TTL, per-user scope) → the current interceptor emits plain messages with no `code`; S10 also asked for stable codes.
- [CONTRACT] S11's possible future token verifier → S11 would mint its own audience (`admission:flash:<id>`), never reuse S22's `admission:<eventId>` → the audience is how a token is kept inside its flow; S22 does not change.
- [CONTRACT] Same-domain S23 → shares only the Nest module family and the barrel; S22 exposes nothing S23 may import; S23's `ShopMembership` reads are replaced with S03's `ShopAccessService.assertMember` in S23's own spec → no S22 involvement.

## LOCAL (affects only this capability's internals)

- [LOCAL] Seat identity = integer `0 … seatCount − 1`, row = ⌊seat ÷ seatsPerRow⌋ → matches code, notes (1 bit per seat).
- [LOCAL] `seatingMode` `SEATED | GENERAL`; `quantity` best-available allowed in both → notes: "Best-available for GA tiers"; P0312 GA variant.
- [LOCAL] Hold 10 min, admission token 10 min, ticket heartbeat 120 s, reconciler 60 s with 120 s grace, close frees holds within 60 s → constants from the notes (`PX 600000`, "short TTL") and existing code.
- [LOCAL] Position tolerance 16 places, eta = ceil(position ÷ rate) → eight sub-queues give ±8 error; stated as a testable bound.
- [LOCAL] Queue maximum 2,000,000 tickets per event, configurable, validated at startup → notes' scale 1M arrivals with headroom; load shedding needs a number.
- [LOCAL] Confirm status `201` first / `200` natural re-confirm; join `201` / `200` → distinguishes created from existing without a body flag.
- [LOCAL] Hold request carries `seats` xor `quantity`, ≤ 10 per request → matches current DTO cap and the per-person limit ceiling.
- [LOCAL] Hold records of a closed event are expired by the reconciler within 60 s, confirm is refused immediately → strict and simple; avoids confirming into a closed event.
- [LOCAL] Bot-check result is one-time and verified through a port with a 2 s timeout, failing closed → notes: "Turnstile token verify at edge"; this is the origin-side hook.
- [LOCAL] No seat prices, no cancellation, no event editing → not in the notes' scope for this section; recorded as Assumptions.
- [LOCAL] Metrics names in AS-58 → `launch_*` prefix, bounded labels (no event or user IDs on counters; queue length gauge labelled by event only for events in `ON_SALE`).
- [LOCAL] Reconciler also hosts the double-booking detector (one query per event) → keeps SC-001 observable in production.
- [LOCAL] The admitter keeps its 1 s timer inside the worker (lease + fencing) instead of the job scheduler → S49's schedule granularity is minutes; the scheduler still owns the per-hold and per-event jobs.
