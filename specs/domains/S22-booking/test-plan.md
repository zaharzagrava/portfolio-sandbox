# Test Plan: S22 — Launch-Event Booking (domain `launch-events`)

Constitution VII.8 table: one row per acceptance scenario in [`spec.md`](spec.md) (62 rows), each proven at the lowest layer that can prove it. A dash means the layer does not test that scenario.

- API e2e files live in `packages/backend/libs/domains/launch-events/`. Each file's top-level `describe` names its feature (VII.8). They boot the real `LaunchEventsModule`, `LaunchEventsWorkerModule` (jobs and the admitter are invoked through their handlers / `tick()` with the injected clock) and `LaunchEventTopicsModule` with the production prefix, `ValidationPipe`, problem+json filter and interceptors, against real Postgres (real migrations), Redis and DynamoDB Local from `docker-compose.test.yaml`. Time is frozen and advanced; nothing mocks the project's own repositories, ORM or stores.
  - `launch-events-queue.e2e-spec.ts` — describe "Launch events: waiting room, admission rate and load shedding"
  - `launch-events-holds.e2e-spec.ts` — describe "Launch events: admission token, seat holds and ticket limits"
  - `launch-events-confirm.e2e-spec.ts` — describe "Launch events: booking confirmation, idempotency and recovery"
  - `launch-events-seatmap.e2e-spec.ts` — describe "Launch events: seat map, deltas and realtime topics"
  - `launch-events-organizer.e2e-spec.ts` — describe "Launch events: organizer routes, status machine and my bookings"
  - `launch-events-operations.e2e-spec.ts` — describe "Launch events: jobs, events, metrics and domain isolation" (includes the VII.4 duplicate-delivery and invalid-payload tests of every job)
- Shops, memberships and users are seeded only through the shared fixture helpers, the identity fixture (`SessionIssuer`/`issueTokensFor` replacement) and tenancy's exported services; no spec injects `ShopModel`, `ShopMembershipModel` or `UserModel` (D-7). Events are created through the organizer route; admission tokens are obtained by running the admitter, not by minting them, except in AS-18 where forged tokens are built on purpose.
- Only system edges are faked: identity token verification, the bot-check provider (AS-13, AS-14), S10's consumption of the voucher command (a spy on the command queue), the realtime transport where a fault is forced, and the clock. Faults (store down, crash between steps, refused outbox append) are injected through the test module's switchable store wrappers at the system edge, never by stubbing a repository.
- Unit specs sit beside the code under `domain/`, are table-driven (`it.each`), and exist only for pure logic (VII.5): `queue-score.spec.ts`, `token-bucket.spec.ts`, `event-state.spec.ts`, `hold-state.spec.ts`, `seat-bitmap.spec.ts` (bit order, `fast-check` for set/clear round trips and position-of-seat), and the client delta reducer in `packages/contracts/src/launch-events/seat-map-reducer.spec.ts`. Controllers, repositories, services, jobs and adapters get no unit tests.
- UI journey (Playwright): none. No web capability in `scripts/sdd/capabilities.tsv` covers launch-event pages and `packages/web` has no launch screen, so VII.7 has no client flow to cover yet. The cross-domain happy path (waiting room, seat booking, voucher, notification) belongs to J03 (`packages/backend/test/journeys`). When a web capability adds the booking screens, it adds one journey `packages/web/e2e/launch-event-booking.spec.ts` (join, wait, admitted, pick seats, confirm) and re-tests no row below.
- Static gates (VII.1): `tsc --noEmit` and ESLint for `packages/backend` and `packages/contracts`; `pnpm check:boundaries`; `pnpm --dir packages/backend check:table-ownership --strict` (AS-61); `pnpm check:module-graph`; `pnpm check:model-registry`.
- Gate 9 (VII.9) fallback/degradation tests that force the fault: AS-11 (queue store down, queue full), AS-12 (limiter down), AS-14 (bot-check provider down), AS-29 (fast lock store down), AS-30 (ledger down), AS-31 (limiter down, fail closed), AS-41 (crash between stores), AS-42 (outbox refused), AS-48 (map store wiped), AS-24 (counter wiped).
- Concurrency tests use `Promise.all` and assert that exactly the allowed number succeed and the invariant holds (VII.3): AS-02, AS-08, AS-16, AS-17, AS-22, AS-23, AS-25, AS-26, AS-35, AS-36, AS-38, AS-43, AS-46, AS-54, AS-60. Each is repeated at least 20 times in the same test.
- Async work (VII.4): there are no message consumers in this capability; the four jobs (`expire-hold`, `open-sales`, `close-event`, `reconcile-seats`) each get duplicate-delivery and invalid-payload tests in AS-60.
- The k6 spike `scripts/load-tests/launch-event.test.js` (`pnpm loadtest:launch-event`) proves SC-004 and SC-001 (zero double-booked seats); it is an ops artifact, not part of this table.
