# Open Decisions for S01 (answered unattended)

Format: `[TAG] question → default taken → why`. BREAKING first, then CONTRACT, then LOCAL. The human reviews BREAKING and CONTRACT lines first. Decision policy: most production-grade option the Interview-Prep notes and the constitution support.

## BREAKING (changes behaviour or an API/UI contract that exists today)

- [BREAKING] Should registration return a session (201 + tokens), or the same answer whether the address exists? → `202 {"status":"accepted"}`, identical for new and taken addresses, no session; the client logs in next; duplicate attempts emit `identity.registration_duplicate_attempted` for a "you already have an account" mail → constitution V.4 and notes 05/01 §5.2 ("Registration, the hard case"); today's `409 Email is already registered` enumerates members.
- [BREAKING] Reuse-detection grace window (today 10 s default: a replay inside it gets a fresh token)? → none: any replay of a spent token revokes the session; simultaneous refreshes of one token: one wins, the session is then revoked → notes 05/02 §2 ("assume theft, revoke the family"); parallel refreshers (BFF) must single-flight (see CONTRACT line for S48).
- [BREAKING] Which credential channels does the API accept? → only `Authorization: Bearer` and the `__Host-access` cookie (with CSRF); the legacy `x-auth-token` header, `x-auth-token` cookie, and the legacy no-`kid` RS256 tokens (static key file) are removed → ambient `x-auth-token` cookie auth had no CSRF protection (notes 05/01 §3), and no-`kid` tokens bypass key rotation and `aud`/`typ` checks.
- [BREAKING] Access-token profile: add `aud: marketplace-api`, `typ: at+jwt`, `nbf`, `jti`, `amr`; lifetime 300 s (today 600 s default, no `aud`/`typ`); no e-mail in tokens → notes 05/02 §2 (validate `aud`, `typ`, short lifetime, no PII); edge-be and tests must pin `aud`/`typ`.
- [BREAKING] Where does the principal come from? → from verified token claims only (`{id, role, sessionId, amr}`), no per-request user lookup; `request.user` is `AuthenticatedUser`, not the full `UserRawDto` (no `email`, no placeholder fields like `passwordResetToken`) → SD-39 scale target "verification is free, zero I/O"; callers needing e-mail use `UserDirectoryService` (R1). Role changes show up at next refresh (≤ 300 s).
- [BREAKING] Cookie attributes and CSRF scheme (today `SameSite=Strict`, plain random double-submit, refresh token returned in body AND cookie)? → `SameSite=Lax` (SD-39), `__Host-access`/`__Host-refresh` HttpOnly + signed double-submit `__Host-csrf` (random part + MAC bound to the session) + Origin/Fetch-Metadata check; cookie delivery is opt-in (`delivery:"cookie"`) and then no token appears in the body → notes 05/01 §3.2 (naive double-submit is defeated by cookie tossing; HMAC binding), constitution VI.2 (tokens never reach browser JS).
- [BREAKING] Client IP source (today trusts `cf-connecting-ip` from any client)? → trusted-proxy chain only; forwarding headers from untrusted peers are ignored → constitution IV.7; the header was a trivial rate-limit bypass.
- [BREAKING] Password policy (today 8–72 chars, bcrypt-era limit)? → 12–128 chars, not equal to the address, not in a breached-password corpus (k-anonymity port, fail-open on 800 ms timeout) → notes 05/02 §5 (HIBP check; Argon2id has no 72-byte limit).
- [BREAKING] Session lifetime: today every refresh extends expiry by 30 days forever → idle 30 days plus absolute 90 days per session, max 20 active sessions (oldest revoked) → bounded-risk sessions; notes ("limits").
- [BREAKING] Brute-force counting (today the account policy counts all attempts, success included) → counts failed attempts only, resets on success; same `429` for unknown addresses → notes 05/02 §5, 05/01 §5.2; avoids locking out a user who just logged in correctly.
- [BREAKING] Response/status changes: `logout-all` 201 → 200 `{revokedSessions}`; `register` 201 → 202; new `DELETE /auth/sessions/:id` (404 for other users' sessions); `GET /auth/sessions` returns an explicit DTO (today the raw stored item incl. storage keys, user ID and family ID leaks); `GET /auth/me` unchanged → constitution V.1 (explicit response DTOs) and V.4.
- [BREAKING] Error contract: stable `code` extension on problem+json; refresh failures are all `invalid_refresh_token` (today a distinct "reuse detected" message) → notes 05/01 §5.3 and OAuth BCP (`invalid_grant`); reuse is audited server-side instead.
- [BREAKING] Public barrel of `@app/domains/identity`: remove `UserModel`, `FederatedIdentityModel`, `SigningKeyModel`, `AuthService`, `KeyStore`, `UsersModule`, `UsersDtoModule`, `UserUtilsModule`, `AdminModule`; add `UserDirectoryService`, `SessionRevocationService`, `SessionIssuer`, `ServiceTokenService`, `ServiceAuthGuard`, `AllowedCallers`, event contracts; `AuthService.issueTokensFor` (unauthenticated token minting, used by 5 e2e specs) is replaced by a test fixture over `SessionIssuer` → constitution X.4, IX.4; D-7/D-12.
- [BREAKING] Password reset is in scope (today missing): `POST /auth/password-reset/request|confirm`, uniform 202, 30-minute single-use token, confirm revokes all sessions → pattern P0506 ("identity (login, reset)") and notes 05/01 §5.2.
- [BREAKING] Service-to-service tokens are net new (nothing in code) → signed, audience-scoped `svc+jwt` tokens, 60 s, per-endpoint caller allowlist, on-behalf-of via `act` claim; chosen over mTLS-only because the stack has no mesh, and over reusing user tokens (IV.7) → notes 05/02 §8 approaches 3 and RFC 8693.
- [BREAKING] Key rotation timings → NEXT published ≥ 24 h before promotion, ACTIVE ≥ 7 days, RETIRED published ≥ 24 h (code keeps 2 days; the rotation also runs on every instance boot); boot-time run is replaced by the scheduled single-run job plus a race-safe lazy bootstrap → SD-39 (daily job) and constitution VIII.6; retention ≥ access lifetime + JWKS cache is what correctness needs.

## CONTRACT (something another capability must provide or consume)

- [CONTRACT] How do other domains get user data? → R1 `UserDirectoryService.getUsersByIds` (batch ≤ 500) and `findByEmail`, returning `UserSummaryDto {id,email,role,createdAt}` → domain-map §3 (`User` readers: tenancy, notifications, chat-sync, ledger) and IX.7 R1; S03/S24/S28/S14 must switch.
- [CONTRACT] How do other domains end sessions (ban, offboarding)? → R1 `SessionRevocationService.revokeAllForUser(userId, reason)`; no direct session-store access → IX.4.
- [CONTRACT] S02 seam → S02 provides `isSecondFactorEnrolled(userId)` and `/auth/mfa/*`; S01 provides `SessionIssuer.issue`, `createChallenge`/`verifyChallenge` (`typ: mfa+jwt`, `aud: mfa`); S02's account linking must not link to password accounts whose address was never verified without invalidating their password and sessions (pre-hijacking) → keeps token types and session creation in one place.
- [CONTRACT] BFF (S48) must serialize refresh per session and use `delivery:"cookie"` only for direct browser calls → strict reuse detection turns a double refresh into a logout.
- [CONTRACT] edge-be and every verifier: ES256 only, check `iss=marketplace`, `aud=marketplace-api`, `typ=at+jwt`, reject purpose tokens, JWKS cached ≤ 300 s with kid-miss cooldown → matches spec FR-022; edge's current `RS256` allowance and missing `aud` check change.
- [CONTRACT] Password-reset delivery → single-consumer message (not a fan-out topic) `identity.password_reset_requested` carries the raw single-use token; S28 consumes it, mails the link, never logs the token → a reset link must reach the user, and storing only a digest in identity means the token has to travel once; the alternative (S28 calling back to mint a token) needs R1 coupling and a stored raw token.
- [CONTRACT] Events: `identity.user_registered`, `identity.registration_duplicate_attempted`, `identity.password_changed` carry IDs only; S28 resolves the address via `UserDirectoryService` → PII stays out of Kafka (IX.8 copies only what a read model needs).
- [CONTRACT] Rate-limit policies `auth.register.ip`, `auth.refresh.ip`, `auth.reset.ip`, `auth.reset.account` are new; `auth.login.account` changes to count failures only → S50 must support failure-only counting and reset-on-success.
- [CONTRACT] `SecretBox.seal/open` gain an optional `context` (bound as additional authenticated data) and a previous-master-key fallback; existing callers (S04, S08, S42) keep working without context but should adopt it → defence against ciphertext swapping between columns; supports rotation (notes 05/02 §9).
- [CONTRACT] `Firewall({sensitive:true})` replaces `@UseGuards(SessionNotRevokedGuard)`; S15 (payouts) and S42 (API keys) mark their sensitive routes → one decorator, one meaning.
- [CONTRACT] Rule for earlier specs: none existed when this spec was written (`specs/web`, `specs/journeys` absent; `specs/domains` held only S01), so nothing was overridden.

## LOCAL (this capability's internals)

- [LOCAL] E-mail verification and "re-authenticate for sensitive actions" → not built → no pattern or capability requires them; revisit with S02/S15.
- [LOCAL] CAPTCHA after repeated failures → not built → needs an external provider; per-address and per-IP throttles cover the notes' minimum.
- [LOCAL] Sessions list pagination → none → ≤ 20 active sessions per user.
- [LOCAL] Sensitive-route revocation check when the revocation store is down → fail closed → security over availability for those routes only.
- [LOCAL] Reset request timing equalisation → not equalised beyond the response being sent before delivery → one extra row write; bounded by rate limits.
- [LOCAL] Hash concurrency 4, queue 64, `503` + `Retry-After: 1` when full → fits the default worker-pool size of 4; configurable.
- [LOCAL] Rehash-on-login update is conditional on the old hash → no lost update if the password changed meanwhile.
- [LOCAL] Refresh exchange is a single atomic write (spend old + store successor, guarded by "session not revoked") → today's three separate steps can strand a session.
- [LOCAL] Token digests: SHA-256 of 256-bit random values (no salt needed) → high-entropy secrets.
- [LOCAL] Admin external-DB-sync tool, empty `UsersController`/`UsersService`, Firebase import in `UsersModule` → out of scope; remove or move to scripts.
- [LOCAL] Audit log failure events for unknown addresses carry a keyed hash of the address → debuggable without storing PII.
- [LOCAL] Issuer string stays `marketplace` → existing consumers (edge, launch-events admission tokens) already use it.
