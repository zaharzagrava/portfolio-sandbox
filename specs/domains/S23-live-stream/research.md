# Research: S23 — Live Launch Stream

No NEEDS CLARIFICATION remain; the questions.md defaults are accepted. These decisions settle how, not what.

**D-1 Stream state on the hot path.** Decision: a per-stream cache entry `{shopId, status}` through S52 `CacheService.getOrLoad` (single flight, negative cache 10 s for unknown IDs, short positive TTL as a safety net). Lifecycle writes refresh it after commit; the reconcile job repairs it. The comment and reaction paths read only this entry, the poster's role (`ShopAccessService.getRole`, tenancy's 15 s cache) and the mute set. Rejected: the global `live:active` set as the liveness test (a Redis wipe makes every stream answer `409`); a relational read per comment.

**D-2 Durability order for a comment.** Decision: (1) validate and moderate synchronously; (2) claim `clientId` (`SET NX`, 10 min, value = comment ID); (3) produce `live.comment_posted` to the event stream; (4) push to the recent list and publish to the private feed. A failure at (3) releases the claim and answers `503 live_unavailable`; a failure at (4) leaves the durable event (history keyed by comment ID makes the retry safe) and answers `503`; the retry with the same `clientId` reuses the stored comment ID and repeats (4) only. Retry returns `200` with the original body. Rejected: publish first (a visible comment that never reaches history, today's bug).

**D-3 Lifecycle events and topic.** Decision: `live.stream_started` and `live.stream_ended` through `OutboxService.append` inside one `@Transactional` with the conditional status update (`UPDATE … WHERE status = :from`, one affected row asserted; a repeat finds the target state and returns `200` without an event). Aggregate type `launch_events` so the topic is `launch_events.events`, as S22 settled (aggregate types cannot contain `-`); the spec's `launch-events.events` is a naming slip, logged under Spec changes in gaps.md. Redis state and realtime `status` are published after commit. Rejected: events from the service after the transaction (lost on crash).

**D-4 High-volume events.** Decision: `live.comment_posted`, `live.comment_removed` (v2) and `live.reactions_aggregated` use `KafkaProducerService` with key `streamId` and the `defineEvent` envelope; no outbox. A removal is durable before it is visible: produce, then LREM and publish `comment_removed`. A 24 h claim marker (`SET NX`) makes at most one `live.comment_removed` per comment; it is released if the produce fails.

**D-5 Pin concurrency.** Decision: one conditional SQL statement per change: `UPDATE "LiveStream" SET pin = :pin, "pinVersion" = "pinVersion" + 1 WHERE id = :id AND "shopId" = :shopId AND status = 'LIVE' AND pin IS DISTINCT FROM :pin RETURNING …`; zero rows is then disambiguated by a read (identical → `200` same version, no event; not `LIVE` → `409`). The row lock serialises concurrent pins, so versions are distinct and consecutive. The product check (`ProductQueryService.getProductsByIds([id], { shopId })`) runs before the update and never inside a transaction. `pinnedAt` is part of the compared value only through the staff-visible fields (productId, text, stockLeft), so an identical re-pin does not bump the version.

**D-6 Mutes.** Decision: table `LiveMute (streamId, userId, mutedBy, mutedAt)`, PK `(streamId, userId)`, `INSERT … ON CONFLICT DO NOTHING`; the Redis set is a cache, loaded whole for a stream on a miss (single flight) and rebuilt by the reconcile job. `cannot_mute_staff` is decided with `ShopAccessService.getRole(shopId, targetUserId)` and the `products.write` permission table. No FK to `User`; FK to `LiveStream` allowed (same owner).

**D-7 Window composition.** Decision: pure `window-composer.ts` takes `{priority, own, sample, seen}` and returns the ascending, deduplicated item list and `rate = (seen + priority.length) × 4`; the existing `Reservoir` keeps the sample. `mine: true` is added per viewer on copies, never on shared objects. Priority and own are unbounded by design (bounded upstream by the per-user rate limit).

**D-8 History key and writes.** Decision: keep `STREAM#<id>#<yyyyMMddHHmm>` / SK = comment ID (spec, notes). Posts and removals are both `UpdateItem` upserts (`SET` of present attributes; the removal sets `removed`, `removedReason` and `expiresAtEpoch` for orphan markers), so they commute. Writes remain grouped by 25 with growing waits; with `UpdateItem` there is no `BatchWriteItem`, so the "groups of at most 25" is a concurrency window of 25 parallel updates (AS-43 asserts the group bound through the store wrapper). Capacity risk: one partition per stream-minute; accepted, noted in the quickstart.

**D-9 Consumer validation.** Decision: each consumer parses every message with the event's zod schema (`defineEvent(...).match`); an invalid message or unknown major version is dead-lettered through the projection framework's rejection path and the rest of the batch continues. The moderation consumer wraps the classifier port in a 2 s timeout, 3 retries with backoff, then dead-letter and `live_moderation_failed_total`; it is its own consumer group (`live-moderation`, distinct from `live-comments-history`).

**D-10 Reconcile job.** Decision: `launch-events.live-reconcile`, recurring 30 s, `overlap: skip`, concurrency 1, handler idempotent: read `LIVE` stream IDs, `SADD`/`SREM` the active set to equality (single Lua/transaction), reload mute caches for them. Registered by a bootstrap provider like S22's `LaunchEventSchedule`, catching `InvalidScheduleError`.

**D-11 Statistics.** Decision: keep the lease loop (`holdLease`, 3 s lease, 1 s tick) in `LiveTicker`, driven by the injected `Clock`, with `tick(now)` public for tests. It reads the active set, skips non-`LIVE` streams, publishes `stats` with `replay: false`, and produces `live.reactions_aggregated` once per (stream, second) (a `SET NX` marker, 30 s TTL) for non-empty totals. Counters expire after 10 s; increments for a closed second are never read again.

**D-12 Gateway in the domain.** Decision: `gateway/` folder with the batcher, viewer registry and SSE controller, imported by `apps/sse-gateway` through `LiveGatewayModule`. Order on connect: authenticate (optional) → cap check → state from cache (`404`/`409`) → rate limit `live.events.ip` → write headers → `registry.join` (subscribe, start buffering) → read snapshot → send `snapshot` → flush buffer. `pin.version` lets the client discard anything older than the snapshot. After `status ENDED` the controller closes each connection within 1 s. Viewer cap and window/sample/threshold come from validated config (AS-53).

**D-13 Author handle.** Decision: `HMAC-SHA256(secret, userId + ':' + streamId)` truncated to 8 bytes, rendered as `viewer-` plus 10 base32 characters; the secret is a validated config value (a deploy-time constant, not user-visible). Deterministic per (user, stream), different across streams, not reversible without the secret.

**D-14 Comment text.** Decision: `normalizeComment(text)`: NFC → remove control (`\p{Cc}`, `\p{Cf}`) and zero-width characters → collapse whitespace → trim → count code points with `[...s].length`. The DTO is replaced by the zod `postCommentRequestSchema` (strict) through the platform's zod pipe so extra properties are `422`. ZWJ emoji sequences contain U+200D (class Cf); the normalizer keeps U+200D and U+FE0F only between emoji so sequences survive; unit table pins this.

**D-15 Rate limits.** Decision: `definePolicies` in `rate-limit-policies.ts` adds `live.snapshot.ip` (slidingWindow 120/60 s, ip, open) and `live.events.ip` (30/60 s, ip, open) to the existing `live.comment`, `live.reaction`. Comment limiter runs before body validation (FR-019) and blocked attempts keep consuming budget because the limiter is a route decorator.

**D-16 Config.** Decision: `live-config.ts` zod schema with `windowMs` 250, `sampleSize` 5, `viewerCap` 50000, `moderationThreshold` 0.7, `bufferLimitBytes` 262144, `handleSecret`; invalid values fail at start naming the setting (S54 config validation).

**D-17 Tests without sleeps.** Decision: the ticker, batcher window and reconcile are driven through `tick()`/`flush()` with the injected clock; SSE assertions wait on a helper that polls a predicate with the runner timeout. This replaces the fixed sleeps in the old `live.e2e-spec.ts` (S51 follow-up).

**D-18 Unverified criteria.** SC-003 (99% of viewers within 1 s at 5,000 comments/s) and SC-014 (50,000 viewers per instance) need the k6 SSE run; they go under "Ops artifacts" in quickstart.md and as rows in `specs/UNVERIFIED.md`. SC-009 (history within 5 s) is covered by AS-43 with the projector running; SC-001/2/4–8/10–13 map to AS rows.
