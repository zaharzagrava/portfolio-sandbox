## BREAKING (changes behaviour or an API/UI contract that exists today)

- [BREAKING] Staff routes `PUT/DELETE /live/:streamId/pin`, `DELETE /live/:streamId/comments/:commentId`, `POST /live/:streamId/mutes/:userId` check a raw `ShopMembership` read and answer `403` to outsiders (`live.controller.ts:76-118`) → moved under `/shops/:shopId/live/:streamId/...` with the shop-scoped guard; a non-member and a stream of another shop get `404`, a read-only member `403`; new `DELETE …/mutes/:userId` (unmute) → constitution V.4 (404 for cross-tenant), IX.4/D-7 (no tenancy model), and the guard gives the permission matrix and shop-status gate for free.
- [BREAKING] Any shop member, even VIEWER, gets `priority` for comments (`live.controller.ts:62`) and `isStaff` is a membership-exists check → priority only for roles holding `products.write` (OWNER, ADMIN, STAFF) via the tenancy R1 `getRole` → a read-only member must not get unsampled, always-delivered comments.
- [BREAKING] `authorName` is the e-mail local part (`live.controller.ts:63`) and is published to every viewer, to history and to events → stable per-(user, stream) non-reversible handle; `authorName` keeps its field name, its value changes → personal data must not leave the platform in a public chat (notes: moderation/privacy; constitution VI secrets rule spirit).
- [BREAKING] Reactions are silently clamped to 20 and unknown emoji / zero counts silently skipped (`live.service.ts:116-117`), the DTO only checks "is an object", and a reaction to an unknown or ended stream is accepted (`live.controller.ts:76`) → strict validation, `422` for the whole body, `404` unknown, `409` not `LIVE`, `202` only when counted → a silent clamp hides a client bug and lets a bot inflate nothing; notes: "≤ 20 per emoji per request".
- [BREAKING] The pin is only in Redis with a 24 h key (`live.service.ts:128`), unvalidated product ID, no version → durable on the stream record, `version` per change, product checked through catalog R1 with the shop filter, `422 product_not_pinnable`, `409` unless `LIVE`, cleared on end → a Redis wipe must not unpin the "Buy now" mid-launch, a pin of another shop's product is a cross-tenant leak, versions make out-of-order events harmless.
- [BREAKING] Mutes are a Redis set with a 7-day TTL (`live.service.ts:149`) → durable `LiveMute` table owned by `launch-events` (new migration, registered in `db/ownership.ts`), Redis only as a cache rebuilt from it → moderation decisions must survive a cache wipe; staff cannot be muted (`422 cannot_mute_staff`).
- [BREAKING] `live.comment_removed` carries `reason` as a free string (`moderator:<id>`, `auto:0.93`) → **v2** `{reason: 'moderator'|'auto', actorId?, score?}` → structured fields, no parsing; no consumer outside this domain exists (history writer is rewritten with it).
- [BREAKING] Removal publishes `comment_removed` and an event for ANY commentId, even unknown or of another stream (`live.service.ts:139-144`), and the history writer drops a removal that arrives before its comment (`live-comments.projector.ts:57`, "nothing to mark") → existence check (`404 comment_not_found`), at-most-one event per comment, durable-first order, history upserts so post and removal commute in any order and delivery count → notes call out out-of-order/duplicate events; today a removal overtaking its comment leaves a visible-in-history toxic comment.
- [BREAKING] Priority comments beyond 10 per window are silently dropped (`live-batcher.service.ts:11,56`) → never dropped (they are staff comments bounded by the per-user rate limit) → notes: "always including" highlighted comments; a silent cap breaks the promise.
- [BREAKING] Snapshot is read and sent before the batcher subscribes (`live-stream.controller.ts:44-47`) so a `pin`/`comment_removed`/`status` published in between is lost forever → subscribe first, snapshot second, ordering by `pin.version` / `stats.second` / comment id on the client → a removed comment that stays on a late joiner's screen is a moderation failure.
- [BREAKING] The event connection answers `404` unless the stream is in the active set (`live-stream.controller.ts:29`) → `SCHEDULED` streams accept connections (pre-show) and get `status LIVE` on start; `ENDED` → `409 stream_ended`; the server closes connections after `status ENDED`; per-instance cap with `503 gateway_full`; `skipThrottle` replaced by an address-level open limit → viewers arrive before the start, ended streams must free connections, an unbounded accept loop is a capacity bug.
- [BREAKING] Stream liveness is decided by the global Redis set `live:active` and `get(streamId)` + a membership query run on EVERY comment (`live.controller.ts:60-62`, `live.service.ts:85`) → per-stream cached state from the authoritative record (miss → one shared read, unknown IDs negatively cached 10 s), zero relational reads on a warm stream, set rebuilt by a 30 s reconcile job → the notes' hot path "nothing touches Postgres"; a Redis wipe today makes every live stream answer 409.
- [BREAKING] Synchronous moderation matches banned terms as word PREFIXES (`moderation.ts:30`, `\bscam` also blocks "scampi") → whole-word match after normalization → false positives on a public launch chat are an incident; the disguised spellings stay covered.
- [BREAKING] Comment send order is Redis list → publish → Kafka (`live.service.ts:91-105`): a Kafka failure leaves a visible comment that will never be in history and a client retry duplicates it → durable event first, then visible; optional `clientId` makes retries idempotent; failures are `503 live_unavailable` → notes (chat design: client-generated message ID so retries don't duplicate).
- [BREAKING] The domain barrel exports models, `LiveService`, `Reservoir`, key helpers, the projector and consumer classes (`index.ts:7-23`) and the gateway logic lives in `apps/sse-gateway/src/live/` → export only `LiveModule`, `LiveWorkerModule`, `LiveProjectorModule`, `LiveGatewayModule`, `LiveTopicsModule` and contract types; move the batcher, registry and controller into the domain → X.1/X.4, D-8, D-7.
- [BREAKING] Anonymous reads (`GET /live/:id`) and the SSE open have no address limit and no cache hint → `s-maxage=1`, `live.snapshot.ip` 120/min, `live.events.ip` 30/min (fail open) → 2M viewers refreshing is the expected load shape.

- [CONTRACT] S22 (same domain): the shared `LaunchEventTopics` registers `stream` with `policy: () => true` (`realtime-topics.ts:17`) → S23 owns a separate `LiveTopicsModule`; S22's file keeps only `event` and `queue`; both modules are imported by the sse-gateway app → S22 questions already state S22 exposes nothing S23 may import and lists `LaunchEventTopicsModule`; the `stream` line is S23's.
- [CONTRACT] S22: `launchEventId` of a stream stays an unvalidated plain ID (no read of `LaunchEvent`) → S22 forbids S23 importing its internals and a query on its table would couple the capabilities; clients resolve the event through the public event route.
- [CONTRACT] New outbox events `live.stream_started`, `live.stream_ended` on topic `launch-events.events` → S28 may notify followers and J03 asserts them; `docs/architecture/domain-map.md` "Emits" lists only `live.comment_posted`, `live.comment_removed`: the implementer extends it with `live.stream_started`, `live.stream_ended`, `live.reactions_aggregated` and the v2 of the removal.
- [CONTRACT] `live.reactions_aggregated` per non-empty second → notes: "per-second totals to ClickHouse"; no consumer exists yet (S40 dashboards may read it); emitted straight to the event stream.
- [CONTRACT] S53: high-volume `live.*` events bypass the outbox and use the plain producer; lifecycle events use `outbox.append` → one relational row per comment would defeat the design; lifecycle changes are relational transactions so IX.6 applies.
- [CONTRACT] S50 policy names `live.comment` (3/10 s) and `live.reaction` (5/s) keep today's values and add `live.snapshot.ip`, `live.events.ip` → registry in `rate-limit.types.ts`.
- [CONTRACT] S49: recurring `launch-events.live-reconcile` (30 s, single-run); the 1-second statistics publisher stays a lease-based in-process loop in the worker (a scheduler is not meant for 1 s ticks) → notes: ticker with per-stream lease.

## LOCAL (this capability's internals)

- [LOCAL] Friends' comments of the notes → not offered (no social graph); "highlighted" = staff + own → no data to define friends.
- [LOCAL] Own comments are included on top of the sample, not inside the 5 → the viewer must always see their message.
- [LOCAL] Comment id = uuidv7 (kept); history key = `STREAM#<id>#<minute>` (kept, notes' D24); sharding inside a minute left to plan.md → notes win; capacity risk noted.
- [LOCAL] History writes become upserts (UpdateItem) for both posts and removals → makes them commute; replaces `PutRequest` + conditional update.
- [LOCAL] Removal dedupe marker lives 24 h in the fast store, claimed before the durable write and released on failure → at-most-one event without a table.
- [LOCAL] `clientId` window 10 min, scoped per user → covers client retry horizons.
- [LOCAL] Text normalization: NFC, strip control/zero-width, collapse whitespace; length counted in code points → `@Length` counts UTF-16 units and double-counts emoji.
- [LOCAL] Banned list stays platform config, no per-shop lists → out of scope.
- [LOCAL] Async classifier timeout 2 s, 3 retries, then dead-letter; threshold 0.7 stays → same as today plus failure handling.
- [LOCAL] Statistics publisher keeps the lease loop (`holdLease`, 3 s lease, 1 s tick); `stats` is published every second even when empty → viewer count is part of it.
- [LOCAL] `stats` and `pin` events carry `second` / `version` so clients can ignore stale ones; no Last-Event-ID replay for comments, replay stays on for `pin`/`status`/`comment_removed` via the hub → notes: chat is ephemeral.
- [LOCAL] SCHEDULED → ENDED allowed as "cancel" → streams created by mistake need an exit; no delete route.
- [LOCAL] Viewer cap default 50,000 per instance (notes' capacity model), configurable → validated at start.
- [LOCAL] Authors' `authorId` stays in comment payloads (needed for mute and `mine`) → pseudonymous UUID, not personal data by itself.
- [LOCAL] No staff list route for streams; streams are found through the ID returned at creation → keep scope.
- [LOCAL] No UI journey: no web capability covers live pages; J03 holds the cross-domain happy path.
