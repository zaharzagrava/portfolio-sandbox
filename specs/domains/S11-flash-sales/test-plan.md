# Test Plan: S11 — Flash Sales (domain `orders`)

Constitution VII.8 table: one row per acceptance scenario in [`spec.md`](spec.md) (46 rows), each proven at the lowest layer that can prove it. A dash means the layer does not test that scenario.

- API e2e files live in `packages/backend/libs/domains/orders/`. Each file's top-level `describe` names its feature (VII.8). They boot the real `OrdersModule` and `OrdersWorkerModule` (jobs are invoked through their handlers, as other specs do) with the production prefix, `ValidationPipe`, problem+json filter and interceptors, against real Postgres (real migrations), real Redis (the same major version as production, no eviction policy that drops keys, the sale's buckets spread as in production), the outbox and the job table, and call HTTP through `supertest`:
  - `flash-sale-schedule.e2e-spec.ts` — describe "Flash sales: scheduling, authorization, listing and cancel"
  - `flash-sale-checkout.e2e-spec.ts` — describe "Flash sales: reserving drop units, admission and fail-closed"
  - `flash-sale-lifecycle.e2e-spec.ts` — describe "Flash sales: load, end, reconcile and never oversell" (includes the VII.4 duplicate-delivery and invalid-payload tests of the jobs)
  - `flash-sale-claims.e2e-spec.ts` — describe "Flash sales: release, convert and claim sweeping"
  - `flash-sale-public.e2e-spec.ts` — describe "Flash sales: public view and cache behaviour"
  - `flash-sale-observability.e2e-spec.ts` — describe "Flash sales: metrics and logs"
- Products, shops and stock are seeded and read in tests only through the shared fixture helpers and the catalog's and tenancy's exported services (`ProductQueryService`, `ProductStockService`, `ShopQueryService`); no spec injects `ProductModel`, `PaymentModel`, `UserModel` or `ShopModel` (D-7). Sales are created through the schedule route and loaded by invoking the `flash-sale.load` handler; no spec calls fast-store classes of the domain. Fast-store content is asserted by reading the sale's keys directly through the shared Redis test client (the store is the persisted state of these scenarios). Every test asserts the response body **and** persisted state (sale, history, reservations, orders, outbox rows, jobs, catalog stock, fast-store buckets and quota) and parses responses with the `packages/contracts` schema (VII.6).
- Only system edges are faked: identity token verification, the payments capability's confirmation (S10 conversion is driven through S10's own handler), the realtime transport, and the clock (frozen and advanced; the admission allowance and the window use the injected clock). Faults use real mechanisms: a store rule making the fast store refuse commands (AS-13, AS-32, AS-40), a crash switch between two steps of a job (AS-21, AS-35, AS-36), a gate (latch) inside the order write, a refused outbox append (AS-37), a Redis snapshot restore (flush plus reload of old values) for AS-27 and AS-28.
- Unit specs sit beside the code under `domain/`, are table-driven (`it.each`), and exist only for pure logic (VII.5): `flash-bucket-plan.spec.ts` (with `fast-check` for the allocation and draw invariants), `flash-sale-state.spec.ts`, `flash-admission.spec.ts`, `flash-drift.spec.ts`. Controllers, repositories, jobs and fast-store glue get no unit tests; the existing `infra/flash-stock.service.spec.ts` (mocked Redis) is deleted.
- UI journey (Playwright): `packages/web/e2e/flash-sale.spec.ts` (owned by the web capability for drop pages) — one happy path: the seller's sale (created through the API fixture) is `UPCOMING` with a countdown, the clock reaches the start, the buyer sees `LIVE`, adds the product, checks out at the drop price and sees a reserved order. It never repeats an edge case from this plan.
- Static gates (VII.1): `tsc --noEmit` and ESLint for `packages/backend` and `packages/contracts`; `pnpm check:boundaries`; `pnpm --dir packages/backend check:table-ownership --strict` (AS-43).
- Gate 9 (VII.9): AS-13 (fast store down), AS-32 (release failure), AS-35 and AS-36 (crash between claim and order), AS-37 (outbox failure), AS-40 (public degradation), AS-27 and AS-28 (store restored with wrong content) each force their fault.
- Concurrency tests use `Promise.all` and assert that exactly the allowed number succeed and the invariant holds (VII.3): AS-02, AS-05, AS-10, AS-17, AS-21, AS-25, AS-29, AS-31, AS-40.
