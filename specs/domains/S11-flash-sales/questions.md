## BREAKING (changes behaviour or an API/UI contract that exists today)

- [BREAKING] The drop sells from the moment of loading (`startsAt − 60 s`): the active marker is written by the load job and lives until `endsAt` (`infra/flash-stock.service.ts:52-57`, `infra/order.jobs.ts:44-64`) → selling is allowed only inside `[startsAt, endsAt)` by the injected clock, loading is a warm-up; the status never decides alone → a drop that opens a minute early or closes late is a pricing and fairness bug; the end job may be late.
- [BREAKING] Loading overwrites buckets with `SET` and a re-run of the job refills sold units (`flash-stock.service.ts:54-56`) → buckets are created only if absent, a missing bucket during a sale is "empty" and never recreated; the whole load is idempotent → a redelivered job today can resurrect sold stock, i.e. oversell; III.6 and note 03/04 §6 (a lock is not enough, make the store enforce it).
- [BREAKING] Release is a bare `INCRBY` on the bucket (`flash-stock.service.ts:83-85`), repeated release inflates stock; quota release is a bare `DECRBY` → release and convert are idempotent per claim (a claim record with state), units return to the bucket they came from → cancel plus expiry plus retry all call release; non-idempotent release creates stock from nothing.
- [BREAKING] Stock leaves and returns by raw `UPDATE "Product"` (`infra/order.jobs.ts:50,106`) → only S05's `applyStockDelta` with `orders:flash:<saleId>:load` / `:return` (reasons `flash.load`, `flash.return`) → IX.4 (3 `Product` accesses in flash code), S05's guarantees (all-or-nothing, never below zero, idempotent, reaches S08's sync).
- [BREAKING] Reservation draws from one bucket and falls through only to buckets that hold the whole quantity (`flash-stock.service.ts:73-81`), so `q = 2` can fail with 2 units left (1+1) → a draw may combine several buckets, all-or-nothing, with the draws recorded for exact release → stranded units at the end of a sale are lost revenue; costs one extra Lua step only when no bucket suffices.
- [BREAKING] The checkout path creates the order (S10 writes it first) and only then reserves; today the flash step runs before the order (`checkout.service.ts:93-125`) → keep "before the order" for flash lines through the seam (see `[CONTRACT]` below) → a refused buyer must create no row; at 99% refusal rate order-first would write one cancelled order per refused attempt.
- [BREAKING] The bucket column on the reservation is the only link between order and Redis (`models/stock-reservation.model.ts:25-26`), no claim id → reservation rows keep `sourceRef = claimId` (draws live in the claim); migrations expand/contract → idempotent release and sweeper need a durable key.
- [BREAKING] Sale statuses `SCHEDULED, LIVE, ENDED, RECONCILED` with a check constraint (`models/flash-sale.model.ts:5`, migration `20261001150000…:75`) → `SCHEDULED, LOADED, ENDED, RECONCILED, CANCELLED, START_FAILED`; `LIVE` migrated to `LOADED`; check constraint replaced by expand/contract → "live" is a clock fact, not a stored state; failures and cancels need terminal states (today a failed load leaves `SCHEDULED` forever).
- [BREAKING] `POST /shops/:shopId/flash-sales` takes `price` and answers the ORM row with `201` (`api/orders.controller.ts:64-76`, `orders.dto.ts:13-48`) → `priceMinor`, new field `admissionRatePerSecond`, response `flashSaleMemberSchema` with `Location`, schema in `packages/contracts` → V.1, V.2, minor-unit naming agreed with S10.
- [BREAKING] Create validation: unknown product → `400` today (`orders.controller.ts:68-69`); no lead time, duration, price or stock checks; overlapping sales allowed → `404 product_not_found` (existence hidden), `422 insufficient_stock | drop_price_above_regular | product_unavailable`, min lead 2 min, max 24 h, overlap `409 flash_sale_overlap` enforced by an exclusion constraint → III.4, III.6; two simultaneous sales of one SKU would double-load stock.
- [BREAKING] The flash route reads the product through the injected `ProductModel` and the controller holds queries and job scheduling (`orders.controller.ts:31-32,68-75`) → controller makes one call into an application service; product check via R1 `getProductsByIds(ids,{shopId})`; jobs scheduled in the service in the same transaction as the sale → II.1, III.3, IX.4.
- [BREAKING] No admission control: every checkout of a drop product reaches stock and the order database → per-sale admission allowance (default 2,000/s) answering `429 flash_sale_busy` with `Retry-After`, plus per-buyer `orders.flash-reserve.user` → P0619; note 06/03 §5 (reject early and cheaply); SD-19 scale target 10k attempts/s on a 150 ms p99 budget.
- [BREAKING] Redis failure during a flash checkout surfaces as an unhandled `500` (`activeFor`/`reserve` are not guarded, `checkout.service.ts:93,106`) → `503 flash_sale_unavailable` + `Retry-After: 2`, fail closed, never fall back to regular stock → note 03/04 §8 ("decide what happens when Redis is down"); selling from Postgres while the sale's units live in Redis would double-count.
- [BREAKING] Quota breach answers a free-text `422` (`checkout.service.ts:104`); sold out answers `out_of_stock` without sale reference → `422 flash_sale_limit_exceeded {limit, flashSaleId}`; `out_of_stock` gains `flashSaleId` → clients need a stable code (V.3).
- [BREAKING] Reconciliation runs once after the sale and only logs drift (`order.jobs.ts:84-114`), a `held > 0` check throws a generic `Error` → periodic verification every 30 s during the sale that clamps phantom stock and remediates oversell; final reconciliation waits for holds with an alert counter, returns through `applyStockDelta` → today an oversell caused by a Redis failover is found after the fact, if at all; "never oversell" must hold through failover (note 03/04 §1: replication is async).
- [BREAKING] Jobs renamed `flash-sale.start` → `flash-sale.load` (its meaning), new `flash-sale.verify`, `flash-sale.sweep-claims`; jobs are enqueued with the sale in one transaction → in-flight jobs of the old name are drained or aliased during rollout → name matches behaviour.

- [BREAKING] `infra/flash-stock.service.spec.ts` unit-tests glue with a mocked Redis client and a mocked `allocateEvenly` → deleted; behaviour proved by e2e on a real Redis; unit tests only for the pure bucket/draw/state/admission/drift functions → VII.2, VII.5 (stubbing the project's own store is forbidden).

## CONTRACT (decides something another capability must provide or consume)

- [CONTRACT] S10's FR-025 writes the order first, then reserves → for source `FLASH` the seam has mode `BEFORE_ORDER`: S10 calls `admit` then `reserve` before the order write, `commit(sourceRef)` after it, `release` on failure; the catalog source stays after-order → refused buyers must not create orders; S10 owns the saga, S11 owns the claim.
- [CONTRACT] The seam carries the buyer ID and returns the unit price and `sourceRef` (`reserve(buyerId, lines) → holds | rejected`) → S10's `reserve(order, lines)` has no order yet in this mode, and the price must come from the sale; S10's spec lists only `reserve(order, lines)`, `release(reservation)`, `convert(reservation)`.
- [CONTRACT] S10 never applies the discount port to flash lines and takes `unitPriceMinor` from the hold (today `checkout.service.ts:117-122`) → the drop price is final.
- [CONTRACT] `out_of_stock {productIds, flashSaleId?}`, `flash_sale_limit_exceeded`, `flash_sale_busy`, `flash_sale_unavailable` are added to S10's checkout problem codes (S10 lists `out_of_stock` already) → clients (W03) must render them; the 429/503 carry `Retry-After`.
- [CONTRACT] S10's reservation row is read by S11 (HELD/CONVERTED sums per sale and per claim, newest unpaid first) through an S10 exported query of the same domain, not through SQL on foreign tables (same owner, so SQL is allowed in `infra/` of `orders`) → verification needs "units held or converted for sale X" and "does a reservation with this claim exist".

- [CONTRACT] S05's `applyStockDelta` idempotency window (30 days) and `insufficient_stock` code → S11 needs ≥ 3 days; load and return share the product with S08's sync (it sees both deltas).
- [CONTRACT] Admission is S11's own; S22's waiting room is not a dependency → S22 lacks a spec dependency list yet; a verifier of a signed admission token can be placed in front of `admit` without changing the checkout contract.
- [CONTRACT] Public read routes `GET /flash-sales/:saleId` and `GET /flash-sales?productIds=` are the R2 target of S48 and of the web drop page; the batch returns at most one view per product → BFF composition (IX.7 R2); polling every 1–2 s replaces a realtime topic.

- [CONTRACT] S52's `getOrLoad` with single-flight and stale-while-revalidate serves the public view; if S52 cannot offer jitter on TTL, the 1 s cache is built locally with a promise-coalescing map → P0324 stampede protection.

## LOCAL (internal to this capability)

- [LOCAL] Default buckets 16, min 1, max 256 → matches SD-19 (16–64 spread over shards); 16 is enough for 2,000/s at ~50k ops/s per shard.
- [LOCAL] Admission default 2,000/s, max 10,000, burst = 1 s of rate, evaluated in the fast store with the app's clock → one atomic step, no per-instance drift.
- [LOCAL] Claim window 60 s, order-write margin 20 s, sweeper every 10 s → bounded leak after a crash; margin ≫ order write (lock timeout 2 s).
- [LOCAL] Verification every 30 s per loaded sale, clamp down only → bias toward under-selling; lost releases are recovered after the end.
- [LOCAL] Final reconciliation at `endsAt + 15 min + 60 s`, retry every 60 s, alert after 10 min waiting → matches S10's hold and sweeper.
- [LOCAL] Load lead 60 s, min scheduling lead 2 min, max window 24 h → the lead must exceed job latency; 24 h bounds key lifetimes.
- [LOCAL] Fast-store call timeout 100 ms, no retry in the buyer path → IV.6; reserve is the hot path.
- [LOCAL] Key TTL = window end + hold + 1 h, with ±10% jitter → avalanche protection (note 03/04 §4).
- [LOCAL] Public cache 1 s, remaining count read with a sweep of N buckets via one pipeline → 16 reads in one round trip.
- [LOCAL] Quota is not re-derived from the database during the sale → cost vs. benefit; breach counted at reconciliation.
- [LOCAL] Exclusion constraint for overlapping windows per product on non-terminal statuses → III.6; a unique-index alternative cannot express ranges.
- [LOCAL] `statusReason` values: `insufficient_stock`, `window_missed`, `cancelled_by_shop`.
- [LOCAL] Realtime push of remaining units: not provided now → polling is enough at 1 s freshness.
