# Research: S36 sponsored listings

No `NEEDS CLARIFICATION` remains: the defaults of `questions.md` are accepted as written and no line was edited by a human. Each entry is a decision the plan relies on. **Check** marks a fact the first task that depends on it must confirm in the running code (it was read at plan time, not executed).

## R-1 Layering: ports in `domain/`, adapters in `infra/` (D-6, L1, L2)
**Decision**: `application/` is split into `campaign-command.service.ts`, `campaign-query.service.ts`, `serving.service.ts`, `click.service.ts`, `billing-statement.service.ts`; the money jobs are `application/hourly-billing.service.ts` and `application/reconciliation.service.ts` called by thin handlers in `infra/ads.jobs.ts`. Ports (interfaces + tokens) in `domain/ads-ports.ts`: `CampaignStore`, `ProductSnapshotStore`, `ShopSnapshotStore`, `BillingStore`, `SpendCounter`, `ImpressionMarker`, `SpamCounters`, `ClickLog` (publisher), `RawClickReader`, `AggregateReader`, `LedgerPort`, `CatalogPort`, `ShopDirectoryPort`. `Clock` from `@app/common/core/clock`. `ADS_CLICKS_TOPIC`, `ClickRecord` move to `domain/`. **Rationale**: pays D-6; lets e2e wrap one adapter with a failure/delay injector (VII.9) without mocking the project's own stores. **Alternatives**: keep concrete classes and spy (hides wiring errors, L-015).

## R-2 Campaign invariants live in the store
**Decision**: one partial unique index `AdCampaign_open_product_uq ON ("productId") WHERE status <> 'ENDED'` (AS-06). The 50-per-shop limit uses a counter row `AdShopQuota("shopId" PK, "openCount" int CHECK (0..50))` changed by `INSERT … ON CONFLICT ("shopId") DO UPDATE SET "openCount" = "AdShopQuota"."openCount" + 1 WHERE "AdShopQuota"."openCount" < 50 RETURNING` (no row returned → `422 campaign_limit_reached`) and decremented in the same transaction by `end` (AS-07, III.6). Transitions are `UPDATE … SET status, "statusReason", "campaignVersion" = "campaignVersion" + 1 WHERE id AND "shopId" AND status = :from` asserting one row (AS-10). **Rationale**: a count-then-insert would let two creates at 49 both win. **Alternatives**: advisory lock per shop (works but hides the invariant outside the schema); `SELECT count(*) … FOR UPDATE` (does not lock absent rows).

## R-3 One transaction per command, outbox inside it
**Decision**: every campaign command is one `TransactionRunner.run` (S54): campaign row, `AdCampaignHistory` row, `AdProductSponsorship` row (only when the sponsored value changes: `UPDATE … WHERE "productId" = :p AND sponsored <> :v` returning the new version), quota, and `OutboxService.append` for `marketing.campaign_*` and `marketing.product_sponsorship_changed`. No network call inside. The R1 call that seeds the snapshots (R-5) runs **before** the transaction. `sponsorshipVersion` is the aggregate version of the sponsorship event; `campaignVersion` that of the campaign event, so each rises by exactly 1 per event of one aggregate (event framework rule). **Rationale**: III.3, III.7, AS-75 (rollback leaves nothing).

## R-4 Event definitions and topic
**Decision**: `defineEvent` for `marketing.campaign_created|paused|resumed|ended` and `marketing.product_sponsorship_changed` in `application/events/ads-events.ts`, aggregate type `marketing` → topic `marketing.events`, `carries: 'state'` for the campaign events (the payload is the full campaign) and `'state'` for the sponsorship (the whole value). Payload schemas live in `packages/contracts/src/marketing/ads.ts` (S32 imports them). The barrel exports the five definitions (S32 reads the sponsorship one). **Check**: `topic-registry.ts` and `topic-policy` accept two aggregate ids (`campaignId`, `productId`) on one topic; if the registry needs one key space, register the topic with `key: 'aggregateId'` and keep `latest-per-key` off (the topic is a log, not compacted).

## R-5 Read models (R3) and staleness
**Decision**: Postgres tables `AdProductSnapshot` and `AdShopSnapshot` owned by `marketing`, written by two projectors in `AdsProjectorModule`: `ads-product-snapshot` on `products.events` (handles `ProductCreated|Updated|Archived|Restored|Deleted` from `@app/domains/catalog`), `ads-shop-snapshot` on `tenancy.events` (`ShopStatusChanged`, `ShopOffboardingStarted`, `ShopDeleted`; the other tenancy events are skipped by the framework). Idempotency mechanism: **versionGuard** — `INSERT … ON CONFLICT (id) DO UPDATE … WHERE "AdProductSnapshot"."productVersion" < EXCLUDED."productVersion"`; zero rows → stale/duplicate → no effect, no campaign change (AS-70). Effects on campaigns (archive → pause `product_unavailable`, delete → end, shop deleted → end all) run in the same transaction as the snapshot upsert, only when the upsert applied. The snapshot keeps `title, category, priceMinor, currency, inStock, status, isSandbox, shopId, productVersion` (`priceMinor` and `currency` are needed by the serving response; the spec's read-model list omits them: added). Seeding at creation: `ProductQueryService.getProductsByIds([id], {shopId})` and `ShopQueryService.getShopsByIds([shopId])` (R1) then the same guarded upsert (AS-74). **Maximum staleness accepted (FR-063): 60 s at the 99th percentile of consumer lag for both read models**; alert on `projection lag > 60 s`; a seller action (pause/end) is immediate because it changes the campaign row itself (SC-009). A snapshot missing for a shop or product means "not served". **Check**: names/exports of `ShopQueryService.getShopsByIds` fields `status`, `shopVersion` (read at plan time: present); tenancy event payload fields `from/to/shopVersion` (spec assumes them; `ShopOffboardingStarted` carries `purgeAt`, `shopVersion`, `ShopDeleted` carries `shopVersion`).

## R-6 Serving query and ranking
**Decision**: one SQL on marketing-owned tables only: `AdCampaign c JOIN AdProductSnapshot p JOIN AdShopSnapshot s WHERE c.status = 'ACTIVE' AND (:category = 'all' OR c.category = :category) AND p.status = 'ACTIVE' AND p."inStock" AND NOT p."isSandbox" AND s.status = 'ACTIVE' AND NOT s."offboarding" ORDER BY c."cpcMinor" DESC, c.id ASC LIMIT 50` (bounded candidate set, `questions.md` LOCAL), served by a partial index on `(category, "cpcMinor" DESC, id) WHERE status = 'ACTIVE'`. Spend counters are read with one `MGET` (100 ms timeout; failure or timeout → `200 {items: []}` and `ads_impressions_total{result="degraded"}`; a database failure → `503`). The pure function `selectSlots(candidates, limit)` (`domain/slot-ranking.ts`) sorts by CPC desc then `campaignId` asc, keeps the best candidate per shop, cuts to `limit`. **Spend counter semantics** (G19): `adspend:{<campaignId>}:<YYYY-MM-DD>` counts **counted valid clicks** (not money); serving admits a campaign when `(clicks + 1) × cpcMinor <= dailyBudgetMinor` (CPC is immutable, so the product is exact); a counted click increments it with `INCR` + `EXPIRE` on first write (TTL 2 days). The click path therefore never reads Postgres and the token never carries a price (FR-012). The counter is a pacing hint; the charge is capped by the billing arithmetic (R-12).

## R-7 Click token
**Decision**: `domain/click-token.ts` (pure, `node:crypto` only): token = `v1.<kid>.<payload>.<signature>`; `payload` = base64url JSON `{i: impressionId uuid, c, s, p uuid, e: expiry epoch ms int, v: viewer hash 32 hex}`; `signature` = full 32-byte HMAC-SHA256 base64url over `v1.<kid>.<payload>`. `kid` = first 8 hex of `HMAC(secret, 'ads:kid')` (so a key ID reveals nothing and rotation selects the key without trying both). Subkeys: signing key = `HMAC(secret, 'ads:token')`; viewer and address hashing keys = `HMAC(secret, 'ads:viewer')`, `HMAC(secret, 'ads:ip')` (domain separation: the same secret never signs and hashes raw). Verification: length ≤ 2,048, exactly 4 segments, kid ∈ {current, previous}, `timingSafeEqual` on equal-length buffers, then zod claims shape, then `now >= e` → `expired`; returns a discriminated union `{ok: true, claims} | {ok: false, reason: 'invalid' | 'expired'}`, never throws. `viewer hash` = first 16 bytes hex of `HMAC(viewerKey, userId | anonymousId | ip)` (the caller passes whichever exists, `user:` / `anon:` / `ip:` prefixed). **Rationale**: FR-013/014, AS-24/25. **Alternatives**: JWT (alg-confusion surface, readable claims we do not want in a standard shape).

## R-8 Click path: ordering, timeouts, never an error
**Decision** (`ClickService.handle(token, meta)` returns a union and **never throws**; the controller maps it to a `302`):
1. HEAD or `Sec-Purpose: prefetch` / `Purpose: prefetch` → verify the token only to choose the `Location`; no marker, no record (AS-31).
2. Verify → invalid/expired → home (`front/`), metric, stop (AS-29).
3. `SET adclick:<impressionId> NX EX 2100` (token life + 5 min) with a 100 ms timeout. Already set → `duplicate`, redirect, stop. Store error/timeout → record `valid 0 / filter_unavailable` (AS-35); no marker exists, so replays of that token inside the outage may publish twice — the raw log and the aggregator both dedupe by `click_id` (first verdict wins).
4. Counters (only after the marker was won, so replays never poison them, AS-40): three single-key Lua scripts in parallel (`INCR`, `EXPIRE` only when the result is 1, fixed UTC minute/hour in the key): address-per-minute, address-per-campaign-per-hour, viewer-per-campaign-per-hour. Each is atomic, so 25 concurrent clicks get counts 1…25 and exactly 20 are valid (AS-38). Single-key scripts stay valid on a clustered Redis. All three share the 100 ms budget.
5. `decideSpam(addressMinute, repeatHour, thresholds)` (pure) → reason or valid.
6. Publish to `ads.clicks` with the idempotent producer and a 1 s timeout, key `campaignId#<murmur3(clickId) mod 10>` (`libs/common/core/murmur3.ts`, deterministic). Failure → `DEL` the marker, metric `record_failed`, redirect anyway (AS-34). A publish that times out but later lands is a duplicate downstream and harmless.
7. On a counted valid click `INCR` the spend counter (fire-and-forget with timeout; failure only logged).
The address is `request.ip` as resolved by the platform bootstrap from `trusted_proxies` (`infrastructure/platform/client-ip.ts`); the service never reads `CF-Connecting-IP` or `X-Forwarded-For` itself (FR-024, AS-32). **Check**: `bootstrap-http.ts` sets express `trust proxy` from `trusted_proxies` so `request.ip` is correct; if it exposes a helper (`resolveClientIp`) use it instead. The click route is `@RateLimitExempt()` and uses `@Firewall({anonymous: true})`; a last-resort `try/catch` in the service maps any unexpected error to `record_failed` + home redirect, so even a bug cannot produce a `5xx` (FR-020). A counter hit by an `ip_burst` verdict still advances the repeat counters (recorded, simple, documented).
Timestamps: `received_at` is `clock.now()` formatted `YYYY-MM-DD HH:mm:ss.SSS` (UTC, ClickHouse `DateTime64(3)` input format); `adClickRecordSchema` validates the format and the verdict pair (`valid 1` ⇒ `invalid_reason null`).

## R-9 Aggregator on the S53 pipeline; ClickHouse writers with dedupe tokens (S53 G-44)
**Decision**: `ClickAggregator` becomes a `TransactionalPipeline.run` spec: `groupId ads-click-aggregator`, `inputTopic ads.clicks`, `fromBeginning true` (G22), `transactionalId = ads-click-aggregator-<ads_aggregator_instance>` where `ads_aggregator_instance` is a **required** config key naming the replica slot (stable across restarts, distinct between live replicas: a StatefulSet ordinal or a fixed task slot), validated at startup (G20; a default would make two replicas fence each other). The handler parses each message with `adClickRecordSchema`; unparseable/invalid ones (including `received_at` > 5 min ahead or > 7 days behind, using the injected clock) are sent to `ads.clicks.dlq` **inside the same transaction** with header `reason` (the DLQ write commits or aborts with the offsets — a poison message never blocks, AS-47). Valid records go through the pure `aggregateBatch(partition, firstOffset, records)` where `firstOffset` is the offset of the batch's first **message** (valid or not), clicks count once per `click_id` per batch (first verdict) and the output is order independent (AS-42). Output to `ads.click-aggregates`. Late clicks (processing time − `received_at` > 2 min) keep their own minute and increment `ads_late_clicks_total` (AS-48). Fencing: the pipeline sets `fenced`; the aggregator increments `ads_aggregator_fenced_total` and exits readiness (the pipeline already stops itself). A start-up failure **fails the worker start** (G23) instead of a warning.
Writers into ClickHouse, replacing the Kafka-engine queue tables and materialised views of `080_ads.sql` (their `read_committed` setting was server-level and untestable): two consumers in `AdsWorkerModule` read `ads.clicks` (log writer) and `ads.click-aggregates` (`isolation read_committed`; aggregate writer) and write with `ClickHouseSink.insert(table, rows, {dedupeToken: '<topic>:<partition>:<first>:<last>'})`. A redelivered batch is deduplicated by the server; a re-batched overlap is collapsed by the key. **Check**: `KafkaConsumerService` can set `readUncommitted: false` (the pipeline does); otherwise use kafkajs directly in `infra/` like `TransactionalPipeline`.
**Raw log** `ad_clicks_log` (new table, `MergeTree`, not Replacing): rows are never replaced at merge time, because "latest wins" is the defect G25; reconciliation reads `GROUP BY click_id` with `argMin(valid, (received_at, ingested_at))` and `min(received_at)`, so the first recorded verdict is kept deterministically (AS-49). **Aggregate table** `ad_click_minute_v2` stays `ReplacingMergeTree` keyed `(campaign_id, minute, source_partition, first_offset)` with a `FINAL` read; the per-minute total sums the partials (AS-46). The old tables stay for one release (contract step in a later task of S36's follow-up; the old queue tables/views are dropped in the same DDL file because they would otherwise keep consuming `ads.clicks` with fields they do not know).

## R-10 Hourly charge: three steps, convergent on the ledger reference
**Decision** (`HourlyBillingService.billHour(hourIso?)`, no clock reads outside `Clock`):
- Hour selection: no payload → `floor((now − 5 min) / 1 h) × 1 h − 1 h`; explicit hour refused with `hour_not_closed` when `now < hourEnd + 5 min` (the stricter reading of FR-040: both "no earlier than 5 minutes after the hour ends" and AS-56 hold).
- Aggregates: `SELECT campaign_id, sum(clicks) FROM ad_click_minute_v2 FINAL WHERE minute >= H AND minute < H+1h GROUP BY campaign_id` through `AggregateReader` (timeout 10 s).
- Per campaign: **tx A** (marketing) `INSERT INTO "AdBillingRun" … ON CONFLICT DO NOTHING` with state `PENDING`, frozen `clicks`, `billableClicks`, `cappedClicks`, `amountMinor` computed from `billable()` and `billedEarlierToday` = net of the same UTC day's earlier hours (`amountMinor` + posted adjustments); orphan aggregate (no campaign row) → skipped + `ads_billing_orphan_aggregate_total`. **tx B** (ledger only, `TransactionRunner.run`) `LedgerService.postJournal({kind:'AD_CHARGE', reference:'ad:<campaignId>:<YYYY-MM-DDTHH>', currency:'EUR', lines:[{accountId: shopAccount(shopId), amountMinor: −amount}, {accountId: LEDGER_ACCOUNTS.PLATFORM_FEES, amountMinor: +amount}]})`; `created:false` is success. **tx C** (marketing) `UPDATE "AdBillingRun" SET state='CHARGED', "journalId" = :id WHERE … AND state='PENDING'`. A run found `PENDING` goes straight to tx B/C with its **stored** amounts (never recomputed, so a crash converges to the amount first decided). Amount `0` → the run is inserted `CHARGED` with no journal (AS-53). `LedgerBusy` fails the job (S49 retries, `maxAttempts` set); nothing runs a network call inside a transaction (FR-043).
- Races: two runs for the same hour both try tx A; one inserts, the other sees the row and continues idempotently; the ledger's `(kind, reference)` uniqueness makes the second posting `created:false`.
`LedgerService` is imported from `@app/domains/payments` (R1) behind `LedgerPort`; `LedgerModule` is still the module that provides it (the barrel exports no narrower token today). The two `sequelize.transaction` sites (`.tx.baseline` = 2) are deleted with their `// S54 T037 audit` comments.

## R-11 Reconciliation and period close
**Decision** (`ReconciliationService.reconcileDay(day?)`): default window = the 3 closed UTC days before today; an explicit `day` is processed whatever its age. Per day: `INSERT INTO "AdReconciliationRun"(day, status 'RUNNING')` guarded by the partial unique index `("day") WHERE status = 'RUNNING'`; a unique violation → this racer is skipped (logged only: AS-76 fixes the metric list, so there is no `skipped` status label), a RUNNING row older than 30 min is first marked `FAILED/abandoned` (crash recovery). Exact clicks come from `RawClickReader.exactValidClicksByHour(day)` (10 s timeout; failure → run `FAILED`, reason `source_unavailable`, no money, job returns normally). For each campaign with raw clicks or runs that day: hour-ordered pure function `exactDay(clicksByHour, cpc, budget)` applies the cap on **exact** clicks (AS-61); `adjust(exactMinor, netMinor)` gives the delta; non-zero → `AdBillingAdjustment(campaignId, hour, sequence = max+1)` inserted `PENDING` (PK collision = lost race, skip), ledger posting `ADJUSTMENT` with reference `ad-adj:<campaignId>:<hour>:<sequence>` (shop line `−delta`, fees `+delta`; negative delta refunds), then marked `POSTED` with `postedAt = now`. An hour with raw clicks and no run creates the run `source = 'reconciliation'` and the `AD_CHARGE` journal with the **same** reference as the hourly job (AS-60). Closed days are never rewritten because adjustments are separate rows dated at posting time; runs, charge journals and earlier adjustments are only read. Drift: `|exactClicks − netBillableClicks| / exactClicks` per day, gauge `ads_reconciliation_drift_ratio{day}` (only the last 7 days' series are kept: bounded label set) and a `warn` above 1%.
Campaign CPC and budget come from the campaign row (immutable, `questions.md` LOCAL), so the recomputation is reproducible.

## R-12 Billing arithmetic
**Decision**: pure `billable(clicks, cpcMinor, dailyBudgetMinor, billedEarlierTodayMinor)` with `billableClicks = max(0, min(clicks, floor((budget − earlier) / cpc)))`, `amount = billableClicks × cpc`, `cappedClicks = clicks − billableClicks` (`domain/billing-math.ts`); `adjust(exact, net) = {delta: exact − net}` in `domain/adjustment-math.ts`. All integers (`Number.isSafeInteger` guard: 10,000,000 × … stays far below 2^53). `fast-check` properties with a fixed seed.

## R-13 Statement
**Decision**: one query over `AdBillingRun` left-joined to `AdBillingAdjustment` (aggregated per `(campaignId, hour)` with `json_agg` ordered by `sequence`), `WHERE "campaignId" = :c AND hour >= :from AND hour < :to` (the campaign is first loaded with `WHERE id AND "shopId"`, so another shop's id answers `campaign_not_found`), ordered `hour DESC`, keyset `(hour)` with a signed cursor (`domain/ads-cursor.ts`). Campaign list cursor `(createdAt, id)` uses the same helper bound to the shop id. **Check**: whether `domain/list-cursor.ts` of S37 can be generalised; it is share-link specific (`code`), so a sibling helper is written, not an edit of S37's file.

## R-19 Pool arithmetic (III.12)
**Decision**: the worker process holds one shared Sequelize pool (`db_pool_max`, default read from `database.module.ts`); S36 adds no pool. Concurrent users of that pool inside the worker are bounded by construction: the hourly job processes campaigns sequentially (one transaction at a time, at most 1 connection held), reconciliation likewise (1), the read-model projectors run in `apps/projector` with their own pool (concurrency of the projection framework per partition, upsert + campaign effect in one transaction: ≤ 1 connection per in-flight batch). Worst case in `apps/worker`: 2 jobs × 1 connection = 2 of `db_pool_max`; in `apps/core` the campaign endpoints hold 1 connection per request, bounded by the rate limiter (60 writes/min/shop). The 3 s acquire timeout already fails fast. Statement and lock timeouts: `TransactionRunner.run` options `lockTimeoutMs: 2000`, `statementTimeoutMs: 5000` on commands, `10000` on the jobs.
