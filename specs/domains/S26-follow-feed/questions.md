# Questions and decisions — S26 Follow graph and home feed

Taken unattended under the decision policy (most production-grade option the notes and constitution support). Sorted by impact: BREAKING first, then CONTRACT, then LOCAL. Review BREAKING and CONTRACT lines first.

## BREAKING

- [BREAKING] Feed cursor and envelope (today `GET /feed?before=<ms>` → `{items, nextBefore}`, ms-only, `feed.controller.ts:16`, `feed.service.ts:139`) → `GET /feed?limit=1..50&cursor=` → `{items, nextCursor, degraded?}` with an opaque cursor of `(time, itemId)`; invalid limit/cursor → `400`; unknown query parameters rejected → items sharing a millisecond are skipped or repeated by a time-only cursor; III.10 requires a unique tiebreaker and an opaque cursor; notes §9 "cursor pagination for free".
- [BREAKING] Deterministic merge order (today the heap compares `ms` only, `merge.ts:25`, so ties are arbitrary) → newest first by `(ms, itemId)` descending everywhere (pushed timeline, celebrity merge, rebuild) → a stable total order is what makes cursors correct.
- [BREAKING] Publishing into the feed (today any domain injects the global `FeedPublisher`/`FeedService` and calls `publish(authorId, kind, title, payload)`; `FeedModule` is `@Global`; `ProductFeedProjector` decides "first sighting" with a 30-day Redis `NX` key, `product-feed.projector.ts:32`) → feed items are created only from events (`catalog.product_*`, `discussion.post_*`, `auction.created|opened`) with one item per `(kind, source)` guaranteed by the store, not a time-limited key; `FeedPublisher` stops being exported; the `FeedModule` global goes → a Redis key that expires or is flushed double-publishes products; IV.1/IV.4 (events, not in-process dual writes); S25 already removed its call.
- [BREAKING] Product items read the catalog (`ProductModel.findAll`, `product-feed.projector.ts:25`, price as `Number(p.price)`) → R3 copy of S05's snapshot events (`productId, shopId, title, priceMinor, currency, status, isSandbox, productVersion`) in a store `community` owns; item payload `{productId, priceMinor, currency}` in integer minor units (today `{productId, price: float}`) → IX.4/IX.7 R3/IX.8, III.8 (no floating-point money); payload shape changes for any client.
- [BREAKING] Item shape → `{itemId, kind, author: {accountId, type, name}, title, payload, createdAt}` with typed payloads per kind (today `{itemId, authorId, kind, title, payload: Record<string, unknown>, createdAt}` and `kind: string`) → V.1/V.2 explicit contract schemas; shop name composed from S03 (R1) so the UI needs no extra call.
- [BREAKING] `GET /me/following` (today unpaged `string[]`, returns the cached set in arbitrary order, `feed.service.ts:74`) → `{items: [{accountId, followedAt}], nextCursor}`, newest first, `limit` 1–100 → III.10 and unbounded responses; a cached set is also a source of truth for "who do I follow", which III.9 forbids.
- [BREAKING] Follow target validation (today a regex only: any well-formed UUID can be followed, shop or user, existing or not; self-follow is `400`, `feed.controller.ts:6,24`) → shops via S03 `getShopsByIds` and users via S01 `getUsersByIds` (R1): unknown, deleted, `DELETING`, `DELETED` → `404 account_not_found`; self-follow → `422 cannot_follow_self`; uppercase UUIDs rejected → follower counts and fan-out pages of ghost accounts are a spam surface; V.4 (422 is semantic validation).
- [BREAKING] Following limit 2,000 per user (today unbounded) → `422 following_limit_reached`, store-enforced under concurrency → the rebuild pulls once per followed author, so its cost needs a bound; III.6.
- [BREAKING] Follower counter and celebrity flag (today a Scylla counter incremented only when a Redis `SADD` says "new", plus a Redis `INCR` and a Redis `CELEBRITIES` set that is the only record of celebrity status, `feed.service.ts:57-59`, `fanout.consumer.ts:41`) → count derived from follower records and reconciled daily; celebrity status derived from the durable count, sticky, rebuilt after a Redis loss → III.9 (cache is never the source of truth); today a Redis flush turns every celebrity into a normal account and resumes millions of pushes.
- [BREAKING] Follow, unfollow writes (today two inserts in parallel then a Redis `SADD`, with no recovery from a crash between them, and unfollow of a missing relation decrements nothing but follow of an existing one with a cold cache increments again) → both directions converge, count equals relations, concurrent follow/unfollow end consistent, daily reconciliation; follow invalidates the pushed timeline so the next read includes the author's recent items → counts and the two tables otherwise drift; following a shop and seeing nothing is a bug for the buyer.
- [BREAKING] Redis keys all get an expiry (today `tl:`, `celeb:`, `following:`, `followers:`, `feed:celebrities` never expire; `active:` does) and every pushed timeline is rebuildable → III.9 (every key has a TTL).
- [BREAKING] Rebuild safety (today `DEL` then `RPUSH` after reading, `feed.service.ts:117-119`, drops items pushed in between; the active marker is set before the rebuild, so a failed rebuild leaves an "active" user with an empty list) → pushes during a rebuild are never lost; the rebuild is recorded complete only when every author was read; a missing timeline for an active user triggers a rebuild → correctness over the cheapest change.
- [BREAKING] Reading past the pushed window (today the list is the only source for non-celebrity items; paging ends at 800 entries) → paging continues from durable per-author history → a feed that dead-ends after 800 items is a defect, notes §9 keeps 800 as a cache bound, not a history bound.
- [BREAKING] Out-of-order pushes (today `LPUSH` appends in arrival order and the merge assumes each list sorted) → the pushed timeline is always read newest-first by `(ms, itemId)` → late events and redelivery otherwise reorder pages.
- [BREAKING] Hydration (today one Cassandra `SELECT` per item with pool concurrency 32, `feed.service.ts:123-136`, and only an "author still followed" filter) → one batch per source per page, parallel with timeouts; deleted posts (S25 R1), non-ACTIVE or sandbox products (own copy), non-ACTIVE shops (S03 R1) hidden; fail closed on visibility with `degraded: true`; page fill (scan ≤ 5 × limit) → notes §9 "deleted or protected tweets must be filtered at hydration time", P0101 (`allSettled` partial responses), N+1 forbidden by IX.7 R1.
- [BREAKING] Redis down → feed served by pull with `degraded: true` (today every read throws `500`) → VII.9 degradation path; availability.
- [BREAKING] Errors → problem+json codes `validation_failed`, `account_not_found`, `cannot_follow_self`, `following_limit_reached`, `invalid_cursor`, `rate_limited`, `feed_unavailable` (today plain `BadRequestException` messages) → V.3.
- [BREAKING] Rate limits → profiles `follow.write` (30/min/user, fail closed) and `feed.read` (120/min/user, fail open); today none on any of the four routes → follow/unfollow churn drives fan-out and counter writes; an uncapped feed read triggers a full rebuild.
- [BREAKING] Event `feed.item_published` (today `{itemId, authorId, ms}` produced straight from `FeedPublisher.publish` after two Scylla inserts, no recovery if the send fails, `feed-publisher.service.ts:49`) → `{itemId, authorId, kind, createdAt}`, recorded with the item and relayed at least once → IV.4 (no dual write); a failed send today loses the fan-out of an item that is already stored.
- [BREAKING] `FeedFanoutConsumer` and `ProductFeedProjector` stop being exported from the barrel; `apps/projector` imports a `FeedWorkerModule`/projector module of the domain instead (`index.ts:11-12`, `projector.module.ts:15,52`) → X.4 and debt D-8.
- [BREAKING] Existing e2e (`feed.e2e-spec.ts` calls services, not HTTP; sets `CELEBRITIES` in Redis directly; replaces the producer with a mock) is replaced by HTTP-level specs → VII.2/VII.6.

## LOCAL

- [LOCAL] Celebrity threshold → 10,000, configurable; hysteresis rejected, status sticky → SD-09 notes say 10k, table says 50k; sticky avoids a window of unpushed items.
- [LOCAL] Active window 7 days, pushed window 800, celebrity recents 200, retention 90 days, rebuild 50 items per author from the last 60 days → SD-09 values; retention is new.
- [LOCAL] Price drop → any decrease, at most one item per product per 24 hours → anti-spam; the first drop wins.
- [LOCAL] Following is naturally idempotent, no `Idempotency-Key` → V.6 does not list follows.
- [LOCAL] Suspended shops can be followed, their items are hidden → a suspension is reversible.
- [LOCAL] Product visibility from the own copy, posts and shops synchronously on read → staleness bound 10 s for products; deletion of posts and suspension of shops must be immediate.
- [LOCAL] Out-of-order: `post_deleted` is remembered 30 days; archived/deleted products hide by version; an event whose product copy is missing is retried ≤ 5 times then dead-lettered.
- [LOCAL] Fan-out dedupe → a completed-event marker plus read-time dedupe; no per-follower dedupe on write.
- [LOCAL] Restock items, seller-authored posts, muting, blocking, who-to-follow → out of scope.
- [LOCAL] Reconciliation runs daily; counts recomputed only for accounts with at least one follower record; the buyer-side record wins on half-written relations.
- [LOCAL] Maximum staleness accepted by this capability for R3 copies (to be repeated in `plan.md`) → 10 seconds.
