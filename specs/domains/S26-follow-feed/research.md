# Research: S26 — Follow graph and home feed

No `NEEDS CLARIFICATION` remains: `questions.md` defaults are accepted as written (no line was edited by a human). The items below are the design decisions the spec leaves to the plan, checked against the code in `libs/domains/community`, `libs/infrastructure/{projections,events,jobs,rate-limit,cassandra}`, `packages/contracts/src/{catalog,auctions,community}` and the S25 plan (whose patterns S26 reuses on purpose: same store technology, same ownership, same missing PostgreSQL table).

## R-1 Follow relation: one conditional write decides, the other side follows by timestamp

- **Decision**: `following_by_user ((user_id), account_id)` (existing) is the truth of a relation. New columns: `active boolean`, `rel_ts bigint` (a per-relation sequence in microseconds). Follow = `INSERT … IF NOT EXISTS`, or, when the row exists with `active = false`, `UPDATE … SET active = true, followed_at = ?, rel_ts = ? IF rel_ts = ?`. Unfollow = `UPDATE … SET active = false, rel_ts = ? IF rel_ts = ? AND active = true`. `rel_ts` of a transition is `max(now_micros, previous + 1)`, so it rises by at least 1 per transition. The three derived rows (`followers_by_account`, `following_by_time`, and the counters) are written **after** the winning conditional write, with `USING TIMESTAMP rel_ts` (inserts and deletes alike). Last-write-wins on the cell timestamp then makes the two directions converge to the transition with the highest `rel_ts` in whatever order the writes land, which is what AS-06 asks for (20 racing follow/unfollow pairs end with both sides equal). Legacy rows (no `rel_ts`, `active` null) are read as active and migrate on first write (`IF rel_ts = null`).
- **Why**: A2/A3 come from "Redis says new" deciding the count and two plain writes that can interleave. A conditional write on the buyer-side row is the single linearisation point; the other side cannot be ordered by a second LWT (different partition), but timestamps taken from the winner's sequence need no further coordination. Inactive rows stay in `following_by_user` (a tombstone with a sequence) instead of being deleted, because a delete would lose the sequence a late follower-side write must lose against.
- **Counters**: `follower_counts` (counter) is incremented / decremented only by the request whose conditional write applied (never by a cache answer), so concurrent identical follows count once (AS-03). A counter cannot be floored, so reads return `max(0, value)` and the reconciliation corrects drift by delta (R-8).
- **Alternatives**: Redis `SADD` as the check (today, III.9 forbids); one logged batch over both sides plus an LWT (Scylla cannot mix LWT and a multi-partition batch); a serial queue per user in Redis (a lock that expires is the S25 C3 defect).

## R-2 Following limit under concurrency

- **Decision**: `following_counts ((user_id)) n int`, reserved **before** the relation write: read `n`, if `n >= limit` and the relation is not already active → `422 following_limit_reached`; else `UPDATE … SET n = n + 1 IF n = ?` (≤ 3 attempts; on exhaustion `409 follow_in_progress` with `Retry-After: 1` is avoided: the third failure re-reads and answers by the then-current state). If the relation write then loses (already active) the reservation is released with the inverse CAS. Unfollow decrements after its conditional write applied. A crash between reserve and write leaves `n` one too high (the safe direction); reconciliation recomputes `n` from `following_by_user` (R-8).
- **Why**: AS-07 needs exactly one of two concurrent follows at limit-1 to win, and "nothing stored" for the loser; reserve-first never exceeds the limit even for an instant, and a re-follow at the limit succeeds because the existing-relation check comes first.
- **Alternatives**: count rows per request (`SELECT COUNT` on a 2,000-row partition per follow, and still check-then-write); insert then verify (rows above the limit visible for a moment, AS-07 "nothing stored" harder to prove).

## R-3 Celebrity status is durable and sticky

- **Decision**: `celebrity_accounts ((account_id)) since timestamp, followers_at_promotion bigint`. After a follow that applied, the service reads the account's counter; when it is ≥ the threshold it runs `INSERT … IF NOT EXISTS` (idempotent, sticky: never deleted by code) and deletes `cel:{account}` so the recents are rebuilt from history. Fan-out asks `CelebrityStatusPort.isCelebrity(accountId)`: Redis set `celeb:set` is a one-hour-TTL read-through cache over the table (miss → table). A Redis loss therefore changes nothing (AS-28).
- **Race (AS-27)**: promotion happens after the follower row exists. An item fanned out before promotion is pushed to active followers and also sits in history; one fanned out after promotion is not pushed but is in the recents (rebuilt from `items_by_author` on a miss, and appended by fan-out when the key exists). Both paths read from the same durable item, and the read-time merge de-duplicates by `itemId`, so each follower sees it once, never zero times.
- **Alternatives**: a Redis flag (C1 defect); recomputing from the counter at every fan-out (a counter read per event is cheap but loses stickiness AS-29).

## R-4 One item per `(kind, source)`: a claim row, not a marker with a TTL

- **Decision**: `item_claims ((kind, source_key)) item_id` written with `INSERT … IF NOT EXISTS` carrying a freshly generated item id; when not applied the existing `item_id` is used, so concurrent and repeated deliveries converge on one id (AS-15). `source_key`: `productId` (`new_product`), `productId:<UTC day>` is **not** used for price drops: the 24-hour rule is a claim `(price_drop, productId)` written `USING TTL 86400` (the spec's rule is time-limited by definition), `postId` (`post`), `auctionId` (`drop_announced`, `auction_started` have different `kind`). The item rows and the announcement row (R-5) are then written in one **logged batch** keyed by that `item_id`; a crash after the claim and before the batch is repaired by the redelivered source event, which finds the claim, reuses its id and re-runs the (idempotent) batch.
- **Item id**: a time-ordered id built from the **event's `occurredAt`** (S25 `domain/ids.ts` `TimeIdGenerator` with an injected clock and random source), so ordering follows source time and a late event does not jump the queue; `sortableId` gives the string used in Redis members and cursors. Order everywhere is `(ms desc, sortableId desc)`.
- **Alternatives**: Redis `NX` with 30-day TTL (B3); deterministic UUIDv5 from the source (no claim table, but the time component is lost, and ordering by creation time is required).

## R-5 Announcements without a SQL transaction

- **Decision**: same pattern as S25 R-3: the logged batch also writes `pending_announcements ((hour_shard), item_id)` (payload = the `feed.item_published` v1 fields). A job `feed.relay-announcements` (every 5 s, S49) reads the current and previous hour for each of 8 shards (full sweep hourly over 48 h), publishes with `EventPublisher.publishMany` (S53; key `authorId`) and deletes the row after success; an invalid row goes to `dead_announcements` with the reason. Repeats are harmless because the consumer is idempotent (R-7). `defineEvent('feed.item_published', 'feed', 1, …)` is registered with a new `FEED_AGGREGATE` topic registration (`feed.events`, key `authorId`, standard retention) through `EventsModule.forAggregates` in the worker module.
- **Alternatives**: the infrastructure outbox (a PostgreSQL table, dual write because community owns no PostgreSQL table, D5); publishing in the projector after the batch (B2 defect).

## R-6 Source consumers on the projection framework

- **Decision**: four `Projector`s (`libs/infrastructure/projections`), none using the `inbox` mechanism (it requires a SQL transaction and throws `InboxTransactionRequiredError`):
  - `feed-products` on `products.events`: `idempotency: 'versionGuard'`, `coalesce: false` (price drops need every step), `handles` the five `catalog.product_*` definitions imported from `@app/domains/catalog` if exported there (else the contract schemas `productEventSchemas` from `@marketplace-sandbox/contracts` wrapped with local `defineEvent` of identical name/version; the parity spec in `infrastructure/events` guards drift). It upserts the **product copy** (`product_copies`) only when `productVersion` is greater (`UPDATE … IF product_version < ?`, `INSERT … IF NOT EXISTS` for the first), then decides the item: `created` + ACTIVE + not sandbox → `new_product`; `updated` with `changedFields ∋ priceMinor` and `priceMinor <` copy's previous price → `price_drop` (claim with TTL 24 h); everything else nothing. `catalog.product_changed` (transitional notification) is not in `handles`, so the framework skips it. `catalog.product_deleted` stores a tombstone state (`status = DELETED`) with its version.
  - `feed-posts` on `discussion.events`: `post_created` → `post` item unless `post_tombstones` has the post; `post_deleted` → tombstone (TTL 30 days). `idempotency: 'natural'` (claims).
  - `feed-auctions` on `auctions.events`: `auction.created` → `drop_announced`, `auction.opened` → `auction_started` (`natural`). Title for these comes from the event's product through the copy (`product_copies`), falling back to the payload; if the copy is missing the event is retried then dead-lettered (as products).
  - `feed-fanout` on `feed.events` (R-7).
- **Missing copy** (FR-025): a `price_drop` candidate or an auction event whose product copy does not exist throws the framework's transient error with `attempts: 5` and backoff, then the dead-letter topic; no partial item.
- **Out of order** (AS-17): the copy keeps the highest version; `product_created` v4 after `archived` v5 finds `status = ARCHIVED` → no item; `post_deleted` first leaves a tombstone, the later `post_created` finds it.
- **Compaction**: the `products` topic is compacted (`latest-per-key`); replay yields the latest snapshot per product: the projector works from snapshots only (no deltas), `price_drop` after a replay is only taken when the version is newer **and** the copy's price is higher, so replays emit no drop for an already-seen price.

## R-7 Fan-out and the timeline store

- **Decision**: `feed-fanout` consumes `feed.events` (key `authorId`, so one partition per author: AS-47). Marker `fanout_done ((item_id))` (TTL 7 days) is read first; absent → run, present → skip (AS-22). Followers are paged with `FollowQueryService.getFollowerIds(accountId, {limit ≤ 1000, cursor?})` (the S28 follow-up, same page contract); per page: one pipelined `EXISTS act:{userId}` batch, then one pipelined batch of Lua `ZADD tl:{u} <ms> <sortableId>` + trim to the window + `EXPIRE 7d` for the active ones. `ZADD` of the same member is idempotent and equal scores order by member, i.e. by `sortableId`: out-of-order and redelivered pushes cannot reorder or duplicate (AS-18, AS-46), so no per-follower dedupe is needed on write. The marker is written after the last page; a failure part-way throws, the framework redelivers, and the replayed pages are no-ops for the followers already done.
- **Backpressure** (FR-037): if a pipelined batch exceeds the latency bound (default 250 ms, configurable) or errors, the consumer throws `SinkBackpressureError` after finishing the current page; the framework pauses the partition and resumes after its cooldown; the counter `feed_consumer_paused_total` is incremented where the error is raised.
- **Celebrity**: `isCelebrity` true → no pushes; `ZADD cel:{author}` only if the key exists (otherwise rebuilt lazily), trim to 200, `EXPIRE 24h`. Result line `{celebrity: true, pushed: 0}` (AS-24).
- **Alternatives**: a runner-level `Promise.all` over all followers (P0609 anti-pattern); a durable per-user timeline table (explicitly decided against in the spec's assumptions).

## R-8 Reading, rebuild and degradation

- **Pipeline of one read**: (1) parse limit/cursor (`FeedCursorCodec`, HMAC'd, payload `(ms, sortableId)`); (2) `act` marker: present → slide 7 d; (3) candidates = pushed timeline `ZREVRANGEBYSCORE` below the cursor ∪ each followed celebrity's recents (parallel, per-call timeout 400 ms, `allSettled`) ∪ **pull continuation** from `items_by_author` of followed non-celebrity authors when the pushed list is exhausted below the cursor (this is how paging passes the 800 window, D3/FR-041); (4) `mergeNewestFirst` (pure, k-way, `(ms, sortableId)` desc, de-dup); (5) hydrate (below); (6) fill loop, ≤ 5 × limit candidates.
- **Rebuild** (FR-042): needed when `act` is absent, or `tlc:{u}` (the "timeline complete" marker) is absent, or `tl:{u}` is absent. One reader per user rebuilds (`SET rb:{u} NX PX 10000`); the others do their own bounded pull for this response without writing, so ten concurrent first reads return identical pages (AS-34). The rebuild reads the followed non-celebrity authors from `following_by_user` (≤ 2,000) with bounded concurrency 16, 800 ms per call, ≤ 50 items per author from the last 60 days (`items_by_author` months), builds a temp ZSET and **`ZUNIONSTORE` into `tl:{u}`** (never `DEL` + push), so pushes that arrived meanwhile survive (AS-35); only after every author was read it sets `tlc:{u}` (7 d) and `act:{u}`; a timed-out author leaves `tlc` unset and the response `degraded: true` (AS-37), and the next read retries.
- **Follow/unfollow** (FR-043, A9): both delete `tlc:{u}` and `cf:{u}` after the write, so the next read rebuilds (union keeps what is there; a re-follow reappears). Unfollowed authors' items already in `tl:{u}` are removed at hydration by the "still followed" check: one `following_by_user` `IN (distinct authors on the page, ≤ 50)` read.
- **Hydration (AS-40)**: after one batch read of `feed_items`, in parallel: `product_copies` (R3, own store), `ShopQueryService.getShopsByIds` (distinct shop ids, one call), `DiscussionQueryService.getPostsByIds` (distinct post ids, ≤ 100), followed-authors check; each under a 600 ms timeout. A source that fails makes the items depending on it vanish from this response (shops → shop-authored items; posts → `post` items; product copy store → product-linked items) and sets `degraded: true`; independent items are still served. `DELETED`, `DELETING`, `SUSPENDED` shops and non-ACTIVE or sandbox products hide the item.
- **Redis unreachable** (FR-048): any timeline-store error is caught at the port; the read switches to the pull path (all followed authors including celebrities, no writes), `degraded: true`, counter `feed_degraded_total{reason="timeline_store"}` and a `warn` line `feed.degraded`. Scylla unreachable → `FeedUnavailableError` → `503 feed_unavailable` with a generic `detail`.
- **Followed celebrities per user**: `cf:{u}` (TTL 1 h) caches the user's followed celebrities (the intersection of `following_by_user` and `celebrity_accounts`); it is a cache only, deleted on follow/unfollow, rebuilt on a miss (AS-49 lists it as "following cache").

## R-9 Reconciliation (FR-009, AS-51)

- **Decision**: job `feed.reconcile` (daily cron, S49 single-run) walks `follower_counts` by token in pages of 200 accounts (job state carries the `pageState`; the handler re-enqueues itself until the end), and per account: recounts `followers_by_account` rows whose buyer-side record is active (a batched `IN` read of `following_by_user`), deletes follower rows without an active buyer-side record (the buyer side wins), adjusts the counter by the difference, and sets the `following_counts` of its followers lazily by a second pass over `following_by_user` in token pages (rows active but without a follower row are completed with `USING TIMESTAMP rel_ts`; `n` recomputed per user). Idempotent and repeatable; it only touches accounts that have at least one follower record or one active following row.
- **Cost**: two full scans a day at 200 rows per page with a pacing delay (default 50 ms between pages). At 10⁸ relations this is a long job; it is acceptable because it is a repair, not the write path, and a page is a unit of resume.
- **Alternatives**: an intent log written before each follow (extra write on the hot path for a rare repair); no scan (leaves AS-51's "one direction only" undetected).

## R-10 Rate limits (S50)

- **Decision**: `follow.write` (30/min/user, token bucket, `failMode: 'closed'`) and `feed.read` (120/min/user, token bucket, `failMode: 'open'`) are added to `communityRatePolicies` (`rate-limit-policies.ts`), the file S25 already registered through `definePolicies`/`forFeature`; controllers use `@RateLimit(…)`. The responses adopt the structured `RateLimit` / `RateLimit-Policy` headers, `429` with `Retry-After`, `503 rate_limiter_unavailable` for `follow.write` when the limiter is down, and `422 rate_limit_cost_exceeded` is documented in the contract (the feed routes declare cost 1, so it cannot occur; it is listed so clients handle the shared code).

## R-11 Module boundaries and barrel (X.4, D-8)

- **Decision**: `FeedModule` (HTTP, not `@Global`, exports `FollowQueryService` only), `FeedWorkerModule` (jobs, relay, reconciliation; `apps/worker`), `FeedProjectorsModule` (the four projectors; `apps/projector`). The barrel exports the three modules and `FollowQueryService`; it stops exporting `FeedFanoutConsumer`, `ProductFeedProjector`, `FeedPublisherModule`. `FeedPublisher` and `feed-publisher.module.ts` are deleted; `DiscussionService` (S25) no longer calls it (S25 removed that call, verified by grep: only `feed*` files and the two app modules still name `FeedPublisher`/`FeedService`/`FeedModule`).
- `apps/core` keeps importing `FeedModule`; `apps/projector` swaps `FeedFanoutConsumer`, `ProductFeedProjector`, `FeedPublisherModule` for `FeedProjectorsModule`.
- ACL adapters (IV.8, the only importers of other domains' exports): `ShopDirectoryAdapter` (S03 `ShopQueryService`), `AccountDirectoryAdapter` (S01 `UserDirectoryService`, already exists as `identity-account-directory.adapter.ts` from S25: extend or reuse), `PostLookupAdapter` (S25 `DiscussionQueryService`, same domain: injected directly as a domain-internal service, no ACL needed).

## R-12 Product images (S29 follow-up)

- **Decision**: no `media.gallery_changed` consumer. The accepted item payloads (AS-43, FR-049: "exactly" the listed fields) carry no image; the feed never reads `ProductMedia`. A client that wants the primary image resolves it from `payload.productId` through the BFF `/batch/media` (S29's contract). If a later spec adds `imageMediaId` to the item payload, the consumer is added in the product copy projector (`mediaIds[0]`, URLs resolved at read time with `getReadyMediaByIds`). Recorded in `gaps.md` "Sibling-spec follow-ups".

## R-13 Staleness bound for R3 copies

The product copy lags S05 by consumer delay: accepted maximum **10 seconds** (restated from `questions.md`). A hidden product reappears or disappears within that bound; posts and shops are read synchronously (R1) and take effect at once.

## R-14 Transactions

`community` opens no transaction (`.tx.baseline` is 0, `grep sequelize.transaction` over the domain finds nothing). No SQL transaction is added; the Scylla conditional writes and logged batches above are the atomicity mechanism. The `inbox` mechanism of the consumer framework is deliberately not used (needs SQL).
