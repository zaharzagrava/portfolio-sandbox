# Questions and defaults: S34 — "Bought Together" Recommendations

Each line is a choice made unattended, with the default taken and why. Sorted by impact: BREAKING first (changes behaviour or a contract that exists today, so existing tests and callers need updating), then CONTRACT (another capability must provide or consume it), then LOCAL.

- [BREAKING] Response is a bare array of `{productId, title, price, score, hops}` → `{type: "bought-together", items: [{productId, title, priceMinor, currency, score, hops}]}` → `price` is a float today (`recommendations.service.ts:11,66`), which breaks III.8 (money is integer minor units); an envelope leaves room for a future `type` without a breaking change (V.7). Callers to update: `packages/web/lib/api/catalog.ts` (`Recommendation`, `recommendationToCard`), `packages/web/app/products/[slug]/page.tsx:26-29`, `libs/composition/bff/product-page.service.ts:40`, `bff/graphql/product.resolver.ts:36-38`, `bff.e2e-spec.ts`, `recommendations.e2e-spec.ts`.
- [BREAKING] `limit` is clamped silently (`Math.min(Math.max(Number(limit) || 8, 1), 20)`, controller) → `400 validation_failed` for anything outside the integer 1–20, plus `400` for unknown parameters → a silent clamp answers a question the caller did not ask (V.3, `forbidNonWhitelisted`); same rule as S33.
- [BREAKING] Unknown or hidden requested product answers `200 []` today → `404 product_not_found` for unknown, archived, sandbox and non-active-shop products, identical body → an empty `200` is cached for 5 minutes at the edge and hides a wrong ID; the identical body keeps hidden products undiscoverable (V.4).
- [BREAKING] Visibility is `quantity > 0` on a direct read of the catalog table → product `ACTIVE`, not sandbox, `inStock`, shop `ACTIVE`, via batched R1 calls (`getProductsByIds`, `getShopsByIds`) → today archived, sandbox and suspended-shop products can be recommended (S32 hides them); IX.4 forbids the direct read (D-7, D-12).
- [BREAKING] Candidate pool is `limit × 2` ranked entries, filtered after hydration (`recommendations.service.ts:34,57`) → the whole bounded pool (≤ 121 products) is checked in one batch and the first `limit` visible ones are returned → with `limit × 2` a few hidden products shrink the rail below `limit` although visible candidates exist.
- [BREAKING] Ranking mixes hops by raw score → direct neighbours always precede 2-hop ones; score descending, ties by `productId` ascending → a measured co-purchase is stronger evidence than an inferred one, and a rail whose first slots are inferred is harder to explain; the existing e2e only asserts the direct item first, so it still passes.
- [BREAKING] A product that lost all edges keeps its old list until the TTL ("stale-but-plausible beats empty", `co-occurrence.jobs.ts:100`) → the list is removed after a complete successful build; a failed or empty-source build removes nothing → three days of a recommendation for a product that no longer qualifies (or was refunded into noise) is wrong data; the guard against wiping on failure keeps the safety the old comment wanted.
- [BREAKING] A pair needs `co ≥ 3` orders only → `co ≥ 3` orders **and** ≥ 3 distinct buyers; baskets gain `buyer_id` and `order_version` (expand/contract: new nullable columns, then replay `orders.events` into the table, then the build requires them) → one account placing three orders can otherwise manufacture a recommendation for its own listing and expose one person's habits; the `order_baskets` DDL (`clickhouse/040_order_baskets.sql`) and the projector change.
- [BREAKING] Basket row identity is `order_id` with no version (redelivery collapses by `FINAL`) → version-guarded upsert by `orderVersion`; lower or equal version changes nothing (IV.5) → deterministic when a redelivery carries different lines.
- [BREAKING] Consumer matches `OrderPaid.match(e)` and drops anything else silently; no payload validation, no dead-letter (`order-baskets.projector.ts:23-28`) → zod validation against S10's `orderEventSchemas`, invalid payloads dead-lettered with a reason, valid-but-irrelevant types ignored → IV.5 and VII.4.
- [BREAKING] Redis or lookup failure surfaces as `500` → `503 recommendations_unavailable` with `Retry-After: 5`, `no-store`, never an unfiltered list; explicit time budgets (store 100 ms, product lookup 100 ms, shop lookup 50 ms) → IV.6 and V.3; the BFF's 300 ms optional-section budget stays intact.
- [BREAKING] Rate limit reuses the `search.query` policy (`recommendations.controller.ts`) → its own policy `discovery.recommendations`, 600/minute per address, fail open → a product page view must not spend the search budget of the same address.
- [BREAKING] Job payload `{days?, buckets?}` is untyped (`co-occurrence.jobs.ts:54`) → validated (`days` 1–390, `buckets` 1–256, unknown keys rejected) → a bad payload today builds `INTERVAL 0 DAY` (empty graph) silently.
