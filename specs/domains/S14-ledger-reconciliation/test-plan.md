# Test Plan: S14 — Double-Entry Ledger, Balanced Journals, Hot-Account Sharding, Balance Read Model, Daily PSP Reconciliation (domain `payments`)

Constitution VII.8 table: one row per acceptance scenario in [`spec.md`](spec.md) (69 rows), each proven at the lowest layer that can prove it. A dash means the layer does not test that scenario.

- API e2e files live in `packages/backend/libs/domains/payments/`. Each file's top-level `describe` names its feature (VII.8). They boot the real `LedgerModule`, `LedgerWorkerModule` and `LedgerProjectorModule` with the production prefix, `ValidationPipe`, problem+json filter and interceptors, against real Postgres (real migrations, partitioned entries, commit-time check), Redis and the durable read-model store from `docker-compose.test.yaml`, and the real outbox. HTTP endpoints are called through `supertest`; services, consumers, projectors and job handlers are invoked directly as the existing `finance.e2e-spec.ts` does (the service-level scenarios have no HTTP surface):
  - `ledger-posting.e2e-spec.ts` — describe "Ledger: balanced journals, append-only, idempotent postings and limits"
  - `ledger-payment-postings.e2e-spec.ts` — describe "Ledger: payment capture, refund and settlement" (VII.4 duplicate and invalid-payload tests for the `orders.events` consumer)
  - `ledger-hot-accounts.e2e-spec.ts` — describe "Ledger: hot-account sharding, sweep and lock order"
  - `ledger-balances.e2e-spec.ts` — describe "Ledger: running balances, read model and balance endpoint" (VII.4 tests for the `ledger.events` projector)
  - `reconciliation-run.e2e-spec.ts` — describe "Reconciliation: daily provider run"
  - `reconciliation-issues.e2e-spec.ts` — describe "Reconciliation: issue board and resolution"
  - `ledger-maintenance.e2e-spec.ts` — describe "Ledger: partitions, invariant checker, jobs and backfill"
  - `ledger-ops.e2e-spec.ts` — describe "Ledger: observability, secrets, configuration and shutdown"
- Fixtures: payments, orders and shops are **not** seeded through their models. Sales and refunds are created by calling `LedgerService.recordPaymentCaptured` / `recordPaymentRefunded` in a test transaction; `order.paid` messages are contract-valid fixtures from `packages/contracts`; shops are plain UUIDs; users and roles come from the S01 fixture; a member of a shop comes from S03's fixture (the S03 capability's own seed helper, not `ShopModel`). The seed and clean helpers may touch every table (IX.6, test code only). Every test asserts the response body **and** persisted state (entries, running balances, journals, outbox rows, read-model values, runs, issues, job rows, provider-call log) and parses responses with the `packages/contracts` schemas `balanceSchema`, `reconciliationRunPageSchema`, `reconciliationIssuePageSchema`, `reconciliationIssueSchema` and the event schemas (VII.6).
- Only system edges are faked: identity token verification, the payment provider (one scriptable double behind the statement port: pages, delays, timeouts, `429`/`5xx`, malformed lines, lookups by reference, with a call log), the rate limiter's store (forced down in two scenarios), the hot read-model store and durable store (forced down in AS-33), and the clock (frozen, advanced by the test). The ledger, the store's commit-time check, locks, deadlock detection, outbox and projectors run for real.
- Consumers and projectors (`orders.events` settlement, `ledger.events` balance projection) have the duplicate-delivery and invalid-payload tests of VII.4 (AS-18, AS-19, AS-30, AS-31).
- Unit specs sit beside the code under `domain/`, are table-driven (`it.each`), and exist only for pure logic (VII.5); money and allocation invariants also get `fast-check` properties: `journal.spec.ts` (balance rule and limits), `account.spec.ts` (account IDs and classes), `fee.spec.ts`, `shard.spec.ts`, `settlement-split.spec.ts`, `lock-order.spec.ts`, `balance-version.spec.ts`, `reconciliation-matcher.spec.ts`, `reconciliation-window.spec.ts`, `run-state.spec.ts`, `issue-state.spec.ts`.
- UI journeys (Playwright, happy path only) are owned by W04 and J01 and are not re-tested edge by edge here. This capability contributes one step to J01 (AS-32). There is no finance console in the web app yet (the issue board would be its own capability); nothing is tested for it.
- Static gates (VII.1): `tsc --noEmit` and ESLint for `packages/backend` and `packages/contracts`; `pnpm check:boundaries`; `pnpm --dir packages/backend check:table-ownership --strict` for the ledger and reconciliation files (AS-67); `check:model-registry`.
- Gate 9 (VII.9): AS-26 (lock wait), AS-33 (stores down), AS-35 (limiter down), AS-45 (provider outage), AS-59 (limiter down, fail closed), AS-62 (drift) and AS-69 (shutdown) each force their fault.
- Concurrency rows (`Promise.all`) are repeated as stated in the spec and assert both the invariant and the exact counts (VII.3).
