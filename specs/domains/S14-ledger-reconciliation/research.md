# Research: S14 — Ledger, Hot Accounts, Balance Read Model, Daily Reconciliation

Phase 0. No `NEEDS CLARIFICATION` remained in the spec; `questions.md` defaults are accepted as written (no human edit). The entries below settle how the spec is built on the platform that exists today. Each was checked against the code (paths are under `packages/backend/libs/` unless stated).

## R-1 One header row per journal decides "once per (kind, reference)"

- **Decision**: new table `LedgerJournal` (PK = deterministic `uuidv5(kind + ':' + reference)`, unique `(kind, reference)`). A posting runs `INSERT … ON CONFLICT ("kind","reference") DO NOTHING RETURNING`. No row returned → read the existing header and compare its `fingerprint` (sha-256 of the canonical, sorted `(accountId, amount)` list + currency): equal → `{journalId, created:false}`; different → `JournalConflict`. No advisory lock, no `EXISTS` before a write.
- **Rationale**: the entries table cannot carry a unique journal ID (PK `(id, createdAt)`, partitioned: a unique index on a partitioned table must contain the partition key). A small unpartitioned header can. Under `READ COMMITTED` a concurrent identical insert waits on the unique index until the first commits, then returns no row; the follow-up `SELECT` sees the committed header (AS-08, 50 at once × 20). It replaces the three ad-hoc idempotency tricks of today (advisory lock in `ledger.service.ts`/`settlement.listener.ts`, PK in ad billing, `ON CONFLICT` on `Payout`).
- **Alternatives**: advisory lock + `EXISTS` (today; two round trips, collides on hash, not store-enforced, FR-005 forbids it); unique index on entries `(journalId, …)` (impossible with the partition key); a separate dedupe table keyed only by reference (no kind, no fingerprint for conflicts).

## R-2 Entries keep `createdAt` as the partition key and as `postedAt`

- **Decision**: no mirrored `postedAt` column on entries. The posting writes `createdAt := postedAt` from the injected clock, once, for all lines (FR-007); the entry model exposes it as `postedAt`. The header also stores `postedAt`. Partitions stay monthly RANGE on `"createdAt"`.
- **Rationale**: re-partitioning on a new column would be a second copy-and-swap of the largest table. `gaps.md` E.1 talked of a mirrored column and a contract step to remove it; with one clock reading there is nothing to mirror and nothing to remove (deviation, harmless: AS-61 only needs one `postedAt` per journal in one partition). New nullable columns on entries: `shard SMALLINT NOT NULL DEFAULT 0`, `currency CHAR(3)`; `paymentId` stops being a foreign key.
- **Alternatives**: partition on `postedAt` (second rewrite); keep DB `now()` per row (breaks FR-007).

## R-3 Append-only by trigger; relocation of the default partition by rebuild, never by `DELETE`

- **Decision**: `BEFORE UPDATE OR DELETE OR TRUNCATE` triggers (raise `restrict_violation`) are created with the commit-time balance trigger inside `ledger_ensure_partitions` and on the default partition, so every present and future partition has both. The parent also gets the statement-level `TRUNCATE` trigger. The default partition is emptied of a month by *rebuild*: take a short `ACCESS EXCLUSIVE` on the parent with `lock_timeout 3s` (retried by the job), `DETACH` the default, create the month's partition, `INSERT … SELECT` that month's rows into it, create a fresh empty default and `INSERT` the remaining rows into it, `DROP` the detached table, all in one transaction; counts and sums are asserted before commit.
- **Rationale**: a trigger rejects any role including a privileged one and has no bypass switch (a session setting that lets maintenance delete could be set by anyone, which would make AS-06 empty). `DROP TABLE` of the detached default is not an `UPDATE`/`DELETE`. The default partition holds only the rows of an outage, so the rebuild is small; the existing function fails today because `CREATE … PARTITION OF` conflicts with rows in the default (A20).
- **Alternatives**: `REVOKE UPDATE, DELETE` from the app role only (a privileged test and the owner role still pass; not what AS-06 says); GUC-guarded bypass (rejected above); `DETACH … CONCURRENTLY` (not allowed with a default partition present).

## R-4 Running balances: one row per (account, shard, currency), locked in sorted order

- **Decision**: `AccountBalance(accountId, shard, currency, balanceMinor BIGINT, version BIGINT, updatedAt)`, PK `(accountId, shard, currency)`, no foreign keys. In one posting: validate (pure) → header insert (R-1; a duplicate ends here) → for each distinct `(accountId, shard)` in ascending order one statement:
  - unguarded: `INSERT … ON CONFLICT DO UPDATE SET balanceMinor = balanceMinor + :d, version = version + 1 RETURNING balanceMinor, version`;
  - guarded (`PAYOUT` debit of a seller account, any line on `PAYOUT_CLEARING`): `INSERT … (0,0) ON CONFLICT DO NOTHING`, then `UPDATE … SET … WHERE key AND balanceMinor + :d >= 0 RETURNING`; zero rows → `insufficient_balance`.
  - then bulk insert of the entries and `outbox.append` of `ledger.journal_posted` v2 carrying each line's `balanceAfterMinor`/`balanceVersion` from the `RETURNING`.
  - a returned balance outside the safe-integer range → `balance_overflow` (the caller's transaction rolls back; nothing is persisted).
- **Rationale**: row locks taken in one global (account, shard) order cannot form a cycle among postings (AS-25); the guard is decided by the same atomic statement that moves the balance (AS-10, III.6); the read of any balance is one indexed row (FR-022). `SET LOCAL lock_timeout='2s'`, `statement_timeout='5s'` through `TransactionRunner`'s per-call options on the caller's transaction → SQLSTATE `55P03`/`57014` map to `LedgerBusy` (AS-26).
- **Contract note (no savepoint)**: the posting never nests a transaction (FR-006), so a failure *after* the first write (`insufficient_balance`, `balance_overflow`, `ledger_busy`) leaves earlier writes in the caller's open transaction. These errors carry `rollbackRequired = true`; every caller (S13's transition, S15's payout run, S36, the resolve endpoint) runs inside `TransactionRunner.run`, which rolls back on throw. Pure validation errors are raised before any write. Cross-posting deadlock freedom holds per posting; a caller that posts several journals in one transaction orders them itself (today none does; documented in [contracts/services.md](contracts/services.md)).
- **Alternatives**: savepoint per posting (nesting, forbidden); `SELECT … FOR UPDATE` then update (two statements, same order guarantee, slower); advisory locks per account (second lock system).

## R-5 Shard choice and the sweep

- **Decision**: `shard = readUInt32BE(sha256(shardKey)[0..4]) mod N`, `shardKey` = payment id for `SALE`/`REFUND` (a refund uses the sale's shard), order id for `SETTLEMENT`, the reference otherwise. Hot classes: `PLATFORM_FEES`, `PROVIDER_CLEARING`, `CLEARING`; every other account is shard 0. `N` is read at post time (`LEDGER_SHARDS`, 1–256, default 32). The sweep moves every `AccountBalance` row with `shard > 0` and `balanceMinor ≠ 0` of a hot account into shard 0, with one `SWEEP` journal per account per window (`reference = '<accountId>:<windowStart ISO hour>'`), lines sorted like any posting, `version` bumped by the same statement.
- **Rationale**: a stable hash gives the 75–125 % spread of AS-23 (32 shards, mean 312 of 10 000, σ ≈ 18). The sweep selects rows that exist, not `1…N−1`, so lowering `N` later strands nothing. A concurrent capture on a shard being swept just waits one row lock; the sweep's journal is balanced by construction (sum of moved shards leaves and enters shard 0). The sweep is an internal kind: `SWEEP` lines name shards, which the public posting API forbids.
- **Alternatives**: random shard per posting (a refund could not find its sale's shard; not deterministic); `shard = payment id mod N` (poor spread for sequential ids).

## R-6 Settlement: net comes from the sale, split by largest remainder, deferral is a job chain

- **Decision**: the consumer (`ledger-settlement` group on `orders.events`, event definition built from `packages/contracts` `order.paid`) validates beyond the contract (non-empty `shopOrders`, integer ≥ 0 subtotals, sum > 0, distinct UUID `shopId`s, currency equal to the sale's) and throws `PermanentError('invalid_payload' | 'currency_mismatch')` with `attempts: 1`, after counting `ledger_consumer_dead_lettered_total{reason}`; the framework writes the DLQ record. It looks the sale up by `orderId` in `LedgerJournal` (`kind='SALE'`, index on `orderId`). Net = the sale's `CLEARING` credit (the header stores `clearingMinor`), shares by `allocate()`-style largest remainder with ties to the lowest shop ID (existing `common/money/allocate.ts` is checked in WP-1: if it ties by index, shops are sorted ascending first, which is the same rule). The journal is `SETTLEMENT`, reference = `orderId`.
  - **Sale missing**: the consumer acknowledges the message after enqueueing job `ledger.settle-order {payload}` (`idempotencyKey = 'settle:'+orderId+':2'`, `runAt` from the pure schedule `[30 s, 60 s, 120 s, 180 s, 210 s]` = 10 min, `maxAttempts: 1`); the job re-enqueues the next step itself and, after the 6th attempt, ends by throwing → the job is `DEAD` (operator-redrivable) and `ledger_settlement_dead_lettered_total` increments with reason `sale_not_found`.
  - **Refund first**: the settlement transaction takes the same advisory lock as the refund path (`pg_advisory_xact_lock(hashtextextended('pay:'+paymentId))`), checks for a `REFUND` header of the payment, and if one exists writes no journal and counts `ledger_settlement_skipped_total{reason="refunded"}`. The refund path takes the lock first and reads whether a `SETTLEMENT` exists. One serialization point per payment: either order ends as (a) or (b) of AS-21.
- **Why a job chain**: `Projector` retries use the platform's 200 ms–5 s backoff and `TransientError` pauses the whole partition, so waiting up to ten minutes in the consumer would stall every other order on that partition; the jobs layer's own backoff tops out near 30 s for six attempts (`jobs/backoff.ts`), so the 10-minute schedule is set by the handler through `runAt`. Both limits are documented where the spec says "6 attempts within about 10 minutes".
- **Why a short advisory lock here**: it is a lock on a *payment*, not a journal-existence trick; the uniqueness of the journal is still the store's (R-1). It is the only way to serialize two different journals (`SETTLEMENT`, `REFUND`) that must see each other.
- **Alternatives**: settle on `payments` events instead of `order.paid` (S10's contract names `order.paid`); read S10's order tables (forbidden, R3); `TransientError` backoff (partition stall).

## R-7 Refund of a settled sale reverses the shops' shares from the settlement journal

- **Decision**: `recordPaymentRefunded` reads the sale header by `paymentId` (`sale_not_found`), checks amount and currency, then looks for the order's `SETTLEMENT` header (`orderId`), under the payment lock of R-6. Unsettled: `PROVIDER_CLEARING +A`, `CLEARING −(A−F)`, `PLATFORM_FEES −F` on the sale's shards. Settled: `PROVIDER_CLEARING +A`, `PLATFORM_FEES −F`, and for every settlement entry on a `SHOP_*` account the opposite amount (read from the settlement journal's entries by `journalId`, a bounded read of ≤ 200 lines); `CLEARING` is untouched. The header records `reversesJournalId`.
- **Rationale**: exact reversal to the cent without re-running the split; works for any split rule S16 introduces later.

## R-8 Balance read model: version-guarded absolute values, hot copy only for unsharded accounts

- **Decision**: projector `ledger-balances` (topic `ledger.events`, `idempotency: 'versionGuard'`) writes, per line, to
  - the **durable** store: DynamoDB table `LedgerBalanceView` (`accountId` HASH, `shard` RANGE, attributes `currency`, `balanceMinor`, `version`, `projectedAt`) with `ConditionExpression attribute_not_exists(version) OR version < :v` — a lost condition counts `ledger_projection_stale_total`;
  - the **hot** store: Redis hash `ledger:balance:<accountId>` field `<shard>` = `"<version>:<balanceMinor>"` through a Lua script that applies only a higher version, then `EXPIRE 86400`.
  - Reads (`ReadModelReader`): **unsharded accounts** (`SHOP_*`): `HGET` hot (100 ms) → Dynamo `GetItem` (300 ms) → `AccountBalance` (`source:"ledger"`). **Sharded system accounts**: durable store `Query` by `accountId` (all shards), never the hot copy, because a hash that expired and was refilled by one shard's event would answer a partial sum. The HTTP endpoint serves only `SHOP_*`; system-account sums for operators come from `getBalances`.
- **Rationale**: absolute value + version makes replay, duplication and reordering harmless (AS-30) and removes the 14-day `SET NX` marker whose expiry double-applies a late redelivery (A11). The durable copy needs no TTL and survives a Redis loss (AS-33). `asOf` is the projection time (`projectedAt`), taken from the injected clock.
- **v1 events** still on the retained topic carry deltas, not balances: the projector handles v2 only; a v1 message is acknowledged and counted (`ledger_projection_legacy_skipped_total`). How S53 expresses "older version, no upcast" (skip vs dead-letter) is confirmed in WP-0; if it dead-letters, a v1→v2 upcast to an empty `lines` array is registered instead (same effect). The read model is seeded from `AccountBalance` by the last phase of `ledger.backfill-balances` and repaired by the checker (R-11), so no replay of v1 is needed.
- **Alternatives**: `HINCRBY` deltas (today; not idempotent beyond 14 days); a Postgres read-model table (a second copy in the primary database, defeats the fast path).

## R-9 The reconciliation port, the run record and the stream

- **Decision**: domain port `ProviderStatement { listLines({fromInclusive, toExclusive, cursor, limit≤100}): Promise<{ lines: unknown[]; nextCursor: string | null }>; findByReference(ref): Promise<unknown | null> }` with an adapter `infra/stripe-statement.adapter.ts` that validates each raw line with zod into a `StatementLine` or an `InvalidRecord{position}` (never the raw body), over a new thin method on `StripeService` (`balanceTransactions.list` with `created[gte|lt]`, `limit`, `starting_after`, `maxNetworkRetries: 0`, 10 s timeout). The runner is an `async function*` consumer: it requests page *n+1* only after page *n* is fully processed (backpressure by construction), keeps one page, calls `ctx.heartbeat()` at least every 1 000 lines, and keeps a set of seen provider line ids *for the day* only as a `Set<string>` of ids (25 000 × ~40 B ≈ 1 MB; stated bound, tested at 25 000) to count repeated lines once (AS-44). Our side is read from `LedgerJournal` by keyset in the same page loop: for a page of statement lines, one `WHERE paymentRef = ANY($1) OR refundRef = ANY($1)` query (≤ 100 refs); the reverse direction (journals without a line) is a keyset scan of that day's `SALE`/`REFUND` headers (index on `(kind, postedAt)`), subtracting the references seen — implemented by marking seen references in a per-run temp table `ReconciliationSeen(runId, reference)` instead of a growing in-memory set when the day exceeds the 1 MB bound, which keeps memory flat. Issues are collected in a per-run staging table and promoted in **one transaction** at the end (a failed run stores none, FR-032).
- **Run record**: `ReconciliationRun` gains `status` (`RUNNING|COMPLETED|FAILED`), `startedAt`, `leaseUntil`, `failureCode`, `providerLines`, `ledgerJournals`, `skipped`. Claim = `INSERT … ON CONFLICT (provider, day) DO UPDATE SET status='RUNNING', leaseUntil=… WHERE status='FAILED' OR (status='RUNNING' AND leaseUntil < now) RETURNING` — zero rows: `COMPLETED` → "already completed", live `RUNNING` → "already running". Transitions are pure (`run-state.ts`). The job layer's lease/heartbeat (S49) is the second guard.
- **Retries**: the adapter does none; the job schedule/enqueue passes `maxAttempts: 3` (S49 follow-up) and the S49 backoff (exponential, full jitter) is the one retry layer (AS-45).
- **Day rules** (`reconciliation-window.ts`): pure, take `now` from the injected `Clock`; closed day = `day < utcDate(now)`; ≤ 90 days; catch-up = the last 7 days without a `COMPLETED` run, oldest first, in the same invocation.
- **Alternatives**: whole day in memory (A17); DB cursor over `Payment` (cross-domain read).

## R-10 Operator API: one transaction for issue change, adjustment, event; idempotency by the platform

- **Decision**: `@Idempotent()` on `POST …/resolve` (S54 facility: header rules, `Idempotency-Replayed`, in-flight `409`, mismatch `422`); `@RateLimit('finance.admin.write')` fail closed; admin gate = `AuthenticatedUser.role === 'admin'` through a `Roles`-style guard already in identity (checked in WP-0; otherwise a 6-line `AdminGuard` in `api/`). The service runs `TransactionRunner.run`: `UPDATE "ReconciliationIssue" SET status='RESOLVED', … WHERE id=$1 AND status='OPEN' RETURNING` (zero rows → re-read: absent `404`, resolved `409`), optional `postJournal({kind:'ADJUSTMENT', reference:'issue:'+issueId, …, correctsDay})`, history row, `outbox.append`. Two admins racing: the conditional update has one winner; the loser's transaction is rolled back before posting (the adjustment is written *after* the winning update, so at most one journal).
- **Adjustment accounts** are validated against the chart (`account_unknown` → `422 adjustment_account_invalid`); no `SHOP_*` existence check.

## R-11 Maintenance jobs

- **Decision**: `ledger.ensure-partitions` (weekly, `0 3 * * 1`, months ahead 3), `ledger.sweep-hot-accounts` (hourly), `ledger.verify-invariants` (`15 2 * * *`), `payments.reconcile-daily` (`30 2 * * *`), `ledger.backfill-balances` (one-off, batches of 5 000 by keyset on `(createdAt, id)`, resumable through a `LedgerBackfillCursor` row). Every handler declares `declareJobType` with a zod contract next to its `JobPayloads` augmentation (S49 follow-up), uses `fleetConcurrency: 1`, catches `InvalidScheduleError`, and schedules/enqueues with `maxAttempts: 3`. The checker reads the entries of the last two *closed* days with a keyset scan and compares: per-journal sum, day sum, `AccountBalance` vs `SUM(entries)` of touched accounts **for the accounts whose first entry is inside the checked window** or, for older accounts, vs `balance at window start + window sum` using the previous run's stored checkpoint (`LedgerCheckpoint(accountId, shard, asOfDay, balanceMinor)`); read model vs `AccountBalance` per touched account; mismatch of the read model is repaired from `AccountBalance`, the others only counted and logged (IDs only). This keeps the work bounded by the window, as FR-043 demands, and still detects an edited running balance.
- **Alternatives**: `SUM` over all entries per touched account (unbounded at 100 M rows, the problem the spec removes).

## R-12 Boundary work: no `User`, no `Shop`, no `Payment` in ledger code

- **Decision**: `ledger-entry.model.ts` loses `UserModel`, `Payment`, `PaymentReason/PaymentStatus/Scopes` clutter (A23); `ledger.module.ts` registers only ledger models (the S13 pass already dropped `User`, `BisOrder`, `Payment`); the buyer is a plain `userId` on the header. The `Shop.stripeAccountId` follow-up: new payments-owned table `ProviderAccount(shopId PK, provider, accountId, createdAt, updatedAt)` with a one-time SQL backfill inside the migration (`INSERT … SELECT "id","stripe","stripeAccountId" FROM "Shop" WHERE "stripeAccountId" IS NOT NULL` — a migration, not application code, is the sanctioned place for a one-time cross-table copy); `PayoutJobs.send` reads it through a `PROVIDER_ACCOUNT_REPOSITORY` port; `finance-worker.module.ts` drops `Shop`. The column drop is the tenancy side (sibling bullet to S03). S15 later owns writing to `ProviderAccount` (onboarding); S14 only creates, backfills and reads it so that `payout.jobs.ts` stops reading `Shop` now. `payout.jobs.ts` is touched anyway (the old `post`/`balance` API and the raw `LedgerEntry` sum disappear), so it is moved to `postJournal`, `listSellerBalances`, and its three direct `sequelize.transaction` sites move to `TransactionRunner.run`; its schedule gets `maxAttempts: 3`. Its behaviour (weekly run, states, provider transfer) is unchanged — S15 owns the rest.
- **Rationale**: `questions.md` says the provider account belongs to S15; the brief says S14 *and* S15 take it over and `payout.jobs.ts` must stop reading `Shop`. Doing the narrow, behaviour-neutral half now satisfies both and keeps S15's scope (table writes, onboarding, the `Payout` API) intact.

## R-15 Probe answers (T003, 2026-10-12; no probe code was left behind)

- **S53, older event version without upcast**: `projections/routing.ts` dead-letters it as `UNSUPPORTED_VERSION` ("no upgrade step from version v to v+1"). So the balance projector registers `upgradeFrom: [{version: 1, upcast}]` turning a v1 payload into a v2 payload with an **empty `lines` array**; the projector counts a v2 event with no lines as `ledger_projection_legacy_skipped_total` and writes nothing. The v2 schema therefore allows `lines: []`; the posting path never emits fewer than 2 lines.
- **Admin guard**: identity already offers `Firewall({ roles: ['admin'] })` (`RolesGuard`, `libs/domains/identity/api/guards/roles.guard.ts`). No `api/admin.guard.ts` is created (T113).
- **`refundRef`**: `PaymentRefundService.refundAtProvider` sends `createRefund(providerRef, 'refund:<paymentId>')`; the `refundSucceeded` transition input carries no provider refund id. `refundRef` is the provider refund id when the transition carries one and falls back to the deterministic `refund:<paymentId>` reference; the optional field on the transition input is the minimal S13-owned edit (T059, listed in `gaps.md` sibling bullets under S13).
- **`allocate()` ties**: ties in the remainder go to the **earlier index** (`a.index - b.index`); the settlement sorts shop ids ascending first, which is the "lowest shop id" rule.
- **`LedgerEntry` constraint/trigger names** (read from migration `20261001160000`; partitions `LedgerEntry_YYYYMM` + `LedgerEntry_default`): one `ledger_balanced` constraint trigger per partition, `PRIMARY KEY (id, createdAt)`, `paymentId` foreign key to `Payment`, indexes `LedgerEntry_account_time_idx`, `LedgerEntry_journal_idx`, `LedgerEntry_payment_idx`. The new migration finds partitions through `pg_inherits` instead of assuming names.
- **`PROVIDER_FUNDS` usages**: `domain/accounts.ts`, `application/ledger.service.ts` (replaced), `finance.e2e-spec.ts` (deleted with the old spec), `payment-refund.e2e-spec.ts:131` (an S13 spec asserting an account map with `PROVIDER_FUNDS: 0`; it follows the rename, an S13 spec edit limited to the account name, listed in `gaps.md`).
- **`JobsService.cancel` callers**: none in `payments` or `marketing` (the only `cancel` hits are S13's `cancelIntent`, a different method).
- **`GET /shops/:shopId/payouts` callers**: none in `packages/web/src`.
