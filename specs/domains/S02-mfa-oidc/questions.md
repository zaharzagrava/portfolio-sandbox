# Open Decisions for S02 (answered unattended)

Format: `[TAG] question → default taken → why`. BREAKING first, then CONTRACT, then LOCAL. The human reviews BREAKING and CONTRACT lines first. Decision policy: most production-grade option the Interview-Prep notes and the constitution support.

## BREAKING (changes behaviour or an API/UI contract that exists today)

- [BREAKING] Enrolling while the factor is already enabled (today `mfa/enroll` sets `mfaEnabledAt = null`, so an access token alone switches MFA off and replaces the secret) → `409 mfa_already_enabled`; the pending secret is kept separate from the active one; state machine `none → pending → enabled` with 15-min pending expiry → notes 05/02 §5 (an enabled factor must not be downgradable by a stolen session); constitution III.7 (illegal transitions are `409`).
- [BREAKING] Google-login for an account whose address matches a password-registered account (today it silently links and issues a session, leaving the squatter's password, TOTP secret and sessions alive) → link only when the provider verified the address, and in the same transaction clear the password, reset the factor and revoke all sessions (`account_linked`); emit `identity.federated_identity_linked` with `passwordInvalidated`/`mfaReset` → pre-hijacking defence; notes 05/02 §4 (link by e-mail only when verified) plus S01's registration never proving e-mail ownership.
- [BREAKING] Shop (`shop:<uuid>`) providers (today the same code path as Google: link by e-mail when `email_verified`, so a shop admin's IdP can claim a victim's address and take over the account) → subject-only trust: never link by e-mail, new account with `email = null`, claimed address kept as a hint on the link → a tenant controls its IdP's claims; notes 05/02 §8 ("validate the token's origin", don't trust what a tenant asserts).
- [BREAKING] Federated login for an account with an enabled factor (today the OIDC callback issues a session directly, bypassing TOTP) → challenge via `__Host-mfa-challenge` cookie and redirect to `/login/mfa`; `amr ["fed","otp","mfa"]` → otherwise the factor protects only the password door (notes 05/02 §5).
- [BREAKING] OIDC start (today `GET /auth/oidc/:provider/start` redirects; state lives only in the cache, not bound to the browser, so an attacker's callback link logs the victim into the attacker's account) → `POST /auth/oidc/:provider/start` returns `{authorizationUrl}` and sets an HttpOnly `__Host-oidc-flow` cookie whose digest is stored with the flow; callback requires it → login CSRF defence (notes 05/02 §4 `state`; 05/01 §3 login CSRF); constitution V.5 (a request that creates state is not a GET). The web client navigates to `authorizationUrl`.
- [BREAKING] Callback failures (today any failure throws a plain `Error` → 500; success redirects with Strict cookies) → every outcome is a `302` to `<front>/login?error=<closed code>`, with `no-store` and `Referrer-Policy: no-referrer`; success uses S01 cookie delivery (`SameSite=Lax`) → the callback is a browser navigation target, not an API call; a redirect with a stable code is not an "error response" under V.3, so no amendment is needed; provider text is never echoed.
- [BREAKING] `returnTo` (today silently replaced by `/` when invalid) → rejected with `400 validation_failed` at start, stricter grammar (no `//`, `\`, control characters, ≤ 512, also after one decode) → silent rewriting hides client bugs and a decode gap is a classic open redirect.
- [BREAKING] Second-factor brute-force limits (today only `auth.login.ip` on `/mfa/verify`; the challenge can be retried for 5 minutes, a 6-digit code is guessable by a botnet) → challenge single-use and burned after 3 wrong codes; 5 failures per 15 min per account (shared with confirm/disable/regenerate); 20/min per IP → notes 05/02 §5 (rate limit per account **and** per IP).
- [BREAKING] TOTP replay guard (today a cache key `mfa:last-step:<id>` with TTL 120 s, read-then-write: racy and lost on flush) → durable, atomic, monotonic last-accepted time step in identity's strongly consistent store → constitution III.6 (invariants by the store, not check-then-write) and III.9 (cache is never the source of truth).
- [BREAKING] Recovery codes (today 10 × 5 random bytes = 40 bits, unsalted SHA-256, read-modify-write on a JSON column so two requests can spend one code) → 10 × 50-bit codes `XXXXX-XXXXX`, stored as keyed digests, spent atomically; regeneration endpoint added → offline guessing after a leak and double-spend are the failure modes; notes 05/02 §5.
- [BREAKING] TOTP secret sealing (today `box.seal(secret)` without context, so a ciphertext copied between rows opens) → seal with context `mfa:<userId>`; existing secrets must be re-sealed by a one-off migration step → notes 05/02 §9 (envelope encryption, bound ciphertext).
- [BREAKING] Error contract for the second factor (today generic `401 Invalid code`, `400 Invalid code` on confirm) → `401 invalid_mfa_code` / `401 invalid_mfa_challenge` at login, `422 invalid_code` in management, `409 mfa_already_enabled | mfa_not_pending | mfa_not_enabled`, `404 identity_not_found`, `409 last_login_method`, `503 oidc_provider_unavailable` → stable machine codes (constitution V.3/V.4); the web client must switch on `code`.
- [BREAKING] One identity per provider per user and store-level uniqueness (today only `UNIQUE(provider, subject)`; nothing stops a second Google subject linking to the same user by e-mail) → add `UNIQUE(userId, provider)`; a different subject with a matching e-mail is refused (`link_conflict`) → recycled or look-alike addresses must not take over a linked account (notes 05/02 §4: subject, not e-mail, is the stable key).
- [BREAKING] Public barrel of `@app/domains/identity` (today exports `FederatedIdentityModel` and `OidcService`; tenancy calls `OidcService.setResolver/register`) → remove both; add `SecondFactorService`, `OidcProviderRegistry`; tenancy registers `shop:` through the registry and passes a plain secret it opened itself → constitution X.4, IX.4; D-7, D-8.
- [BREAKING] Web `/mfa?token=<mfaToken>` (today `login-form.tsx:53` puts the challenge token in the URL) → the token is held in memory/route state (password flow) or in the `__Host-mfa-challenge` cookie (Google flow); never in a URL → tokens in URLs leak through history, logs and `Referer`.
- [BREAKING] Provider tokens (today the ID-token claims are read and the rest dropped implicitly) → stated rule: access, refresh and ID tokens are used inside the callback only and never stored or logged; scope fixed to `openid email profile` → notes 05/02 §4 (ID token is for the client, never an API credential).

## CONTRACT (decides something another capability must provide or consume)

- [CONTRACT] S01's challenge helpers are `createChallenge(userId)` / `verifyChallenge(token)` with no first factor and no single-use → S02 needs `createChallenge({userId, firstFactor: 'pwd'|'fed'}) → {token, jti}` and `verifyChallenge(token) → {userId, firstFactor, jti}`; S02 keeps single-use and attempt counts keyed by `jti` → `amr` of the final session depends on the first factor; spending must be atomic and lives with the factor logic. S01 adopts the signature when it is implemented.
- [CONTRACT] Host of S01's `isSecondFactorEnrolled(userId)` → exported `SecondFactorService.isSecondFactorEnrolled`; true only for state `enabled` (a pending enrolment never changes login) → S01 FR-015 named the method, not the service.
- [CONTRACT] `amr` vocabulary → `pwd` (S01), `fed`, `otp`, `rcv`, `mfa`; sessions with `mfa` passed a second factor → lets later capabilities (payouts S15, API keys S42) demand it without calling identity.
- [CONTRACT] S01 password reset and MFA → reset must not change the factor state (AS-22), and S01 reset only serves accounts that have a password, so accounts created or linked through Google have no password path → keeps a mailbox compromise from bypassing the factor; recorded as an accepted limit.
- [CONTRACT] S03 per-shop SSO → `OidcProviderRegistry.registerResolver('shop:', resolver)` and `invalidate(id)`; settings `{issuer, clientId, clientSecret (plain), scope?}`; trust forced to subject-only; issuers must be `https` and pass the SSRF guard; S03 owns `ShopSsoConfig`, the login-URL display and membership provisioning (it may subscribe to `identity.user_registered` / `identity.federated_identity_linked`) → keeps identity free of tenancy data (IX.7) and the trust rule in one place.
- [CONTRACT] S50 policies `auth.mfa.ip` (20/min, per IP), `auth.mfa.account` (5 failures/15 min per user ID, failures only, resettable on success), `auth.oidc.ip` (30/min per IP), all fail-closed → names exact; S50 declares them.
- [CONTRACT] S54 outbound HTTP port with per-call timeout (3 s), response-size cap (1 MB) and the SSRF guard of `infrastructure/net`; startup config validation for Google settings → IV.6/IV.8 and P0507; the SSRF guard is proven by S41/S43 and reused here.
- [CONTRACT] S53/S28 events `identity.mfa_enabled`, `mfa_disabled`, `mfa_recovery_code_used`, `mfa_recovery_codes_regenerated`, `federated_identity_linked`, `federated_identity_unlinked` (envelope per S01 FR-094, ids and flags only) → S28 sends the security mails; names exact.
- [CONTRACT] W01/S48 cookie delivery for OIDC → callback sets host-only `__Host-` cookies, so web and API must share one origin (path-routed), otherwise W01 must use the BFF session; W01 renders `/login?error=<code>`, `/login/mfa`, `?linked=google`, starts flows with `POST …/start` → keeps tokens out of browser JavaScript (VI.2) without a one-time-code exchange endpoint.

## LOCAL (affects only this capability's internals)

- [LOCAL] TOTP parameters → SHA-1, 6 digits, 30 s, ±1 step, 160-bit secret → maximum authenticator-app compatibility.
- [LOCAL] Attempt budgets → 3 per challenge, 5 per 15 min per account, 20/min per IP verify → see BREAKING line; numbers configurable.
- [LOCAL] Pending enrolment lifetime → 15 min, lazy expiry (no job) → small and cleanup-free.
- [LOCAL] Recovery codes → 10 per set, regeneration replaces all; recovery code cannot regenerate codes → prevents code-for-code laundering.
- [LOCAL] Step-up scope → current code needed for confirm, regenerate, disable and explicit link when enabled; unlink needs only a sensitive session → unlinking never grants access.
- [LOCAL] No general re-authentication challenge, no passkeys, no SMS, no device trust → not required by any pattern/capability (S01 deferred re-auth to S02/S15; S15 can read `amr`).
- [LOCAL] Flow lifetime 10 min, callback budget 10 s, provider call timeout 3 s, no retry of the code exchange, discovery cache 1 h, unknown-key reload ≤ 1 per 30 s, response cap 1 MB, ID token cap 8 KB → IV.6 (retries only on idempotent calls).
- [LOCAL] `email_verified` honoured only as boolean `true` → string `"true"` seen in some providers is treated as unverified (fail safe).
- [LOCAL] Accounts without a password cannot gain one here; unlinking the only identity is refused (`last_login_method`) → avoids lock-out without adding a password-set flow.
- [LOCAL] Google `hd`, name and picture ignored; only subject and e-mail hint stored → data minimisation.
- [LOCAL] Existing `User` columns `mfaSecretEnc`, `mfaEnabledAt`, `mfaRecoveryCodes` → the plan may keep or move them into an identity-owned table; the spec fixes behaviour only.
- [LOCAL] Provider names accepted → `google` and `shop:<uuid>` shapes only; anything else is `404` before any lookup.
