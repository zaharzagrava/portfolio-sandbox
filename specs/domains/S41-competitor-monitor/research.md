# Research: S41 — Competitor Price Monitor

No `NEEDS CLARIFICATION` remains: `questions.md` defaults are accepted as written. This file records design decisions that the spec leaves open, the verified state of `gaps.md`, and the cross-spec follow-ups.

## Decisions

**D-01 Module split.** `CompetitorsModule` (core: controller, watch service, repositories, billing/catalog imports), `CrawlerWorkerModule` (scheduler, fetch loops, purge, evaluation; loads `ProductQueryModule` and tenancy's membership query module — R1 needs them in the worker process, FR-028), `CompetitorProjectorModule` (two consumers). Shared providers live in a `CompetitorStoresModule` imported by all three. Alternative: keep one module with three roles (today's `crawler.module.ts`) — rejected, D-6 and L-018 (each app must boot alone).

**D-02 Status vocabulary.** `CrawlTarget.lastStatus` is a closed string union: `ok, unchanged, no_price, out_of_stock, disallowed_by_robots, robots_unavailable, gone, blocked_by_site, http_4xx, http_429, http_503, http_5xx, history_unavailable` plus the S54 kinds `blocked_address, unresolvable, invalid_url, redirect_refused, redirected_host, too_many_redirects, unsupported_content_type, timeout, tls_error, network_error`. Mapping from `SafeRequestError.kind` is identity; the table (status → next interval) lives in `domain/schedule.ts` with an `assertNever` switch (III.7). `unresolvable` and `tls_error` follow the `network_error` ladder (1 h doubling to 24 h); `blocked_address`, `invalid_url`, `redirect_refused` → 24 h; `redirected_host` → 24 h; `unsupported_content_type` → 24 h; `too_many_redirects` → 24 h. (Spec only fixes some of these; the rest are unspecified, so the conservative 24 h is chosen.)

**D-03 `safeGet` reuse, no new HTTP client.** `SafeFetcher` adapter wraps S54 `safeGet` with `{userAgent, maxBytes: 2 MiB, requestDeadlineMs: 10 s, maxRedirects: 3, sameHostRedirectsOnly: true, allowedPorts:[443], allowedContentTypes: html}` and passes the fixture allowlist only when `CRAWLER_FIXTURE_HOSTS` is set outside production. The crawl-level 30 s budget is an `AbortSignal`/deadline checked between robots, page and hops. `Crawl-delay`, back-off and lease are the frontier's, not the client's. If `safeGet` lacks anything AS-25/AS-27/AS-28 need (e.g. content type `application/xhtml+xml`, `truncated`), the gap is closed in `libs/infrastructure/net` by an additive option, never by a second client.

**D-04 Limit serialisation.** `pg_advisory_xact_lock(hashtextextended('competitor-watch:'||shopId,0))` as the first statement of the registration transaction, then count shop watches and product watches, then insert. III.6 allows "a row lock"; the shop read-model row is foreign-to-nothing here (we own it) but may not exist yet, so an advisory lock on the shop id is the stable choice. The entitlement read (`EntitlementsService.checkLimit('SHOP', shopId, 'maxCompetitorWatches', current)`) is network/DB I/O of another domain, so it runs **before** the transaction with a count read, and the in-transaction count is re-checked against the returned `limit` (limit is stable; count is the contended part). Failure → `503 entitlements_unavailable`. `maxCompetitorWatches` is not in billing's `LIMIT_KEYS` today (`['maxProducts','seats']`): see Follow-up F-2.

**D-05 Idempotent registration and concurrency.** Within the transaction: `INSERT … ON CONFLICT (url) DO NOTHING` for the target then select it; `INSERT … ON CONFLICT ("productId","targetId") DO NOTHING RETURNING` for the watch; `RETURNING` empty → replay → `200` with the stored row. Target `nextCheckAt` is pulled forward only `WHERE "lastCheckedAt" <= now() - interval '1 hour' AND "nextCheckAt" > now()` (AS-11). The seen-set check precedes the insert as a negative filter only; counters per FR-010.

**D-06 Observation step (FR-023/AS-41/AS-42).** Order: (1) fetch + extract + fingerprint (no I/O to DB beyond the earlier read); (2) if observation: `observationNo' = read+1`; insert history row to ClickHouse with insert-dedup token `"<targetId>:<observationNo'>"` (failure → set `history_unavailable`, `nextCheckAt = now+15 min`, state untouched); (3) one transaction: `UPDATE "CrawlTarget" … SET observationNo = :n+1 … WHERE id = :id AND "observationNo" = :n` — zero rows → stop silently (a concurrent worker won; AS-42) — then evaluate watches in batches of 500, each batch its own transaction with outbox rows (D-08); (4) after commit: archive (best effort). Because the target update commits before the batches, a crash between them could skip evaluation; this is closed by marking the target `evaluatedNo` (= last `observationNo` fully evaluated) in the same step as each batch cursor and having the scheduler re-run evaluation for targets with `evaluatedNo < observationNo` (idempotent via per-watch `lastEvaluatedObservationNo`, AS-48 "at most once per watch per counter").

**D-07 Per-watch evaluation.** `CompetitorWatch.lastEvaluatedObservationNo` + `lastEvaluatedPriceMinor`. For observation N, a watch is processed iff `lastEvaluatedObservationNo < N` (conditional update, the at-most-once guard). Alert iff `alert-rule`: same currency, product `ACTIVE`, shop `ACTIVE`, `competitor < yours`, and (`lastEvaluatedPriceMinor` is null or `competitor < lastEvaluatedPriceMinor`). Event `eventId` = UUIDv5-style hash of `(watchId, priceVersion, ownerId)`. A shop with closed status (`SUSPENDED`, `DELETING`, `DELETED`) is paused, so never evaluated; a retest of S03 `403 shop_suspended` / `409 shop_offboarding` is added to AS-07.

**D-08 Evaluation reads.** Products via `getProductsByIds(≤500 ids)`, owners via `getMembersByShopIds(≤500 shopIds, ['OWNER'])`, both **before** opening the batch transaction (III.3: no cross-domain I/O inside the transaction; the R1 reads are in-process but may touch other stores). Prices are read at evaluation time, never copied.

**D-09 Shop read model.** New table `CompetitorShop {shopId PK, plan, status, version}` (S40's `SellerInsightsShop` holds name/slug only and is S40's). Consumers: `tenancy.shop_created|shop_plan_changed|shop_status_changed|shop_deleted`. Version-guarded upsert (`WHERE version < :v`), `shop_status_changed` before `shop_created` creates a row with the event's status, `plan = NULL` (ordered as `STARTER`) and that version; a later `shop_created` with version ≥ stored fills `plan` and status (AS-51). Pause/resume: updating `status` also updates `CompetitorWatch.status` for that shop in the same transaction (`ACTIVE` ↔ `PAUSED`; `DELETING`/`SUSPENDED` pause). Deleting: delete watches, read-model row, retire unwatched targets (`retiredAt = now()`), idempotent. Shop-status events carry `from/to`; `to ∈ ACTIVE|SUSPENDED|DELETING|DELETED`. The existing `tenancy.shop_offboarding_started/_cancelled` events are not consumed: offboarding is signalled by `shop_status_changed to DELETING`.

**D-10 Frontier.** Keep the ZSET + per-host list design of `infra/frontier.ts`; add `{shard}` hash tags (`crawl:{s}:ready`, `crawl:{s}:host:<host>`), carry the target id in the list value (not the URL; URLs stay out of Redis and logs), store `delayMs` and `Retry-After` handling in `release(host, delayMs)` with the 300 s / 1 h caps applied in domain code, and renew the lease only by the crawl budget (30 s < 60 s). Queue marks `crawl:queued:<targetId>` NX with 15 min TTL; **the mark is deleted by target id** (the old code deleted `crawl:queued:${next.url}`, a key never written — bug in A12). Retired target taken from the queue is dropped without a request.

**D-11 Seen-set.** Redis Bloom adapter. Reuse "the existing Bloom implementation shared with the penetration guard" (gaps D.4) if `grep -r bloom libs` finds it; otherwise a minimal Bloom (`SETBIT`/`GETBIT` over `K` hashes of the sha256 of the normalised URL, sized for 10 M entries at 1 % → ~12 MB, key TTL refreshed on write). Counters per AS-31. Alternative: RedisBloom module — rejected, not in the test stack (L-011).

**D-12 Robots cache.** `crawl:robots:<scheme>://<host>:<port>` JSON `{rules, delay}` with TTL by outcome (24 h / 1 h / 15 min); `robots_unavailable` is cached as a full-disallow with 15 min TTL. `Crawl-delay` capped at 300 s in the parser result's consumer.

**D-13 Config.** `CrawlerConfig` (zod) reads: `crawler_fetch_loops` (1–64, default 16), `crawler_min_gap_ms` (≥ 1000), `crawler_max_body_bytes` (≤ 8 MiB), `crawler_fixture_hosts` (non-production only; setting it with `node_env=production` fails startup naming the key), scheduler cap, lease. Replaces the use of `webhooks_allow_private_hosts` (A8).

**D-14 Metrics.** Through the S54 metrics registry: `crawler_fetch_total{outcome}`, `crawler_robots_total{result}`, `crawler_alert_events_total`, `crawler_archive_failed_total`, `crawler_overdue_targets`, `crawler_oldest_overdue_seconds`, `crawler_ready_hosts`, `seen_set_*` counters, `truncated`. Gauges are refreshed by the scheduler job.

**D-15 Retention.** `crawler.purge-targets` daily: delete `CrawlTarget WHERE retiredAt < now() - 30 d AND NOT EXISTS watch` using `FOR UPDATE SKIP LOCKED` batches so two replicas never double-delete. History TTL 2 y: ClickHouse table `TTL`; archive 7 d: bucket lifecycle rule asserted by reading the bucket configuration (AS-54).

**D-16 Existing data.** The expand migration re-normalises `CrawlTarget.url` using the new rules (executed in JS inside the migration with the same pure function, copied inline because migrations may not import app code), merges duplicate targets (keep oldest, re-point watches, drop duplicate watches on `(productId,targetId)`), then adds unique indexes. Old `lastStatus` values (`disallowed-by-robots`, `http-429`, `no-price`) are mapped to the underscore vocabulary.
