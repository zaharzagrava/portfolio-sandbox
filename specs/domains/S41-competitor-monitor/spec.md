# Feature Specification: S41 — Competitor Price Monitor (polite crawling, robots, SSRF-safe fetch, price extraction, alerts) (domain `seller-insights`)

**Feature Branch**: `S41-competitor-monitor` (spec directory `specs/domains/S41-competitor-monitor`)

**Created**: 2026-10-06

**Status**: Draft

**Input**: User description: "Competitor price monitor: polite crawling, robots, SSRF-safe fetch, price extraction, alerts (domain `seller-insights`)". Sources: `docs/showcase/sections/SD-35-competitor-price-monitor.md`, note 10-System-Design/09 §35 (web crawler), patterns P0507 (SSRF guard), P1103 (Bloom filter) and P1104 (SimHash change detection) of `docs/architecture/pattern-map.md`, constitution v3.1.0 (VII, IX, X), and the specs already written for S03, S05, S18, S28 and S40.

## Scope

**In scope**

- **Watches**: a shop with a paid entitlement registers the public URL of a competitor's product page against one of its own products, lists its watches, removes a watch, and reads the observed price history of a watch.
- **Crawling**: re-crawling every registered page politely (a URL frontier with one queue per host, `robots.txt` fetched and cached, `Crawl-delay` honoured, one in-flight request per host across the whole fleet, an identifiable user agent, back-off on `429`/`503`), with an adaptive re-crawl interval, priority by shop plan and by change frequency, and a seen-set of normalised URLs (Bloom filter, P1103).
- **SSRF-safe fetch** (P0507): every request, including `robots.txt` and each redirect hop, resolves the host, requires every address to be public, and connects to the address that was checked.
- **Price extraction and change detection**: structured data first (JSON-LD `Product/Offer`), then OpenGraph/meta tags, never free text; content fingerprint (SimHash, P1104) so unchanged pages are cheap; price history; raw page archive for changed pages.
- **Alerts**: when a competitor's price falls below the shop's own price for the watched product, the shop's owners are alerted. This capability publishes a domain event; it does not send notifications.
- Reacting to shop and product events (suspension, plan, deletion) and the read model of shops this capability needs (IX.7 R3).

**Out of scope** (owned elsewhere)

- Delivering the alert (inbox, e-mail, preferences, dedupe at the recipient) — **S28**. Shop membership, roles, permission matrix, shop status gate — **S03**. Product data and the products' prices — **S05**. Plan limits and entitlement values — **S18**. The reusable resilient/SSRF-safe HTTP client, metrics, clock and error format — **S54**. Outbox, consumers, dead letters — **S53**. Job scheduling — **S49**. Rate-limit engine — **S50**. The competitor screens of the seller web app (watch form, price chart, "your price" line) — a later web capability; "your price" on that screen is composed by the BFF (R2).
- Leaderboards, live dashboard, seller stats — **S40**, same domain.
- Not built (see Assumptions): scraping prices from free text or by running page scripts, login-protected pages, per-variant prices, user pause/resume of a watch, automatic repricing, competitor discovery, link crawling (we fetch registered URLs only, we never follow links).

## User Scenarios & Testing *(mandatory)*

Notation used by the scenarios. Time is frozen at `T0 = 2026-10-06T12:00:00Z`. Shops: `A` (plan `PRO`, `ACTIVE`; owners Ann and Olga, staff Stan, viewer Vic), `B` (`PRO`, owner Bo), `C` (`STARTER`, owner Cy), `D` (`SUSPENDED`). Shop `A`'s entitlement `maxCompetitorWatches` is 5, shop `C`'s is 0. Products: `PA` (shop A, `priceMinor 99900`, `EUR`, `ACTIVE`, title "iPhone 17"), `PA2` (shop A, 50000 EUR), `PX` (shop A, `ARCHIVED`), `PB` (shop B, 85000 EUR). The competitor site `rival.test` is a fixture server (the only system-edge fake besides the clock and the resolver); `U1 = https://rival.test/p/iphone`, `U2 = https://rival.test/p/ipad`. A fixture page shows a JSON-LD offer with a configurable price and currency. Amounts are integer minor units. "Target" means one normalised URL (shared by every shop watching it); "watch" means one shop's product linked to a target; "observation" means one recorded price of a target. "Cycle" is one run of the scheduler (every minute). Every endpoint test also checks `401` without credentials, and the problem+json fields `type, title, status, detail, instance, requestId, code` on every error.

### User Story 1 — A seller registers a competitor URL (Priority: P1)

A seller on a paid plan picks one of their products and pastes the URL of the same product at a competitor. The URL is checked, cleaned and remembered; nothing else about the competitor is needed.

**Why this priority**: nothing else in the capability exists without a watch, and the registration is where untrusted URLs enter the system.

**Independent Test**: `POST /shops/:shopId/competitors` as a member, then read the persisted rows.

**Acceptance Scenarios**:

1. **AS-01** (create) — **Given** shop `A` member Stan (`products.write`) and product `PA`, **When** `POST /shops/A/competitors {productId: PA, url: "HTTPS://Rival.test:443/p/iphone/?utm_source=ads&b=2&a=1#reviews"}`, **Then** `201 {id, productId: PA, url: "https://rival.test/p/iphone?a=1&b=2", host: "rival.test", status: "ACTIVE", lastPriceMinor: null, currency: null, lastCheckedAt: null, lastStatus: null, nextCheckAt: "2026-10-06T12:00:00Z", createdAt}` parsed by the contracts schema; one target and one watch exist; the target is queued by the next cycle (AS-16); no request has gone to `rival.test`.
2. **AS-02** (idempotent replay and equivalent spellings) — **Given** AS-01 done, **When** the same body is sent again, and then `{productId: PA, url: "https://rival.test/p/iphone?a=1&b=2&fbclid=z"}`, **Then** both answer `200` with the same `id`, and the counts stay at one target and one watch; **When** `PA` is watched with the different URL `U2`, **Then** `201` with a new `id` (two watches on `PA`).
3. **AS-03** (one target for many shops) — **Given** AS-01 done, **When** Bo (shop B) watches `U1` for `PB`, **Then** `201` with a different watch `id`, the same target (one `CrawlTarget` row, one URL), and the target's `nextCheckAt` unchanged; the target is fetched once per cycle however many shops watch it (AS-16).
4. **AS-04** (validation) — **Given** the endpoint, **When** the body: omits `productId` or `url`; has a `productId` that is not a UUID; has a `url` that is empty, not a URL, longer than 2048 characters, or with a scheme other than `https` (`http`, `ftp`, `javascript`, `file`); carries credentials in the URL (`https://u:p@rival.test/`); has an unknown field, a repeated field or a non-JSON content type, **Then** each answers `400 validation_failed` with the failing field in `errors[]` and nothing is stored.
5. **AS-05** (SSRF and policy refusal at registration) — **Given** a resolver double, **When** the URL is `https://169.254.169.254/latest/meta-data`, `https://127.0.0.1/`, `https://10.0.0.5/`, `https://192.168.1.1/`, `https://172.16.0.1/`, `https://[::1]/`, `https://[fc00::1]/`, `https://[::ffff:127.0.0.1]/`, `https://2130706433/` (decimal form of 127.0.0.1), `https://localhost/`, a host that resolves to one public and one private address, a URL on port `8443` or `22`, **Then** each answers `422 url_not_allowed` with a generic `detail` (no resolved address, no resolver message) and nothing is stored; a host that does not resolve answers `422 url_unresolvable`; a host that resolves only to public addresses is accepted (AS-01).
6. **AS-06** (product ownership) — **Given** `PB` (shop B), a random UUID, and archived `PX`, **When** Stan posts a watch for each on shop `A`, **Then** `PB` and the random UUID answer the same `404 product_not_found` (byte-identical apart from `instance` and `requestId`: another shop's product is indistinguishable from a missing one) and `PX` answers `409 product_archived`; nothing is stored.
7. **AS-07** (tenant isolation and permissions) — **Given** the routes of AS-01, AS-12, AS-13 and AS-14, **When** Bo (not a member of A) calls any of them on shop `A`, a malformed shop id, or an unknown shop id, **Then** each answers the same `404 shop_not_found`; **When** Vic (viewer) writes (`POST`, `DELETE`), **Then** `403 permission_denied`, while his reads (`products.read`) answer `200`; **When** a member of suspended shop `D` writes, **Then** `403 shop_suspended` and reads answer `200`; **When** Stan calls `DELETE /shops/A/competitors/<watch of shop B>` or reads its prices, **Then** `404 watch_not_found`, identical to an unknown id; the answer order is `401`, `404`, `403`, status gate.
8. **AS-08** (limits) — **Given** shop `A` with four watches and a limit of 5, **When** a fifth distinct watch is added, **Then** `201`; **When** a sixth is added, **Then** `422 watch_limit_reached {scope: "shop", limit: 5}`; **Given** product `PA` with five watches, **When** a sixth watch is added for `PA`, **Then** `422 watch_limit_reached {scope: "product", limit: 5}`; **Given** shop `C` (limit 0), **When** Cy adds a watch, **Then** `422 watch_limit_reached {scope: "shop", limit: 0}`; replaying an existing watch (AS-02) at the limit still answers `200`; the limit read is made through the entitlement service (S18) and a failure of it answers `503 entitlements_unavailable` and stores nothing (fail closed).
9. **AS-09** (concurrency) — **Given** an empty shop `A`, **When** ten identical `POST`s are sent at once (`Promise.all`), **Then** exactly one `201` and nine `200`, all with one `id`, one watch row; **Given** four watches and a limit of 5, **When** three requests with three different URLs are sent at once, **Then** exactly one `201` and two `422 watch_limit_reached`, and the shop has five watches.
10. **AS-10** (rate limit) — **Given** shop `A` that sent 30 writes in the last minute, **When** the 31st arrives, **Then** `429 rate_limited` with `Retry-After` and nothing is stored; shop `B` is unaffected; **When** the limiter's own store is down, **Then** writes answer `503 service_unavailable` (fail closed) and reads are served.
11. **AS-11** (a re-registration never forces a fetch) — **Given** the target of `U1` last checked at `T0 − 30 min` with `nextCheckAt = T0 + 5 h`, **When** shop B registers `U1`, **Then** `nextCheckAt` is unchanged; **Given** the target last checked at `T0 − 2 h` (due at `T0 + 4 h`), **Then** registering pulls `nextCheckAt` forward to `T0`; a never-checked target stays due; repeating the registration 100 times never makes the target due more than once per hour.

### User Story 2 — A seller manages watches and reads price history (Priority: P2)

The seller sees all watches (with the last price seen), removes the ones that are no longer useful, and opens the price history of one watch.

**Why this priority**: it turns the data into something a seller can use; the happy path is the web journey.

**Independent Test**: seed watches and observations, call the three read/delete routes.

**Acceptance Scenarios**:

1. **AS-12** (list) — **Given** shop `A` with 7 watches (limit raised), **When** a member calls `GET /shops/A/competitors?limit=3`, **Then** `200 {items: [{id, productId, url, host, status, lastPriceMinor, currency, lastCheckedAt, lastStatus, nextCheckAt, createdAt}], nextCursor}` newest first with `id` as the final tiebreaker, no item of another shop, no target id or internal field; following `nextCursor` yields all 7 once, without gaps or repeats while a watch is added in between; `productId=PA` filters; the default `limit` is 50, the maximum 100; `limit=0`, `limit=101`, a malformed `cursor` and an unknown parameter answer `400 validation_failed`.
2. **AS-13** (remove) — **Given** shops A and B watching `U1`, **When** Stan calls `DELETE /shops/A/competitors/<id>`, **Then** `204`, the watch is gone, shop B's watch and the target stay; **When** the call is repeated, **Then** `404 watch_not_found`; **When** Bo removes his watch (the last one), **Then** `204` and the target is retired: it is no longer scheduled, a frontier entry already queued for it is dropped without a request when taken, its history stays until retention (AS-54); a `DELETE` racing a crawl of the same target neither fails nor leaves a watch behind.
3. **AS-14** (price history) — **Given** a watch whose target has observations `89900` at `T0 − 10 d`, `94900` at `T0 − 5 d` and `89900` at `T0 − 1 d`, **When** a member calls `GET /shops/A/competitors/<id>/prices?days=30`, **Then** `200 {watchId, currency: "EUR", from, to, points: [{observedAt, priceMinor}] (oldest first), lowestMinor: 89900, lowestAt: <earliest instant at 89900>, latestMinor: 89900}`; `days=7` returns the last two points; a watch with no observation answers `200` with `points: []` and `lowestMinor: null`; `days` default 30, minimum 1, maximum 365, `days=0`, `days=366`, `days=abc` answer `400 validation_failed`; at most 1000 points are returned (the newest).
4. **AS-15** (analytics store down) — **Given** the history store is unreachable, **When** a member reads prices, **Then** `503 history_unavailable` within 3 s with a generic `detail`, while `GET /shops/A/competitors` still answers `200` with `lastPriceMinor` taken from the operational store.

### User Story 3 — Pages are fetched politely and safely (Priority: P1)

Every registered page is re-crawled on a schedule without ever hammering a competitor's site, without ever touching a page the site forbids, and without ever letting a seller point our servers at our own network.

**Why this priority**: an impolite or unsafe crawler gets the platform blocked or breached; this is the capability's reason to be a showcase.

**Independent Test**: run the scheduler and the fetch loop against fixture sites with robots files, delays and hostile redirects.

**Acceptance Scenarios**:

1. **AS-16** (scheduling) — **Given** targets `T1..T4` due (hosts `rival.test` ×3 and `other.test`), watched by 1, 3, 1 and 1 shops, and `T3` watched by an `ENTERPRISE` shop, **When** the scheduler runs, **Then** each due target is queued exactly once (four entries, not six), a second run in the same cycle queues none, a target whose queue mark is older than 15 minutes is queued again, and with a per-run cap of 2 the two targets of the highest shop plan (`ENTERPRISE`, then `PRO`, then `STARTER`) go first, ties by the earliest `nextCheckAt`; a retired target (no watch) is never queued; a target of a paused watch only (AS-51) is never queued.
2. **AS-17** (the frontier is rebuildable) — **Given** queued targets, **When** the shared fast store is emptied, **Then** the next cycle queues every due target again and the crawl continues; **Given** a worker that took a target and died before finishing (never released the host), **When** the lease time (60 s) has passed, **Then** the host is available again, and the target is crawled again no later than 15 minutes after it was due; no target is lost.
3. **AS-18** (robots disallow) — **Given** `robots.txt` with `User-agent: *` and `Disallow: /private`, and a watch on `https://rival.test/private/deal`, **When** the target is crawled, **Then** the only request that reached `rival.test` was `GET /robots.txt`, `lastStatus` is `disallowed_by_robots`, `nextCheckAt` is `T0 + 24 h`, no observation, no archive, no event.
4. **AS-19** (robots rules, pure) — **Given** the rule evaluator, **Then** the table-driven cases hold: the group naming our product token (`marketplacepricebot`, matched exactly and case-insensitively, never as a substring: `User-agent: bot` does not match) beats `*`; consecutive `User-agent` lines share one group; the longest matching rule wins, a tie is allowed; `*` and `$` work; `Allow:` with an empty value is ignored while an empty `Disallow:` allows everything; field names are case-insensitive, comments and `\r\n` and a leading byte-order mark are ignored; the rule is matched against path plus query; `Crawl-delay` is read as a non-negative number and ignored otherwise; an empty file allows everything; a file of 600 KiB is parsed up to its first 500 KiB.
5. **AS-20** (robots fetch outcomes) — **Given** the origin answers `robots.txt` with: `200` valid; `404` or `410`; `403`; `500`; `503`; a connection reset; a body slower than the deadline; a redirect to another origin, **Then** `200` → the rules apply and are cached 24 h; `404`/`410` → everything allowed, cached 1 h; `403` and every other `4xx` → everything allowed, cached 1 h; `5xx`, connection failure or timeout → the page is **not** fetched (treated as a full disallow), `lastStatus` is `robots_unavailable`, `nextCheckAt` is `T0 + 1 h`, cached 15 min; a redirect to another origin is not followed and counts as unavailable; every robots request uses the same SSRF guard and limits as page requests (AS-26, AS-28).
6. **AS-21** (robots cache is fleet-wide) — **Given** two targets of origin `https://rival.test`, crawled by two different worker instances within 24 h, **Then** `robots.txt` was requested once; **When** the clock passes `+24 h`, **Then** the next crawl requests it again and a changed rule takes effect; the cache key includes scheme, host and port, so `rival.test` and `rival.test:8443` never share rules (the latter is refused by AS-05 anyway).
7. **AS-22** (Crawl-delay) — **Given** `Crawl-delay: 2` and two due targets on `rival.test`, **When** the loop runs, **Then** the second request reaches the site at least 2 s after the first finished; without a `Crawl-delay` the minimum gap is 1 s; a `Crawl-delay: 86400` is capped at 300 s; a negative or non-numeric value means the default.
8. **AS-23** (one in-flight request per host, fleet-wide) — **Given** two worker instances with 16 fetch loops each, ten due targets on `rival.test` (a fixture counting concurrent requests) and three due targets on each of `a.test`, `b.test`, `c.test`, **When** all loops run, **Then** the fixture observed at most 1 concurrent request on `rival.test` and consecutive requests were at least the delay apart, while the other three hosts were served in parallel (at least 3 requests in flight at some moment overall); all 19 targets were crawled once.
9. **AS-24** (back-off) — **Given** a page that answers `429` (then `503`, then `429` with `Retry-After: 120`, then `429` with `Retry-After: 99999`), **When** crawled, **Then** the host is not touched again for `max(10 × delay, Retry-After)`, with `Retry-After` capped at 1 h; the target's `lastStatus` is `http_429`/`http_503`; its `nextCheckAt` is `T0 + 6 h`; the price and the observation counter are untouched.
10. **AS-25** (an identifiable, minimal client) — **Given** any page or robots request, **Then** the fixture received `GET`, `User-Agent: MarketplacePriceBot/1.0 (+https://marketplace.dev/bot)`, an `Accept` for HTML, `Accept-Encoding: identity`, and no cookies, no `Referer`, no `Authorization` and no header that identifies a shop or user.
11. **AS-26** (SSRF at crawl time; no rebinding) — **Given** `U1` accepted at registration (public address), **When** its host later resolves only to `127.0.0.1`, **Then** nothing is requested from `127.0.0.1`, `lastStatus` is `blocked_address`, `nextCheckAt` is `T0 + 24 h`; **Given** a resolver double that answers a public address to the guard's lookup and a private one to any later lookup, **Then** the connection goes to the address that was checked (the fixture bound to it receives the request, the private one receives nothing); an IPv6 or IPv4-mapped private address is refused alike.
12. **AS-27** (redirects) — **Given** the page answers: `301` to another path of the same host; `302` to `https://169.254.169.254/`; `302` to `http://rival.test/x`; `302` to `https://other.test/x`; four chained same-host redirects; a `301` without `Location`, **Then** the first is followed (the final page is processed; `finalUrl` is not stored as a new target); the second → `blocked_address`; the third → `redirect_refused` (https only); the fourth → `redirected_host`, not followed, no request to `other.test`, the watcher sees the status; the fifth → `too_many_redirects` (at most 3 hops); the sixth → `http_3xx`; each hop re-runs the address check.
13. **AS-28** (fetch limits) — **Given** pages that: send 5 MiB; send `application/pdf` or `image/png`; send one byte per second; accept the connection and never answer; answer after 9 s, **Then** the first is cut at 2 MiB, the prefix is processed and the outcome counter `truncated` increments; the second is refused after the headers (`unsupported_content_type`, body not read); the third and fourth end at the overall request deadline of 10 s (`timeout`), the whole crawl of one target (robots + page + redirects) never exceeds 30 s, and the host lease is released; the fifth succeeds; memory per request never exceeds the cap.
14. **AS-29** (status mapping) — **Given** a page answering each status, **Then** `200` → processed; `404` and `410` → `gone`, interval ×2 per consecutive occurrence from 12 h up to 48 h; `401`/`403` → `blocked_by_site`, interval 24 h; other `4xx` → `http_4xx`, 12 h; `500`, `502`, `504`, a reset connection, a timeout, a DNS failure → `http_5xx`/`network_error`/`timeout`, retry in 1 h doubling up to 24 h; `429`/`503` → AS-24; none of them changes the last known price or sends an event.
15. **AS-30** (graceful shutdown) — **Given** a worker with in-flight fetches, **When** it is told to stop, **Then** it takes no new target, finishes (or abandons at 30 s) the in-flight ones, releases their host leases, and exits; the abandoned target is crawled again by AS-17.
16. **AS-31** (seen-set) — **Given** a seen-set of normalised URLs in front of the target table, **When** a never-seen URL is registered, **Then** the target is created; **When** a registered URL is registered again, **Then** the seen-set answers "probably seen" and the authoritative table confirms it (AS-02); **Given** the seen-set forced to answer "probably seen" for every URL (a false positive), **Then** registering a brand-new URL still creates its target and it is crawled; **Given** the seen-set emptied (loss), **Then** every behaviour is unchanged and it refills lazily; the counters `seen_set_definitely_new`, `seen_set_confirmed_hit`, `seen_set_false_positive` account for each lookup. No fetch is ever skipped because of the seen-set.

### User Story 4 — Prices are read reliably and changes are never missed (Priority: P1)

From each fetched page the capability extracts one price, recognises pages that did not change, and records price changes.

**Why this priority**: a wrong or missed price turns every alert into noise or silence.

**Independent Test**: crawl fixture pages with different markup and prices, read the target state, the history and the archive.

**Acceptance Scenarios**:

1. **AS-32** (first observation) — **Given** `U1` serving a JSON-LD offer `899.00 EUR`, **When** crawled, **Then** `lastStatus: ok`, `lastPriceMinor 89900`, `currency EUR`, `lastCheckedAt T0`, `nextCheckAt` between `T0 + 5 h 24 min` and `T0 + 6 h 36 min` (6 h ± 10 % jitter), one history row `{observedAt T0, priceMinor 89900, currency EUR}`, the page archived once in object storage under a key that holds the date, the host and the target id and that expires after 7 days, the observation counter is 1.
2. **AS-33** (extraction rules, pure) — **Given** the extractor, **Then** the table-driven cases hold. JSON-LD: `Offer`, `AggregateOffer.lowPrice`, `@graph`, `@type` as an array, `offers` as an array, a price as number or string; prices are exact decimals converted by the currency's minor-unit exponent: `"1.005" EUR → 101` (half up, no floating-point drift), `"19.99" → 1999`, `"1999" JPY → 1999`, `"1.234" KWD → 1234`; a price using `,` as decimal or thousands separator (`"1.299,00"`, `"1,299.00"`), `0`, a negative number, a value above 10^12 minor units, `NaN`, an empty string → no price; a missing or unknown currency (`""`, `"EURO"`, `"XXX"`) → no price (never defaulted); currency lower case is upper-cased; offers whose availability is out of stock or discontinued are skipped, all out of stock → outcome `out_of_stock`; offers in two currencies → no price (ambiguous); several Product nodes → the first in document order that yields a price; malformed JSON-LD is skipped and the next script is read; a JSON-LD block wrapped in CDATA or an HTML comment is read. Meta fallback (only when no JSON-LD yields a price): `product:price:amount` + `product:price:currency`, `og:price:*`, `itemprop` price + `priceCurrency`, attributes in any order and quoting; a free-text "was €199, now only €149!" never yields a price.
3. **AS-34** (a one-token price change is not missed) — **Given** AS-32 and `PA` at 99900, **When** the competitor changes the price to `1099.00` and the page is crawled again, **Then** `lastPriceMinor 109900`, a second history row, observation counter 2, `lastStatus ok` (not `unchanged`), even though the page text differs by one token (SimHash alone would call it unchanged: extraction always runs).
4. **AS-35** (unchanged page backs off) — **Given** AS-32, **When** the page is crawled again unchanged (same price, SimHash distance ≤ 3 bits), **Then** `lastStatus unchanged`, `unchangedStreak` 1, no history row, no archive, counter unchanged, `nextCheckAt` ≈ `T0 + 12 h`; the next unchanged crawls give streak 2 → 24 h, streak 3 → 48 h, streak 4 → 48 h (cap); any observation of a changed price resets the streak to 0 and the interval to 6 h; every interval carries ±10 % jitter and is never shorter than 1 h.
5. **AS-36** (SimHash, pure) — **Given** the fingerprint function, **Then**: identical text gives distance 0 and the same 16-hex-digit hash on every run; a page whose only change is a rotated "people also bought" widget is within 6 bits (≤ 3 for the fixture of the unit table); an unrelated page is more than 15 bits away; text shorter than three words, empty text and text with only markup all produce a valid hash; the distance is symmetric (property-based), `d(a, a) = 0`, `d(a, c) ≤ d(a, b) + d(b, c)`; script, style and noscript content is ignored by the visible-text step.
6. **AS-37** (page changed, price not) — **Given** a known price, **When** the page changes by more than 3 bits but the extracted price is the same, **Then** it is archived, `unchangedStreak` resets to 0, no history row, counter unchanged, interval 6 h.
7. **AS-38** (no price) — **Given** a known price `89900`, **When** a crawl finds a page with no price (or only out-of-stock offers), **Then** `lastStatus` is `no_price` (or `out_of_stock`), the last price is kept (never zeroed), no history row, no event, the page is archived once per fingerprint change; three consecutive `no_price` crawls move the interval to 24 h; a later page with the price is a normal observation.
8. **AS-39** (currency change) — **Given** a known `89900 EUR`, **When** the page switches to `949.00 USD`, **Then** a new observation is recorded (`94900 USD`, counter +1); `lowestMinor` of the history endpoint is computed within the latest currency only; a comparison against a product priced in another currency is never made (AS-46).
9. **AS-40** (URL normalisation, pure) — **Given** the normaliser, **Then** the table-driven cases hold: host lower-cased and punycode-encoded (`BÜCHER.test` → `xn--bcher-kva.test`); default ports dropped (`:443`); fragment removed; `utm_*`, `gclid`, `gclsrc`, `dclid`, `fbclid`, `msclkid`, `yclid`, `igshid`, `mc_cid`, `mc_eid`, `_ga`, `_gl`, `ref`, `ref_`, `spm` removed, other parameters (including `tag`, `color`, `variant`, `id`) kept, remaining parameters sorted by name then value, a repeated parameter keeps all its values; a trailing slash dropped except for the root; an empty query `?` dropped; percent-escapes upper-cased; dot segments resolved; normalisation is idempotent (property-based); a URL of more than 2048 characters, with credentials, with a scheme other than `https` or with a port other than 443 is refused.
10. **AS-41** (a failing store never loses or invents a price) — **Given** the history store is down during a crawl that finds a changed price, **Then** the target's price and counter are **not** advanced, `lastStatus` is `history_unavailable`, the crawl is retried in 15 min and, when the store is back, records the observation exactly once (the history row is written with a deduplication token made of target id and counter, so a retry after a half-finished attempt adds no second row); **Given** object storage is down, **Then** the observation is recorded, the archive is skipped, the counter `archive_failed` increments and a warning is logged.
11. **AS-42** (two workers on one target) — **Given** a lease that expired during a slow crawl so that two workers fetch the same target and both find price `89900` (new), **When** both finish at once, **Then** exactly one observation is recorded (counter +1, one history row), exactly one event per owner results (AS-43), and the second worker's update is a no-op (the update is conditional on the counter it read).

### User Story 5 — Owners are alerted when a competitor undercuts them (Priority: P1)

When a competitor's price falls below the seller's own price for the product, the shop's owners get one alert, once per price drop, in the right currency.

**Why this priority**: this is the outcome the seller pays for.

**Independent Test**: crawl pages with controlled prices and read the outbox, with the real notifications path replaced by an event spy (S28 consumes the event).

**Acceptance Scenarios**:

1. **AS-43** (undercut → one event per owner) — **Given** `PA` at `99900 EUR`, shop `A` with owners Ann and Olga (and staff Stan, viewer Vic), and a watch on `U1`, **When** the first crawl finds `899.00 EUR`, **Then** exactly two outbox rows of type `seller_insights.competitor_price_dropped` on topic `seller-insights.events` exist, one per owner, with envelope `{eventId, type, version: 1, occurredAt: T0, aggregateId: <watchId>}` and payload `{watchId, shopId: A, productId: PA, productTitle: "iPhone 17", host: "rival.test", competitorPriceMinor: 89900, yourPriceMinor: 99900, currency: "EUR", ownerId, priceVersion: 1}` parsed by the contracts schema; the two events differ in `eventId` and `ownerId` only; `eventId` is derived deterministically from (watch id, `priceVersion`, owner id); the competitor URL's path and query never appear in the event; nobody else is alerted.
2. **AS-44** (no alert when not undercut) — **Given** `PA` at 99900, **When** the competitor price is `1099.00` (higher) or `999.00` (equal), **Then** the observation is recorded and no event is written.
3. **AS-45** (an alert per new drop, not per crawl) — **Given** AS-43 done (alerted at 89900), **When** the next crawls find `89900` again (unchanged), `84900`, `95000`, `90000`, `120000`, `125000`, **Then** events are written only for `84900` (lower than the previous price and below yours; `priceVersion 2`) and `90000` (lower than `95000`, below yours; `priceVersion 4`), not for the unchanged price, `95000` (a rise, though below yours), `120000` (above yours) nor `125000` (a rise); each event has the observation counter of its observation as `priceVersion` (the observations are counted 1 to 6); replaying the same observation never repeats an event (AS-48).
4. **AS-46** (comparison basis) — **Given** a competitor price of `949.00 USD` and `PA` priced in `EUR`, **Then** the observation is recorded, no event, outcome `currency_mismatch`; **Given** the product was archived or deleted since registration, **Then** no event, outcome `product_unavailable`; `yourPriceMinor` is always the product's price at the moment of evaluation read through the catalog's batch service, never a copy; a change of the product's price takes effect at the next observation (an alert is not re-evaluated on a product price change).
5. **AS-47** (several watchers of one target) — **Given** `U1` watched by shop A (`PA` at 99900) and shop B (`PB` at 85000) and a competitor price of 89900, **Then** only shop A's owners are alerted, once each; a competitor price of 80000 alerts both shops (each with its own `yourPriceMinor`); the evaluation of one observation handles up to 500 watches per transaction and continues with the next batch, so 1200 watches produce 1200 evaluations and no event twice.
6. **AS-48** (atomic and replay-safe) — **Given** an outbox insert that fails (a trigger), **When** a crawl finds a changed undercutting price, **Then** the whole step rolls back (counter, price and watch evaluation unchanged), the crawl is retried in 15 min and, with the fault removed, records the observation and writes the events once; **Given** a crash after commit and a re-run of the same observation, **Then** no second event row exists (same deterministic `eventId`), and the evaluation of watch W for counter N happens at most once.
7. **AS-49** (a new watch is evaluated at once) — **Given** the target of `U1` already observed at `89900` and `PA` at 99900, **When** Stan registers the watch, **Then** in the same transaction one event per owner is written with `priceVersion` equal to the target's current counter; **When** `PA` is at 85000 instead, no event; a replay of the registration (AS-02) writes nothing more.
8. **AS-50** (no recipient, paused shops) — **Given** a shop whose owners resolve to nobody, **Then** the observation is recorded, no event, outcome `no_recipient` and a warning; **Given** shop `D` (`SUSPENDED`), **Then** its watches are never crawled or evaluated (AS-51).

### User Story 6 — The monitor follows its sources and stays operable (Priority: P2)

Shops are suspended, upgraded and deleted; products are deleted; the system must follow without cross-domain reads, and operators must see what the crawler is doing.

**Why this priority**: correctness over time, erasure, and the constitution's boundary rules.

**Independent Test**: deliver tenancy and catalog events to the consumers; read metrics, logs and ownership checks.

**Acceptance Scenarios**:

1. **AS-51** (shop events; duplicates and out of order) — **Given** the shop read model `{shopId, plan, status, version}` fed by `tenancy.shop_created`, `tenancy.shop_plan_changed`, `tenancy.shop_status_changed`, `tenancy.shop_deleted`, **When** shop `A` is suspended (`shopVersion 3`), **Then** its watches are paused (not scheduled, not crawled, not evaluated, listed with `status: "PAUSED"`) and reinstating it (`shopVersion 4`) resumes them (due immediately if overdue); **When** the events arrive in the order 4, 3, 4, 3, **Then** the state is the one of version 4 and each event had one effect; a `shopVersion` at or below the stored one is ignored; **When** `tenancy.shop_plan_changed {plan: "ENTERPRISE", shopVersion 5}` arrives, **Then** the priority of its targets changes at the next cycle (AS-16); **When** `tenancy.shop_deleted {shopId}` arrives, **Then** all watches of the shop and its read-model row are deleted, targets without watchers are retired, and a delivery of the same event again changes nothing; an event of a shop not yet known creates its row (`shop_status_changed` before `shop_created` is applied once `shop_created` arrives with a higher or equal version).
2. **AS-52** (product deleted) — **Given** watches on `PA` and `PA2`, **When** `catalog.product_deleted {productId: PA, shopId: A, productVersion: 7}` arrives (twice), **Then** the watches of `PA` are deleted once (targets retired if unwatched) and those of `PA2` stay; an event for a product without watches is acknowledged without effect.
3. **AS-53** (invalid payloads) — **Given** messages that lack the shop id, carry a non-UUID id, an unknown plan, an unknown status, a non-integer version, or an unsupported envelope version, **When** each is delivered, **Then** each is dead-lettered with a reason code, changes no state, and the next valid message of the same batch is applied; an unrelated event type on the same topic is ignored without a dead letter.
4. **AS-54** (retention) — **Given** a target with no watch for 30 days, **When** the daily purge runs (twice, and concurrently on two replicas), **Then** the target row is deleted once, a target with a watch or a younger one is kept; the raw page archive expires after 7 days (lifecycle rule asserted on the bucket configuration) and history rows after 2 years (table retention asserted); no table or archive holds a competitor page longer than that.
5. **AS-55** (observability) — **Given** crawls of every outcome, **Then** the counters `crawler_fetch_total{outcome}` (`ok`, `unchanged`, `no_price`, `disallowed_by_robots`, `robots_unavailable`, `blocked_address`, `http_4xx`, `http_429`, `http_5xx`, `timeout`, `network_error`, `redirected_host`, `unsupported_content_type`, …), `crawler_robots_total{result}`, `crawler_alert_events_total`, `crawler_archive_failed_total` and the gauges `crawler_overdue_targets` and `crawler_oldest_overdue_seconds` and `crawler_ready_hosts` are exposed; every log line carries `requestId` or a `crawlId`, the `targetId` and the `host`, and never the full URL, the query string, a page body or an address resolved for a refused URL.
6. **AS-56** (configuration) — **Given** the configuration, **When** the application starts with a private-host allowlist for fixtures while the environment is production, or with fetch loops outside 1–64, or a politeness minimum below 1 s, or a per-request cap above 8 MiB, **Then** startup fails with a message naming the key; with valid values it starts; the allowlist is honoured only outside production.
7. **AS-57** (table ownership and boundaries) — **Given** the code of this capability, **Then** `pnpm --dir packages/backend check:table-ownership --strict` reports no finding for `seller-insights` crawler files, the `CompetitorWatch`, `CrawlTarget` and shop read-model tables are in the ownership registry, the two tables hold no foreign key to another domain's table, and `pnpm check:boundaries` passes (static gate, no runtime test).

### Edge Cases

- A page lists several products with JSON-LD (a "related items" carousel): the first Product node with a price in document order wins; a seller whose competitor markup puts the related item first can see a wrong price and must pick a better URL (documented limitation, Assumptions).
- A competitor sells in a currency with another minor-unit exponent than the shop's: prices are stored in the competitor's own currency and compared only within a currency (AS-33, AS-46).
- The registered host redirects to `www.` — the seller must register the final URL; the status `redirected_host` says so (AS-27).
- A watch is registered by a shop later suspended or deleted (AS-51); a product archived (AS-46, AS-06).
- A competitor page with a price that flaps between two values on every crawl: each drop below the seller's price is an alert; the history and the per-watch evaluation make that visible (AS-45).
- Two different shops registering the same URL concurrently: one target, two watches (AS-03, AS-09).
- Clock skew across workers: the lease, delay and interval use the shared store's and database's clocks; tests freeze the clock.
- A target that fails every crawl for months: back-off reaches 24 h; the watch list shows the status; the target is not deleted while watched.

## Requirements *(mandatory)*

### Functional Requirements

**Watches**

- **FR-001**: A member with `products.write` registers a watch with `POST /shops/:shopId/competitors`; the URL is validated, normalised (FR-017), checked by the SSRF guard (FR-012) and stored once per normalised URL; the response is `201` for a new watch and `200` for an existing one with the same product and normalised URL (AS-01, AS-02, AS-04, AS-05).
- **FR-002**: The product must belong to the shop and be `ACTIVE`: ownership and status are read through the catalog's exported batch service (IX.7 R1, `getProductsByIds(ids, {shopId})`); a product of another shop and a missing product are indistinguishable (AS-06).
- **FR-003**: Limits: at most 5 watches per product, and at most the shop's entitlement `maxCompetitorWatches` (read through the entitlement service, R1) per shop; the count, the check and the insert are serialised per shop so concurrent requests cannot exceed the limit; an unavailable entitlement service refuses the write (AS-08, AS-09).
- **FR-004**: Registration never forces an immediate fetch of a target checked within the last hour; a never-checked or older target becomes due at once (AS-11).
- **FR-005**: A member with `products.read` lists the shop's watches with a cursor (default 50, max 100, newest first, unique tiebreaker) and optionally filters by product; no other shop's watch, no internal identifier of the target is ever returned (AS-12).
- **FR-006**: A member with `products.write` removes a watch (`204`; unknown or foreign id `404 watch_not_found`); removing the last watch of a target retires the target; removal is safe while the target is being crawled (AS-13).
- **FR-007**: A member with `products.read` reads a watch's price history for 1–365 days (default 30) with the lowest and latest price of the latest currency; at most 1000 points; an unavailable history store answers `503 history_unavailable` without breaking the list (AS-14, AS-15).
- **FR-008**: Tenant resolution and answer order follow S03 (`401`, `404 shop_not_found` for non-members, unknown or malformed shops, `403 permission_denied`, then the status gate); every lookup of a watch has the shop in its predicate (AS-07).
- **FR-009**: Writes are rate-limited per shop (30 per minute, fail closed); reads are not limited by this capability (AS-10).
- **FR-010**: The seen-set of normalised URLs (Bloom filter, P1103) is a fast negative filter in front of the authoritative target table: "definitely new" skips the lookup, "probably seen" is always confirmed against the table, and neither a false positive nor a lost seen-set changes any outcome or skips any fetch (AS-31).

**Fetching**

- **FR-011**: The scheduler, once per minute and once across replicas, queues each due, watched, non-paused target at most once per cycle, ordered by the highest plan among its watchers (`ENTERPRISE`, `PRO`, `STARTER`), then by earliest due time, up to a per-run cap; a queue mark expires after 15 minutes so a lost entry is queued again; the frontier is fully rebuildable from the database (AS-16, AS-17).
- **FR-012** (SSRF guard, P0507): every outgoing request (page, `robots.txt`, each redirect hop) uses `https` on port 443 only (a fixture allowlist exists outside production), carries no credentials in the URL, resolves the host once, requires **every** returned address to be public (loopback, private, link-local including the metadata address, carrier-grade NAT, unique-local, multicast, reserved, IPv4-mapped and documentation ranges refused), connects to the address that was checked, and re-runs the check on every redirect; refusals are reported as `url_not_allowed` at registration and `blocked_address` at crawl time without leaking addresses (AS-05, AS-26, AS-27).
- **FR-013**: Redirects: at most 3 hops, same host only, `https` only; any other redirect ends the crawl with a status naming the reason (AS-27).
- **FR-014**: Limits per request: 2 MiB body (the prefix is processed), HTML content types only, 10 s overall deadline per request, 30 s per target crawl, no content encoding requested, no cookies stored (AS-25, AS-28).
- **FR-015**: Politeness: one queue per host; at most one in-flight request per host across all worker instances (a host lease of 60 s, released after each fetch); the minimum gap between two requests to a host is `max(1 s, Crawl-delay)` (Crawl-delay capped at 300 s); different hosts are fetched in parallel by up to the configured number of loops per instance; `429`/`503` extend the host's wait to `max(10 × delay, Retry-After)` with `Retry-After` capped at 1 h (AS-22, AS-23, AS-24).
- **FR-016** (robots): `robots.txt` of the origin is fetched through FR-012 and FR-014, cached for the fleet (24 h for a valid file, 1 h for "not found / other 4xx", 15 min for "unavailable"), parsed per RFC 9309 (product-token group before `*`, longest match, `*` and `$`, 500 KiB), and consulted before every page fetch; a disallowed path is never requested; an unavailable file (5xx, network failure, timeout) blocks the page for now (AS-18–AS-21).
- **FR-017**: URL normalisation produces the one canonical form of a page (the identity of a target): the rules of AS-40; it is idempotent and shared by registration, deduplication and the seen-set.
- **FR-018**: Every request identifies the crawler with `MarketplacePriceBot/1.0 (+https://marketplace.dev/bot)` and sends no cookies, referrer, authorization or shop/user identifier (AS-25).
- **FR-019**: Status mapping and re-crawl intervals follow AS-29 (errors), AS-35 (unchanged) and AS-37/AS-38; every interval carries ±10 % jitter and is at least 1 h; the interval resets to 6 h when a price change is observed (change frequency drives the interval, FR-011 drives the order).
- **FR-020**: A graceful shutdown stops taking work, finishes or abandons in-flight fetches within 30 s and releases leases (AS-30).

**Extraction, history, alerts**

- **FR-021**: Price extraction follows AS-33: structured data first, meta tags second, never free text; exact decimal arithmetic with the currency's minor-unit exponent; currency mandatory; ambiguous formats and ambiguous pages produce no price rather than a guess.
- **FR-022** (SimHash, P1104): the visible text of every page is fingerprinted; a page is "unchanged" only if the price is equal **and** the fingerprint is within 3 bits of the stored one; extraction always runs (AS-34, AS-35, AS-36, AS-37).
- **FR-023**: A price observation (first price, a different price, or a different currency) increments the target's observation counter, appends one history row (idempotent on target id and counter) and updates the target, in that order; a failure of the history store leaves the target untouched and is retried (AS-41); the observation step is conditional on the counter read, so concurrent crawls of one target record one observation (AS-42).
- **FR-024**: Changed pages are archived to object storage (7-day lifecycle); an archive failure never blocks an observation (AS-41).
- **FR-025**: After an observation, every active watch of the target is evaluated (batches of 500, each batch one transaction): the alert condition is *competitor price < your price, same currency, product active, shop active, and (the watch has no previous evaluation or the competitor price is lower than the one at the watch's previous evaluation)*; the watch's evaluated price is then updated to the current one (AS-43–AS-47).
- **FR-026**: An alert is the outbox event `seller_insights.competitor_price_dropped` v1, one per owner of the shop (owners resolved through tenancy's batch service, R1), written in the same transaction as the watch's evaluation (IX.6); `eventId` is deterministic from (watch, `priceVersion`, owner); redelivery of an observation writes no second row; no notification is sent by this capability (AS-43, AS-48).
- **FR-027**: A new watch is evaluated against the target's current observation in the registration transaction (AS-49).
- **FR-028**: Product price and currency for the comparison are read through the catalog's batch service at evaluation time; the module that evaluates runs in the worker process that loaded that service (AS-46).

**Reactions, retention, operability**

- **FR-029**: A shop read model `{shopId, plan, status, version}` (IX.7 R3, owned by this capability) is maintained from `tenancy.shop_created`, `tenancy.shop_plan_changed`, `tenancy.shop_status_changed` and `tenancy.shop_deleted`, with a version guard and idempotent, replayable consumers; watches of a shop that is not `ACTIVE` are paused; deleting a shop deletes its watches (AS-51, AS-53).
- **FR-030**: `catalog.product_deleted` deletes the product's watches (AS-52); no foreign key and no cascade crosses the domain boundary (AS-57).
- **FR-031**: Invalid or unsupported messages are dead-lettered with a reason and cause no change; duplicates have one effect (AS-51–AS-53).
- **FR-032**: Retention: raw pages 7 days; history 2 years; targets without watchers are purged after 30 days by a daily, single-run, idempotent job (AS-54).
- **FR-033**: Metrics, logs and the configuration checks of AS-55 and AS-56 hold; scheduled jobs run once per schedule across replicas (VIII.6).
- **FR-034**: Errors are problem+json with a stable `code` (`validation_failed`, `url_not_allowed`, `url_unresolvable`, `product_not_found`, `product_archived`, `watch_limit_reached`, `watch_not_found`, `shop_not_found`, `permission_denied`, `shop_suspended`, `rate_limited`, `history_unavailable`, `entitlements_unavailable`, `service_unavailable`); request and response bodies parse with schemas in `packages/contracts` (VII.6).
- **FR-035**: Competitor data is private to the owning shop's members: the capability exposes no route, event or export that shows one shop's watches, prices or alerts to another shop or the public; the shared target's other watchers are never revealed (AS-07, AS-12).

### Key Entities

- **Watch**: one shop's product linked to one target: id, shop, product, status (`ACTIVE`, `PAUSED`), last evaluated price, creation time. Unique per (product, target).
- **Target**: one normalised URL and its crawl state: host, last price and currency, observation counter, fingerprint, unchanged streak, last status, last and next check, queue mark. Shared by all watchers.
- **Observation**: one price of a target at a time (in the analytics store): target, instant, price, currency, counter.
- **Shop read model**: `{shopId, plan, status, version}` copied from tenancy events.
- **Archived page**: raw HTML of a changed page, 7 days.
- **Frontier**: per-host queues and the ready-host schedule (derived, rebuildable).
- **Robots rules**: per-origin cached rules (derived).
- **Price-drop alert**: the outbox event of FR-026.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: No fixture host ever sees more than one request in flight, nor two requests closer than its delay, in any test, with at least two worker instances (AS-23).
- **SC-002**: Zero requests reach a disallowed path, a private address, a non-443 port or a cross-host redirect target in any test (AS-18, AS-26, AS-27).
- **SC-003**: A competitor price change below the seller's price produces exactly one alert per owner within 2 minutes of the crawl that sees it, and never a duplicate under redelivery, concurrency or crash-and-retry (AS-43–AS-48).
- **SC-004**: A one-token price change is detected in 100 % of the table-driven cases (AS-34, AS-33), and an unchanged page costs no history row and no archive (AS-35).
- **SC-005**: A newly registered URL is fetched for the first time within 2 minutes (scheduler cycle plus lease), unless it was checked within the last hour (AS-11).
- **SC-006**: Registration answers in under 500 ms at p95 excluding name resolution of the competitor's host; the history read answers in under 300 ms at p95 for 365 days.
- **SC-007**: Design target, checked by a load run and not by CI: 10 million watched URLs re-crawled every 6 hours is about 460 fetches per second fleet-wide; throughput scales by adding hosts to the frontier partitioning and worker instances, and the per-host politeness bound of SC-001 holds at any scale.
- **SC-008**: All 57 acceptance scenarios pass; the table-ownership gate for this capability reports zero findings (AS-57).

## Assumptions

- Defaults above are the ones chosen unattended; each is also a line in [`questions.md`](questions.md).
- **Source conflict**: the notes' step list names a Bloom filter shared with the penetration guard; the implementation notes say it was deliberately not used because a false positive would skip a fetch. The pattern map (P1103) binds this capability to it. Resolved by using it only as a *negative filter* backed by the authoritative table (FR-010), so the false-positive risk the notes name cannot occur.
- **Plans and entitlements**: the right to watch is an entitlement (`maxCompetitorWatches`, S18), not a plan name; the plan from the shop read model only orders the crawl queue (FR-011). The notes' "Pro shops" is realised by that entitlement being 0 on `STARTER` and the free tier; the numbers are S18's.
- **Recipients**: alerts go to the shop's owners (as in the notes); a shop with several owners produces one event per owner so the notification capability needs no membership lookup and receives one `ownerId` as it requires.
- **Evaluation moment**: alerts are decided when a target is observed or a watch is registered, not when the seller changes the product's price; the seller sees the comparison live in the web screen (R2).
- **Ambiguity policy**: a missing currency, an ambiguous decimal format, mixed-currency offers or a page with several products' prices produce no price rather than a guess; a wrong price is worse than a missing one.
- **Politeness bounds**: minimum gap 1 s, Crawl-delay cap 300 s, host lease 60 s, per-request 10 s, per-crawl 30 s, body 2 MiB, 3 redirect hops, base interval 6 h, ladder to 48 h, ±10 % jitter, queue mark 15 min, scheduler cap 5000 per run. They are configuration with these defaults and the bounds of AS-56.
- **Stores** (domain map): Postgres for watches, targets and the shop read model; the shared fast store for the frontier, leases, queue marks, robots cache and the seen-set (all derived and rebuildable); ClickHouse for price history; object storage for archived pages.
- **Hosting**: core serves the HTTP routes; worker runs the scheduler, the fetch loops and the purge; projector runs the shop and product consumers; the worker loads the catalog's and tenancy's exported services (R1) for the comparison and the recipients.
- **Not built**: user pause/resume of a watch (the shop-status pause exists), re-crawl on demand, scraping from free text or scripts, per-variant prices, authentication to competitor sites, proxies and egress IP publication (the user agent URL is the identification), a per-host manual block list.

- **S03 (`tenancy`)**: the guard `ShopScoped(permission)` with the status gate and `404 shop_not_found` (S03 AS-09, AS-12, FR-011–FR-013); permissions `products.write` and `products.read` as in S03 FR-020; R1 `MembershipQueryService.getMembersByShopIds(shopIds: ShopId[], roles?: ShopRole[]): Promise<Map<ShopId, {userId: UserId; role: ShopRole}[]>>` (≤ 500) called with `['OWNER']`; events `tenancy.shop_created` v1 `{shopId, ownerId, name, slug, plan, region, shopVersion}`, `tenancy.shop_plan_changed` v1 `{shopId, plan, shopVersion}`, `tenancy.shop_status_changed` v1 `{shopId, from, to, reason?, shopVersion}` (`to` ∈ `ACTIVE|SUSPENDED|DELETING|DELETED`), `tenancy.shop_deleted` v1 `{shopId}`. The alert is written only for `ACTIVE` shops; `DELETING` pauses like `SUSPENDED`.
- **S05 (`catalog`)**: R1 `ProductQueryService.getProductsByIds(ids: ProductId[], options?: {shopId?: ShopId}): Promise<Map<ProductId, ProductDto>>` (≤ 500) with `ProductDto = {id, shopId, title, priceMinor, currency, status: 'ACTIVE'|'ARCHIVED', …}`; event `catalog.product_deleted` v1 `{productId, shopId, productVersion}` on `products.events` keyed by `productId`; the provider must be loadable in the worker app.
- **S18 (`billing`)**: R1 entitlement check `checkLimit('SHOP', shopId, 'maxCompetitorWatches', current): Promise<{allowed: boolean; limit: number; remaining: number}>`; a new numeric key `maxCompetitorWatches` in S18's plan table (`[CONTRACT]` in questions.md: not defined there today); failure rejects `entitlements_unavailable`.
- **S54 (platform toolkit)**: an SSRF-safe outbound HTTP GET with an injectable resolver and the guarantees of FR-012–FR-014: `safeGet(url, {userAgent, maxBytes, requestDeadlineMs, maxRedirects, sameHostRedirectsOnly, allowedPorts, allowedHosts?}) → {status, headers, body, truncated: boolean, finalUrl, redirects: number}` rejecting with a typed error `blocked_address | redirect_refused | redirected_host | too_many_redirects | unsupported_content_type | timeout | network_error`; the injectable clock; metrics registry; structured logger with redaction; problem+json filter; validated configuration with startup failure; graceful shutdown hooks.
- **S53 (events and queues)**: `outbox.append(event)` inside the domain's transaction (IX.6); the consumer framework (envelope check, schema validation, own consumer group, dead-letter with reason, idempotent and version-guarded consumption, replay).
- **S49 (job scheduler)**: `upsertSchedule`, `@JobHandler`, one run per schedule across replicas, UTC cron.
- **S50 (rate limiter)**: policy registration with fail-closed mode and `429` with `Retry-After`.
- **S01 (`identity`)**: `Firewall()` and `@User()`.
- **Infrastructure**: object storage with a 7-day lifecycle rule on the archive prefix; the analytics store table `competitor_prices` with 2-year retention and insert deduplication; the shared fast store for the frontier, leases, caches and the seen-set.

Cross-domain data used by S41 (constitution IX.7): **R1** — catalog's `ProductQueryService`, tenancy's `MembershipQueryService`, billing's entitlement service; **R3** — a shop read model fed by tenancy events and watch cleanup fed by `catalog.product_deleted`; **R2** — none (the web screen composes "your price" through the BFF; this capability's own API never calls another domain over HTTP). No JOIN, association, foreign key or direct query touches another domain's table.
