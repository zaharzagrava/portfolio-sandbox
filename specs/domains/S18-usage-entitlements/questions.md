# Questions and decisions: S18 — Usage metering and entitlement checks

Decisions taken unattended under the decision policy (production-grade, notes and constitution first). BREAKING first, then CONTRACT, then LOCAL. Format: `question → default → why`. ## BREAKING

- [BREAKING] Late events are found by `ingested_at > previous invoice's usageMeasuredAt` and only for the immediately previous invoice (`billing.jobs.ts:100-108`, `usage.service.ts:46-60`): an event arriving after the *next* invoice measured is never billed, and a period can be examined twice → a settlement ledger per `(subscription, period, metric)` with a conditional-update settle; each unit billed exactly once, any number of invoices later (P0614: adjustments referencing the original period; invariant checked) → lost or double billing is a correctness bug.
- [BREAKING] Late units are priced entirely at the overage rate, ignoring the included allowance, and rounded up per adjustment (`billing.jobs.ts:109`: `Math.ceil(late / 1000) * per1000`) → adjustment = increase in the period's overage price (`ceil` of the new total minus the already-settled price), allowance respected, snapshot of the period's allowance and rate → customers under their allowance were charged, and many small adjustments each paid a started block.
- [BREAKING] `UsageService.record` fire-and-forget produce that drops the event on error (`usage.service.ts:30-32`, exported through `index.ts:16`, provided again in `assistant.module.ts:32`, `knowledge.module.ts:39`, `onboarding.module.ts:34`) → removed; usage enters only by events (`usage.recorded` from developer-platform, `llm.call_completed` from S46); consumers are durable and idempotent → IV.5, IX.7 R3, debt D-14; silent usage loss is silent revenue loss.
- [BREAKING] `UsageProjector` silently filters events that fail `UsageRecorded.match` and has no inbox, validation or DLQ (`usage.projector.ts:19-25`) → a consumer with schema validation, identity de-dup, DLQ with reason → IV.5.
- [BREAKING] Usage events are not validated: any metric string, `quantity` any positive int, any `ts` (`usage.service.ts:11-15`) → metric allowlist pattern, quantity ≤ 1e9, `ts` within `[now−90d, now+5min]` → a bad producer could create unbounded bills or hide usage in the far past/future.
- [BREAKING] LLM calls record `Math.max(1, tokens)` (`llm-meter.ts:54`) → zero-token calls record nothing → billing a unit for nothing.
- [BREAKING] The entitlement guard answers `403` with a plain message and fails closed with `403` on a missing shop context (`entitlements.service.ts:56-62`) → `403 entitlement_required` problem+json with `feature`; a route that has the guard without shop scoping or with an unknown key fails at startup; source down → `503 entitlements_unavailable` → V.3, and a misconfiguration should be impossible to ship, not a runtime 403.
- [BREAKING] `EntitlementsService.get` loads with raw SQL over `Subscription ⋈ Price ⋈ Plan` (`entitlements.service.ts:30-37`) → loads only through S17's `SubscriptionBasisService` (batch-capable); the cache entry carries the basis `subscriptionVersion` → no second reader of S17's tables; versions make out-of-order events harmless.
- [BREAKING] Invalidation is a plain key delete and a `getOrLoad` that may repopulate with a result loaded before the delete (`entitlements.service.ts:28-44`) → version-guarded invalidation: a load that started before a newer invalidation never stores its result; a failed invalidation is reported and the event redelivered → a slow load must not resurrect an old plan.
- [BREAKING] A failed load has no defined behaviour (`loaded ?? {}` returns an empty object, which the guard reads as "no features") → stale entry up to 60 min, else `entitlements_unavailable`; never "free tier" when unknown → availability without giving paid features away.
- [BREAKING] `index.ts` exports five models, `UsageService`, `UsageProjector` (`index.ts:7-17`) and the module is `@Global` exporting `BillingService`, `UsageService` (`billing.module.ts:20-26`) → barrel exports only `BillingModule`, `BillingWorkerModule`, `EntitlementsService`, `RequiresShopEntitlement`, the entitlement types (and S17's events/services); no `@Global` → X.4, IX.4, D-7, D-8; other domains import the module they use.
- [BREAKING] `billing.e2e-spec.ts` stubs `UsageService.totalFor/lateFor` (`:62-63`) → usage is exercised against the real usage store with real events (only the clock and external edges are faked) → VII.2 bans mocking the project's own services and stores.

## CONTRACT

- [CONTRACT] S17 says `linesFor` is read-only and returns only lines → returns `{lines, settlement}` and S17 calls `UsageSettlementService.settle({invoiceId, subscriptionId, settlement})` inside its invoice transaction, passing the plan unchanged → exactly-once billing of late usage needs a durable record of what was billed, written atomically with the invoice; a read-only provider cannot give that without parsing invoice descriptions. S17 must add one call (same domain, same transaction, allowed by IX.4/IX.6).
- [CONTRACT] S17 stores `usageMeasuredAt` on the invoice and passes `measuredAt` → S18 no longer needs it for correctness (the ledger is bound to quantities, not time) but S17 keeps storing it (audit) → no S17 change beyond the call above.
- [CONTRACT] The domain map exports `hasEntitlement(subjectId, feature)` → `hasEntitlement(subjectType, subjectId, feature)` → shop and user ids are both UUIDs, and the cache and basis are keyed by type; the map's shape is ambiguous and `get` already takes the type.
- [CONTRACT] S05 hoped for "an R1 check S18 exports that `ProductCommandService.create` would call" → `checkLimit('SHOP', shopId, 'maxProducts', currentCount)` is exported; S05 may adopt it when it wants plan limits (S05 does not enforce today) → count limits are the caller's data; billing only compares.
- [CONTRACT] Quota checks for API calls and assistant tokens → `checkQuota(subjectType, subjectId, key)` exported (R1); the caller decides fail-open or fail-closed when it rejects `usage_unavailable` → developer-platform and assistant own their request path; billing owns the plan numbers and the usage totals.
- [CONTRACT] developer-platform must publish `usage.recorded` v1 `{metric, quantity ≥ 1, ts}` with `aggregateId = subjectId` and a stable `eventId` per recorded batch/call → this is today's shape (`usage.service.ts:11-15`); the identity is what makes retries safe.
- [CONTRACT] `llm.call_completed` exists (`assistant-events.ts:5`) with `userId`, an enum `purpose` (`chat|summary|rag|extraction`), token counts and `aggregateId = callId`, but no billed subject and no metric → S46 adds `subjectId`, `metric` (`llm.assistant.tokens`, `llm.kyc_extraction.tokens`) and `billableTokens` additively and publishes it through the outbox (debt D-14); S18 consumes it and keys identity on `llm:<aggregateId>` → the producer knows what is billable and to whom (S04 bills a shop, the assistant a user); S18 must not guess from a purpose enum or from `userId`. S04's `{subjectId: shopId, scopeId, callId, purpose}` report (S04 AS-36) is the same record.
- [CONTRACT] S17's `billing.subscription_status_changed` v1 carries `subscriptionId` and `subscriptionVersion` (S17 spec) → S18 relies on `subscriptionVersion` strictly increasing per subscription and compares versions only for the same `subscriptionId`; an event for a different `subscriptionId` of the subject (re-subscription after cancel) always invalidates → a version counter is per subscription, so across subscriptions only "different" is safe to assume.
- [CONTRACT] `invalidate` rejects when it cannot drop the entry (S17 expects a void call; S17 may treat a rejection as "retry after commit via the event") → a swallowed invalidation leaves a customer on the wrong plan for up to the TTL.
- [CONTRACT] Usage in a cancelled subscription's last period is not invoiced (S17 FR-026: no invoice on cancel) → left unbilled and documented; if finance wants it, S17 adds a final invoice that calls `linesFor`/`settle` → keeps S17's scope; revenue leak is bounded to one period.
- [CONTRACT] Free-tier entitlements are owned by S18 (`FREE_SHOP`, `FREE_BUYER`) and tenancy keeps its own tier label `STARTER` (S17 question) → unchanged; S03's seat limit is S03's.

## LOCAL

- [LOCAL] Cache TTL 300 s, stale-on-error 60 min, one load per process on a cold key → matches today's TTL; the rest is new and bounded.
- [LOCAL] Late window 90 days at ingestion; period final at `periodEnd + 91 days` → events cannot be older than 90 days at ingestion, so a period cannot gain events after day 90; day 91 is the margin.
- [LOCAL] Quota window = UTC calendar month → entitlements are named "PerMonth"; invoices use billing periods.
- [LOCAL] Metric allowlist `^(api\.calls|llm\.[a-z][a-z_]{0,31}\.tokens)$`; metric → quota key map: `api.calls`→`apiCallsPerMonth`, `llm.assistant.tokens`→`assistantTokensPerMonth` → closed set, extended by a spec change.
- [LOCAL] Quantity cap 1,000,000,000 per event; `ts` future skew 5 min → sanity bounds.
- [LOCAL] Usage read months: current back to 12 months → support window.
- [LOCAL] Usage read limit 60/min per subject, fail closed → read hits the analytical store.
- [LOCAL] `linesFor` timeout 5 s (S17's) → same.
- [LOCAL] Reconciliation daily at 03:15 UTC, report only, never auto-correct → money; a human decides.
- [LOCAL] The hourly rollup (`usage_hourly`) has no reader; keep until a dashboard owner claims it, drop otherwise → not part of this spec.
- [LOCAL] Migration backfills ledger rows from invoices of the last 90 days using the usage that existed at each `usageMeasuredAt` → avoids losing adjustments across the deploy; older periods are final.
- [LOCAL] No `Idempotency-Key` on the usage read routes → `GET` only (V.5).
- [LOCAL] No negative adjustments (usage reversal) → events are append-only; credits are operator tooling, out of scope.
