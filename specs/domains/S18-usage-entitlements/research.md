# Research: S18 — decisions that the spec left to the plan

No `NEEDS CLARIFICATION` remains. Sources: the code under `packages/backend/libs/domains/billing`, `libs/infrastructure/{cache,llm,clickhouse}`, the follow-ups in the task input.

**R-1 Entitlement cache mechanism.** Decision: use the S52 `CacheService` (`getOrLoad` with `ttlMs 300_000`, `staleIfErrorMs 3_600_000`, `versionOf: e => e.subscriptionVersion ?? 0`; `invalidate` and `invalidateIfOlder`). It already provides single flight, stale-on-error and L2 failure reporting (`invalidate` resolves `{l2, deleted}`). Rationale: S52 owns those mechanisms; re-implementing them is the failure the cache toolkit was built to end. Rules on top: (a) `invalidate` rejects `entitlement_invalidation_failed` when `l2 === 'failed'` (AS-20, FR-014); (b) the consumer calls `invalidateIfOlder` with the event's `subscriptionVersion` for the same `subscriptionId`, and a plain `invalidate` when the `subscriptionId` differs; (c) a free-tier entry has `subscriptionVersion null` → stored as version 0, so any event drops it. Open point verified at task time: that `getOrLoad` refuses to store a load that began before an `invalidate` (AS-17). If S52 does not guarantee it, the adapter keeps a per-key generation counter bumped by invalidation and discards a result whose generation changed. Alternatives: own Redis code (rejected: duplicates S52).

**R-2 Free buyer tier vs DS-1.** DS-1 and AS-02 say the free buyer tier is `{}`. S46 (built) reads `assistantTokensPerMonth` for every buyer, has no local default, and added `FREE_BUYER = {assistantTokensPerMonth: 200_000}`. Decision: keep S46's number; free buyer = `{assistantTokensPerMonth: 200000}`. The test for AS-02 asserts that exact object for `w`; `hasEntitlement('USER', w, 'freeShipping')` stays `false`. Rationale: removing it breaks a built capability, and the follow-up is explicit. Recorded under "Spec changes" in `gaps.md` (DS-1/AS-02 deviation; the spec text is not edited here).

**R-3 `llm.call_completed` shape.** The event already carries `subjectId`, `metric`, `billableTokens` (`libs/infrastructure/llm/llm-call-completed.ts`), so G9's "needs S46" is done. Consumer rules: identity `llm:<aggregateId>`; `billableTokens 0` → ignored (`reason=zero_quantity`); the metric must pass the allowlist (`llm.rag.tokens` and `llm.kyc_extraction.tokens` match); `ts` = envelope `occurredAt` (the payload has none) and goes through FR-018 limits. S47 rule: `subjectId: "anonymous"` with outcomes `failed|refused|aborted` is stored as platform cost under that subject; it has no quota key, is shown to no one, and is never invoiced (no subscription for it). The old `Math.max(1, tokens)` is removed with `llm-meter`'s dependence (that file no longer exists in the assistant).

**R-4 Usage store identity.** `usage_events` is a `ReplacingMergeTree` ordered by `(subject_id, metric, event_id)`; reads use `FINAL` so duplicates are collapsed (FR-025). `event_id` holds `eventId` or `llm:<aggregateId>`. Same event id with a different payload is a producer bug; first write wins is not guaranteed by Replacing, so the consumer also keeps the inbox record per identity (source of the dedup counter and of AS-23's "third time after restart"). Insert: synchronous with `wait_for_async_insert=1`, failure rejects so the message is redelivered (AS-30). Time parameters use `DateTime64(3,'UTC')` via a formatter (`YYYY-MM-DD HH:MM:SS.mmm`) instead of `.replace('Z','')` (G8, G21).

**R-5 Consumer pattern.** Follow `tenancy.consumers.ts`: `Projector` with `idempotency: 'inbox'`, `InboxService.recordOnce(consumerName, identity)` inside `runner.run`, `PermanentError(reason)` for dead-lettering (reasons `invalid_payload`, `unknown_metric`, `ts_in_future`, `too_old`). The inbox record and the usage insert are in different stores, so the order is: insert first (idempotent by `FINAL`), then `recordOnce`; a crash between the two re-inserts the same identity, which collapses. Rationale: never record "seen" before the write is durable (AS-30).

**R-6 Settlement algorithm.** Per `(subscription, periodStart, metric)`: `price(used) = ceil(max(0, used − included) / 1000) × rate`. `linesFor` computes, for the period that ended, a new entry `from 0 → to used` with the price's current `included`/`rate` snapshot, and for each open ledger row an adjustment entry `from settledQuantity → to exact total` priced with the row's snapshot: `amount = price(to) − settledAmountMinor`, `quantity = overUnits(to) − overUnits(from)`, line only when `amount > 0`, entry still advances. `settle` for each entry: first entry (`from 0`, no row) inserts with `ON CONFLICT DO NOTHING` and rejects `settlement_conflict` if the row exists with another invoice; later entries do `UPDATE … SET settledQuantity = :to, settledAmountMinor = :amount, lastInvoiceId = :inv WHERE id = :id AND settledQuantity = :from`, zero rows → conflict unless `lastInvoiceId = :inv AND settledQuantity = :to` (idempotent replay). Rows with `periodEnd + 91 d <= measuredAt` close on that settlement. Invariant checked by a `fast-check` property (SC-002). Alternative rejected: parsing invoice lines to learn what was billed.

**R-7 Where S17 changes.** `renewal.service.ts` calls `linesFor` (already outside the transaction) and must call `settle` inside its invoice transaction and keep `usageMeasuredAt`. The provider interface in `domain/ports.ts` becomes `Promise<{lines, settlement}>`; `timeoutMs` stays in the input. Same domain, so no sibling rule applies; the S17 live-spec page and `billing-run.e2e-spec.ts` fixtures adapt (the provider double there returns an empty settlement).

**R-8 Guard startup validation.** A `OnApplicationBootstrap` validator walks `DiscoveryService` controllers; a handler with `RequiresShopEntitlement` metadata must also carry `ShopScoped` metadata and a key in the allowlist, else it throws naming `Controller.method` (AS-10). Keys validated at decoration time too (TypeScript union plus a runtime check in the decorator).

**R-9 Plan code never leaves.** The S38 follow-up (callers target on `plan` themselves) cannot be met by S18 without breaking "plans are never named" (spec Assumptions). Decision: S18 exports no plan getter; callers use S17's subscription read. Recorded as a sibling bullet.

**R-10 Reconcile job.** `billing.usage-reconcile`, `upsertSchedule` cron `15 3 * * *` UTC with the S17 pattern in `billing.jobs.ts`; handler reads open rows in keyset pages of 500, computes exact totals with the same store port, sets gauge `usage_ledger_drift`, logs subscription/period/metric only.

**R-11 `usage_hourly`.** Left as is (LOCAL question default: keep until a dashboard owner claims it); not part of this plan.

**R-12 Unverified criteria.** SC-004 (99% visible in 30 s) and SC-006 (p99 < 20 ms, both stores down) need load or timing runs, SC-009 needs a populated database; none is provable by e2e. See `quickstart.md` "Ops artifacts" and `specs/UNVERIFIED.md`. SC-001, SC-002, SC-003, SC-005, SC-007, SC-008 are proven by tests (property tests and e2e) as mapped in `quickstart.md`.

## Decisions taken while building

**R-13 `usage_hourly` (T044).** Decision: keep. It has no reader in the repository (searched `usage_hourly` in code and ClickHouse DDL: only its own DDL), it holds no money and the billing code never reads it. Dropping it is a separate expand-safe change for the owner of a dashboard to request; not part of S18.

**R-14 Topics (T002).** Nothing is missing. `billing.events` is registered by `BILLING_AGGREGATE` (billing), `usage.events` by `developer-platform-core.module.ts` (aggregate `usage`) and `llm.events` by `libs/infrastructure/llm/llm.module.ts` (aggregate `llm`). No queue is added (L-001, L-002, L-020).

**R-15 Inbox belongs to the runner.** A consumer declared `idempotency: 'inbox'` is wrapped by the S53 runner (`invokeInbox`): the runner records `(consumer, eventId)` in the transaction of the effect and hands only the fresh events to `project`. S18's three consumers therefore do not call `recordOnce` themselves; `testing/runner-delivery.ts` repeats that wrapper (inbox record + handler in one transaction, `PermanentError` is a dead letter, anything else is rethrown) so the specs prove duplicates and rollbacks with the real inbox table. Consequence: `entitlement_invalidations_total` has the outcomes `applied` and `stale_event`; a duplicate never reaches the consumer and is counted by the runner (`projection` events metric, outcome `duplicate`).

**R-16 Cache version fence.** A versioned invalidation raises the cache's minimum accepted version for 30 s (`minimumRetentionMs`). A load that began before the event and returns an older state is refused by the store. The cost is that a free-tier entry (version 0) loaded in those 30 s after a cancellation event is served but not stored. S52 had no way to read an entry, so `CacheService.peek` was added (read-only, covered by `cache-peek.e2e-spec.ts`).

**R-17 Backfill rule for pre-release invoices.** The previous implementation billed the late events of period P on the invoice that follows the one that measured P. The ledger row of P therefore starts from the usage that existed at the measurement of that following invoice when it exists, otherwise at the measurement of the invoice that billed P. Taking only the first measurement would bill those late units a second time (AS-48 tests both).

**R-18 Problem codes.** `too_many_ids` and `amount_out_of_range` are raised with billing's own text but not registered in the problem catalog: orders and payments already own those codes with other status or wording and the catalog refuses two definitions of one code.
