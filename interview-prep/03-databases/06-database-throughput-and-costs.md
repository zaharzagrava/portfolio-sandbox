# Database throughput and costs

How much Postgres (and the alternatives) really takes, and what storage and compute cost on AWS. us-east-1 list prices checked Oct 2026; verify before quoting. Queue/stream equivalents: [../06-distributed-systems/01](../06-distributed-systems/01-messaging-queues-kafka-sqs.md). When to pick each analytical/document DB: [05](05-analytical-and-document-databases.md).

**Read this first.** The throughput numbers below are **rules of thumb, rough orders of magnitude**. Real numbers move 2–10x with hardware, row/item size, number of indexes, durability settings (`synchronous_commit`, Multi-AZ, write concern, replication factor), cache hit rate and client concurrency. Use them to sanity-check a design in an interview, not to size production. Prices are on-demand list prices with no Savings Plans, reserved instances or free tier unless stated.

### Shape of the costs

- **Instance-priced** (RDS, Aurora provisioned, ElastiCache nodes, OpenSearch, self-managed Scylla): a fixed monthly floor, then cheap per extra request until you need a bigger box.
- **Request-priced** (DynamoDB on-demand, Keyspaces, Athena): near zero at low volume, linear with volume. At sustained high write rates they cost more than instances.
- At TB scale, **storage price per GB-month** usually decides the bill: $0.023 (S3) vs $0.10–0.23 (Aurora, RDS gp3) vs $0.25 (DynamoDB, Keyspaces), times replication.

## 3. Sizing examples: workload → instance → load → price

**How to size any database (the method, not the numbers).**

1. Write the workload down: ops/s **at peak** per kind (key read, insert, update, scan), row/item size, total data, how much of it is hot.
2. **RAM first.** Hot data + indexes must fit in RAM (Postgres, Mongo, Redis, OpenSearch). If not, every miss is a disk read and CPU numbers stop mattering.
3. **CPU second.** Divide peak ops by a per-vCPU rate (below), target **~50% CPU at peak** (room for spikes, failover, vacuum, deploys).
4. **Check the ceilings that no instance size fixes:** one hot row (Postgres), one hot partition (DynamoDB 1k writes/s), one shard's single thread (Redis), per-prefix S3 limits.
5. **Price** = instance-hours × copies (Multi-AZ standby, replicas, RF=3) + storage GB × rate × copies. Request-priced services (DynamoDB, Keyspaces, Athena) = ops × unit price.
6. **Then load-test the chosen instance** (`pgbench`, k6 against your real queries). The rates below get you within ~2x; only a test gives the real number.

**Postgres planning rates** (small rows, data in RAM, pooled connections, 100% CPU on one vCPU; halve for the 50% target): PK read ~5–10k/s · single-row insert/update with 2–3 indexes ~1–2k/s (needs many concurrent connections so commits are flushed together) · batched inserts ~10–20k rows/s · `COPY` ~30–100k rows/s. **One connection** doing one commit per row is capped by commit latency, not CPU: ~0.5–2 ms per commit (more with Multi-AZ) → ~500–2k/s whatever the instance.

Prices: RDS on-demand us-east-1, **Single-AZ, instance + gp3 storage per month**; Multi-AZ ≈ 2x. Instances: db.t4g.medium (2 vCPU burstable, 4 GB) ≈ $47 · db.r7g.large (2 vCPU, 16 GB) $174 · db.r7g.xlarge (4 vCPU, 32 GB) ≈ $349 · db.r7g.2xlarge (8 vCPU, 64 GB) $698 · db.r7g.4xlarge (16 vCPU, 128 GB) ≈ $1,396. gp3 $0.115/GB-mo. ## 4. Worked example: chat app, 300M messages/day

Assumptions: ~300 B per message, ~3.5k writes/s average, 10k/s peak, ~90 GB/day, ~33 TB/year raw. One write per message. Reads are paged queries by conversation and cost far less than writes here. Totals are rough, on-demand, compute + storage only (no backups, transfer, ops time).

- **Can a single Postgres primary take it?** The write rate, yes: 10k inserts/s peak on an 8–16 vCPU instance is realistic if the app batches (multi-row inserts) or uses enough concurrent connections for group commit, and the table is partitioned by time so indexes stay small. Commit-per-row from one connection would not. What breaks is the **volume**: 33 TB/year plus indexes runs into vacuum and index maintenance pain long before the 64 TiB RDS limit. So: one primary + time partitions + move old partitions to S3, or shard by conversation ID.
- **Postgres on RDS, 90 days hot + archive in S3:** 1 × db.r7g.2xlarge Multi-AZ ≈ $1,400/mo + 1 read replica ≈ $700. Hot data ~8 TB raw ≈ 12 TB with indexes × $0.23 (Multi-AZ gp3) ≈ $2,800. Archive as compressed Parquet in S3 (assume ~5x compression → ~7 TB/year) ≈ $150/mo, queryable with Athena (~$35 per full-year scan). **≈ $5k/month.**
- **Sharded Postgres (RDS), keep a full year online:** 4 shards × db.r7g.2xlarge Multi-AZ ≈ $5,600 + ~50 TB with indexes × $0.23 ≈ $11,500 at month 12. **≈ $7k (early) to $17k/month (end of year 1)**, plus resharding and cross-shard query work.
- **DynamoDB on-demand:** writes 300M × 30 ≈ 9B WRU × $0.625/1M ≈ **$5,700/mo** (one GSI doubles it). Storage grows ~120 GB/day with the per-item overhead ≈ 3.6 TB/month: ≈ $900 in month 1, ≈ $11,000 in month 12 at $0.25/GB. **≈ $7k → $17k/month** across year 1. With TTL at 90 days + export to S3: ≈ $8–9k/month steady. Provisioned with auto scaling (~5k WCU average) cuts the write part to ≈ $2,400/mo. Fit: good if the key is (conversationId, timestamp) and no single conversation exceeds 1,000 writes/s.
- **Keyspaces:** same us-east-1 unit prices as DynamoDB, so about the same bill. Fit: you want the CQL / Cassandra data model without running nodes.
- **ScyllaDB self-managed:** throughput needs only 3 nodes. Storage sets the size: 90 days ≈ 8 TB × RF 3 ÷ ~2x compression ≈ 12 TB + compaction headroom → 3 × i3en.6xlarge ≈ **$6k/mo** on-demand (≈ $2.6k with 3-yr reserved). A full year online ≈ 6 nodes ≈ $12k/mo. Plus the people to run it. ScyllaDB Cloud: quote only.
- **Takeaway for the interview:** at this rate the write throughput fits on one well-tuned Postgres primary; the deciding factor is **storage growth and retention**. Keep a hot window in the database and push history to S3; pick DynamoDB/Scylla when you want write scaling without sharding work and the access pattern is "by conversation, by time".
